# r62t-protocols · Standardization plan

Make **AG-UI the run transport for admin, desktop, and visitor chat**. Use **ACP for coding-agent CLI sessions**, **MCP for tools**, **MCP Apps for tool-owned views**, and **A2UI for agent-generated views**. Jini owns each protocol adapter. Tovu supplies its routes, authentication, authorization, storage, and UI bindings through existing ports.

**Phase 1 has four READY Jini sheets and one READY Tovu test sheet.** The production admin repoint waits for a working resume flow. At the inspected bases, Jini turns a marked approval into an interrupt and stops reading the run. Tovu’s canary renders that approval as a card and continues reading. The earlier `TV-AG1` attempt stopped for this reason.

Bases verified from Git objects: Tovu `0973a5fdc8`, Jini `de4e555b9`, both `integ/merge-10-2026-11-21`. The reported packed contract result is **9/9 for Tovu’s admin AG-UI golden suite**. Combine-10 fixed site-chat’s stale Jini lock entries, while its transport test still had a recorded file-level failure and its lock lacked a resolved `@ag-ui/core` entry. The historical copies of architecture sections 13 and 14 and project memory were available in Tovu Git history. The dispatch’s exception covered the absent `AI-Dev-Shop` bootstrap. This design pass made no file changes and ran no tests or builds. ## Target architecture

```text
Tovu admin / desktop / visitor
        ↕ AG-UI run input and events over HTTP or existing Electron IPC
Jini chat transport port ↔ Jini AG-UI adapter ↔ Jini run engine
                                                     ├─ ACP ↔ supported coding CLI
                                                     └─ MCP ↔ local or remote tools

Tool-owned view       ↔ MCP Apps sandbox bridge ↔ host authorization
Agent-generated view  ↔ A2UI renderer/actions  ↔ pending host exchange
Runtime telemetry     → Jini observability port → OTel provider → OTLP
Public HTTP contracts → OpenAPI where a public consumer needs the description
```

Use one Jini implementation per protocol, including its client and server roles where needed. Keep SDK imports and protocol-library behavior in provider-style adapter packages behind existing ports. Phase 1 edits the existing Jini seams in place. Package moves and dependency changes belong to the cloud migration that can verify public exports and packed consumers together.

Keep internal typed events and the durable run ledger. End the custom frames at the Jini adapter so UI clients consume AG-UI. Electron can keep its IPC channels and subscription IDs while carrying AG-UI events as the run payload. AG-UI can announce an MCP App or A2UI surface, whose messages still use their native protocol. Tovu keeps CMS tools, same-origin authentication, visitor policy, and `@tovu/sdk`.

Track protocol revision and SDK version separately. For AG-UI, pin the core/client/encoder versions together and use the existing packed writer/reader goldens plus lifecycle, approval and replay fixtures. For ACP, pin the schema revision and test transcripts against known CLI versions before changing advertised capabilities. For MCP and MCP Apps, pin the SDKs and run the upstream conformance suites for the revisions actually advertised, with fixture checks for Tovu’s authorization and pagination semantics. For A2UI, pin the upstream fixture commit and test the catalogs we ship. Use the existing combine and release process for these checks.

## Ordered phases

Each phase can ship on its own. Combine runs the named tests and mutations before enabling traffic or removing a transport.

1. **Pin current contracts and repair ACP negotiation.** Run the four Jini sheets below. Stage the Tovu wire test in the next qualifying Tovu batch. These edits remove no transport and do not change the enabled agents. The only production behavior change is an early refusal when the CLI explicitly reports an unsupported ACP revision.
2. **Update the AG-UI dependencies and ship one visitor path.** OPUS-CLOUD pins and verifies the Jini AG-UI candidate first, then handles `deps/lockfile-1121` for Tovu. `AG2-T` follows the `AP-T` fix from `origin/codex/tv-rs3` (`f064021231`) and recovery of the existing site-chat transport test. Pin text, public error, normal and early close, abort, split SSE frames, directives, and confirmation in both renderers. Switch `/chat` once the agreed transition condition is met, then remove its named SSE wire parser and writer. Keep the confirmation endpoint for this release. Risk is visitor chat and form/navigation behavior. Chrome looks cover both renderers.
3. **Ship resume, then retire the duplicate UI transports by host.** Start with the existing Jini `readConfirmationResume`, pause store and authorization exchange. Assert accept, deny, expiry, wrong owner, replay, second settlement, and disconnect before switching the site `/confirm` flow to AG-UI resume (`AG3-T`). Then wire admin interrupts and resume and repoint the canary drain, including explicit host response ending and the normal-completion zero-cancel test. Promote admin AG-UI after Local CLI and BYOK both prove stop, stable IDs, tool cards, saved turns and reattach. Delete those legacy UI codecs and the canary switch at that point. Port desktop in its own release, retaining Electron subscription isolation and durable cursor behavior, then remove `workspace-chat-transport.ts`’s raw run-event projection. Enable frontend tool delivery (`AG4-T`) only with the existing registry’s `begin`, bound invocation ID, and one-use acknowledgement. A `TOOL_CALL_END` event alone grants no execution. Chrome and packaged Electron looks are owed for their respective releases.
4. **Prove OpenCode ACP parity in parallel with phases 2–3.** Re-run the existing 12-point parity checklist on an allowed model host. Include a live turn, resume/reseed, model and effort, MCP delivery, approval, cancel, auth, and cleanup. `ACP-8` enables the pilot after parity, in a separate change. Retire the native OpenCode path after the enabled pilot passes Tovu’s supported entry points. Retain native paths for CLIs without sufficient ACP support.
5. **Converge tool and view protocols.** First migrate one MCP federation connection behind the existing session port. Compare list/call pagination, authorization, expiry and redaction on both legacy and current peers. Migrate server hosting independently, then delete the handwritten federation protocol implementation when all users move. Next migrate one MCP Apps card family against the reference lab, preserving sandbox isolation and allowlisted calls. Delete legacy action messages family by family. Finally, use the existing A2UI v1.0 fixtures to drive the smallest catalog/action gap that a shipped surface needs. These releases carry the highest risk at extension interoperability and authorization.
