## Purpose
Defines the durable server-side entity state (the `NavMenuEntry` lifecycle + the derived
location-binding index) and the admin UI's local component state, as actually implemented.
There is no Redux/store layer in the shipped frontend — `Menus.tsx`/`MenuEditor.tsx` use plain
React `useState`, so Section 3 below documents that thinner reality rather than the template's
richer action-catalog shape.

## 1) Durable Entity State Shape (`NavMenuEntry`, `src/navigation/types.ts:158-176`)
| Field | Type | Nullable | Initial Value (on create) | Description |
|---|---|---|---|---|
| `id` | `UUID` (string) | no | generated by `idGen.newId()` | Menu identity |
| `workspaceId` | `UUID` (string) | no | caller-supplied | Workspace scope |
| `slug` | `string` | no | caller-supplied, lowercased/trimmed | Stable machine handle, unique per workspace |
| `title` | `string` | no | caller-supplied, trimmed | Human menu name |
| `status` | `MenuStatus` (`"draft" \| "published" \| "trash"`) | no | `"draft"` | See Section 3 — `"published"` is declared but never reachable |
| `doc.items` | `NavItemNode[]` | no (array, may be empty) | `[]` or caller-supplied initial tree | The ordered/nested item tree |
| `locations` | `string[]` | no (array, may be empty) | `[]` | Location keys this menu currently fills — source of truth for assignment |
| `updatedAt` | `ISODateTime` (string) | no | `clock.nowIso()` at create | Last write timestamp |
| `version` | `integer` | no | `1` | Optimistic-concurrency counter |

## 2) Derived Index State Shape (`NavLocationBindingRow`, `types.ts:194-201`)
| Field | Type | Nullable | Description |
|---|---|---|---|
| `workspaceId` | `UUID` | no | Workspace scope |
| `locationKey` | `string` | no | The theme location key |
| `menuId` | `UUID` | no | The menu currently bound to this location |
| `boundAt` | `ISODateTime` | no | Timestamp of the last (re)assignment |

**Storage reality:** both shapes above live only in-process, in a plain JS array inside
`InMemoryMenuRepo`/`InMemoryNavLocationBindingRepo` (`repo.memory.ts`). Nothing persists across
a process restart. There is no SQLite-backed adapter for either shape in the shipped code.

## 3) Entity Lifecycle / Transition Catalog
Menus has a real, testable state machine on `status`, plus a version counter that advances on
every mutation. This replaces the template's Redux-style action catalog, since there is no
client-side store to document — the server *is* the state owner here.

| Transition | Trigger (impl function) | Precondition | State Change | Failure Handling |
|---|---|---|---|---|
| (none) → `draft` | `createMenu` (`menu-service.ts:196-224`) | Slug not already used in workspace; title/slug pass format validation; item tree passes bounds/target validation | New row, `status: "draft"`, `version: 1`, `locations: []` | Throws `MenuValidationError` (bad title/slug/tree) or `MenuConflictError` (duplicate slug) — no row is created on failure |
| `draft`/`trash` → same status, tree replaced | `updateMenuTree` (`menu-service.ts:275-313`) | Menu exists; `expectedVersion` matches stored `version`; new title/slug/tree pass validation | `doc.items` replaced wholesale, `version += 1`, `updatedAt` refreshed | Throws `MenuNotFoundError`, `MenuConflictError` (stale version or slug collision), or `MenuValidationError` — stored row is unchanged on failure |
| `draft`/`published` → `trash` | `deleteMenu`, 1st call on a non-trashed menu (`menu-service.ts:469-478`) | Menu exists and `status !== "trash"` | `status: "trash"`, `version += 1` | Throws `MenuNotFoundError` if the id does not exist |
| `trash` → row removed | `deleteMenu`, 2nd call on an already-trashed menu (`menu-service.ts:480-496`) | Menu exists, `status === "trash"`; no location binding references it, or `force: true` | Row removed from `MenuRepoPort`; every binding row for this `menuId` removed from `NavLocationBindingRepoPort` | Throws `MenuLocationBoundError` (bindings exist, no `force`) — row and bindings untouched on failure |
| n/a — **never implemented** | (no function sets `status: "published"` anywhere in `menu-service.ts` or any route) | — | — | **`published` is a dead value.** Every `MenuStatus` consumer (`AdminMenuDto.status` in the UI, `menu-service.ts`) treats it as a legal type-level value, but no code path in the shipped feature ever produces it. This is flagged in `feature.spec.md` as Deviation D-10 / Open Question OQ-03, not silently normalized away here. |

## 4) Location-Binding Index Transitions
| Transition | Trigger | Precondition | State Change | Failure Handling |
|---|---|---|---|---|
| (none) → bound | `assignLocation`, location previously unbound (`menu-service.ts:367-418`) | Target menu exists | New/updated `nav_location_bindings` row for `(workspaceId, locationKey)`; target menu's `locations` gains the key, `version += 1` | Throws `MenuNotFoundError` if `menuId` does not exist; no binding write attempted |
| bound to menu A → bound to menu B | `assignLocation`, location already bound elsewhere | Target menu exists; a different menu currently holds the location | Binding row's `menuId` overwritten (last-writer-wins, `InMemoryNavLocationBindingRepo.upsert`); menu A's `locations` loses the key, `version += 1`; menu B's `locations` gains the key, `version += 1` | Same as above. **No rollback exists** if the binding-index write fails after the menu-field writes succeed (or vice versa) — the two writes are sequential, not transactional (documented gap, `menu-service.ts:349-356` doc comment) |
| bound → unbound | `deleteMenu` purge step (`removeByMenu`) | Menu is being force/clean-purged | All binding rows for that `menuId` removed | n/a — this is the only way a binding is removed in the shipped code; there is no direct "unassign" route/function |

## 5) Frontend Local State (`Menus.tsx`, `MenuEditor.tsx` — plain `useState`, no store)
| Component | State Field | Type | Initial | Notes |
|---|---|---|---|---|
| `Menus` | `menus` | `AdminMenu[] \| null` | `null` | `null` renders "Loading menus…"; set once by `load()` on mount |
| `Menus` | `error` | `string \| null` | `null` | Any caught fetch/mutation error message |
| `Menus` | `locationDrafts` | `Record<string, string>` | `{}` | Per-row draft text for the "Assign location" input, keyed by `menuId` |
| `MenuEditor` | `menu` | `AdminMenu \| null` | `null` (create mode) | Loaded menu in edit mode; stays `null` in create mode |
| `MenuEditor` | `title`, `slug` | `string` | `""` | Bound to the title/slug inputs |
| `MenuEditor` | `items` | `AdminMenuItem[]` | `[]` | The in-editor working copy of the tree — mutated via the `mapAtPath`/`removeAtPath`/`addChildAtPath`/`moveAtPath` helpers |
| `MenuEditor` | `message` | `string \| null` | `null` | Save-success text (e.g. `"Saved · version 3"`) |
| `MenuEditor` | `error` | `string \| null` | `null` | Save/load error text |
| `MenuEditor` | `loading` | `boolean` | `!isNew` | `true` while an existing menu is being fetched; always `false` immediately in create mode |

**No optimistic updates, no rollback, no request de-duplication** exist in either component —
every mutation is a plain `await api.<call>()` followed by a state `set*` and, for list-level
actions, a full `load()` re-fetch.

## 6) State Invariants
- [x] A menu's `version` never decreases and increases by exactly 1 per successful mutating
  call that touches it (create sets `1`; every subsequent successful write does `+1`).
- [x] The binding index never holds two rows for the same `(workspaceId, locationKey)` —
  `upsert` always replaces (`repo.memory.ts:171-182`).
- [x] A menu's `status` transitions only `draft → trash → (removed)` in the shipped code —
  never `draft → published` or `trash → draft` (see Section 3's dead-value note).
- [x] `Menus.tsx`'s `menus` field is `null` only before the first successful `load()`; after
  that it is always an array (possibly empty), even after a failed subsequent action (the
  component does not null it out again on error).
