## Context

Tovu has 40+ accepted ADRs and a strong debate/audit discipline at the *design* level, but that process doesn't currently look at *structural* drift — duplication, complexity, and layering violations that accumulate as code, not as decisions. This ADR is the first graph-backed structural audit: it queries the actual call/import graph rather than relying on convention or memory, to separate "architecture that's actually working" from "architecture that's decaying."

Two things worth naming about the audit method itself: (1) the graph was stale at the start of this review (matched an earlier session's snapshot, missing 3 landed commits) and was re-indexed before any finding below was trusted; (2) one finding from the prior handoff (`src/headless` unwired status) had already resolved itself between sessions — it now has an `INFO.md` and 4 real callers — which is flagged here as a caution against treating any single audit snapshot as durable without re-verifying against current `HEAD`.

## Findings — what's working (recorded so it isn't re-litigated)

1. **Event bus is real infrastructure, not a decorative abstraction.** `src/core/events` (memory-bus + a durable outbox-worker adapter) has 18 distinct production/test callers spanning `newsletter/send-pipeline.ts`, `server/{app,deps}.ts`, `forms/notify-subscriber.ts`, `redirects/hit-sink.ts`, and `core/commands/{command,revert}.ts`. This lines up with the FEAT-015 outbox/durability work already landed.
2. **Ports/adapters discipline is consistent across ~12 feature modules** (`post`, `presentation`, `settings`, `workspace`, `forms`, `integrations`, `members`, `navigation`, `newsletter`, `redirects`, `seo`, `origin`): each has `ports.ts` + `repo.memory.ts` + `repo.sqlite.ts` + a `repo.contract.test.ts` proving the two adapters interchangeable. This is ADR-006's rule-of-two actually enforced by tests, not just asserted.
3. **No circular imports, no god-files.** Complexity is well-controlled: only 12 of 1,352 functions exceed cognitive complexity 12. Independent fan-in/fan-out layer detection confirms the intended core/entry split (`core`/`identity`/`media`/`integrations`/`routing` = high fan-in core tier; `server`/`newsletter` = entry tier) almost everywhere.
4. **`comments` is confirmed genuinely unwired** (zero inbound imports from outside its own directory) — matches its self-declared ADR-031 stub status. Not a bug; don't "fix" it.

## Decision

Adopt the following five remediation items. None are architecturally risky; all are contained refactors inside existing module/layer boundaries.

**As-built correction (2026-07-15, Fable's `/debate` Round 1 finding, independently verified by the Coordinator):** the text below originally described the *plan*, not what shipped — item 1's signature and scope, and item 5's file count, drifted from the landed code without the ADR being updated. Both are corrected in place below rather than left as phantom drift for a future audit to rediscover.

1. **Extract a shared SQLite repo lookup base.** The `repo.sqlite.ts` pattern (finding #2 above) is structurally consistent but duplicates near-identical (`jaccard 1.0`) `findById`/`findBySlug`/`findByX` methods across ~35 call sites in 11 adapters (`post`, `forms`, `navigation`, `newsletter`, `settings`, `workspace`, `presentation`, `integrations`, `redirects`, `identity`, `members` — not "~12 times" as originally estimated). Shipped as `findOneBy(db, table, conditions, mapper)` in `src/infra/sqlite/repo-helpers.ts` (not the originally-sketched `findByField(table, column, value)`), composed by every matching call site. This is the single highest-leverage item. **`/debate` D1 (unanimous):** amended with `.limit(1)` (the shipped version fetched unbounded rows and took `rows[0]`, leaving "one row" implicit) and a direct unit test of the helper's own null/mapped-row/multi-match contract (`src/infra/sqlite/__tests__/repo-helpers.test.ts`) — previously only certified indirectly through 11 modules' contract suites.
2. **Split `registerAdminSettingsRegisterDefinitionsRoute`'s inline op-dispatch** (register/rename/retype/deprecate/tombstone — cyclomatic 20, cognitive 57, the highest in the codebase). This was two decisions bundled in one commit (`/debate` D2/D3 split them; recorded separately from here on):
   - **2a. Write-service dedupe** (`deprecateDefinition`/`tombstoneDefinition` → shared `transitionDefinitionStatus` in `features/settings/write-service.ts`, public signatures unchanged): zero objections across audit or debate, either round. Settled.
   - **2b. Route dispatch table** (`NON_REGISTER_DEFINITION_OPS` in `src/features/settings/definitions-dispatch.ts`): the *initial* shipped version was a plain `Record<string, Handler>` — `/audit-work` found and fixed a real blocker here (finding A-01: `op="constructor"` resolved via the prototype chain to `Object`, returning a false 200 instead of 400). **`/debate` D2 (unanimous convergence, round 2):** the null-prototype patch closed the specific vulnerability but not the defect class — an untrusted string was still an open runtime dispatch key. Amended to a closed-union boundary: `parseNonRegisterDefinitionOp(op)` narrows the untrusted string to `NonRegisterDefinitionOp` (`"rename"|"retype"|"deprecate"|"tombstone"`) *before* any lookup; the table itself is `satisfies Record<NonRegisterDefinitionOp, DefinitionOpHandler>` (compile-time exhaustive — a 5th op added without a handler is now a type error, not a silent gap), still `Object.create(null)`-based as defense-in-depth. **`/debate` D3 (unanimous):** full edge-schema validation (Zod or similar, validating every field of the request body, not just `op`) is a stronger *eventual* target — but the repo has zero validator dependency today, and adopting one is a codebase-wide convention decision touching every route registrar. Deferred to its own future ADR, not smuggled into this remediation; the closed-union work isn't wasted when that lands (a future schema's output type *is* this union).
3. **Resolve `src/infra/sqlite/content-db.ts → src/server/seed.ts`.** Infra importing from server is a layer-direction violation with no discovered justification (unlike the documented `core → features` exception in `appliers.ts`). `openContentDb`/`seedContentDb` now take seed data as an explicit `ContentDbSeedData` parameter (defined in infra's own vocabulary); `server/deps.ts` supplies it. **`/debate` D4 (unanimous, both rounds):** this genuinely resolves the violation rather than relocating it — the composition root already owns every port/adapter selection; knowing one more infra-defined parameter type is that pattern working, not hiding. A `SeedProviderPort` was explicitly considered and rejected as premature (no competing seed source exists).
4. **Freeze `MailPort`'s shape deliberately before building a real adapter.** **As-built correction:** `src/mail` was NOT interfaces-only when this item shipped — `ConsoleMailerAdapter` (`src/members/mailer.console.ts`) already implements `MailerPort` (Fable's `/debate` Round 1 finding); what's genuinely absent is a production external-provider adapter. The port already had fan-in from `newsletter`, `members`, and `forms`. Reviewed templating, attachments, retries, `MailerSendResult` union per ADR-037; added optional `attachments?: readonly EmailAttachment[]` to `OutboundEmail` and a **required** `supportsAttachments` field to `MailerCapabilities` (not purely additive — every implementer/double needed updating, confirmed in the same commit). **`/debate` D5 — split decision, recorded not resolved:** Fable, agy, and Primary held that freezing now was correct (3 real consumers already exist; the shape-change cost only grows once a real adapter lands). **Dissent (Codex, recorded, not adopted):** would have deferred the specific `attachments`/`supportsAttachments` fields until a real consumer or adapter defined actual provider constraints, given the ADR's "interfaces-only" justification was factually wrong. Both sides agree the review's *negative-space* decisions (templating stays out, retry re-homed to the generic ADR-009 outbox worker) were correct regardless. **`/debate` D6 (unanimous — the one thing all 4 participants agreed on independent of D5):** the one genuine gap was left unpinned — an adapter receiving an attachment while `supportsAttachments:false` had undefined behavior (silent drop vs. typed failure). Fixed: `MailerPort.send()`/`sendBatch()` now MUST fail closed with `{ok:false, retryable:false, errorCode:"ATTACHMENTS_UNSUPPORTED"}` (documented in `src/mail/ports.ts`, enforced in `ConsoleMailerAdapter`, regression-tested).
5. **Extract the duplicated `bootAuthenticated`/`boot` test helper.** Confirmed byte-identical (`jaccard 1.0`, not just "similar") across 14 files under `src/server/__tests__/**` (originally estimated "10+"). Low priority, mechanical, cheap. **`/debate` D7 (unanimous, both rounds):** no changes — the extraction actually improved test hygiene (centralized `t.after` teardown prevents any suite from forgetting to close its listener).

## Considered and rejected

- **Collapsing `apps/admin/src/sections/Pages.tsx` and `Posts.tsx`** into one parameterized component was raised as a candidate — the graph shows them as exact duplicates (file-level and function-level `jaccard 1.0`; `createPage`/`createPost` are structurally the same function). The domain model already treats a page as `post` with `kind: "page"` (`src/features/post/post.ts`), which is what made this look attractive.
  **Owner decision: keep them separate.** Recorded here so this isn't re-proposed by a future audit pass without new context.
  **`/debate` D8 (2026-07-15) — reaffirmed 3-vs-1, recorded not unanimous.** Fable, agy, and Primary held that "kept separate" needed a sharper justification than owner precedent alone — jaccard similarity is a *detector*, not a *decision rule*. The test that emerged (independently, in different words, from Fable and agy): **"if the two copies diverged tomorrow, would that be a bug or a feature?"** Item 1's 35 repo-lookup sites share one invariant that must never diverge (bug if it does → extract). Pages/Posts encode two domain concepts with a disclosed, scheduled roadmap divergence (tags attach to posts, not pages; pages get hierarchy) — divergence there is the plan, not a defect (feature → keep separate). Fable's falsifiable tripwire, adopted into this record: **revisit if either (a) a third list screen of the same shape appears, or (b) the tags/hierarchy work lands and the two screens are still structurally identical** — i.e., the predicted divergence didn't happen. **Dissent (Codex, recorded, not adopted):** held that today's actual shared invariants (same editor route, same CRUD shape, zero behavioral conditionals) already meet a stricter "change correlation" extraction test, and proposed extracting a shared `ContentListScreen`/hook with thin `Pages`/`Posts` facades now rather than waiting for a tripwire. No code changed for this item — the majority position matches what's already shipped.

## Consequences

- Items 1–2 reduce the two areas of the codebase most likely to grow worse under continued feature velocity (repo boilerplate scales with every new module; the settings dispatch scales with every new op type).
- Item 3 is the one open correctness/layering question in an otherwise clean dependency graph — closing it either removes the last unexplained boundary violation or documents it as deliberately as the `appliers.ts` case already is.
- Item 4 is preventive: it's cheap now and expensive after `newsletter`/`members`/`forms` are all coupled to a shape that turns out wrong once a real SMTP/HTTP adapter is built.
- Rejecting the Pages/Posts merge means that duplication (~150 lines) is accepted as a standing cost — noted, not hidden.

No action required to keep the status quo; explicit sign-off would formally close them.
