## Final recommendation

Accept **Option A′ with required amendments**: reusable widget instances remain entry-native; each site-wide region is composed in a seeded, revisioned `widget_area` entry; a thin table maps theme region keys to those entries; dynamic widget behavior runs through bounded, core-controlled resolvers; widget failures are isolated; and Contact Form ships in v1 as an adapter over the existing Forms subsystem.

This follows Tovu’s governing constraints: mutable operator state receives revision/revert protection, runtime behavior stays behind typed boundaries, and plugin-provided behavior remains capability-gated.

## D1 — Region structure and concurrency

**Current position:** Adopt A′. Store each region’s ordered widget-reference list in a seeded `widget_area` entry. Keep `widget_region_bindings` as a thin `(workspace, region_key) → area_entry_id` mapping.

**Changed since Round 1:** Yes. I previously preferred a versioned binding aggregate because it was the smallest correction to the draft. Fable and the Primary correctly identified that A′ is not merely richer—it is the faithful ADR-029 pattern. The ordered list is operator-authored composition, not mapping metadata. Tovu’s UF-07/UF-08 requirements also favor revision and recovery for editor state.

**Strongest argument for the lighter aggregate:** A dedicated head/version plus binding rows could provide OCC and audit history with less JSON mutation and without creating a system entry type.

**Why it does not win:** It recreates revision, revert, change-set integration, reference extraction, authorization, and audit behavior beside the entry substrate. A′ reduces conceptual machinery even if its initial schema looks larger.

**What would move me:** Evidence that regions commonly contain hundreds of items, sustain high-frequency concurrent edits, or require independently addressable placement records. That would favor normalized membership plus a versioned aggregate.

## D2 — Widget resolution contract

**Current position:** Add an explicit, server-side resolver contract. Resolution must be typed, request-scoped, cost-bounded, batched where possible, observable, and completed before Liquid receives render context.

Static widgets may bypass behavioral resolution after validation. Dynamic widgets—Recent Entries, Menu Reference, Contact Form—use registered resolvers that produce validated Render IR or a resolved component model.

The minimum cache story should be:

- Request-scoped memoization and batching in v1, keyed by workspace, widget revision, locale, route context, and normalized dependencies.
- A dependency manifest returned by resolution, identifying entries, terms, menus, form definitions, or query scopes consulted.
- Optional cross-request fragment caching only through a cache port.
- Invalidation from relevant outbox events and widget revision changes.
- TTL as a safety backstop, not the sole correctness mechanism.
- A cache miss or invalidation failure may hurt performance but must not expose stale private data or abort rendering.

**Changed since Round 1:** Strengthened substantially. I identified the missing resolver and failure-budget question, but the Round 2 ledger makes cache dependencies and batching part of the acceptance boundary rather than a follow-up detail.

**Strongest opposing argument:** Avoid specifying caching in this ADR; define only `resolve()` and let the rendering subsystem optimize later.

**Why it does not win:** Resolver output cannot be cached correctly unless dependency identity is part of the contract from the beginning. Retrofitting dependency reporting later changes the interface and risks broad, stale cache invalidation.

**What would move me:** Evidence that Tovu intentionally performs no cross-request render-fragment caching in v1. I would then retain dependency reporting but defer the cache adapter and event consumers.

## D3 — Registry: data versus code

**Current position:** Replace “widget types are data, not code” with a three-part distinction:

1. Type metadata and configuration schema are declarative registration data.
2. Static rendering is core-owned code operating on validated data.
3. Dynamic resolution is executable behavior, core-owned for v1 and ADR-024 capability/trust-tier gated for plugin contributions.

Registry data may name only an allowlisted resolver identifier. It must never carry a module path, arbitrary function name, query text, or executable expression.

**Changed since Round 1:** Clarified. My Round 1 answer already argued for core-controlled resolvers, but Fable’s formulation identifies the exact false abstraction in the ADR.

**Strongest opposing argument:** Every widget ultimately renders through code, so even the registration/behavior distinction is cosmetic.

**Why it does not win:** Declarative schema registration can remain Tier-1-safe and introspectable even though a trusted renderer interprets it. The important security boundary is whether a type contribution installs new executable behavior.

**What would move me:** If ADR-024 already classifies every component registration as executable Code tier, the new ADR should reference that uniform rule rather than introduce a static/dynamic tier distinction.

## D4 — `entry_refs` completeness

**Current position:** Every ref-typed configuration field inside a widget instance must be extracted at the normal entry-write chokepoint, not merely the placement’s reference to the widget.

**Changed since Round 1:** Expanded. I previously called out the general mismatch for binding-row sources, but not the second-order references inside widget configuration.

There is one important qualification to the Primary’s “low-cost fix”: it is low-cost for targets already representable by ADR-022’s reference schema. Live repository comments indicate term-target integrity may not yet be compatible with the existing `entry_refs` representation. Therefore:

- Entry targets—menu entry, success-page entry, form-definition entry if modeled as an entry—reuse existing `ref` extraction.
- Term/taxonomy filters reuse it only if the installed schema supports target kinds.
- Otherwise, ADR-047 must not pretend term safe-delete is free; it needs the already-named extended-reference/term-reference seam.

**Strongest opposing argument:** Query filters such as “category = news” are parameters, not ownership references, and safe-delete can tolerate their disappearance.

**Why it does not win:** They are still semantic dependencies. Deleting one can silently alter Recent Entries output. At minimum they need where-used diagnostics and deterministic missing-target behavior.

**What would move me:** A product decision explicitly classifying selected filters as soft references, accompanied by specified fallback behavior and no safe-delete guarantee.

## D5 — Contact Form v1

**Current position:** Include Contact Form in v1 as a thin reference-and-render adapter over the implemented Forms feature.

**Changed since Round 1:** Yes. My conditional exclusion was based on incomplete evidence. The corrected repository evidence shows an existing submission service, rate limiting, outbox notification subscriber, and implemented `MailerPort`. The widget must reuse those paths and must not create another submission pipeline.

Inclusion remains gated by integration tests proving that the widget-rendered form submits through the existing public Forms route with the same validation, anti-enumeration response behavior, rate limit, and outbox delivery semantics. This is verification of reuse, not a new subsystem requirement.

**Strongest argument for v1.1:** Existing backend pieces do not automatically prove that the generated frontend markup, CSRF/origin posture, accessibility, and route integration are production-ready.

**Why it does not win outright:** Those are acceptance tests for the wrapper. They no longer justify architectural descoping unless the tests reveal an actual Forms defect.

**What would move me:** Evidence that the existing route requires trusted admin context, cannot safely accept the generated public form, lacks required browser security controls, or has unresolved production blockers.

## D6 — Inline embed guardrails

**Current position:** Confirm the block-level atomic `widgetEmbed`, prohibition on recursive widget-in-widget embedding, and a configurable per-document count clamp.

**Changed since Round 1:** No, but the clamp is now a server-enforced invariant rather than editor-only UX. Both live-editor and server-side/AI mutation paths must validate it.

**Strongest opposing argument:** A count clamp is arbitrary and could block legitimate directory or landing-page layouts.

**Why it does not win:** The clamp is a performance and abuse budget, not a design judgment. It can be policy-configurable within a platform maximum.

**What would move me:** A resolver architecture that proves cost independently of embed count, though recursion prohibition should remain for v1.

## D7 — Reuse versus duplication

**Current position:** Default to reuse when placing an existing instance. “Create new” and “Duplicate” remain explicit commands. At edit time, show “used in N places” and offer either change-everywhere or detach/copy-and-edit-here.

AI operations must encode intent explicitly: `widgets.placeExisting`, `widgets.createAndPlace`, or `widgets.detachPlacement`.

**Changed since Round 1:** The substance is unchanged, but Fable’s edit-time choice is better than presenting the same modal during every placement.

**Strongest opposing argument:** Default reuse creates the more damaging surprise: editing one visible item changes many pages.

**Why it does not win:** The surprise occurs during editing, so that is where the system has full where-used information and should intervene. Silent duplication at placement destroys the central-reuse promise permanently.

**What would move me:** User testing showing operators consistently understand placements as local copies and find edit-time warnings too late. Then placement could require an explicit choice without changing the data model.

## D8 — Render-time failure isolation

**Current position:** A widget failure must never abort the page render. Core converts each failure into a typed resolution outcome and renders either nothing or a safe theme-compatible placeholder according to environment and policy.

Public output must not expose stack traces, configuration secrets, recipient addresses, or internal identifiers. Preview/admin output should expose a correlation ID and actionable diagnostic.

**Changed since Round 1:** No; this was already a required correction. It is now explicitly tied to the resolver result type and observability contract.

**Strongest opposing argument:** Silently degrading hides serious publishing defects.

**Why it does not win:** Isolation and visibility are separate. Public availability should survive while preview diagnostics, logs, metrics, and admin alerts make the defect conspicuous.

**What would move me:** Nothing toward page-wide failure for ordinary widgets. A separately classified critical component might block publishing during preflight, but not crash an already-published public page.

## D9 — Region scope

**Current position:** Site-wide bindings only in v1. Inline embedding handles page-specific placement. Preserve a future seam for bounded scopes, without implementing fallback inheritance now.

**Changed since Round 1:** No. A′ further reinforces this because a future scoped binding can point to another area entry without changing area composition.

**Strongest opposing argument:** Inline embedding cannot express a shared sidebar for all pages in a section or content type.

**Why it does not win for v1:** That is a real future use case, but it requires explicit precedence and explainability. Shipping a premature override hierarchy would create the UF-07-style “why did this page not update?” problem.

**What would move me:** A committed v1 requirement for section-wide or content-type-wide shared composition that cannot be represented by theme structure.

# Concrete artifacts

## 1. Sample design

### Region and entry shapes

```sql
-- Existing entries table, shown conceptually.
entries (
  id            uuid primary key,
  workspace_id  uuid not null,
  type          text not null,       -- includes system type 'widget_area'
  slug          text not null,
  status        text not null,
  body_json     json not null,
  version       integer not null,
  ...
);

create table widget_region_bindings (
  workspace_id  uuid not null,
  region_key    text not null,
  area_entry_id uuid not null references entries(id),
  primary key (workspace_id, region_key),
  unique (workspace_id, area_entry_id)
);
```

Seeded area entry:

```json
{
  "id": "area_footer",
  "workspaceId": "ws_1",
  "type": "widget_area",
  "slug": "__region/footer",
  "status": "published",
  "version": 7,
  "bodyJson": {
    "schemaVersion": 1,
    "items": [
      {
        "placementId": "plc_social",
        "widgetRef": "widget_social",
        "enabled": true
      },
      {
        "placementId": "plc_contact",
        "widgetRef": "widget_contact",
        "enabled": true
      }
    ]
  }
}
```

`placementId` is stable within the aggregate for diagnostics, patch generation, and UI keys. It does not become an independently mutable database entity.

Required invariants:

- The binding and area entry belong to the same workspace.
- `area_entry_id` references only `type = 'widget_area'`.
- A region key has exactly zero or one binding per workspace.
- `items` is ordered and contains unique `placementId` values.
- Widget references point to compatible, non-trashed widget instances.
- Area mutation uses the existing entry version precondition and revision transaction.
- Region areas cannot be embedded as widgets.

### Resolver and registry sketch

```ts
type WidgetCapability =
  | "static"
  | "entry-read"
  | "bounded-query"
  | "form-reference";

interface WidgetTypeRegistration<TConfig> {
  typeKey: string;
  configSchema: JsonSchema;
  placementContexts: readonly ("region" | "rich-text")[];
  capability: WidgetCapability;
  rendererId: string;
  resolverId?: WidgetResolverId; // allowlisted identifier only
  maxResolveCost: number;
}

interface WidgetResolveContext {
  workspaceId: string;
  locale: string;
  route: ResolvedRouteContext;
  preview: boolean;
  deadline: AbortSignal;
  loaders: WidgetRequestLoaders;
}

interface WidgetDependency {
  kind: "entry" | "term" | "menu" | "form-definition" | "query-scope";
  id: string;
  version?: string | number;
}

interface WidgetResolution {
  node: RenderIR;
  dependencies: readonly WidgetDependency[];
  cache: {
    visibility: "public" | "private" | "uncacheable";
    maxAgeSeconds: number;
  };
  cost: number;
}

type WidgetResolutionResult =
  | { ok: true; value: WidgetResolution }
  | {
      ok: false;
      code:
        | "unknown-type"
        | "invalid-config"
        | "missing-dependency"
        | "budget-exceeded"
        | "timeout"
        | "resolver-failed";
      diagnosticId: string;
    };

interface WidgetResolver<TConfig> {
  resolve(
    instance: ValidatedWidgetInstance<TConfig>,
    context: WidgetResolveContext
  ): Promise<WidgetResolutionResult>;
}
```

The orchestrator enforces the deadline and cost budget; a resolver cannot merely claim compliance. Request loaders batch identical entry, menu, form, and bounded-query reads.

## 3. Specs-level requirements

### Region-area aggregate

- **RA-01:** Creating or activating a theme region binding creates or selects exactly one same-workspace `widget_area` entry.
- **RA-02:** Add, remove, reorder, enable, and detach operations require the area entry’s base version.
- **RA-03:** One successful mutation atomically updates the entry, increments its version, writes a revision, refreshes extracted references, appends audit data, and emits its outbox event.
- **RA-04:** A stale base version performs no partial write and returns a typed conflict containing the current version.
- **RA-05:** Restore of an earlier revision restores ordering and reference projection through the same chokepoint.
- **RA-06:** Missing, trashed, cross-workspace, or incompatible widgets are rejected on new writes; legacy invalid references resolve diagnostically without crashing public rendering.
- **RA-07:** The area entry is system-managed: it cannot be routed publicly, selected as an ordinary widget, or recursively embedded.
- **RA-08:** Concurrent reorder tests must prove that one of two writes against the same base version conflicts.

### Resolver contract

- **WR-01:** All configuration is schema-validated before resolver invocation.
- **WR-02:** Each type declares supported placement contexts, resolver/renderer identifier, capability class, maximum item count, and cost budget.
- **WR-03:** Recent Entries enforces an absolute platform maximum independent of user configuration and performs no unbounded scan.
- **WR-04:** Resolution receives only scoped read loaders, never a raw database handle.
- **WR-05:** Duplicate dependency reads within one page render are batched or memoized.
- **WR-06:** The page orchestrator enforces per-widget deadline and total page widget budget.
- **WR-07:** Resolvers return validated IR plus dependencies and cache visibility. Invalid IR is treated as resolver failure.
- **WR-08:** Unknown type, invalid configuration, missing target, timeout, budget excess, and unexpected exception each produce deterministic diagnostics and an isolated fallback.
- **WR-09:** Public error output leaks no secret or internal identifier; logs and preview diagnostics share a correlation ID.
- **WR-10:** Cache tests prove invalidation after widget updates and dependency updates. Private/contextual results must never enter a public cache.
- **WR-11:** Resolver contract tests run against every built-in dynamic widget.

### Contact Form adapter and references

- **CF-01:** Configuration contains a ref-typed `formDefinitionId`; it is included in where-used extraction where the target model supports it.
- **CF-02:** Rendering reads only public/renderable form fields and never exposes notification recipients or delivery configuration.
- **CF-03:** Submission uses the existing Forms public route/service without bypassing its validation or rate limiter.
- **CF-04:** A successful submission follows the existing persistence, outbox, notification, and webhook behavior.
- **CF-05:** Missing or unpublished definitions produce an isolated unavailable placeholder and an admin diagnostic.
- **CF-06:** Integration tests cover valid submission, invalid payload, rate limit, notification enqueue, inaccessible definition, and duplicate-submit behavior already guaranteed by Forms.
- **REF-01:** Every declared config reference has an extractor contract test.
- **REF-02:** Soft references must be explicitly labeled and have specified missing-target behavior.

## Non-technical overview

This design lets someone create a useful item—such as a contact form, menu, recent-post list, or social-links panel—once and safely reuse it around the site. Site areas such as footers retain revision history and can be restored after a mistaken edit. Data-driven widgets have strict speed and safety limits, and one broken widget cannot take down an entire page. Contact forms reuse Tovu’s existing protected submission and email system instead of creating a second implementation.

## Remaining framing gap

The ledger covers the immediate ADR decision, but one decomposition should remain explicit: **widgets are reusable referenced components, not the universal representation of every local content block**. Future page-building work should retain cheap inline-value blocks for one-off local presentation and use widget references only when persistent identity or dynamic behavior is valuable. Otherwise every heading, callout, or decorative fragment risks becoming library clutter.

That does not require another v1 mechanism beyond the atomic reference node. It is a boundary statement preventing ADR-047 from expanding later into an all-purpose mini-plugin or page-builder system.
