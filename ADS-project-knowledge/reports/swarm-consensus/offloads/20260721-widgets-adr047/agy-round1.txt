^D### 1. Recommended Option: Option A (Entry-native widget instances, dual placement)
Option A is the only architecture that robustly satisfies all stated requirements without violating existing constraints. By defining widgets as seeded `entries`, it brilliantly leverages the massive amount of generic infrastructure Tovu has already built and audited (ADR-022, 029, 016). It directly answers the owner's requirement to build one configured instance and reuse it across multiple pages by explicitly separating the widget's *identity* from its *placement*. Because it hooks into the `entry_refs` index, AI agents can immediately diagnose broken placements and answer "where is this used?" without needing bespoke widget-crawling logic. Furthermore, resolving these instances *before* they hit the Liquid renderer perfectly honors the ADR-020 boundary: the theme remains pure, dumb, and sandboxed.

### 2. Rejected Options
**Option B (Pure stateless blocks):** I strongly reject this because it structurally fails the "same configured instance on multiple pages" requirement. If a non-expert user (or an AI) configures a complex Contact Form with specific routing rules, and places it in both a sidebar and a footer, Option B duplicates that state. When the user later asks the AI to "update the contact form email," the AI now has to hunt down disconnected block nodes across the site to avoid state drift. This breaks the promise of centralized management that the word "widget" implies.

**Option C (Page-local structured composition only):** I reject this because it completely abandons the concept of theme-declared global regions, which are fundamental to the non-expert CMS mental model. Forcing a user to manually construct headers, footers, and sidebars on a per-page basis using local arrays is an exhausting UX. While it works for headless systems like Payload, it violates Tovu's requirement to serve non-expert users who expect a theme to provide a cohesive, site-wide structural scaffolding out of the box.

### 3. Positions on the 5 Open Questions (under Option A)
1. **Region binding scope:** Site-wide only for v1. Introducing per-page region overrides creates a complex, cascading inheritance model that is notoriously difficult for both non-experts and AI to debug (e.g., "Why didn't my sidebar update on the About page?"). If a specific page needs a bespoke layout, the user should rely on the inline TipTap embed (`widgetEmbed`) for that specific page, leaving the global region predictable.
2. **Freeform inline embed vs. structured blocks-array:** Stick with the freeform inline embed (TipTap `widgetEmbed` node). Tovu already relies on TipTap/ProseMirror for agentic document editing (ADR-016). Adding a separate "blocks-array" field creates two parallel ways to build a page's content, fracturing the AI's toolset and the user's mental model.
3. **Shared-instance vs. duplicate-on-place default:** Default to "shared-instance" (reuse), but the UI must make this explicit. When placing a widget, the flow should be: select type -> create new instance OR pick from existing instances. The mental model of a "widget" inherently implies a reusable object.
4. **Core v1 widget-type list:** The drafted list (Text, Contact Form, Recent Entries, Social Links, Menu) is highly pragmatic. Capability requirements should be strictly bounded: Contact Form needs an outbox/mailer capability; Recent Entries needs scoped, read-only entry querying; the rest are pure data and require no escalated system capabilities. 
5. **Region-binding concurrency:** Do not over-engineer this. Since a region is an ordered list that changes infrequently, use optimistic concurrency control on the region's overall state (e.g., a version integer on the region binding group), or adopt fractional indexing (lexicographical strings) for the `position` column so reorders don't require rewriting all rows.

### 4. Blind Spots
- **Unlisted Option:** We failed to list a "Global Entry" hybrid. What if a region (like a sidebar) is literally just a standard `entry` document (type='region'), and we rely *exclusively* on the inline TipTap `widgetEmbed` to place widgets inside it? This would collapse the two placement mechanisms down to one.
- **Missing Question:** "How are widget data resolutions batched to avoid N+1 query performance cliffs?" If a page loads a sidebar with 5 widget references, does the server-side resolution step execute 5 separate DB queries before passing the IR to the Liquid renderer, or is there a dataloader/batching guarantee?
- **Wrong Assumption:** The framing assumes that non-expert users naturally understand the database distinction between an "instance" and a "placement." In reality, users often edit a widget in a sidebar WYSIWYG interface expecting *only* that specific sidebar to change. The assumption that users want strict data DRY-ness (Don't Repeat Yourself) over local WYSIWYG edits is a major UX risk that requires careful UI signaling when an AI or human edits a shared instance.

### 5. Unlisted-option check
There is a strong architectural simplification not listed: **Option D (The "Regions as Entries" model).** Instead of building a new `widget_region_bindings` table, we define "Regions" as regular content entries (e.g., a persistent entry with `slug='global-sidebar'`). The theme's Liquid renderer simply queries this single entry and renders its `bodyJson`. Widget placement is then handled *entirely* by Option A's inline TipTap `widgetEmbed` mechanism inside that entry. This is stronger because it removes the need for the second placement mechanism (the binding table) entirely, allowing the AI to edit sidebars using the exact same CopilotKit document-editing tools it uses for standard pages. However, Option A as drafted remains acceptable and highly defensible for v1 if strict structural schemas (rather than rich-text documents) are preferred for regions.
