# E2E-1108: Playwright journeys run on cloud/combine

Report only. Nothing in the product or the tests was changed.

- **Base:** Tovu `cloud/combine` @ `f4b2d1531`, Jini `cloud/combine` @ `60807a9ca` (linked into Tovu with `npm run link:jini`).
- **Report branch:** Tovu `cloud/e2e-1108`.
- **Box:** 4 cores, 16 GB, no swap, no Postgres. Node 24.22.2 (nodejs.org tarball). Playwright 1.61.1 driving headless Chromium.
- **Wall clock used:** about 2 h 15 min of the 4 h cap. Two lanes (at most 2 browser workers). Free memory never went below about 10 GB.
- **Raw output:** `cloud/reports/raw-e2e-1108/` holds every lot's list output as `<lot>.txt`, plus its `.stderr.txt` and memory samples.
- **Screenshots:** `cloud/reports/e2e-1108-shots/` (5 PNGs, 212 KB).

## Plain-language summary

**What is proven end to end here.** Real headless Chromium drove the real admin bundle against the real API server on throwaway scratch sites, and these journeys passed (40 tests):

- **Pages:** an HTML page is created, published and served on the public site. The page preview sandbox blocks `target=_top`, `window.top` scripts, and popups that would replace the admin.
- **Collections:** a content type is defined in the modal, an entry is added and published, and it renders publicly. Conflict copy for two tabs, single publish on double-click, duplicate-slug refusal, required-field refusal, and escaping of unicode and markup all work.
- **Forms:** a form is built, embedded, and submitted by a logged-out visitor, and the admin sees the answer. Honeypot hits are discarded. The browser shows an alert when rate-limited. Anonymous callers cannot list submissions.
- **Themes:** activating a theme changes the public home and reverting restores it. Double-click activates once.
- **Menus and widgets:** an unknown widget id renders nothing (no 500). Two-tab conflicts and simultaneous saves never both win. Double-save creates one menu. A `javascript:` URL is neutralised.
- **Settings and accessibility:** the chosen language persists and drives the nav. Admin screens at 390 px have no sideways scroll. Skip-to-content works. The post status select has a name.
- **Assistant (real tool call):** this runs through the real agent daemon with the fake BYOK model server. A scripted `tool_use` creates a real row, invalid tool input is rejected, and double-clicking Send runs one turn. No real model and no credentials were used.
- **Release 0.1.13 operator journeys:** menu HTML mode persists. Themes Explore "Save as original" and Reset work. Theme cards get their own captures. Recent errors are grouped, expand, copy and refresh.
- **Posts:** 60 posts are all reachable from the list.
- **Isolated (cold) bug pins:**
  - Plugin install by ZIP drop, folder upload and WebMCP.
  - Agent-plugin upgrade 1.0.0 → 1.0.1 and fixture cleanup.
  - Per-IP rate limiting on the public site-chat endpoint.
  - The login screen names the real cause when the API is down.

**What is NOT proven.**

1. **`npm run e2e:journeys` as shipped runs 0 tests.** Two files throw while loading, and Playwright aborts the whole suite:
   - `smoke.journey.ts`: "ADMIN_PANELS not found or empty".
   - `admin-visual.pins.journey.ts`: "ADMIN_PANELS must be a literal array".

   Both parse `apps/admin/src/panels.tsx` expecting an array literal. Since `3b8c3a13` (2026-11-03, route-level lazy loading) that export is `PANELS.map(...)`. Everything else here was run by naming the other 33 files explicitly.
2. **Almost every bug pin fails in setup.** This covers 289 of the 304 offline pin tests: all except the 15 `@isolated-site` (cold) pins. The warm pin site (`resettable-pin-api.ts`) waits 60 s for an agent daemon it expects to have started at boot. Since `b389d729` (2026-11-03) the daemon supervisor only registers at boot and spawns on demand ("Registration is cold. Demand callers await…", `daemon-supervisor.ts:673`). So the daemon never starts, and the pin fails with "Pin snapshot failed; site cannot be reused" / "The owned pin daemon never became ready".
   - I watched it live: no daemon child ever appeared under the pin API process.
   - A solo re-run with nothing else on the box failed the same way (`s1-solo-users-pin.txt`).
   - Each such pin spends about 65 s in setup before failing (the 1–8 ms durations in the tables are only the test body). Running all of them would have taken about 5 h, past the cap. So each warm-pin file was run with `--max-failures=3`, enough to show the same cause per file. Its remaining tests are listed as **not run (blocked)**, not as pass or fail.
3. **Core content flows are unverified by these journeys:**
   - Post lifecycle (create → publish → public → unpublish).
   - Post stress tests.
   - Media upload, trash and delete.
   - Users and roles.

   The tests are stale against current UI (New Post, the Upload button, the login card); see the classifications. The product may well work, but no journey proved it.
4. **Visual baselines prove nothing on Linux.** All 628 committed screenshots are `*-chromium-darwin.png`. Every `toHaveScreenshot` failed with "A snapshot doesn't exist … -linux.png". I ran with `--update-snapshots=none` so no baseline files were written into the repo.
5. **Stubbed assistant card journeys fail here.** These are `assistant.journey.ts` and part of `release-0113-ui.journey.ts`. The dock shows "No usable CLI is selected" and the composer stays disabled, because no agent CLI exists on this box by design.
6. **Not run at all:** the desktop app (Electron), soak tests, and every live, real-service or credentialed spec. See the lists below.

**Product-bug candidates.** These are side effects and logs, not failing assertions:

- **Background workers outlive their store.** After the pin API stops every boot module and closes the store (`resettable-pin-api.ts` `close()`), these loops keep firing against the closed database: `[site-search] reconcile`/`backfill`, `[webhooks] delivery tick`, `[post-go-live-sweep]` and `[domain-dns] due-bindings sweep` all log "TypeError: The database connection is not open". Their module `stop()` does not stop them.
- **A journey wrote into the repo checkout.** During the run, `content/themes/.preview-refresh.json` appeared in the checkout at 06:47. It was written by the theme preview-refresh path (`theme-preview-refresh.ts` / `theme-static-assets.ts`), i.e. into bundled content rather than the scratch site dir. I deleted it. In a packaged app that location would be inside the app bundle.
- **Copy mismatch on the empty Media page.** It says "Use Upload image above…" (`apps/admin/src/features/media/Media.tsx:1123`), but the button is now "Upload image or video".

No failing journey turned out to be a confirmed product bug. Every one of the 138 failures is classified below as a stale test (102) or environment (36). Three of those calls are marked *probable* in the evidence column.

## Canary (≤25 min): passed

- `npx playwright install chromium` failed: the proxy refused `cdn.playwright.dev` with 403 "no rule or allowlist entry allows host" (`canary-pw-install.txt`).
- The box already has Chromium (`/opt/pw-browsers`, revision 1243). Playwright 1.61.1 wants revision 1228, so I pointed `PLAYWRIGHT_BROWSERS_PATH` at a scratch folder of symlinks (`chromium-1228 → chromium-1243`). Nothing in the repo or `/opt` changed. This is the real browser, not a mock.
- One scratch site booted. `users.journey.ts` ran in a real browser in 50 s: 3 tests, which failed on a stale selector. Both scratch trees were deleted.

## How it was run

- Every lot ran under `env -i` with only `HOME`, `PATH` (Node 24 first, no `claude` binary), `LANG`, `TERM` and `PLAYWRIGHT_BROWSERS_PATH`. There were no tokens, no `ANTHROPIC_*`/`GH_TOKEN`/cloud credentials, and no proxy variables, so nothing could reach a real service. The harness additionally blanks vendor keys.
- The command was `playwright test --config=development/playwright.journeys.config.ts --update-snapshots=none …`, with the config's own one worker per run and two lanes on disjoint port bases (9100/9200).
- Lots:

  | Lot | What it ran |
  |---|---|
  | `b1-pages` | pages, pages.pins |
  | `c1-nonpin` | all 14 remaining non-pin journey files |
  | `p-<file>` | each warm-pin file, `--max-failures=3`, excluding `@isolated-site`, `@live`, `@real-service` |
  | `p-cold` | every `@isolated-site` pin |
  | `p-auth-full` | `auth.pins.journey.ts` in full |
  | `m1-mobile-visual` | the separate mobile-visual config |
  | `s1`, `s2` | solo confirmation re-runs |

- A first attempt (`x-interrupted-*.txt`) was stopped with SIGINT after it showed the warm-pin setup cost. Its two `admin-chat-width` results, which run on the main site, are included.
- **Cleanup proof:**
  - The harness reporter logged `[journeys cleanup] Deleted isolated site and runtime: …` for each config-level site.
  - Pin trees whose own cleanup failed ("Pin file cleanup failed") were removed by the harness's worker fallback. One orphan from the interrupted run was removed by hand with `chmod -R u+w` then `rm -rf`.
  - At the end, `ls -d /tmp/tovu-*` gives "No such file or directory". No playwright, start-journey-site, agent-daemon or chrome processes remain.
  - `development/test-results`, `development/playwright-report`, `/tmp/playwright-transform-cache-0` and the stray `content/themes/.preview-refresh.json` were deleted.
  - The committed screenshots were copied out of test-results first. Trace paths cited in raw output no longer exist.
