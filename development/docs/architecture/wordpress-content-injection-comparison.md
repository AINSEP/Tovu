# WordPress vs. Tovu: Content-Injection Capability Comparison

**Status:** research/decision-support document, not a spec. Written to inform the design of Tovu's content-injection system (how blocks, widgets, menus, partials, and raw HTML get placed into pages and themes) by comparing it against what WordPress does in the same space today.

**Scope note on "today."** WordPress-side claims are sourced against current `developer.wordpress.org`/`wordpress.org` documentation via live web search, not model memory — every mechanism below carries a citation. WordPress 7.0 shipped May 20, 2026 ([WP Engine's release writeup](https://wpengine.com/blog/wordpress-7-0-release/); [Make WordPress Core, block visibility dev note](https://make.wordpress.org/core/2026/03/15/block-visibility-in-wordpress-7-0/)), so this reflects the current release, not the WordPress most engineers still picture from the shortcode/widget era.

**Scope note on Tovu's state.** Grounded by reading source directly at `HEAD 22aa4ba2fad1b6469a3a787d5582510f673299fc` on `refactor/jini-admin-extraction`, cross-checked against `codebase-memory-mcp`'s indexed snapshot of the same commit. As of this analysis, **the in-flight marker-vocabulary unification** (folding to exactly `data-embed-type` / `data-embed-id` / a JSON `data-embed-config`, adding `type="partial"` for theme partials and an `html` widget type for saved raw-HTML snippets) **had not landed** — no matching commit on any branch, no uncommitted working-tree changes. Today's real shape is `data-embed-type` / `data-embed-id` / `data-embed-name` / `data-embed-variant` (four flat attributes, `src/widgets/html-embeds.ts:43-56`), with four registered embed types (`widget`, `form`, `media`, `post` — `src/widgets/resolver-service.ts:540-545`) and theme partials still resolved through a *separate* mechanism (`data-tovu-slot`, `src/features/theme/static-render.ts:259-285`), not through the embed pipeline at all. Everywhere this document discusses the planned unification, it is named explicitly as *planned*, not observed.

**A documentation-drift catch, disclosed because it's directly relevant to trusting citations below.** `development/docs/themes/theme-authoring-guide.md` §8.2 states "nested nav/submenus never render, on any static theme." That was true until the commit at the current `HEAD` (`77f567d feat(themes): nested menu tree rendering + docs sidebar in basic`, same day, same session) added `renderMenuTree()` and an opt-in `data-embed-variant="tree"` marker (`src/features/theme/static-render.ts:130-165`, wired into one marker in one theme — `src/themes/static/basic/pages/blog-sidebar-template.html:28`). The guide itself wasn't regenerated after that commit landed. Treat the guide as slightly behind `HEAD` on this one point; this document uses the verified-against-source state instead.

## Part 1 — Capability table

| Mechanism | What WordPress does | What Tovu does | Verdict |
|---|---|---|---|
| **Shortcodes** | `[tag attr="x"]` macros parsed out of post content and replaced by a registered PHP callback (`add_shortcode()`); introduced WP 2.5 specifically so authors could trigger dynamic behavior without writing raw PHP/HTML ([Shortcode API, developer.wordpress.org](https://developer.wordpress.org/apis/shortcode/); [Shortcodes, Plugin Handbook](https://developer.wordpress.org/plugins/shortcodes/)) | `data-embed-type="X" data-embed-id="Y"` empty-div markers in `body_html`, scanned by regex and substituted server-side (`src/widgets/html-embeds.ts:139-164`) — same *purpose* (author-typed inline dynamic token), different syntax (HTML attribute convention instead of a bracket macro language) | **Has it, different shape.** Tovu's version is arguably better-shaped for its context (no custom mini-parser, degrades safely to inert markup on a match failure — see html-embeds.ts's own header) but only self-closing markers are supported; WP shortcodes support enclosing content (`[tag]...[/tag]`) passed to the callback, which Tovu's convention structurally cannot do (see html-embeds.ts:24-31 on why empty-div-only was chosen). |
| **Gutenberg blocks** (HTML-comment-delimited markup, `block.json`, static vs. dynamic rendering) | Post content is a sequence of blocks serialized as HTML comments (`<!-- wp:paragraph {...} --> ... <!-- /wp:paragraph -->`), one per block instance, each carrying JSON attributes in the comment itself ([Markup representation of a block](https://developer.wordpress.org/block-editor/getting-started/fundamentals/markup-representation-block/)). `block.json` declares `name`, `attributes`, `supports`, `render` (PHP file for server-side/dynamic rendering), `editorScript`/`script`/`viewScript`, `parent`/`ancestor`, `variations`, etc. ([block.json reference](https://developer.wordpress.org/block-editor/reference-guides/block-api/block-metadata/)). Static blocks save their markup into the DB; dynamic blocks regenerate output on every render via `render_callback`/`render` ([Static or Dynamic rendering](https://developer.wordpress.org/block-editor/getting-started/fundamentals/static-dynamic-rendering/)) | Two different, non-unified analogs. (1) `doc`-format Posts store a TipTap `bodyJson` tree — structured, versioned, but a proprietary rich-text schema with no per-node `render_callback`/attribute-schema/registry-with-versioning story (`src/widgets/types.ts:212-216`'s `WidgetEmbedNode` is the one "component-like" atom inside it). (2) The `declarative` theme tier *does* have a real block-registry-and-block-tree model — `{"type":"doc","content":[...]}` referencing a fixed `COMPONENTS` registry (`tovu/site-header`, `tovu/hero`, `tovu/section`, etc. — `render.ts:614-627` per the theme guide) — structurally close to Gutenberg's static-block model. But it has exactly one theme, explicitly labeled "reference only — not wired into any site" (theme-authoring-guide.md §2.2) | **Partially has it, split across two unconnected mechanisms, neither used for real authoring.** No unified "typed, versioned, registry-backed content atom with a stable serialization format" spanning both Posts and Pages the way a WP block spans post/page/pattern/template-part uniformly. |
| **Block patterns** (unsynced) | A named, insertable starting arrangement of blocks — copy-once, no ongoing link back to a source (`register_block_pattern()`, PHP: `title` + `content` (raw block HTML) + optional `description` — [reference](https://developer.wordpress.org/reference/functions/register_block_pattern/); [Block Patterns docs](https://wordpress.org/documentation/article/block-pattern/)) | Nothing equivalent. A widget instance is a single typed leaf (`src/widgets/registry.ts:29-141` — exactly 5 types: `text`, `social-links`, `recent-entries`, `menu`, `contact-form`); there is no "save this arrangement of N widgets as a starting point" primitive | **Lacks it.** |
| **Synced patterns** (formerly "reusable blocks") | The same pattern concept, but WordPress-managed and DB-stored so an edit anywhere propagates everywhere the pattern is placed — renamed from Reusable Blocks in WP 6.3 ([Synced Patterns docs](https://wordpress.org/documentation/article/reusable-blocks/); [Synced Patterns: The Evolution of Reusable Blocks](https://wordpress.org/news/2023/07/synced-patterns-the-evolution-of-reusable-blocks/)). Cannot be created programmatically — they only exist as DB content, per environment ([same source](https://wordpress.org/documentation/article/reusable-blocks/)) | Nothing equivalent — no "one editable source, many placements" composition primitive of any kind | **Lacks it.** This is the sharpest gap: Tovu has reusable *leaf* widgets (one widget instance, many `widgetEmbed`/`data-embed-type="widget"` placements already share this "edit once, updates everywhere" property at the single-widget level — see `resolvePageWidgets`, `src/widgets/resolver-service.ts:174-231`) but nothing that groups multiple widgets/content into one reusable, synced *composition*. |
| **Template parts / Full Site Editing** | Header/footer/sidebar/etc. moved out of theme PHP files into `wp_template_part` posts — ordinary revisioned, permission-gated, block-editable content, registered via `theme.json`'s `templateParts` array (`{name, title, area}`) and discoverable/editable in the Site Editor ([Template Parts, Theme Handbook](https://developer.wordpress.org/themes/global-settings-and-styles/template-parts/); [Site Editing Templates](https://developer.wordpress.org/block-editor/explanations/architecture/full-site-editing-templates/)). This landed with FSE (WP 5.9, 2022) | **Slots** (`data-tovu-slot="nav"`/`"footer"`) resolve to raw files on theme disk (`nav.html`, `footer*.html`), matched by filename convention or `theme.json`'s `slots` map (`src/features/theme/theme.ts:124-142`), read once at server boot with **no hot reload** (theme-authoring-guide.md §8.9) and **no revision history, no permission model distinct from filesystem access, no admin-UI editing** short of the `theme_write_file` agent tool or a direct file edit | **Lacks it — and this is the exact decision in flight right now.** The planned `type="partial"` unification (per this dispatch's brief) could either (a) genuinely move partial content into revisioned CMS entries, closing this gap the way WP's FSE did, or (b) just rename the existing file-backed mechanism to look like the other embed types while the content still lives on disk with none of the properties that make WP template parts valuable. See Part 2's #1 build item — this is the highest-leverage decision on the table. |
| **Widgets + widget areas** | Historically: `WP_Widget` PHP classes placed into `register_sidebar()`-declared areas, rendered via `dynamic_sidebar()` ([Sidebars, Theme Handbook](https://developer.wordpress.org/themes/classic-themes/functionality/sidebars/); [`register_sidebar()`](https://developer.wordpress.org/reference/functions/register_sidebar/)). Since WP 5.8, the Widgets screen is block-based — classic widgets appear via a compatibility "Legacy Widget" block ([Block-based Widgets Editor](https://wordpress.org/documentation/article/block-based-widgets-editor/); [Legacy Widget block](https://developer.wordpress.org/block-editor/how-to-guides/widgets/legacy-widget-block/)). Block themes have **no** Widgets screen at all — widget areas became template parts (see row above), and the classic `WP_Widget` model is only reachable via a separate Classic Widgets plugin, and only on classic (non-block) themes | 5 typed widget kinds (`text`, `social-links`, `recent-entries`, `menu`, `contact-form` — `src/widgets/registry.ts`), each a seeded `entries` row (`type='widget'`), each declaring a `WidgetCapability` (`static \| query \| form \| entry-reference` — `src/widgets/types.ts:71`) and enforced `clamps` (`maxItems`, `timeoutMs` — `types.ts:90-93`). Placed into theme-declared `regions` (`theme.json`'s `regions` field, `theme.ts:56-64`) or embedded inline. **Zero live themes declare a `regions` field** (theme-authoring-guide.md §6.5, verified: zero `"regions"` hits under `src/themes/`) | **Has the core mechanism, ahead on typing/safety, behind on real-world usage.** WP's widget/widget-area system is genuinely legacy scar tissue mid-migration (see Part 2); Tovu's typed-capability version is a cleaner design that simply has no live consumer yet — worth noting as a "not yet exercised" risk, not a design gap. |
| **`theme.json`** (settings + styles + template registration) | Two-part contract: **settings** = design tokens exposed as UI controls in the editor (color palette, font sizes, spacing scale) that authors pick from; **styles** = the CSS those settings (plus arbitrary custom CSS) compile to, applied globally/per-element/per-block; also registers template parts ([Global Settings and Styles](https://developer.wordpress.org/themes/global-settings-and-styles/); [theme.json overview](https://developer.wordpress.org/themes/core-concepts/global-settings-and-styles/)) | A `theme.json` that means something different: identity (`id`/`name`/`version`), `tier` (which render engine), `regions`, `slots`, `modes`/`defaultMode`, `postTemplate` — structural/behavioral configuration (`src/features/theme/theme.ts:38-122`). Design tokens live in a **separate** file, `tokens.json`, a flat CSS-custom-property map with **no editor-facing exposure at all** — an AI-authored Page follows a soft convention ("reference a token with a literal fallback," `src/features/pages/skeleton.ts:33-36`) rather than being constrained/assisted by any UI picker | **Same filename, unrelated concept — and Tovu's design-token story is the weaker one.** WP's settings→UI-control pipeline means an author literally cannot pick an off-palette color by accident in the block editor; Tovu's tokens are invisible to any authoring surface, enforced only by convention. |
| **Custom HTML block + `unfiltered_html` capability** | A block that accepts raw HTML verbatim, PLUS, since WP 7.0, separate CSS/JS editing panels — but those panels (and unsanitized raw output generally) are gated behind the `unfiltered_html` capability; a user without it gets the HTML run through `wp_kses()` before save, stripping `<script>`/`<iframe>` etc. ([Custom HTML block docs](https://wordpress.org/documentation/article/custom-html/); [Custom HTML, Block Editor Handbook](https://developer.wordpress.org/block-editor/reference-guides/core-blocks/core-blocks-widgets/core-block-html/)). Single-site Administrators have this capability; on Multisite, only Super Admins do | `bodyFormat: "html"` Pages accept `body_html` as trusted, unsanitized-by-this-layer markup by design (`html-embeds.ts:33-36`'s own disclosure: "nothing this file does widens that trust boundary"). Tovu **already designed** the WP-equivalent gate — SPEC-047 REQ-9 calls for a distinct `pages.edit_html` permission grantable to `admin` but not `editor` — but it **is not seeded yet**, so both `pages_read_html`/`pages_write_html` currently check only the ordinary `content.read`/`content.write` permissions, explicitly disclosed as "a gap and not a decision" (`src/features/pages/tool-registrations.ts:25-31`) | **Designed but not finished, not absent.** This is the one row where Tovu isn't behind conceptually — it's behind on wiring a decision it already made. Closing it is a config/seed change, not new design (Part 2 build item #2). |
| **oEmbed** | A safelisted-provider mechanism (YouTube, Twitter/X, Vimeo, etc.) that turns a pasted URL into a rich embed automatically, extensible via `wp_oembed_add_provider()` and the `oembed_providers` filter ([oEmbed, Advanced Administration Handbook](https://developer.wordpress.org/advanced-administration/wordpress/oembed/); [`wp_oembed_add_provider()`](https://developer.wordpress.org/reference/functions/wp_oembed_add_provider/)) | Nothing equivalent. The `media` embed type resolves *internal* assets (`resolveMediaTypeEmbeds`, `resolver-service.ts:400-467`) — no path for embedding a third-party URL (YouTube video, tweet) at all | **Lacks it.** |
| **Hooks and filters** (`the_content` and the ~2,000+ other core filters, as third-party render-pipeline extension points) | Actions run code at a point with no return value; filters intercept and transform a value and must return it. `the_content` is the canonical example — every registered callback gets to rewrite post content before display ([Hooks, Plugin Handbook](https://developer.wordpress.org/plugins/hooks/); [`the_content`, hook reference](https://developer.wordpress.org/reference/hooks/the_content/)) | No equivalent extension point of any kind. `HTML_EMBED_RESOLVERS` (`resolver-service.ts:540`) and `CORE_RESOLVERS` (`resolvers/index.ts`, per `registry.ts`'s own header) are **closed maps** — adding a resolver is a core code change, explicitly ADR-024-gated for any future plugin-contributed type, never a runtime registration a third party can hook into | **Deliberately lacks it — correctly.** See Part 2: this is WP's single largest security/stability liability, not a feature worth copying. |
| **Block bindings** | Binds a specific block *attribute* (not the whole block) to a live data source — `core/post-meta`, `core/post-data`, `core/term-data`, `core/pattern-overrides` are the built-in sources; custom sources register via `register_block_bindings_source()` (PHP) / `registerBlockBindingsSource()` (JS). Currently limited to a fixed attribute allowlist per block (e.g. `core/image`'s `url`/`alt`/`caption`, `core/paragraph`'s `content`) ([Block Bindings API reference](https://developer.wordpress.org/block-editor/reference-guides/block-api/block-bindings/)) | No per-attribute binding of any kind. A widget instance's `config` is validated once against its type's whole `configSchema` (`registry.ts`'s per-type schemas) — there's no way to point one field of one widget at a live value computed elsewhere | **Lacks it.** |
| **Interactivity API** | A standardized client-side reactivity model (directives + a store) for block front-end behavior, introduced WP 6.5, meant to replace ad hoc jQuery/vanilla-JS-per-theme patterns ([About the Interactivity API](https://developer.wordpress.org/block-editor/reference-guides/interactivity-api/iapi-about/)) | Static themes ship their own hand-rolled `js/*.js` per theme (e.g. `theme-toggle.js`, theme-authoring-guide.md §3.3) — no shared client-side interaction framework or convention at all | **Lacks it — probably fine.** Framework-shaped scar tissue WP needed because it has thousands of themes with divergent JS conventions; Tovu has 7 static themes it fully controls. Low priority (see Part 2). |
| **Menus / nav locations** | `register_nav_menu(location_key, label)` ties menu *assignment* to keys the **active theme** declares; `wp_nav_menu(['theme_location' => key])` renders whatever's assigned ([Navigation Menus, Theme Handbook](https://developer.wordpress.org/themes/classic-themes/functionality/navigation-menus/); [`register_nav_menu()`](https://developer.wordpress.org/reference/functions/register_nav_menu/); [`wp_nav_menu()`](https://developer.wordpress.org/reference/functions/wp_nav_menu/)). Switching to a theme with different location keys orphans existing assignments — a well-known WP pain point | Menus are seeded `entries` (`type='menu'`, `NAV_MENU_CONTENT_TYPE` — Jini `packages/cms/src/navigation/types.ts:37`), and **may bind to an unregistered location key specifically so assignments survive a theme switch** — called out explicitly in the type's own doc comment as "fixes WP's 'lose your menus on theme change' sin" (`navigation/types.ts:203-208`) | **Ahead, and it's a deliberate, disclosed design choice**, not an accidental improvement. |
| **Reference integrity on delete** (where-used / safe-delete) | No general mechanism. WordPress's only native cleanup is narrow and reactive: `_wp_delete_orphaned_draft_menu_items()` sweeps orphaned **draft** nav-menu items after the fact ([reference](https://developer.wordpress.org/reference/functions/_wp_delete_orphaned_draft_menu_items/)) — there is no pre-delete "this post is referenced by 3 menus and 2 widgets" warning, and no equivalent for shortcode-embedded or Custom-HTML-embedded references at all. Third-party plugins (WP-Sweep, the `orphan` WP-CLI command) exist specifically to fill this gap | `extractEntryRefs`/`extractHtmlEntryRefs` (`src/core/entry-refs/extractor.ts`) index every widget-area placement, `widgetEmbed` node, ref-typed config field, AND every `data-embed-type` reference in an html Page's body — into one `entry_refs` table, written in the **same transaction** as the triggering write (INV-06, `extractor.ts:1-19`), backing SPEC-043's where-used/safe-delete checks (REQ-34/REQ-42) | **Ahead, verified, not scar-tissue-avoidance — a genuine design win.** See Part 2. |

## Part 2 — Analysis

### 2.1 Which gaps matter, and which are WordPress's scar tissue

WordPress carries two decades of backward compatibility. Some of what it does is a real capability Tovu should build; some of it is a wound WordPress is still healing from and Tovu should not reopen by copying the syntax.

**Don't copy — these are WP's own liabilities, not features:**

- **Bracket shortcode syntax.** The *need* shortcodes serve (an author-typed inline dynamic token) is already served by `data-embed-type`. Adding a second, string-macro-based syntax alongside it would be reintroducing exactly the "two parallel systems" problem WP itself is still migrating out of (see next point) — for zero capability gain.
- **The years-long two-paradigm coexistence (classic `WP_Widget`/shortcodes AND blocks, running side by side since 2018).** This is the single clearest cautionary tale in the whole comparison. WP still ships a Legacy Widget compatibility block, a separate Classic Widgets plugin, and dual code paths seven years after Gutenberg's introduction. Tovu should treat "one canonical embed/placement mechanism" as non-negotiable — which is exactly what the in-flight `data-embed-type`/`data-embed-id`/`data-embed-config` unification is doing, and is the right instinct.
- **Hooks/filters as a third-party render-extension point.** This is WP's largest attack surface and stability liability — arbitrary plugin PHP intercepting `the_content` and everything else, unsandboxed, unversioned, silently order-dependent. Tovu's closed-resolver-map stance (ADR-020's "no untrusted code," ADR-024's Tier-2/3 gating for any future plugin-contributed type) is the *correct* call, not an omission. If Tovu ever wants third-party extensibility here, the sandboxed-template precedent it already has (Liquid/Handlebars worker isolation + allowlists) is the right model to extend, not an open PHP-style hook system.
- **The Interactivity API.** A real, well-designed piece of engineering, but it solves a problem WP has because it has thousands of independently-authored themes with incompatible JS conventions. Tovu has 7 static themes it fully controls; a shared client-side reactivity framework is solving a coordination problem Tovu doesn't have yet. Revisit only once theme count and JS-behavior duplication actually grow.

**Do copy the underlying capability (not necessarily the syntax) — these are real gaps:**

- **Template parts as revisioned content**, not files on disk (#1 below — highest leverage item on this whole list).
- **A composition/pattern primitive** — nothing in WP's shortcode/widget era offered this; it only arrived with synced patterns, and it fills a real hole in Tovu today (a single reusable widget already updates everywhere it's placed; nothing lets an author reuse a *group*).
- **oEmbed** — small, well-bounded, no scar tissue, real author value (paste a YouTube URL, get a player) that nothing in Tovu currently provides.
- **Design tokens wired into an authoring UI**, the way WP's `theme.json` settings drive editor color/typography pickers — Tovu's tokens are currently invisible outside a code comment convention.

### 2.2 Where Tovu is already ahead

Verified against source on both sides, not assumed:

1. **Reference integrity (`entry_refs`) is a real, structural advantage, not scar-tissue-avoidance.** WordPress's *only* native cleanup mechanism here is `_wp_delete_orphaned_draft_menu_items()` — reactive, draft-menu-item-only, after the fact. There is no WP-core equivalent of "show me everywhere this is used before I delete it," across menus, widgets, and embedded HTML references, the way `extractEntryRefs`/`extractHtmlEntryRefs` do in one transaction with the triggering write. This gap is well-known enough in the WP ecosystem that third-party tools (WP-Sweep, the `orphan` WP-CLI command) exist specifically to compensate for its absence.
2. **The widget capability/clamp model has no WP equivalent.** A WP widget (classic or block) can perform arbitrary PHP I/O with no declared cost class and no core-enforced timeout or item-count ceiling. Tovu's `WidgetCapability` (`static | query | form | entry-reference`) plus orchestration-layer-enforced `clamps.maxItems`/`clamps.timeoutMs` (enforced independent of a resolver's own discipline, per `registry.ts`'s `RECENT_ENTRIES_REGISTRATION` comment) is a defense-in-depth resource-governance model WP doesn't have anywhere in its widget/block system.
3. **Menus that survive a theme switch is a deliberate, disclosed fix for a specific, real, well-known WP pain point** — not an incidental difference. `register_nav_menu()`'s theme-owned location keys orphan menu assignments on theme change; Tovu's menus can bind to unregistered keys specifically to avoid that (`navigation/types.ts:203-208`).
4. **A capability-tiered raw-HTML gate was designed into the spec from day one** (SPEC-047 REQ-9's `pages.edit_html`), even though it isn't wired yet — WP's `unfiltered_html` model is a retrofit onto a system that started with no such gate at all. Tovu's gap here is "finish wiring a decision already made," not "invent the decision."
5. **Sandboxed template tiers** (`templated`/`handlebars`, `worker_threads` isolation + tag/filter allowlists — theme-authoring-guide.md §2.3/§2.4) vs. WP theme PHP, which runs with full server-side privileges and is the root cause of the entire hooks/filters attack surface.

### 2.3 Ordered build list

1. **Decide, explicitly, whether `type="partial"` makes partials real content — and build it that way if so.** *Rationale:* this is literally happening right now on another branch of this same work; getting it wrong means Tovu re-lives WP's pre-FSE decade (partials as opaque theme files) under a new attribute name instead of actually closing the gap. Land it as a revisioned `entries` row (mirrors how `widget`/`widget_area` are already entries, not files) with the same `entry_refs`/where-used integrity every other content type gets, editable through an admin surface, hot-reloadable without a server restart. File: extends `src/features/theme/theme.ts`'s partial-loading path and `static-render.ts`'s `resolveSlots`; the content-storage side likely wants a new content type alongside `WIDGET_CONTENT_TYPE`/`WIDGET_AREA_CONTENT_TYPE` in `src/widgets/types.ts` or a sibling `partials/` module.
2. **Seed `pages.edit_html` and wire it into `src/features/pages/tool-registrations.ts`.** *Rationale:* the design already exists (SPEC-047 REQ-9); this is a seed-data change plus swapping `content.write`/`content.read` for the dedicated permission at `tool-registrations.ts:68,95` — the cheapest, most fully-speced item on this list, and it closes Tovu's one real security-posture gap versus WP's `unfiltered_html` model.
3. **Wire `tokens.json` into an actual authoring surface** (an admin color/typography picker, or at minimum AI-tool-visible token metadata) instead of leaving it as a convention only `skeleton.ts`'s doc comment enforces. *Rationale:* WP's `theme.json` settings→editor-control pipeline is the mechanism that makes off-palette mistakes structurally hard; Tovu's current design makes them merely discouraged. File: `src/features/theme/theme.ts` (token schema), plus wherever the Pages/theme admin surface lives.
4. **Add a composition/pattern primitive** — a saved, named group of widget placements, editable in one place, insertable by reference into multiple regions/pages. *Rationale:* the single sharpest capability gap in the table; nothing today lets an author reuse a *group* the way a single widget instance already reuses a *leaf*. File: likely a new content type/document shape sitting next to `WidgetAreaDoc` in `src/widgets/types.ts`, with its own resolver in `src/widgets/resolver-service.ts`.
5. **Add an `oembed` embed type** — a new entry in `HTML_EMBED_RESOLVERS` (`resolver-service.ts:540`) resolving a safelisted external URL (YouTube, Vimeo, etc.) to embed markup, mirroring how `media` already resolves internal assets. *Rationale:* small, well-bounded, real author value, zero scar tissue to inherit.
6. **(Low priority) Generalize the nested-menu tree beyond one opt-in marker in one theme.** *Rationale:* `renderMenuTree()` already exists and is correct (`static-render.ts:130-165`) — this is a per-theme CSS/markup rollout task, not a design gap, now that the primitive itself is built. Worth noting only because the authoring guide's own §8.2 is stale on this point as of this document.

## What I could not find a source for

Nothing in the comparison table above is unsourced — every WordPress mechanism carries a `developer.wordpress.org`/`wordpress.org` (or, for the WP 7.0-specific items, `make.wordpress.org`) citation. Two items were deliberately left out of the table rather than included half-verified:

- **Custom Post Types and custom fields/meta boxes** — a legitimate WP content-model mechanism, but it's a *data-modeling* concern (schema per content type), not a *placement/injection* concern, so it's out of this document's scope rather than an omission.
- **The Block Directory / third-party block marketplace** — touches distribution/trust, not the injection mechanism itself; would belong in an "extensibility ecosystem" comparison, not this one.

No claim about the *current, in-flight* embed-unification work is made beyond what this document's opening section already discloses (no commits, no working-tree diff, found via `git log --all --grep` and `git status`/`git diff --stat` on the relevant files at the time of this analysis) — its actual shape when it lands should be checked against this document rather than assumed to match the brief's description exactly.
