# WordPress vs. Tovu: Content-Injection Capability Comparison

**Status:** research/decision-support document, not a spec. Written to inform the design of Tovu's content-injection system (how blocks, widgets, menus, partials, and raw HTML get placed into pages and themes) by comparing it against what WordPress does in the same space today.

**Scope note on "today."** WordPress-side claims are sourced against current `developer.wordpress.org`/`wordpress.org` documentation via live web search, not model memory — every mechanism below carries a citation. WordPress 7.0 shipped May 20, 2026 ([WP Engine's release writeup](https://wpengine.com/blog/wordpress-7-0-release/); [Make WordPress Core, block visibility dev note](https://make.wordpress.org/core/2026/03/15/block-visibility-in-wordpress-7-0/)), so this reflects the current release, not the WordPress most engineers still picture from the shortcode/widget era.

**Scope note on Tovu's state.** Grounded by reading source directly, twice: first at `HEAD 22aa4ba2fad1b6469a3a787d5582510f673299fc` (nothing of the marker-spine unification had landed anywhere, committed or uncommitted, at that point), then again after the unification started landing live in the working tree mid-task. What's actually true now, verified directly against the current uncommitted diff rather than assumed from a description, is a **three-way split**:

1. **Unchanged — still today's real shape for the generic embed pipeline** (`widget`/`form`/`media`/`post` — `src/widgets/resolver-service.ts:540-545`): four flat attributes, `data-embed-type` / `data-embed-id` / `data-embed-name` / `data-embed-variant` (`src/widgets/html-embeds.ts:43-56, 98`). This file is untouched by the migration as of this writing.
2. **Already migrated, uncommitted, confirmed live in the working tree** (`src/features/theme/static-render.ts` — menu markers and theme-partial slots only): `data-embed-type`/`data-embed-id` stay as flat attributes for type/id identity; every *auxiliary* field (the old `data-embed-variant`, `data-nav-current`, `data-slot-variant`) has moved into one new JSON-valued `data-embed-config='{"variant":"...","current":"..."}'` attribute (`parseEmbedConfig`, `static-render.ts:184-202`; sequencing disclosed in `resolveSlots`'s own doc comment, `static-render.ts:319-339`, as two independently-landable migration tasks). The legacy `data-tovu-slot`/`data-nav-current`/`data-slot-variant` spelling is deprecated but still accepted (one `console.warn` per render, not per occurrence) for themes outside this repo. Concrete, live example: `content/themes/static/basic/pages/blog-sidebar-template.html:30` — `<nav ... data-embed-type="menu" data-embed-id="docs-themes-menu" data-embed-config='{"variant":"tree"}'>`.
3. **Reported, not observed anywhere in the repo yet:** a further consolidation folding `type`/`id` themselves into `data-embed-config` too — a single JSON attribute carrying everything, `data-embed-config='{"type":"...","id":"...", ...}'`, superseding an earlier three-attribute proposal that was floated and overruled during this same work. This may be a further step the two already-landed tasks are sequenced toward, or may not happen — this document treats it as *reported plan* only, labeled as such wherever it appears, never as observed fact. Also reported on the same basis: a new `html` **widget type** — a leaf entry in `WIDGET_TYPE_REGISTRATIONS` (`src/widgets/registry.ts`) for a saved, reusable raw-HTML snippet, distinct from a whole `bodyFormat: "html"` Page.

`type="partial"` for theme partials is **not** in the reported-only bucket — it's already landed and directly observable (item 2 above).

**A documentation-drift catch, disclosed because it's directly relevant to trusting citations below — and because it happened twice in one session, which is itself informative.** `development/docs/themes/theme-authoring-guide.md` §8.2 states "nested nav/submenus never render, on any static theme." That was true until a commit right at the original `HEAD` (`77f567d feat(themes): nested menu tree rendering + docs sidebar in basic`, same day, same session) added `renderMenuTree()` and an opt-in tree-variant marker (`static-render.ts:130-165`), wired into one marker in one theme. That marker's own spelling has since moved *again* — from the bare `data-embed-variant="tree"` attribute `77f567d` shipped to `data-embed-config='{"variant":"tree"}'` (the in-progress migration, item 2 above) — a second, smaller illustration of the same point: every marker-syntax example in this document is a snapshot of a moving target, verified at time of writing, not a stable contract. The authoring guide wasn't regenerated after either change landed; this document uses the verified-against-source state at each point instead.

| **Synced patterns** (formerly "reusable blocks") | The same pattern concept, but WordPress-managed and DB-stored so an edit anywhere propagates everywhere the pattern is placed — renamed from Reusable Blocks in WP 6.3 ([Synced Patterns docs](https://wordpress.org/documentation/article/reusable-blocks/); [Synced Patterns: The Evolution of Reusable Blocks](https://wordpress.org/news/2023/07/synced-patterns-the-evolution-of-reusable-blocks/)). Cannot be created programmatically — they only exist as DB content, per environment ([same source](https://wordpress.org/documentation/article/reusable-blocks/)) | Nothing equivalent — no "one editable source, many placements" composition primitive of any kind | **Lacks it.** This is the sharpest gap: Tovu has reusable *leaf* widgets (one widget instance, many `widgetEmbed`/`data-embed-type="widget"` placements already share this "edit once, updates everywhere" property at the single-widget level — see `resolvePageWidgets`, `src/widgets/resolver-service.ts:174-231`) but nothing that groups multiple widgets/content into one reusable, synced *composition*. |

## Part 2 — Analysis

### 2.1 Which gaps matter, and which are WordPress's scar tissue

WordPress carries two decades of backward compatibility. Some of what it does is a real capability Tovu should build; some of it is a wound WordPress is still healing from and Tovu should not reopen by copying the syntax.

**Don't copy — these are WP's own liabilities, not features:**

- **Bracket shortcode syntax.** The *need* shortcodes serve (an author-typed inline dynamic token) is already served by `data-embed-type`. Adding a second, string-macro-based syntax alongside it would be reintroducing exactly the "two parallel systems" problem WP itself is still migrating out of (see next point) — for zero capability gain.
- **The years-long two-paradigm coexistence (classic `WP_Widget`/shortcodes AND blocks, running side by side since 2018).** This is the single clearest cautionary tale in the whole comparison. WP still ships a Legacy Widget compatibility block, a separate Classic Widgets plugin, and dual code paths seven years after Gutenberg's introduction. Tovu should treat "one canonical embed/placement mechanism" as non-negotiable — which is exactly what the in-flight `data-embed-type`/`data-embed-id`/`data-embed-config` unification is doing, and is the right instinct.
- **Hooks/filters as a third-party render-extension point.** This is WP's largest attack surface and stability liability — arbitrary plugin PHP intercepting `the_content` and everything else, unsandboxed, unversioned, silently order-dependent. Tovu's closed-resolver-map stance (ADR-020's "no untrusted code," ADR-024's Tier-2/3 gating for any future plugin-contributed type) is the *correct* call, not an omission. If Tovu ever wants third-party extensibility here, the sandboxed-template precedent it already has (Liquid/Handlebars worker isolation + allowlists) is the right model to extend, not an open PHP-style hook system.
- **The Interactivity API.** A real, well-designed piece of engineering, but it solves a problem WP has because it has thousands of independently-authored themes with incompatible JS conventions. Tovu has 7 static themes it fully controls; a shared client-side reactivity framework is solving a coordination problem Tovu doesn't have yet. Revisit only once theme count and JS-behavior duplication actually grow.

**Do copy the underlying capability (not necessarily the syntax) — these are real gaps:**

- **Template parts as revisioned content**, not files on disk (#1 below — highest leverage item on this whole list).
- **A composition/pattern primitive** — nothing in WP's shortcode/widget era offered this; it only arrived with synced patterns, and it fills a real hole in Tovu today (a single reusable widget already updates everywhere it's placed; nothing lets an author reuse a *group*).
- **oEmbed** — small, well-bounded, no scar tissue, real author value (paste a YouTube URL, get a player) that nothing in Tovu currently provides.
- **Design tokens wired into an authoring UI**, the way WP's `theme.json` settings drive editor color/typography pickers — Tovu's tokens are currently invisible outside a code comment convention.

### 2.2 The composition gap, made precise

The capability table calls this "lacks it," which is true but undersells how close Tovu already is for the single-item case, and overstates how far it is from the group case. Worth separating cleanly, because the fix is much narrower than "build a patterns system from scratch."

**What Tovu already has that matches synced patterns' core value proposition.** WP's synced patterns exist to solve one problem — edit a piece of content once, have every placement of it update together. Tovu already has this, for exactly one component at a time: a single `widget` entry, embedded via `data-embed-type="widget"` (or a `widgetEmbed` TipTap node) at N different places, resolves fresh from the *same* entry on every render (`resolvePageWidgets`/`resolveWidgetInstances`, `resolver-service.ts:131-231`). Edit the widget once, every placement updates — no propagation step, no sync flag, because there was never a copy to fall out of sync in the first place. This is arguably a cleaner mechanism than WP's own: synced patterns are opt-in via a toggle on an otherwise copy-by-value pattern, so there's a real "did I forget to sync this" failure mode in WP that structurally cannot happen in Tovu's reference-by-default model.

**What's actually missing is composition, not reuse.** WP's synced patterns aren't valuable because a single block updates everywhere — they're valuable because an *arrangement* of several blocks (a hero + a 3-up feature grid + a CTA, say) can be saved, named, and reused as one unit, staying in sync as a whole. Tovu has no equivalent of "group N widgets and give the group its own identity." The closest existing thing, `WidgetAreaDoc.placements` (`types.ts:154-158`), is an ordered list of widget placements — but it's bound to exactly one `regionKey` in exactly one workspace at a time (`WidgetAreaEntry.regionKey` is "the source of truth for which region this area fills," `types.ts:161-165`), not a portable, independently-nameable, multiply-placeable unit. Composing the same arrangement in two different places today means hand-re-authoring the same sequence of embed markers twice, with zero propagation between the copies.

**Why this is a narrow, cheap gap to close, not a new subsystem.** Almost all of the machinery a "widget group" needs already exists and is proven: batched resolution (`resolveWidgetInstances`), the ref-extraction/safe-delete integrity path (`extractEntryRefs`), the placement-node shape (`WidgetPlacementNode`). A group primitive is closer to "give `WidgetAreaDoc`'s placement-list shape its own standalone entry type, decoupled from a single region binding, embeddable by reference like any other embed target" than to building pattern-editing UI, a diff/sync engine, or anything WP-scale.

### 2.3 The menu precedent: does it transfer to partials?

Tovu already has exactly one working example of "content that used to live in theme files became a first-class, revisioned, theme-switch-surviving entry": navigation menus. Before treating that as proof the same move works for partials, it's worth checking what actually makes the menu version work — because not all of it transfers, and getting this wrong is exactly how the in-flight `type="partial"` work could ship a new marker spelling without closing the real gap.

**What makes the menu model work:**
1. A menu's content is a **narrow, homogeneous, typed tree** — every node is `{id, label?, target, attrs?, children?}` (`NavItemNode`, Jini `packages/cms/src/navigation/types.ts:124-132`), where `target` is one of exactly four kinds (`entryRef | termRef | url | route`). There is nothing else a menu item can be.
2. **Content and presentation are fully separated.** The stored tree carries zero markup — no classes, no wrapper elements, no theme-specific structure. A theme never touches the stored document; it receives an already-resolved `ResolvedNavItem[]` (concrete `href`, `available`, `isCurrent`/`isActive` — `navigation/types.ts:229-241`) and renders that data however its own CSS needs, via `renderMenuLinks`/`renderMenuTree` (`static-render.ts:101-165`). This is the render-IR boundary — "theme receives resolved data, never resolves refs" — stated as a design principle in both the navigation and widgets packages' own file headers.
3. Because of (1) and (2), the theme's role shrinks to: declare which **location keys** it wants filled (`NavLocationDescriptor`) and supply the **rendering rules** for whatever tree it's handed. The content itself is fully portable across any theme whose renderer can walk a `ResolvedNavItem[]`.

**Where a raw-HTML partial (`nav.html`, `footer.html`) differs, and it's not a small difference.** A partial today isn't narrow, typed, or presentation-free — it *is* the presentation. It's an arbitrary blob of theme-specific markup: wrapper elements, theme-authored class names (`basic`'s own `.main-nav { display: flex }`), icons, inline structure, occasionally a copyright string or tagline. There's no fixed vocabulary a "partial document" could serialize to the way `NavItemNode` serializes a menu item — a nav partial and a footer partial don't even share a shape with each other, let alone across themes. The codebase's own disclosed constraint on the one place it already tried to generalize menu-*shaped* content across themes confirms exactly this limit: `renderMenuTree`'s nested-list output had to be made opt-in per marker specifically because "every static theme's nav CSS today targets direct `<a>` children of a flex container... unconditionally introducing a `<ul>` wrapper would collapse each of those navs to a single flex child" (`static-render.ts:113-118`). If even a *typed, narrow* menu tree can't render portably across themes without per-theme opt-in, a *whole arbitrary partial* certainly can't.

**So: the menu model's "make it an entry" half transfers; its "core resolves data, theme just renders" half does not — not without first doing to partials what was already done to menus, factoring out a narrow typed vocabulary, which is a separate and much larger project than this one.** The more honest structural analog for "partial as raw HTML, stored as a revisioned entry, embeddable by reference, scanned for its own embedded references" is Tovu's *own* `bodyFormat: "html"` Page mechanism — `body_html` as trusted entry content, `extractHtmlEntryRefs` indexing whatever embed references live inside it, `resolveHtmlPageEmbeds` resolving them at render time. That machinery already exists, already handles exactly this shape of content (arbitrary theme-relevant HTML with embedded references), and moving partials onto it is a smaller lift than it looks: a partial entry is functionally an html Page whose "route" is a slot key instead of a URL slug.

**What the theme still owns, concretely, once a partial is an entry:**
- **Which slot keys exist**, and their `activeAttr`/`variants` metadata — unchanged. This is exactly what `ThemeManifest.slots`/`ThemeSlotDescriptor` (`theme.ts:124-142`) already declares today, and nothing about moving the *content* to an entry requires moving this *declaration* off the theme.
- **A default value for each declared slot**, so a fresh workspace with zero partial entries still renders a real nav/footer rather than a blank one. The theme's on-disk `nav.html`/`footer.html` doesn't disappear — it becomes the **seed** for that slot's first entry, the same role `seed.ts:255`'s hardcoded `activeThemeId` plays for presentation settings, or `DEFAULT_THEME_SLOTS` already plays as the fallback when a theme declares no `slots` map at all (`theme.ts:148-151`).
- **The fallback discipline on an unresolved reference** — and this one has an exact, already-shipped precedent, not just a suggestion: `injectMenuEmbed` already leaves a menu marker's own authored content untouched when the referenced menu doesn't resolve, specifically so "an active static theme must render identically to how it did before this feature existed, never an empty nav" (`static-render.ts:204-217`). A partial entry that hasn't been created yet, or fails to resolve, should degrade the same way — to the theme's own last-known-good content, never to blank.

Net: partials-as-entries is the right move, and the menu precedent proves the *general* pattern (theme-owned declaration + entry-owned content + survives a theme switch + a safe fallback) works in this codebase. But it should be modeled on the `bodyFormat: "html"` Page mechanism, not copy-pasted from the menu mechanism — the two existing precedents solve different problems, and a partial's problem (arbitrary theme-coupled markup) is the Page one, not the menu one.

### 2.4 Where Tovu is already ahead

Verified against source on both sides, not assumed:

1. **Reference integrity (`entry_refs`) is a real, structural advantage, not scar-tissue-avoidance.** WordPress's *only* native cleanup mechanism here is `_wp_delete_orphaned_draft_menu_items()` — reactive, draft-menu-item-only, after the fact. There is no WP-core equivalent of "show me everywhere this is used before I delete it," across menus, widgets, and embedded HTML references, the way `extractEntryRefs`/`extractHtmlEntryRefs` do in one transaction with the triggering write. This gap is well-known enough in the WP ecosystem that third-party tools (WP-Sweep, the `orphan` WP-CLI command) exist specifically to compensate for its absence.
2. **The widget capability/clamp model has no WP equivalent.** A WP widget (classic or block) can perform arbitrary PHP I/O with no declared cost class and no core-enforced timeout or item-count ceiling. Tovu's `WidgetCapability` (`static | query | form | entry-reference`) plus orchestration-layer-enforced `clamps.maxItems`/`clamps.timeoutMs` (enforced independent of a resolver's own discipline, per `registry.ts`'s `RECENT_ENTRIES_REGISTRATION` comment) is a defense-in-depth resource-governance model WP doesn't have anywhere in its widget/block system.
3. **Menus that survive a theme switch is a deliberate, disclosed fix for a specific, real, well-known WP pain point** — not an incidental difference. `register_nav_menu()`'s theme-owned location keys orphan menu assignments on theme change; Tovu's menus can bind to unregistered keys specifically to avoid that (`navigation/types.ts:203-208`). See §2.3 for the fuller anatomy of why this works.
4. **A capability-tiered raw-HTML gate was designed into the spec from day one** (SPEC-047 REQ-9's `pages.edit_html`), even though it isn't wired yet — WP's `unfiltered_html` model is a retrofit onto a system that started with no such gate at all. Tovu's gap here is "finish wiring a decision already made," not "invent the decision."
5. **Sandboxed template tiers** (`templated`/`handlebars`, `worker_threads` isolation + tag/filter allowlists — theme-authoring-guide.md §2.3/§2.4) vs. WP theme PHP, which runs with full server-side privileges and is the root cause of the entire hooks/filters attack surface.

### 2.5 Ordered build list

1. **Model partials as `bodyFormat: "html"`-shaped entries, not widget-shaped ones — see §2.3.** *Rationale:* this is literally happening right now on another branch of this same work, and the menu precedent shows the *pattern* (theme-owned declaration + entry-owned content + safe fallback) works in this codebase — but a partial's content is theme-coupled raw markup, not a narrow typed tree, so it should reuse the Pages `body_html`/`extractHtmlEntryRefs` machinery, not the menu machinery. Theme still owns: the `slots` map declaring which keys exist (`theme.ts:124-142`, unchanged), and a **seed default** per slot (the theme's own current `nav.html`/`footer.html` becomes the first entry's seed content, exactly as `DEFAULT_THEME_SLOTS` already seeds an undeclared-`slots` theme — `theme.ts:148-151`), so a fresh workspace with zero partial entries still renders a real nav, never a blank one — the same never-blank discipline `injectMenuEmbed` already enforces for unresolved menu references (`static-render.ts:204-217`). File: extends `src/features/theme/theme.ts`'s partial-loading path and `static-render.ts`'s `resolveSlots`; content storage likely reuses `features/pages/html-document-store.ts`'s shape rather than `src/widgets/types.ts`'s.
2. **Seed `pages.edit_html` and wire it into `src/features/pages/tool-registrations.ts`.** *Rationale:* the design already exists (SPEC-047 REQ-9); this is a seed-data change plus swapping `content.write`/`content.read` for the dedicated permission at `tool-registrations.ts:68,95` — the cheapest, most fully-speced item on this list, and it closes Tovu's one real security-posture gap versus WP's `unfiltered_html` model.
3. **Wire `tokens.json` into an actual authoring surface** (an admin color/typography picker, or at minimum AI-tool-visible token metadata) instead of leaving it as a convention only `skeleton.ts`'s doc comment enforces. *Rationale:* WP's `theme.json` settings→editor-control pipeline is the mechanism that makes off-palette mistakes structurally hard; Tovu's current design makes them merely discouraged. File: `src/features/theme/theme.ts` (token schema), plus wherever the Pages/theme admin surface lives.
4. **Add a composition/pattern primitive — see §2.2 for why this is narrower than it looks.** *Rationale:* Tovu already matches synced patterns' core value (reference-based reuse) at the single-widget level; what's missing is grouping. Give `WidgetAreaDoc`'s placement-list shape (`types.ts:154-158`) its own standalone, independently-nameable entry type, decoupled from a single `regionKey` binding, embeddable by reference like any other embed target — reusing `resolveWidgetInstances`'s existing batching rather than building new resolution machinery. File: a new content type/document shape sitting next to `WidgetAreaDoc` in `src/widgets/types.ts`, with its own resolver in `src/widgets/resolver-service.ts`.
5. **Add an `oembed` embed type** — a new entry in `HTML_EMBED_RESOLVERS` (`resolver-service.ts:540`) resolving a safelisted external URL (YouTube, Vimeo, etc.) to embed markup, mirroring how `media` already resolves internal assets. *Rationale:* small, well-bounded, real author value, zero scar tissue to inherit.
6. **(Low priority) Generalize the nested-menu tree beyond one opt-in marker in one theme.** *Rationale:* `renderMenuTree()` already exists and is correct (`static-render.ts:130-165`) — this is a per-theme CSS/markup rollout task, not a design gap, now that the primitive itself is built. Worth noting only because the authoring guide's own §8.2 is stale on this point as of this document.
