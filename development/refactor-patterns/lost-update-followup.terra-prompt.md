## Basis rules (owner decision 2026-11-13 — apply to EVERY row)
- **Own-read CAS is not editor protection.** A compare against a version the server read itself only stops a write landing over a change made during that one request.
- **B1 editor and read-derived writes carry the ORIGINAL basis**: the version of the read the change was computed from. Editors send it; jobs, imports and publish pass the version of the read they planned against; a retry resends its ORIGINAL basis and never re-reads to refresh it.
  - Tools: required (`requireExpectedVersion`).
  - HTTP in THIS job: `parseExpectedVersion` (optional), because the admin screens do not send it yet. At the parse site write the reason as a comment: `// Missing basis = documented last-write-wins until <admin file> sends it; the ui-lane row for this screen switches this route to requireEditorVersion (428).` The UI lane makes the switch in the same commit that makes the screen send the basis.
- **B2 a service with no basis falls back to the FIRST read used for the computation** (`optional.expectedVersion ?? existing.version`, where `existing` is the read the new record is built from). It must never fall back to a later read. Example: Jini forms `withFirstReadBasis` (commit `cbfe0cf6a`).
- **B3 own-read CAS is enough for these writes only (E2/E4):** status flips, role-name, username and email assignments, and opaque password or secret replacement.
- **B4 login stamps write only their own column** (`last_login_at`), with no version change.
- **B5 background writers never write a whole stale record.** These are token refresh, sign-in callbacks, plugin adoption and rename sync. Each one does one of two things:
  - a column-scoped UPDATE of only the columns it owns, with a guard on those columns;
  - or, for an operator-visible change, a version bump plus a CAS against the version it read.
- **B6 one write, one transaction.** A request that changes several things commits all of them under one compare-and-set, or none of them.
