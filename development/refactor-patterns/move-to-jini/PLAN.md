### 1.2 Type-inclusive cycles: 18 type-only back edges

After C1-C5 the runtime graph is a DAG. These type-only edges point "up" that DAG and must be cut so the type-inclusive graph is acyclic too (`--include-type --drop "<C1-C5>,<these 18>"` -> `sccs=0 mutual-pairs=0`, verified):

How (one recipe, stage 03): MOVE THE SHARED TYPE DOWN. Each imported name is a type. Follow re-exports to the declaring file. R1: declared in Jini -> import it from Jini. R2: the declaring file is types-only -> `git mv` it to `apps/website/src/contracts/core/<feature>/` and leave a one-line `export type *` shim at the old path. R3: otherwise the declaration (plus same-file types it references) moves to `apps/website/src/contracts/core/<feature>/<declaring-basename>.ts`; the declaring file imports it back with `import type` and keeps its `export type { ... }` line so other importers need no change. A referenced type from another feature, a runtime value in a type position, or >600 moved lines = that edge is BLOCKED. `contracts/core` is the existing lowest Tovu layer (50 files, imports only Jini/npm/platform). Why types and not ports: `publish-content/type-registry.ts` (lines 3-33) aggregates the port types of every content feature into `PublishContentPorts`; the features import publish-content's runtime kit, so the aggregate must be built from types that live below both.

## 4. Release / versioning (how stages ship without blocking)

Facts: Tovu depends on every `@jini-ai/*` package as `^0.7.0` (root `package.json`); Jini publishes all 40 packages in lockstep (0.7.1). Tovu's release gate is the published-package typecheck. `npm run link:jini` symlinks Tovu's node_modules at a Jini checkout (`JINI_PACKAGES_DIR`), and `check-no-linked-jini.mjs` fails any build while linked.

Rules:
1. Jini half first, Tovu half second, in that order inside each MOVE stage. A Jini half is ADDITIVE ONLY: new files and new named exports on an existing subpath; it never removes or renames an export Tovu still imports. So every published Jini 0.7.x stays compatible with the live Tovu `main`.
2. During the refactor Tovu consumes the Jini refactor clone through `link:jini`, never a published build. HARD: the Tovu clone's `node_modules` is a symlink to `/Users/la/Programming/Tovu/node_modules` (the LIVE tree); `link:jini` there would relink the live tree. Before stage 06 the coordinator replaces that symlink with an APFS copy (`rm /Users/la/Programming/tovu-terra-d1/node_modules && cp -cR /Users/la/Programming/Tovu/node_modules /Users/la/Programming/tovu-terra-d1/node_modules`, same for `apps/admin/node_modules` and `apps/site-chat/node_modules` if present), then `JINI_PACKAGES_DIR=/Users/la/Programming/jini-terra-d1/packages npm run link:jini`. Every MOVE and SPLIT prompt checks this before touching anything; if `node_modules` is still a symlink or resolves into a live tree, the job does the Jini half only and reports "Tovu half skipped" (it never relinks anything itself).
3. Each Tovu stage commit message records the Jini commit it needs: a `Jini-Base: <sha>` trailer. Rolling back a Tovu stage never needs a Jini rollback (rule 1).
4. Publishing: one coordinated lockstep release when the owner says merge (stage 16): 0.8.0 (minor: stage 16 removes Jini exports that only existed for Tovu shims, plus the Express-subpath cleanup if it lands). If Tovu CI must typecheck against published packages before that, publish prereleases `0.8.0-refactor.N` under the npm dist-tag `refactor` (never `latest`), and the refactor branch pins exact versions. Live Tovu `main` stays on `^0.7.0` and is untouched until the merge.
5. Version ranges move once, in stage 16: `^0.7.0` -> `^0.8.0` for all `@jini-ai/*`, `npm run unlink:jini`, published typecheck.

## 5. Shared mechanics every stage prompt repeats (summary)

- READY check per row (mechanical, before any edit): file exists; for a MOVE, every import of the file resolves to (a) npm packages already in the target Jini package's `dependencies`, (b) `@jini-ai/core` or the target package itself, (c) files in the same stage's move set, or (d) a port named in the row. Anything else (a `#src/` or relative import outside the set, another `@jini-ai/<pkg>` value import, `express`, `react` outside a `react/` subfolder, the word "Tovu" in code or comments that cannot be made neutral by deleting a Tovu ID) -> the row is BLOCKED: do not move it, list it in the report with the blocking import. Blocked rows roll into stage 12.
- Jini destination: `packages/<pkg>/src/<dir>/` where `<dir>` is the folder of the source file behind the `"./<subpath>"` export (dist path -> src path); empty subpath -> `src/`. A subpath not in the exports map -> BLOCKED (new subpaths are an Opus decision).
- Moved code: keep every comment (why-comments move with code); replace Tovu SPEC/ADR/U/D IDs in comments by nothing (keep the sentence); args `(required, optional = {})` preserved as written (do not refactor signatures in a move); no new `as any`, `@ts-ignore`, `eslint-disable`, non-null `!`.
- Preflight (stages 03 and 06-16): the Jini clone must be writable AND installed (`test -d /Users/la/Programming/jini-terra-d1/node_modules`); no install = stop and report "Jini clone not installed" (Jini tsc, vitest, build and `jini-cycles.py` all need it; the coordinator installs, jobs never do). TODAY THE JINI CLONE HAS NO `node_modules`, so stage 03 and later cannot start until the coordinator installs it. MOVE/SPLIT jobs also check Tovu `node_modules` is the APFS copy linked to the Jini clone (4.2); if not, Jini half only.
- Tests move with code: a Tovu test whose only subjects are moved files moves to `<dir>/__tests__/` in Jini. The conversion is fixed: `node:test` names -> vitest (`before` -> `beforeAll`, `after` -> `afterAll`), `t.after(fn)` -> `onTestFinished(fn)`, keep `node:assert/strict`; any other `t.*` context use or a node:test options object = the test stays in Tovu, repointed to the Jini import (as do tests using `mock`, Tovu fixtures, or more than the moved subject). After converting, `grep -nE "\bt\.|node:test"` on the Jini test prints nothing. A moved file left with no Jini test is reported `NO-JINI-TEST` (Jini's 100% coverage gate, measured in the cloud run).
- Own-package imports: a moved file's `@jini-ai/<pkg>/...` import of its own target package is rewritten to the DECLARING leaf file (never an entry/barrel that will re-export the moved file: that is `index -> moved -> index`). `jini-cycles.py <pkg>` runs before and after each Jini half and must show no new module cycle.
- Public API shape: every exported function a row moves into Jini must take `(required, optional = {})`. Terra converts it only when it has <=3 parameters, <=10 direct call sites (never passed as a value or re-exported under another name) and is not a framework protocol hook; otherwise the row is BLOCKED -> stage 12 kind G.
- Logging: moved code never calls `console.*` (a Jini consumer would lose the host's redaction).
