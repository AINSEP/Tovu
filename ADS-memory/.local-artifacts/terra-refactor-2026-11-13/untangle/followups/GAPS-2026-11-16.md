### 1.1 Decisions

- **CH1. Delete the `{ db }` wrapper. Do not move it into core and do not keep it.** `createChatHistoryStore({ db })` and `createChatHistoryMaintenance({ db })` in `store/sqlite/index.ts:33-46` are the only reason chat runtime-imports db. They convenience-wrap `sqliteKernel(db)`. The kernel-taking pair is already public, already used by Tovu, and already the documented path:
  - `createSqliteChatStore({ kernel, scope, clock })`
  - `createSqliteChatMaintenance({ kernel })`

  The host now does what the wrapper did: `createSqliteChatStore({ kernel: sqliteKernel<ChatDatabase>(db), scope, clock })`, with `sqliteKernel` imported from `@jini-ai/db/kernel/sqlite` inside the host's composition root. No new core contract is needed. `StorageKernel` and `SqliteClient` already live in `core/contracts/storage` (C3), and chat's other store files already import only those.
- **CH2. The frozen `sqlite` forwarder (Q2) keeps its public names by holding the wrapper itself.** `packages/sqlite/src/index.ts:16` re-exports `createChatHistoryStore` and `createChatHistoryMaintenance` from `@jini-ai/chat/store/sqlite`, and `sqlite/src/__tests__/old-surface.json:27,31` pins both names. Q2 freezes that surface until the next major. The two functions move **verbatim** (doc comments included) into a new file `packages/sqlite/src/chat-history-compat.ts`. That file imports `sqliteKernel` from `@jini-ai/db/kernel/sqlite` and `createSqliteChatStore`/`createSqliteChatMaintenance` from `@jini-ai/chat/store/sqlite`, both edges sqlite already has. `index.ts:16` then exports them from `./chat-history-compat.js`, and the file is deleted with the package at the next major.

  This is **not** a new shell. It is the same frozen Q2 exception, and the code lands in the one package that is allowed to hold it. **If the owner prefers to break `@jini-ai/sqlite` now, see §5 Q-G2.**
- **CH3. Every other chat → Jini edge goes through a port that chat declares, and the host binds it:**
  - E2: the C5 D3 recipe, unchanged (chat calls core's `redactSecretsWithCounts` with `CHAT_PATTERNS`; its fallback is a `redactUserText` option, which already exists in `UserTextRedactionOptions`).
  - E3 and E4: C6 §5 `ChatAgentFailurePort` / `ChatAgentPolicyPort`, unchanged.
  - E5: the ChatKit in §1.3.

  **Nothing new goes into core for chat.** Every contract here has exactly one consumer (chat), so B4's rule applies: the consumer declares it.
- **CH4. The manifest after this sheet:**
  - `dependencies`: `@jini-ai/core`, `@jini-ai/protocol`, `kysely`.
  - `peerDependencies`: React, the optional drivers and the optional `@mcp-ui/client`/radix/`@ag-ui` peers, all unchanged. **No `@jini-ai/*` peers.**
  - `devDependencies`: `@jini-ai/db` stays, for the **`/testing` entry only** (CH5). Remove `@jini-ai/ui-kit`, `@jini-ai/ui`, `@jini-ai/agentic`, `@jini-ai/agent-runtime` and `@jini-ai/diagnostics`.
- **CH5. Storage tests keep real SQL through `@jini-ai/db/testing`.** A fake `StorageKernel` cannot run Kysely SQL. A chat-local re-implementation of the SQLite kernel would copy about 190 lines of `BEGIN IMMEDIATE`, owned-transaction and turn-lock semantics (`db/src/kernel/sqlite/driver.ts`), and the race and two-connection suites would then prove the copy instead of the real kernel. That is the dishonest route that `honest-testing` bans.

  Q5 already allows a test-only import of another package's `/testing` entry. db gains one (`./testing`), and the existing `./testing/pg-fixture` folds into it. The exact exports are in §1.4 D1. **Owner confirmation asked in §5 Q-G1**, because D-CHAT says "no Jini package". The alternative is to move every SQL suite to `packages/integration-tests`.
- **CH6. React tests render through a fake ChatKit and fake surfaces, and never through ui-kit, ui or agentic.** Tests whose subject is *the real binding* (a real MCP-UI iframe, a real registry component inside an A2UI card, the real DOM page driver filling the composer) move to `packages/integration-tests/chat/` (Q5). They are not deleted, so the behaviour stays covered.

## 2. Origin policy: sheet `C-ORIGIN-PORT` (executable)

### 2.0 Problem

`core/src/contracts/server/origin.ts:31` `guardSameOrigin` calls `isLocalSameOrigin` through a **core-internal relative import** (`'../../origin-validation.js'`). The host passes environment *fields* (`OriginContext = { resolvedPortRef, env, allowedOriginsEnvVar, webPortEnvVar, bindHostEnvVar }`). It does not pass a decision. A test that wants "this request is same-origin" therefore has two ways to get it:
- (a) spy on `guardSameOrigin` by `vi.mock('@jini-ai/core/contracts/server')`. This is what 19 daemon test files + `daemon/src/http/__tests__/fixtures/same-origin-gate.ts` do.
- (b) `vi.mock('@jini-ai/core')` `isLocalSameOrigin`. `http-kit/src/__tests__/{origin,adapter}.test.ts` still do this, and since wave B moved the guard, that mock **no longer reaches the guard** (the fixture's own header says so).

Both are `vi.mock` of another package, which D-FAKES forbids, and (b) is already silently hollow.

### 2.1 Decision: the decision itself is the port

The host injects a `SameOriginPolicyPort` (a function object), not the policy's environment fields. Core keeps the pure default policy as a factory (it is pure: `isLocalSameOrigin` reads only the `env` it is handed). Tests pass a fake policy. Nothing is mocked.

```ts
import { isLocalSameOrigin, type OriginValidationEnvConfig, type OriginValidationLoggerPort, type RequestWithOriginHeaders } from '../../origin-validation.js';
import type { ServerApiError } from './api-error.js';
import { err, ok, type Result } from './result.js';

/** Decides whether a request comes from one of the host's own pages. The host injects it, and tests pass a fake. */
export interface SameOriginPolicyPort {
  isSameOrigin(required: { readonly req: RequestWithOriginHeaders }, optional?: Record<string, never>): boolean;
}

/** What a route host hands every same-origin-guarded route. */
export interface OriginContext {
  readonly originPolicy: SameOriginPolicyPort;
}

/**
 * The standard local-daemon policy: loopback/bind host, the resolved port, and the host's allow-list env var.
 * `port` is read on every call, because the listener binds after the routes are built.
 * The host passes the same `env` it gives the origin-guard middleware, so both halves of one decision read one environment
 * (the reason the old OriginContext carried `env`; keep that comment here).
 */
export function createLocalSameOriginPolicy(
  required: { readonly port: () => number; readonly env: Readonly<Record<string, string | undefined>>; readonly config: OriginValidationEnvConfig },
  optional: { readonly logger?: OriginValidationLoggerPort } = {},
): SameOriginPolicyPort {
  return { isSameOrigin: ({ req }) => isLocalSameOrigin({ req, port: required.port(), env: required.env, config: required.config }, optional) };
}

export function guardSameOrigin({ req, origin }: { readonly req: RequestWithOriginHeaders; readonly origin: OriginContext }, _optional: Record<string, never> = {}): Result<void> {
  if (origin.originPolicy.isSameOrigin({ req })) return ok({ value: undefined });
  const error: ServerApiError = { code: 'FORBIDDEN', message: 'cross-origin request rejected' };
  return err({ error });
}
```

/** Every request passes. For route tests whose subject is not origin policy. */
export const allowAllOrigins: SameOriginPolicyPort = { isSameOrigin: () => true };
/** Every request is refused, so a route's 403 path runs with core's real FORBIDDEN answer. */
export const denyAllOrigins: SameOriginPolicyPort = { isSameOrigin: () => false };
/** A policy whose verdict a test can flip, recording each request it was asked about. */
export function createRecordingOriginPolicy(_required = {}, optional: { allow?: boolean } = {}): SameOriginPolicyPort & { readonly calls: RequestWithOriginHeaders[]; set(required: { allow: boolean }): void }
