What the adapters use from the kernel: `run(fn(handle))`, `transaction`, `lockKey`, `dialect`/`transport` checks, `inTransaction`. Raw `query`/`execute` is used only by db itself, the server preset, Tovu, and 7 domain test fixtures; cms `create-tables.ts` already declares its own structural `FormsTablesKernel`. Transactions are already library-neutral (`kernel.transaction(async () => …)`).

**Finding:** the repository-port pattern already exists. Every domain except commerce already keeps its Kysely code in its own SQL adapter subpath behind a neutral repository port (`CommentRepo`, `ChatStore`, `AgentSessionStore`, `PaymentsLedger`…). What ties those adapters to db, and Kysely to core, is the *kernel type*: `StorageKernel<DB>` hard-codes `Kysely<DB>`.

## Options weighed
| Option | What moves | Size | Verdict |
|---|---|---|---|
| **A. Neutral kernel generic over the query handle; Kysely stays in each domain's existing SQL adapter subpath; the host binds** | core gets `StorageKernel<Handle, Schema>` (names no library); db adds `KyselyKernel<DB>`; adapters write `StorageKernel<Kysely<DB>, DB>`; commerce splits `rows.ts` | ~95 type-arg rewrites, 1 split (~45 lines), 0 adapter files moved | **Recommended** |
| B. Move every Kysely repo into db (`db/adapters/<domain>`) | 47 files / 7.2k lines + their tests; db must restate every domain record type (it cannot import domains) | ~1.5M Sonnet | Rejected: db becomes a dump of domain SQL and policy; huge duplication |
| C. Move the Kysely repos to the host (server preset or Tovu) | same 7.2k lines; Tovu would hold domain SQL | ~1.5M | Rejected: same cost, and a second host copies it all |
| D. A neutral query/statement DSL in core | rewrite all 7.2k lines against a home-made builder | >2M | Rejected: reinvents Kysely |

Why A satisfies the owner rule: core names no library or driver. Domain logic depends only on its own repository port. The Kysely implementation of that port is an adapter subpath that imports only its own package, core and the third-party `kysely`; it never imports db. The host picks the adapter and the kernel and wires them. Swapping Kysely (or the whole storage layer) means a new kernel package plus new adapters for each port, chosen in the host's wiring; no domain logic and no core file changes. Test fakes implement the repository port in memory (they already exist: `repo.memory.ts`, `InMemoryChangeSetRepo`…) or a `StorageKernel<FakeHandle>` with no Kysely.

## Decisions
- **D1 Neutral kernel.** Core `StorageKernel<Handle, Schema = unknown>` keeps every library-neutral member (`dialect`, `transport`, `capabilities`, `ready`, `run`, `transaction`, `lockKey`, `inTransaction`, `require`, `backupTo`, `close`). `query`/`execute` take Kysely `RawBuilder`s, so they move to db's `KyselyKernel<DB> extends StorageKernel<Kysely<DB>, DB>`. The schema witness stays (now on `Schema`), so a kernel missing tables is still rejected.
- **D2 `StorageTransport` becomes `string` in core.** The old literal union named drivers, and adding a driver would have meant editing core. db keeps the union as `DbTransport`, and `KyselyKernel.transport` narrows to it. The Tovu `switch (kernel.transport)` in `assistant/persistence/agent-session-store.ts` stays exhaustive because that kernel is a `KyselyKernel`.
- **D3 What core gets:** the neutral kernel, capabilities and its error; the pure helpers `toBool`, `isUniqueViolation` and `toBytes`, plus the `ColumnInfo` type; the row helpers `DbRow`, `row`, `rows` and `parseJsonOrUndef`; Jini's own sync-SQLite client *shapes* (`SqliteClient`, `SqliteDb`, `SqliteSyncOpener`…; these are structural interfaces Jini defines, implementable by better-sqlite3, node:sqlite or bun:sqlite, and they import nothing); and `MigrationContext`/`MigrationStep<Kernel>`.
  - **Not** moved: `StorageOps`, `DbOpsPort` and the restore types (only db and the frozen infra forwarder use them); db's `JsonObject` (only the frozen sqlite forwarder uses it).
  - **No ports** go into core. Each runtime need has a single consumer, so B4 applies: the consumer declares the port locally (R lanes).
- **D4 Migrations: descriptors out, host runs.** A domain exports `readonly MigrationStep<StorageKernel<Kysely<unknown>>>[]` plus its ledger table name from its SQL adapter subpath. The host calls db's `runMigrations(kernel, steps, { ledgerTable })`. The steps stay Kysely code inside the adapter. Rewriting them as dialect SQL text would change shipped DDL and is not needed for swapping, because a new storage layer brings new adapters, migrations included.
- **D5 Pinned commerce checksums.** commerce's pin test hashes each step file's *whole* text, imports included (`__tests__/migrations.vitest.test.ts:31-37`), and the four shipped step files must change their import lines. The ledger checksums recorded in databases must never change. So C3a splits the pin in two:
  - `COMMERCE_PAYMENTS_MIGRATION_CHECKSUMS` stays byte-identical: it is the ledger identity.
  - A new `COMMERCE_PAYMENTS_SOURCE_DIGESTS` holds the edit guard, re-pinned once for this reviewed, behavior-free edit.
  - The db owner-store history hashes only its DDL string, so it is unaffected. Tovu's 52 pinned step files DO change (their facade imports are repointed); D7 applies the same split to Tovu.
- **D6 Kysely confinement gate (new rule `L8-storage-adapter`, coordinator applies it to C0's `check-package-layers.ts`).**
  - In domain packages, `kysely` and every driver specifier (`better-sqlite3`, `pg`, `@electric-sql/pglite`, `drizzle-orm`) may be imported only by files matched by the manifest's new `jini.storageAdapters` globs.
  - No file outside those globs may import a file inside them.
  - Exempt: db and the host presets (`server`, `cli`).
  - commerce's `payments/ledger/rows.ts` chain goes into the debt baseline until R6.
  - Globs per package:
    - chat `["src/store/sql/**","src/store/sqlite/**","src/store/pglite/**","src/store/postgres/**","src/store/legacy/**","src/store/runtime/**"]`
    - cms `["src/*/sql/**"]`
    - commerce `["src/catalog/database.ts","src/catalog/repo.ts","src/catalog/repo.*.ts","src/payments/ledger/repo.sql.ts","src/payments/ledger/sql.ts","src/payments/ledger/sql-tables.ts","src/payments/ledger/migrations/**"]`
    - daemon `["src/store/event-log/sqlite.ts","src/store/event-log/sqlite-kernel.ts","src/store/agent-sessions/{sql,sqlite,pglite,postgres}.ts"]`
    - plugins `["src/host/sql/**"]`
  - In each R lane, `kysely` moves from `dependencies` to an optional peer (chat and daemon list it as a hard dependency today).
- **D7 Tovu facades are deleted; Tovu gets the D5 split (coordinator B1 ruling 2026-11-15; supersedes the old D7 and the OWNER OVERRIDE re-stamp).**
  - Why no DB write is needed: Tovu's ledger stores the *pinned literal*, never a hash of the source. `migrations/index.ts:73` `pinned(id)` reads `MIGRATION_CHECKSUMS[id]`, each factory stores it as `step.checksum`, and db `migrate/runner.ts:138` compares `row.checksum !== step.checksum`, `:151` inserts `step.checksum`. Only `__tests__/checksums.test.ts` derives a value from the source text. `legacyBaselineChecksum()` hashes the frozen drizzle chain and `POSTGRES_BASELINE`, neither of which C3t edits. Checked 2026-11-15: no runtime path hashes a Tovu step's TS source, so no stored checksum can change and no re-stamp ships.
  - `apps/website/src/platform/db/kernel/port.ts`, `kernel/dialect.ts` and `migrations/step.ts` are deleted. No exception, no alias, no forwarder. Their 228 import lines (131 files, 52 of them pinned step files) are rows in `C3t.repoint.tsv`.
  - `MIGRATION_CHECKSUMS` (`migrations/checksums.ts`) stays byte-identical: it is the ledger identity.
  - A new `migrations/source-digests.ts` holds the edit guard for the 51 source-hashed ids whose file text changed (all pinned ids except `0000_legacy_baseline`).
- **D8 Repoint rules during C3 (debt lines stay single).** When a domain file still holds a db *value* import that its R lane will remove (`listColumns`, `sqliteKernel`, `runMigrations`, `openSqliteConnection`), its `StorageKernel` becomes `KyselyKernel` on that same db spec. This adds no new debt line. Domain test files that call `kernel.query/execute` do the same (a test-only edge under Q5). Everything else in a domain goes to the core form.
- **D9 Events** are unchanged from the first design. They are pure types with no storage library, so they are still valid: `core/contracts/events` plus the new `ExecuteCommandFn`. The difference is that the old cms definitions are deleted, not re-exported.

```ts
// packages/core/src/contracts/storage/kernel.ts
/**
 * @file The storage kernel contract: the ONE async way a repository adapter reaches its database, on every driver.
 * Package: `@jini-ai/core/contracts/storage`. Names no query library and no driver: `Handle` is whatever query handle
 * the host's storage package passes to {@link StorageKernel.run} (`@jini-ai/db` binds its own handle type).
 *
 * A repo is ONE query body for every dialect. It never holds a raw handle, never runs `BEGIN`, never calls a driver
 * API. It asks the kernel:
 *
 * - {@link StorageKernel.run} — run statements on the right executor: the open transaction when the
 *   caller is inside {@link StorageKernel.transaction}, else the base handle.
 * - {@link StorageKernel.transaction} — one unit of work. A NESTED call joins the outer one (no
 *   savepoint), so a service composing two repos that each wrap themselves still commits or rolls
 *   back as one. Calling it from inside a `run()` body throws: that body holds the handle a
 *   transaction would wait for.
 * - {@link StorageKernel.lockKey} — the explicit concurrency strategy for "nothing else may
 *   interleave here" (read-then-write sequences such as a ledger append). A transaction alone does
 *   not give that on Postgres (READ COMMITTED); this does, on every dialect.
 *
 * Three separate things describe a kernel (never inferred from each other, never cached per process):
 * the SQL {@link StorageDialect}, the connection {@link StorageTransport}, and its
 * {@link StorageCapabilities}. Asking for a capability the kernel lacks throws
 * {@link UnsupportedCapabilityError}; nothing silently downgrades (e.g. a transaction never becomes
 * "run the statements one by one").
 *
 * Drivers live in the host's storage package (`@jini-ai/db`: the `sqlite`, `pglite` and `postgres` subpaths).
 * None of them imports a driver package: the consumer passes its own client, pool or class in.
 */

/** SQL family: decides which dialect helper fragment applies. */
export type StorageDialect = "sqlite" | "postgres";

/**
 * The connection underneath, named by the storage package that opened it (`@jini-ai/db`: `DbTransport`).
 * Open-ended so a new driver needs no change here.
 */
export type StorageTransport = string;

/* StorageCapabilities, StorageCapability, UnsupportedCapabilityError: verbatim from db port.ts:40-60 */

declare const storageKernelSchema: unique symbol;

export interface StorageKernel<Handle, Schema = unknown> {
  /** Type-only schema witness: retain Schema independently of the handle's structural method
   * signatures so stores reject kernels missing required tables.
   * Optional so existing host implementations need no runtime property. */
  readonly [storageKernelSchema]?: Schema;
  readonly dialect: StorageDialect;
  readonly transport: StorageTransport;
  readonly capabilities: StorageCapabilities;
  /** Resolves once the driver is open and its schema is in place. Every call below awaits it. */
  readonly ready: Promise<void>;
  run<T>(fn: (handle: Handle) => T | Promise<T>): Promise<T>;
  /** Throws {@link UnsupportedCapabilityError} without `interactiveTransactions`. */
  transaction<T>(fn: () => Promise<T>): Promise<T>;
  /* lockKey (with its 5-line doc), inTransaction, require, backupTo (with its doc), close: verbatim from port.ts:84-98 */
}
```

```ts
import type { StorageKernel } from "./kernel.js";
/**
 * @file What a migration step is. Steps form ONE ordered history for every dialect; the host's runner
 * (`@jini-ai/db/migrate` `runMigrations`) by default applies each pending one in its own transaction and records it in
 * the consumer's ledger table. A package ships steps as data from its storage-adapter subpath; it never runs them.
 */
/* MigrationContext: verbatim from db step.ts:12-21 */
/** `Kernel` is the kernel the step's body needs: `MigrationStep<StorageKernel<Handle>>` for the host's query handle type. */
export interface MigrationStep<Kernel extends StorageKernel<unknown, unknown> = StorageKernel<unknown>> {
  readonly id: string;
  /** sha256 hex of what the step does, pinned by the consumer (a test re-derives it with `sourceChecksum`). */
  readonly checksum: string;
  /** Runs OUTSIDE the transaction, only when the step is pending (backups: they cannot run inside one). */
  prepare?(kernel: Kernel, context: MigrationContext): Promise<void>;
  /** Runs inside the step's transaction, after the runner holds the migration lock. */
  up(kernel: Kernel, context: MigrationContext): Promise<void>;
}
```

```ts
// packages/db/src/kernel/port.ts — whole body replaced (db keeps owning everything Kysely-typed)
import type { Kysely, RawBuilder } from "kysely";
import type { StorageKernel } from "@jini-ai/core/contracts/storage";

/**
 * @file `@jini-ai/db`'s kernel: the neutral `@jini-ai/core/contracts/storage` {@link StorageKernel} bound to a Kysely
 * handle, plus raw statements. Hosts that chose Kysely type their kernels with this; domain packages see only the core
 * contract (`StorageKernel<Kysely<DB>, DB>` in their SQL adapter subpaths) and never import this package.
 *
 * - {@link KyselyKernel.query} — a portable Kysely `sql` statement returning rows. For dialect
 *   helpers, migrations and introspection (`dialect.ts`), not for repos.
 */

/** The connections this package's drivers open (core's `StorageTransport` is open-ended). */
export type DbTransport = "better-sqlite3" | "pglite" | "node-postgres" | "pglite-socket";

export interface KyselyKernel<DB> extends StorageKernel<Kysely<DB>, DB> {
  readonly transport: DbTransport;
  query<Row>(statement: RawBuilder<Row>): Promise<Row[]>;
  /** {@link query} for a statement that returns no rows (DDL, a write without `RETURNING`). */
  execute(statement: RawBuilder<unknown>): Promise<void>;
}
```
