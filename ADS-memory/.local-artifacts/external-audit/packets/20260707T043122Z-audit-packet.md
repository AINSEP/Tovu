## Focus areas (what the owner most wants scrutinized)

1. **Cross-spec coherence** — contradictions or drift *between* specs: shared terminology,
   the Drizzle data-layer reconciliation, error-code namespace overlap/collision, and
   ownership boundaries between features (e.g. who owns slug uniqueness, who owns the DB
   schema, how the plugin `ext.*` fields interact with content authoring and the command
   gateway).
2. **Testability & acceptance criteria** — are ACs concrete, measurable, and TDD-ready?
   Flag ambiguous "should" language, untestable assertions, and missing negative/error
   cases behind happy-path ACs.
3. **Completeness & failure modes** — missing error paths, edge cases, recovery/rollback,
   and unspecified state transitions the happy-path text glosses over.
4. **Traceability integrity** — do the `traceability.spec.md` files actually map every
   requirement → acceptance criterion → error code with no orphans, dangling refs, or
   IDs that appear in one file and not another?
5. **OPEN — gaps the owner did NOT name.** The owner explicitly asked "what else am I not
   thinking of?" Surface load-bearing STRUCTURAL gaps across the suite — entire concerns
   or dimensions that are absent, not cosmetic nits (e.g. missing auth/z model, migration
   strategy, concurrency/versioning semantics, multi-tenant assumptions, upgrade path,
   observability). If you see a strong reframing or decomposition the suite is missing,
   describe it and why it's stronger.

## Threat Model & Scope Contract (FROZEN — TM-SPEC-001)

**Risk tier:** medium → **score floor = 8.5**.
This is a positive ALLOWLIST of in-scope *blocking* failure domains for a SPEC-quality
audit. A finding is BLOCKING only if it maps to exactly one domain below AND would, if left
unfixed, cause implementers to build the wrong or an unbuildable system. Anything outside
this list is advisory (or goes in `out_of_scope_fatal_warnings`).

- **D1 — Contradiction:** two specs (or two files in one spec) assert requirements that
  cannot both be satisfied.
- **D2 — Untestable requirement:** a normative requirement/AC that no test could
  deterministically pass or fail as written.
- **D3 — Traceability break:** a requirement, AC, or error code referenced but not defined,
  or defined but orphaned, such that coverage cannot be verified.
- **D4 — Missing failure mode:** an error/edge/recovery path whose absence would let an
  implementer ship data loss, corruption, or an unrecoverable state.
- **D5 — Boundary ambiguity:** ownership of a shared concern (schema, slug, error
  namespace, plugin field mutation) is unassigned or doubly-assigned across specs.

**Mandatory invariants (must hold across the suite):**
- INV-1: Every normative requirement is testable (maps to D2 if violated).
- INV-2: Every referenced ID (req/AC/error) resolves to exactly one definition (D3).
- INV-3: No two specs contradict on shared concepts/terms (D1/D5).
- INV-4: Every mutation/persistence path names its failure + recovery behavior (D4).

**Allowed actors:** spec readers/implementers (TDD engineer, architect) acting in good faith.
**Out of scope for blocking:** prose/style, template boilerplate, naming taste, and choices
already explicitly deferred to a named Open Question (OQ-*) or ADR — note these as advisory.
