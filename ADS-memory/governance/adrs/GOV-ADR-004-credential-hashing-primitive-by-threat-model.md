# GOV-ADR-004: Credential-Hashing Primitive Is Chosen By Threat Model, Not By Copying The Nearest Existing Pattern

- **Enforcement:** DEFAULT

## Rule

When this codebase mints a new kind of secret credential, the hashing/storage primitive is chosen by the credential's actual threat model, not by copying whichever hashing pattern already exists nearby:

- A **low-entropy, human-chosen** secret (a password) MUST use a deliberately slow, memory-hard KDF (this codebase's standard: **argon2id**, via `PasswordHasherPort` / `identity/hasher.ts`) — the slowness is the point, because the secret itself is guessable and must resist offline brute-force from a leaked hash.
- A **high-entropy, machine-generated** secret (a session token, an API key, or any future opaque bearer credential minted by `crypto.randomBytes`) MUST use a fast, deterministic hash (this codebase's standard: **SHA-256**, via `identity/token-crypto.ts`'s `hashOpaqueToken`) compared by exact equality on lookup (mirrors `sessions.findByTokenHash` / `api_keys.findByKeyHash`) — the secret is never brute-forced from its hash because guessing 256 random bits is already infeasible before hashing enters the picture, so a slow KDF only taxes every legitimate verification for zero security benefit.

## Why

SPEC-006's `ISSUE_API_KEY`/`REVOKE_API_KEY` design (ADR-021, ADR-048) needed a hashing choice for API keys. The obvious "reach for the pattern that's already there" move would have been reusing `PasswordHasherPort`/argon2id, since it was the only hashing seam this library had built so far. That would have been wrong: argon2id's ~19 MiB memory + 2-iteration cost per call exists specifically to slow down an attacker guessing a low-entropy password from a leaked hash — a threat model that does not exist for a 256-bit random API key, which is never guessed from its hash under any realistic attack. Applying it anyway would tax every API-authenticated request for no real security gain, directly contradicting SPEC-006 REQ-08's own stated expectation that a key "authenticates identically to a session."

This codebase already had the *correct* answer sitting one file away and unrecognized as a reusable rule: `auth-service.ts`'s session-token hashing (`hashToken`/`newRawToken`, SHA-256 + `randomBytes`) is the right pattern, but it existed as private, unexported functions with no accompanying rule explaining *why* it's right or *when* to reach for it instead of argon2id. Without this rule recorded somewhere durable, the next feature that mints a machine credential (a webhook signing secret, a personal access token, an agent delegation token) is likely to make the same "just reuse `PasswordHasherPort`, it's already there" mistake — this ADR exists to make the correct choice discoverable independent of which feature happens to need it next.

## Enforcement

- [ ] Code review checklist item: any new secret-credential-minting code must state which threat-model bucket (low-entropy/human-chosen vs. high-entropy/machine-generated) the secret falls into and cite this ADR's rule for the corresponding primitive.
- [ ] `adr-governance` skill path-match lookup: any PR touching `src/identity/**` or introducing a new `*token*`/`*api-key*`/`*credential*` file should be checked against this ADR before a new hashing choice is finalized.
- [ ] Manual review only for now — no automated linter distinguishes "low-entropy secret" from "high-entropy secret" mechanically; this requires human/reviewer judgment about the credential's actual generation method (was it typed by a human, or generated by `crypto.randomBytes`?).

## Comply-or-Explain (DEFAULT rules only)

Valid reasons to deviate:
- A future credential type has a threat model that is neither purely "low-entropy human-chosen" nor purely "high-entropy machine-generated" (e.g. a credential with a human-chosen component and a machine-generated component) — explain the hybrid model and derive the primitive from first principles rather than defaulting to either bucket.
- A regulatory or partner-integration requirement mandates a specific algorithm regardless of threat-model fit (e.g. a partner's webhook-signature spec requires HMAC-SHA256 with a shared secret) — cite the external requirement.
- A future KMS/secrets-manager primitive is added to this codebase for an unrelated reason, making an HMAC-with-server-side-pepper scheme newly cheap to adopt (this was explicitly rejected in ADR-048 Pattern Evaluation §B *only* because no secret-custody primitive existed at decision time) — cite the new primitive and re-run the comparison.

Exception record goes in `governance/adrs/ADR-EXCEPTIONS.md`.

3+ exceptions against this ADR within 90 days triggers mandatory re-evaluation.

## Consequences

**Positive:** Prevents a recurring, easy-to-make mistake (defaulting to whichever hashing seam already exists, rather than reasoning about threat model) as this codebase adds more machine-facing credential types over time (agent delegation tokens are named as a near-term follow-on in ADR-021 §6/SPEC-006 OQ-01). Keeps the reasoning — not just the two current implementations — durable and discoverable.

**Negative:** One more governance ADR to consult before adding any new secret-credential code; the DEFAULT enforcement level means it's possible to deviate without being blocked, so it depends on reviewer diligence rather than a hard gate.

## Re-evaluation Triggers

- A third credential type is added (agent delegation tokens, per SPEC-006 OQ-01) — re-confirm this rule still cleanly covers it or needs a third bucket.
- 3+ documented exceptions within 90 days (per the standard governance re-evaluation policy).
- Any future addition of a KMS/secrets-manager primitive to this codebase (re-opens the rejected HMAC-pepper option named in ADR-048).
