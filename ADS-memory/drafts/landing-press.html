I

The premise

Most platforms bolt a chatbot onto the admin. This one hands the admin over.

Not screen-reading, and not a second API written to imitate the first. The tool and the button reach the same operation.

So can it do that? stops being a roadmap question. If the admin does it, the toolset does it.

IV

Themes

Five tiers. Pick by how much power the author needs.

  1. declarativeJSON blocks. A closed vocabulary the renderer will not step outside of.
  2. templatedLiquidJS, against an AST-walked tag and filter allowlist.
  3. handlebarsHelper allowlist. No partials, no decorators.
  4. staticPlain HTML, CSS and JavaScript. This page is one.
  5. codeReserved. Nothing ships on it yet.

Whichever tier, rendering happens inside a worker_threads sandbox with a wall-clock timeout and heap caps, falling back to a built-in body on any failure.

V

Running it

Clone it, or build the image.

Sourcebash

$ git clone https://github.com/leonaburime-ucla/Tovu.git
$ tovu serve my-site        # site and admin, one port
$ tovu export my-site       # static export
$ tovu introspect           # the CLI's own manifest, as JSON

Containerbash

$ docker build -t tovu:local .

tovu introspect prints the command surface an agent reads — generated from the CLI itself, so it cannot describe a flag that does not exist.
