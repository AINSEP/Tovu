## Open Questions Resolved (from feature.spec.md)

- **OQ-01 (runtime-mode signal mechanism):** Resolved → a dedicated environment variable, `TOVU_RUNTIME_MODE`. Rationale: resolution must happen before any config-store/DB connection opens (REQ-02/behavior.spec.md §1.1 boot-check sequence step 1 precedes everything else) — a config-store-backed signal would create a bootstrapping circularity (you'd need to know the mode to safely decide how to open the store that tells you the mode). An env var has no such dependency.
- **OQ-02 (inventory artifact format):** Resolved → a typed TypeScript module, `src/server/capability-inventory.ts`, exporting `CAPABILITY_INVENTORY: readonly CapabilityInventoryEntry[]` as a `const`. Rationale: REQ-03/REQ-04's boot-time checks must consult this data at runtime, not just read it as documentation — a typed in-repo module gives compile-time field completeness (TypeScript will not compile a `CapabilityInventoryEntry` missing a required field) and needs no separate parser, consistent with this codebase's existing convention of typed-data-as-code (e.g. `identity/permissions.ts`'s `BASE_CATALOG`).

## Scope Adjustment Disclosed (not in feature.spec.md, found during outline work)

**No CI infrastructure exists in this repo** — confirmed via direct search: no `.github/workflows/`, no ESLint config of any kind. REQ-11 ("`dependency-cruiser` shall run in CI in report-only mode") and REQ-12 (CI/review-gate staleness check) as literally worded assume a CI pipeline to add a step to. Since standing up CI infrastructure is a separate, larger concern outside ADR-046 Phase 0's scope, this outline narrows REQ-11/REQ-12's *implementation* to: runnable local npm scripts (`npm run check:boundaries`, `npm run check:inventory`) that produce the exact same report/flag output REQ-11/REQ-12 specify, wired into `package.json`. Whoever stands up CI later wires these two scripts in as steps — this outline does not invent a CI pipeline to satisfy them. This is a scope narrowing at the implementation-mechanism level only; the AC-21 through AC-24 acceptance criteria are unaffected (they test the script's behavior directly, not "the CI job passes").

## Downstream Handoff Notes

- Coordinator task-generation constraints: C-001/C-002 have no dependencies on each other and can be built in parallel (`[P]`); C-003/C-004 depend on both; C-005 depends only on C-001 (not C-002/C-003) and can be built in parallel with them; the `deps.ts`/`app.ts` wiring (W-001/W-002) and the `members`/`forms` call-site updates (W-003/W-004) both depend on C-005 existing first.
- TDD focus: prioritize C-003's aggregated-failure case and C-005's EC-04 unknown-lane case — both are the "looks fine per-item, breaks in aggregate/edge" shape this repo's own adversarial-test-design skill flags, and both are exactly where the ADR-046 debate found real bugs on the *first* pass (BR-04, the purpose collision) — treat them as high-risk by construction, not by assumption.
- Programmer architecture audit focus: confirm C-003/C-005 never throw an uncaught exception on a failing sub-check (must always resolve to a structured failure/refusal, per their Effect Boundary column); confirm `deps.ts`'s W-001 ordering is genuinely enforced (not just "usually runs first") — a route registered before the gate check completes is a full INV-001 violation, not a minor ordering nit.
- Open risks or ambiguities: **the `MailerSendOptions` discriminating field itself has no staleness/completeness check** analogous to REQ-12's inventory staleness check — a future third mailer call site could add itself without being caught by anything until it hits EC-04's runtime fail-closed behavior (which is safe, but silent/undiscovered until then). Flagging this as a real gap for whoever scopes Phase 1 or a Phase-0 follow-up, not fixing it here (out of SPEC-022's approved scope — would need its own REQ/AC).
