## RT-006 Resolution (Constitution Flag Anchor)

Red-Team's one CONSTITUTION_FLAG (RT-006, Article VI) is resolved here, plainly, as the frame for this entire ADR: **capability enforcement in this design is API-surface-level, not a sandbox.** An in-process ESM plugin module can call `node:fs`, read `process.env`, or open a raw network socket directly, bypassing every SDK-level capability check this ADR specifies. Nothing in this document, in the `@tovu/sdk` package, in its documentation, or in any admin-facing text may describe capability tokens, the load pipeline, or the SDK boundary as a *security sandbox* or *isolation mechanism*. This is the accepted v1 tradeoff for **first-party and explicitly-local plugins only** (this is exactly ADR-024's Tier-3: "today's in-process ESM reality... local/first-party/explicitly sideloaded only, and honestly labeled at install"). Real isolation is ADR-024 §4 Rung 1 (per-site process) and Rung 2 (capability sandbox), both explicitly deferred until the marketplace forcing function (ADR-024 §2) makes them necessary. This ADR's Complexity Justification and Risks sections carry this forward concretely rather than treating it as a one-line disclaimer.

## Context

Tovu has no plugin concept today. `src/features/plugins/` is a false cognate — it implements ADR-023's core-mediated `dataModule` DDL-mediation engine for compiled-in first-party features (newsletter, SEO, the `store` spike), not a loader for installable third-party-shaped code. This ADR designs the real thing: an artifact envelope, a load pipeline, a capability-scoped SDK package boundary, the one `content.entry.beforeSave` hook wired into the actual content-save path (`src/features/post/post.ts`'s `createPost`/`updatePost` — the spec's own citation of `createEntry` is a naming drift against the real function names, not a different file), and the bundled `word-count` plugin exercising that pipeline end to end.

System drivers:
- **Complexity**: not CRUD — a multi-step trust pipeline (verify → version-check → import → capability-gate → hook-attach) with a real security boundary and fail-closed semantics.
- **Coupling**: new external I/O (filesystem artifact reading, dynamic `import()` of foreign code) that must never contaminate `features/post`'s existing, heavily-tested write path.
- **Team shape / release cadence**: single team, single deployable (ADR-011 standalone single binary is the CI-enforced primary topology) — no case for microservices or a separate plugin-host process yet.
- **Audit**: REQ-07 requires the existing SPEC-001 gateway/change-set mechanism for enable/disable — this is already a solved problem in this codebase (`presentation.ts`'s `setActiveTheme` is the direct precedent) and must be reused, not reinvented.
- **Longevity / ecosystem stakes**: this is the highest-stakes point in the whole decision. ADR-005 requires the SDK compatibility promise to exist *before the first third-party plugin* — once real plugins exist, the hook signature and SDK export surface are nearly one-way doors. ADR-024 §3 (ratified after SPEC-005's approval) froze the ABI shape specifically because of this irreversibility, and named this exact hook as needing an audit against that freeze.
- **What happens if we do nothing**: the `plugins` nav entry (SPEC-045) stays permanently inert, and `word-count`/the SDK/the capability model never exist to prove any of tovu-v2-design §3's kernel registries actually work end to end.

## Decision

Build the plugin system as a **Tier-3 (ADR-024 vocabulary), in-process Microkernel/Plugin-Host architecture**, realized through **Hexagonal ports-and-adapters** inside the existing **Modular Monolith**, delivered as a new **vertical-slice feature module** (`src/features/plugin-runtime/`, deliberately distinct from the unrelated `src/features/plugins/`), plus one new **npm workspace package** (`packages/sdk`, published as `@tovu/sdk`) for the public plugin-author contract.

**Pattern(s) selected:** Microkernel (Plugin-Host) macro shape + Hexagonal ports-and-adapters (SDK boundary, activation repo, hook port) + Vertical Slice module placement, inside the existing Modular Monolith.

Concretely, on top of what SPEC-005 already specifies, this ADR makes four binding architecture-level decisions the spec package left as gaps or ambiguities:

1. **ADR-024 §3 ABI compliance (ties REQ-05/REQ-08 to the newer governing ADR).** The `content.entry.beforeSave` filter is treated as **always-awaited** by core regardless of whether a given filter function is `async` (the SDK type is `(entry, ctx) => ExtPatch | Promise<ExtPatch>`), the `ContentEntryDraft` passed to a filter is a **plain, deep-cloned, structured-clone-safe snapshot** — never a live Drizzle row, ORM entity, or class instance — and the capability-scoped SDK object a plugin receives is a **freshly-built handle of plain closures**, never a reference to a live core singleton (repo, hook registry, etc.). This satisfies ADR-024 §3's "asynchronous only / serializable payloads only / no live core objects, capabilities by handle" rule without changing any AC, error code, or manifest field — it is a transport/typing decision, not a behavior change, and needs no Spec Agent revision. A low-priority housekeeping note is recommended (see Risks) to sync `state.spec.md`'s `SdkSurface` type text.

2. **`definePlugin` / `addFilter` shape.** `@tovu/sdk` exports `definePlugin(def: PluginDefinition): Plugin` where `PluginDefinition = { setup(sdk: PluginSdk): void }`. Core calls `definePlugin`'s registered `setup` function **once per load, immediately after `import()`**, passing a capability-scoped `PluginSdk` object built fresh for that specific plugin instance (never a shared module-level singleton). `PluginSdk.addFilter(hookName, fn)` is how a plugin attaches to `content.entry.beforeSave` (REQ-05's literal API), gated by the `hooks.attach` capability; `PluginSdk.content.read`/`.extend` are gated by `content.read`/`content.extend`. This setup-callback shape is chosen over a bare top-level `import { addFilter } from '@tovu/sdk'` specifically to avoid a module-singleton registration queue that would require strict serialized-import ordering to attribute filters to the correct plugin — the chosen shape makes cross-plugin attribution structurally impossible to get wrong, at zero extra cost.

3. **SDK resolution mechanism** (see dedicated sub-decision below) — a Node `module.register()` customization hook, registered once at boot, redirects `@tovu/sdk`/`@tovu/*` bare-specifier resolution to the runtime's own bundled SDK build for every dynamic `import()` of plugin code, regardless of the plugin file's location on disk or any node_modules that might exist near it.

4. **Built-in plugins (`word-count`) skip the tarball/integrity-file mechanics but not the validator.** A built-in is source-compiled into the runtime, not unpacked from a `.tovu-plugin` artifact, so there is no packaged-file integrity hash to check — but it still declares an in-code manifest-equivalent object and passes through the *same* manifest/capability/hook validator as a site-installed plugin (one validator, two surfaces, per feature.spec.md's own Article IV framing), with the integrity step trivially satisfied (compiled-in code is definitionally not tampered).

## Default Heuristic Alignment

- Default heuristic: modular monolith at the macro level, vertical slices for feature ownership, hexagonal boundaries only where external I/O or business-critical logic justifies them.
- Alignment: **FOLLOWS**
- Notes: This is closer to a textbook case for the default heuristic than most features in this codebase — external I/O (filesystem, dynamic import of foreign code) and business-critical logic (the capability/trust boundary) are exactly the two named justifications for adding hexagonal ports inside a vertical slice, rather than defaulting to plain feature code. No departure is needed or proposed; a single-process microservice-per-plugin shape was considered and rejected (see Pattern Evaluation and Runner-Up Comparison) precisely because ADR-011 and ADR-024 already sequence that later, not now.

## Rationale

- Driver: security-critical trust boundary with irreversible-once-shipped SDK surface → addressed by Hexagonal ports (capability-scoped SDK as an explicit boundary object, not ambient access) + the ADR-024 ABI freeze folded in now, while zero third parties exist to break.
- Driver: existing, working audit/revert mechanism (SPEC-001 gateway) → addressed by reusing `presentation.ts`'s `setActiveTheme` shape verbatim for plugin enable/disable, rather than inventing a second activation pattern.
- Driver: single deployable, no case for distributed complexity yet → addressed by keeping the whole loader in-process (Tier-3), with the ABI freeze specifically preserving the *option* to move to out-of-process isolation later at near-zero retrofit cost.
- Driver: must not regress the heavily-tested existing `post.ts` write path → addressed by threading the hook as an **optional** `BeforeSaveHookPort` dependency that defaults to a no-op merge, so every existing caller/test that doesn't know about plugins keeps compiling and behaving identically (this is also why `behavior.spec.md`'s own default table states "zero-plugin path is a no-op").

## SDK Resolution Mechanism — Sub-Decision

**Problem**, not addressed by SPEC-005's `state.spec.md` §7: a plugin's prebuilt `server/index.mjs` does `import { definePlugin } from '@tovu/sdk'`, but that file is dynamically `import()`-ed from `<install-dir>/plugins/<id>/<version>/server/index.mjs` — a directory the runtime binary's own `node_modules` (where `@tovu/sdk` actually lives, per ADR-011's standalone single-binary topology) is not an ancestor of. Ordinary Node module resolution (walking `node_modules` up from the importing file) will not find it, and ADR-004 rule 2 already decided `@tovu/sdk` is **externalized** (not bundled into each plugin), so this cannot be sidestepped by having `tovu plugin build` inline the SDK at plugin-build time.

## Overall Strengths

- Reuses three already-proven codebase patterns verbatim (gateway-backed activation from `presentation.ts`, repo-port rule-of-two, discovery/validation shape from the theme system) instead of inventing new mechanisms, which is exactly what the spec's own dependency table asks for.
- The ABI freeze folded in now (rather than retrofitted later) buys most of the adaptability of a much larger out-of-process redesign at a fraction of the cost, and does so while there are zero third parties who could be broken by it.
- The optional, no-op-by-default `BeforeSaveHookPort` means this feature can be built and merged without any risk to `post.ts`'s existing, heavily-relied-upon test suite.

## Overall Weaknesses

- The security story has a real, disclosed ceiling (RT-006): this architecture cannot, by itself, stop a malicious or buggy in-process plugin from doing anything a compiled-in feature could do. This is accepted for v1, not solved.
- No numeric performance budget exists for hook composition in the save path — this is a genuine gap, not merely an unscored optional axis.
- Operability for a non-technical operator is thin until the deferred admin UI (OQ-02) lands; today's only lever for a broken plugin is a raw API call.

## Tradeoff Tension

We are trading a real, enforced security sandbox for delivery speed and walking-skeleton simplicity in v1 — capability enforcement is an API-surface convention honored by cooperating plugin code, not a boundary the runtime can defend against hostile code, and this is deliberately not marketed otherwise.

## Why This Won

The in-process Microkernel/Hexagonal combination wins because every REQ in the approved spec is written against it (REQ-03's `import()`, REQ-04's SDK-boundary capability check, REQ-07's gateway-backed activation), because ADR-011 forecloses a separate-process topology as the default, and because ADR-024 already sequences real isolation as a *later*, marketplace-gated milestone rather than a v1 requirement. The decisive factor over the out-of-process runner-up is not that isolation is undesirable — ADR-024 clearly wants it eventually — it is that **nothing in the current spec or constitution demands it now**, and the ABI freeze this ADR applies specifically preserves that future move as a cheap swap rather than a rewrite, which is the Adaptability First principle doing exactly its job: pay a small cost now (frozen async/serializable shape) to avoid a much larger one later (ecosystem-breaking hook redesign).

## Runner-Up Comparison

- Runner-up: out-of-process plugin host (ADR-024 §4 Rung 1/Rung 2, pulled forward to v1).
- Why it lost: no requirement in SPEC-005 asks for it (Article III Simplicity Gate), it contradicts ADR-024's own explicit sequencing rationale, and it is a materially larger, unauthorized scope expansion of this dispatch (which is already the largest single architecture surface this project has approved to date). The ABI freeze this ADR applies is precisely the mechanism that keeps this runner-up available as a near-free future swap (ADR-024 itself calls per-site isolation "a near-free runtime swap because of the §3 ABI freeze") rather than a forced ecosystem break — so selecting the in-process pattern now does not foreclose the runner-up, it prices it correctly for later.

## Consequences

**Positive:**
- The SDK compatibility promise (ADR-005) and its snapshot test exist before any third-party plugin does, as ADR-005 requires.
- `word-count` gives a real, working, testable proof that the artifact → load → capability → hook → `ext` → gateway loop functions end to end.
- The optional `BeforeSaveHookPort` means this feature adds zero regression risk to the existing, heavily-tested `post.ts` write path.

**Negative / Tradeoffs:**
- Capability enforcement is not a security boundary (RT-006) — accepted, not solved, for v1.
- A single throwing plugin can halt all content saves site-wide until disabled — accepted (RT-004), with the recovery path now explicit in the spec.
- No performance budget exists for hook composition — a real, open gap.

**Risks:**
- Risk: the `tier` manifest field ADR-024 introduces (`plugin.tier`, driving install consent and marketplace-listability) has no home in SPEC-005's current REQ-01 manifest schema, and REQ-01 explicitly rejects unknown top-level keys → plan: a small, mechanical Spec Agent amendment (see below), same shape as RT-002's `engine` fix, before TDD certifies REQ-01's manifest-validation tests.
- Risk: `module.register()` requires Node ≥18.19/20.6, and `package.json` currently pins no `engines` field → plan: Programmer adds `"engines": {"node": ">=20.6.0"}` (the dev environment already runs Node 24.2) as part of this feature's implementation, flagged here so it isn't missed as an incidental afterthought.
- Risk: adding npm workspaces at the root could interact unexpectedly with `apps/admin`'s existing separate `npm --prefix` install pattern → plan: Programmer's Architecture Audit explicitly smoke-tests `admin:install`/`admin:build` after the `workspaces` field lands (already captured as the `cost` axis mitigation above).

## API / Event Contract Summary

- `PLUGINS_LIST` (`GET /api/admin/v1/workspaces/:workspaceId/plugins`) and `PLUGIN_SET_ENABLED` (`PATCH .../plugins/:pluginId`) — as specified in `api.spec.md`, implemented as thin route handlers mirroring `src/server/routes/admin/posts/create.ts`'s `executeCommand`-wrapped shape for the enable/disable mutation; `PLUGINS_LIST` is a plain read (no gateway involvement, matching `PLUGIN_NOT_FOUND` etc. being route-level guards before the gateway per errors.spec.md §4).
- `BeforeSaveHookPort` (new, defined in `src/features/post/post.ts`): `runBeforeSave(entry: Readonly<ContentEntryDraftSnapshot>): Promise<JsonObject>` — the one contract `post.ts` depends on; implemented by `plugin-runtime/hook-registry.ts`, optional at the `CreatePostDeps`/`UpdatePostDeps` level (absent ⇒ identity/no-op, per behavior.spec.md §10's own default rule).
- `@tovu/sdk` public exports (REQ-08, ADR-005 rule 1, ADR-024 §3 ABI-compliant): `definePlugin`, `PluginDefinition` (`{ setup(sdk: PluginSdk): void }`), `PluginSdk` (`{ content?: { read, extend }, addFilter?(hookName, fn) }`, each surface present only per granted capability, absent surfaces represented by a `CAPABILITY_DENIED`-throwing stub, never a bare `undefined` — see Critical Internal Constraints U-003), the `content.entry.beforeSave` hook-point name constant, and the three capability token constants. Pinned by the REQ-08/AC-10 public-API snapshot test.
- `PluginActivationRepoPort`: `getActivation({workspaceId, pluginId})`/`save(record)`/`listAll()` — shaped identically to `PresentationSettingsRepoPort`, two adapters (memory, SQLite) from day one.
