## Item 2 — DONE. Commit `7caa2b71`.

`createPost` (`apps/website/src/features/post/post.ts`) never called `emitStatusTransitionEvent`/
enqueued anything, unlike `updatePost`/`deletePost`. Confirmed no `publish`/`enqueue`/`entry.*`
reference anywhere in `createPost`'s body before this fix. `status: "published"` is a documented,
first-class input on both the HTTP create routes and the `content_post_create`/`content_page_create`
assistant tools (verified: `resolveCreateStatus` validates the caller-supplied value against
`draft`/`published`, defaulting to `draft` only when *absent*), so a post/page published at creation
never invalidated `features/seo/sitemap.ts`'s no-TTL `Map` cache and stayed permanently absent from
`sitemap.xml` until an unrelated post in the same workspace was later updated.

**`createPage` check:** there is no separate `createPage` function — confirmed via grep, no match
anywhere in the tree. `pages/create.ts` calls the exact same `createPost` chokepoint with
`kind: "page"` (same table, same editor, per `PostKind`'s own doc). This fix covers both create
paths with one change; no second gap to close.

**Design decision — `CreatePostDeps.outbox` is OPTIONAL**, unlike `UpdatePostDeps.outbox`/
`DeletePostDeps.outbox` (both required). Matches this exact interface's own established
precedent for `beforeSaveHook?: BeforeSaveHookPort` ("OPTIONAL... absent ⇒ behaves exactly as it
did before this feature"). Rationale: ~9 test files call `createPost` directly with no outbox in
their fixture deps; making it required would force edits across all of them (out of this task's
scope, and higher risk on a shared tree several other agents are actively editing tonight). Optional
keeps every existing caller compiling and behaving identically, while all 3 real production callers
now supply a real one and drain it:
- `apps/website/src/server/inbound/admin-http/routes/posts/create.ts`
- `apps/website/src/server/inbound/admin-http/routes/pages/create.ts`
- `apps/website/src/features/post/tool-registrations.ts`'s `content_post_create` handler

Each mirrors `posts/update.ts`'s/`content_post_update`'s own already-proven
`processOutbox({ outbox, bus, clock })` drain call placed right after `executeCommand` succeeds and
before the response is sent — no new drain mechanism invented. Reused
`classifyStatusTransition`/`emitStatusTransitionEvent` verbatim (no parallel publish path), passing
`"draft"` as the synthetic previous-status baseline for a brand-new record — this is exactly what
the review's own suggested fix specifies, and correctly no-ops (no event) for a plain draft create,
unchanged from today.
