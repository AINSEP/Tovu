## Class 2 — Wired but unreachable

### `execute_delegated_tool` unconditionally declares `readOnlyHint: false` — blocks the ENTIRE native tool catalog under a read-only-only external runtime, not just writes
USER-VISIBLE: **yes, today**, for any external MCP-injected CLI whose policy requires
`readOnlyHint: true` to admit a tool call headlessly (codex exec is the confirmed case
per the dispatch's own known example).
EVIDENCE:
- `Jini/packages/agent-runtime/src/defs/codex.ts:245` — `externalMcpInjection: 'codex-toml'`,
  confirming codex is genuinely wired for injection (Class 1 passes; this is a downstream
  Class 2 failure).
- `Jini/packages/mcp/src/server/tools/delegated-tool.ts:1-14` — module doc: `execute_delegated_tool`
  proxies `POST /api/delegated-tool-calls`, described as **"the one and only thing that
  calls into `createDelegatedToolBridge`"** — i.e. it is the sole gateway from an
  externally-injected MCP CLI into Tovu's ~29-domain native tool catalog (`Tovu/apps/website/src/server/runtime/composition/tool-catalog-manifest.ts`).
- `delegated-tool.ts:156-162`:
  ```ts
  annotations: {
    readOnlyHint: false,
    idempotentHint: false,
    destructiveHint: false,
    openWorldHint: false,
    title: 'Execute a Jini-registered tool',
  },
  ```
  This annotation is a static literal on the meta-tool's own definition — it does not vary
  per delegated call. There is no per-`toolId` derivation (no read of the underlying
  domain tool's own `sideEffects`/`derivedRisk`, the fields `Tovu/apps/website/src/features/*/tool-registrations.ts`
  already carry for every native tool, e.g. `renderUiDerivedRisk` in `render-ui-tool.ts:70`).
- `grep -rln readOnlyHint Jini/packages/mcp/src` returns exactly 4 files
  (`run-tools.ts`, `delegated-tool.ts`, `tool-catalog-tools.ts`, `component-catalog-tools.ts`).
  `tool-catalog-tools.ts`/`component-catalog-tools.ts` cover only `search_tools`/`get_tool`/
  `search_components`/`describe_component` (pure discovery, correctly `readOnlyHint: true`).
  There is **no companion read-only delegated-execution tool** — `execute_delegated_tool`
  is the only way to actually run any of the ~29 native domains' tools this way, whether
  the underlying call is `content_post_list` (a pure read) or `content_post_delete` (a
  write).
- Consequence: the dispatch's framing — "the call died before leaving the process" for
  this one tool — understates the blast radius. Under a runtime that gates on
  `readOnlyHint: true`, **100% of the native catalog is unreachable** through MCP
  injection, not just the destructive half, because there is only one gateway and it is
  marked non-read-only unconditionally.
DERIVED AT: `Jini/packages/mcp/src/server/tools/delegated-tool.ts:156-162` — the one
static `annotations` block. Any fix has to either (a) split into a read-only-declared
variant that still fails closed for actual writes at the daemon's `ToolExecutor`
deny-by-default gate (the module doc already says that gate exists independently), or
(b) derive the annotation per call from the target `toolId`'s own `derivedRisk`, which
would require the annotation to become dynamic rather than a static tool-definition field
— note MCP's protocol may not support that shape at all; flagging the tension, not
prescribing the fix.
FIX SHAPE: one file, `delegated-tool.ts` — but the shape of the fix (split tool vs.
protocol-level limitation) needs a design call, not a one-line change.

### Ruled out: A2UI tools (`assistant_render_ui`, `assistant_demo_a2ui`) do NOT need `MCP_UI_REDEEMABLE_TOOL_IDS`
Checked because both open a real `SurfaceExchangeStore` exchange
(`Tovu/apps/website/src/assistant/render-ui-tool.ts:127`, `demo-a2ui-tool.ts:181`) the
same way the confirmation-shape tools that DO need the allowlist do, and neither tool id
(`assistant_render_ui`, `assistant_demo_a2ui`) appears in
`Tovu/apps/website/src/assistant/mcp-ui-tool-calls.ts:36-132`'s 10-entry allowlist. Ruled
out by reading `Tovu/apps/website/src/assistant/a2ui-actions-route.ts:8-64`: A2UI's answer
channel is a **separate, unguarded route** (`/api/admin/v1/a2ui/actions`) by explicit
design — its own doc states "there is no allowlist here because there is no execution
surface to allowlist" (it only ever calls `SurfaceExchangeStore.deliver`, never
`ToolExecutor.execute`). Not a gap; the allowlist genuinely does not apply to this
transport. No finding.

## Class 4 — Catalog entry with no implementation

USER-VISIBLE: **yes, today**, via the one agent tool that reaches this catalog

EVIDENCE:

  `integrated: true`.

  registered provider ids (aihubmix, fishaudio, openrouter, openai, senseaudio,
  volcengine, elevenlabs, grok, nanobanana, imagerouter, custom-image, minimax); `fal` and
  `leonardo` are absent.
- `Tovu/apps/website/src/features/media-generation/agent-tools.ts:38-68`
  (`IMAGE_MODEL_IDS`, written/updated **today**, 2026-09-02) already documents this exact
  gap in its own comment: *"Two providers included by this filter (`fal`, `leonardo`) are
  catalogue-`integrated: true` but have no adapter registered yet — selecting one of their
  models reaches the dispatch engine's own clean `no renderer configured...` error at

DERIVED AT: `Jini/packages/integrations/src/media-providers/dispatch/vendor-registry.ts`'s
