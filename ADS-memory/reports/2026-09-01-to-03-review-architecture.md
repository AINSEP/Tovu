## Findings

### F1 — CONFIRMED · HIGH (DI / duplicated seam) · A security fix explicitly scoped as "fixed as a class, not an instance" only reached one of two real callers of the same executor-decorator stack

`1bb6fa67` (2026-09-02, "carry the read-only constraint into the execution so a decorator cannot launder a write") is a real, well-designed fix: `withToolFailureRecovery` can dispatch a remedy tool id the caller never named, and a caller that explicitly picked the read-only MCP gateway (`execute_readonly_delegated_tool`, wire flag `requireReadOnly`) could have a write laundered through it. The fix attenuates the `Principal` (`constrainPrincipalToReadOnlyTools`) and adds `withReadOnlyToolConstraint` as the **innermost** layer of the executor stack, and extracts the whole three-layer composition into a new file, `assistant/tool-executor-stack.ts`, specifically — per that file's own header — because "the gap this defect lived in was exactly 'route check tested, composition not'": the old composition was inlined once, in `agent-daemon-server.ts`, where nothing could exercise it without booting Express.

`createAssistantToolExecutor` (`tool-executor-stack.ts:58-67`) is wired into `agent-daemon-server.ts` (the MCP/daemon path). It is the **only** caller. The commit's own PR-note header lists two real callers of the underlying pattern; the second one — `assistant/byok-tool-surface.ts`'s `createByokToolSurface` (the admin BYOK chat path, `/api/admin/v1/assistant/byok-turn`) — builds its executor **inline**, by hand, in the exact same file, same window, but does not call `createAssistantToolExecutor` and does not wrap with `withReadOnlyToolConstraint` at all:

```
byok-tool-surface.ts:434  const rawExecutor = createToolExecutor({ registry });
byok-tool-surface.ts:435-436  const auditedExecutor = options.toolAttemptAudit
                                 ? withToolAttemptAudit(rawExecutor, ...) : rawExecutor;
byok-tool-surface.ts:455  const executor = withToolFailureRecovery(auditedExecutor, { surfaceExchanges, registry });
```

`1bb6fa67` touches exactly 6 files (`git show --stat`) — `read-only-tool-constraint.ts`, `tool-executor-stack.ts`, `tool-failure-recovery.ts`, `agent-daemon-port.ts`, `agent-daemon-server.ts`, and the new composition test — `byok-tool-surface.ts` is not among them, before or after.

Consequence today: `requireReadOnly` is a wire flag only `@jini-ai/mcp`'s `execute_readonly_delegated_tool` route sets (verified — `command grep -rn "requireReadOnly"` across `apps/website/src` and `apps/admin/src` hits only `agent-daemon-server.ts` and this file's own doc comments; no admin route or UI ever sets it), so no BYOK principal is ever attenuated today and the missing wrap has no live exploit path right now. The consequence is architectural, not a live CVE: `tool-executor-stack.ts` exists specifically so this composition cannot silently drift per-caller, and it already has — the new regression suite this same commit ships, `read-only-tool-constraint.composition.test.ts` (371 lines), drives `createAssistantToolExecutor` exclusively (`import { createAssistantToolExecutor } from "../tool-executor-stack.js"`, both test bodies at lines 111 and 289); no test anywhere asserts `withReadOnlyToolConstraint`/`constrainPrincipalToReadOnlyTools` against the BYOK stack (the only `readOnly`-adjacent hit in `assistant/__tests__` outside that file is `tool-registrations.contracts.test.ts:573`, which asserts a descriptor's static `readOnly` flag, not executor-level enforcement). The moment BYOK gains any restricted-principal concept — plausible, since the daemon already has one and BYOK already mirrors the daemon's audit/failure-recovery wrapping "byte-for-byte" by convention — the exact write-laundering bug `1bb6fa67` fixed reopens silently in the second caller, with zero test coverage to catch it.

Fix: `createByokToolSurface` should call `createAssistantToolExecutor({ registry, auditSink, surfaceExchanges, workspaceId })` (wrapping the conditional-audit case in a no-op sink, or widening `AssistantToolExecutorDeps.auditSink` to accept `undefined`) instead of hand-composing three decorators inline; then extend `read-only-tool-constraint.composition.test.ts` (or add a BYOK-specific composition test) to drive the BYOK stack the same way.

### F2 — CONFIRMED · MEDIUM (duplicated seam) · A security-relevant `EgressPolicy` (the ADR-038 SSRF guard) is hand-copied three times, byte-for-byte, with no shared constant

`9eebf39d` (2026-09-01, the first commit of this window — "let the agent verify and call a saved custom credential") adds `customCredentialsHttpClient: HttpClientPort` to `RouteDeps` and constructs it independently in both composition roots:

- `server/runtime/composition/deps.ts:1137-1144` (`customCredentialsHttpClientPolicy`)
- `server/runtime/composition/app.ts:791-798` (inline literal, `satisfies EgressPolicy`)

Both are **field-for-field identical** to each other, and to the pre-existing `mailHttpClientPolicy` a few lines above in `deps.ts:1115-1122` (added for the mailer, before this window): `allowedSchemes: ["https"]`, `denyPrivateAddresses: true`, `devHostAllowlist: []`, `maxRedirects: 0`, `connectTimeoutMs: 10_000`, `maxResponseBytes: 1_000_000`, `maxDecompressedBytes: 1_000_000` — seven fields, zero variation, three separate object literals. `routes/types.ts:392-394`'s own doc comment on `customCredentialsHttpClient` concedes this directly: "Built with the identical policy shape ... both composition roots already use for `mailHttpClientPolicy`" — the duplication is disclosed, not hidden, but no shared constant exists anywhere (`command grep -rn "EgressPolicy = {" apps/website/src` and a search of `platform/http` for a `DEFAULT_EGRESS`-style export both come up empty).

Consequence: this is exactly the `TOVU_ADMIN_DEV_PROXY_URL`-in-two-modules shape from the 09-04/05 review's F6, generalized from an env var to a full security policy object. A future tightening of the SSRF guard — e.g. lowering `maxResponseBytes` after an incident, or `EgressPolicy` gaining a new required field the type system would force onto all three call sites but a human might satisfy with copy-pasted defaults rather than the intended new value — has three edit sites to keep in sync by hand instead of one. Two of the three (both new in this window) are the outbound path for `custom_credential_make_request`, an agent tool that makes authenticated requests to an **operator-typed, arbitrary base URL** — the highest-stakes consumer of this exact policy in the codebase, per `credentialed-request.ts`'s own header ("THIS module's target host is exactly the opposite [of hardcoded review URLs]: an arbitrary, operator-typed `baseUrl`").

Fix: one `export const DEFAULT_EGRESS_POLICY: EgressPolicy = {...}` in `platform/http/`, imported by both composition roots and both policy variables (`mailHttpClientPolicy`, `customCredentialsHttpClientPolicy`), so a future change is one edit instead of three, and app.ts/deps.ts can no longer read differently by accident.
