**Smallest proposed design**

Keep analytics in `@jini-ai/analytics`, operational signals in `@jini-ai/diagnostics`, logging in the existing core `Logger`, and consent in CMS. Tovu supplies site/workspace policy and composition. Proposed additions—not existing APIs—look like:

```ts
type Options = { signal?: AbortSignal };
type Surface = "site" | "admin" | "desktop";
type Properties = Readonly<Record<string, string | number | boolean>>;

interface AnalyticsCapturePort { // analytics: browser/renderer input
  capture(required: {
    kind: "pageview" | "event"; surface: Surface; path: string;
    eventName?: string; properties?: Properties;
  }, optional?: Options): void;
}
interface ErrorReportingPort { // diagnostics
  report(required: { error: unknown; surface: Surface; operation: string },
    optional?: { requestId?: string; release?: string }): void;
}
interface TelemetryLifecyclePort { // diagnostics: bounded draining
  flush(required: { timeoutMs: number }, optional?: Options): Promise<void>;
  shutdown(required: { timeoutMs: number }, optional?: Options): Promise<void>;
}
```

- Reuse existing `AnalyticsSinkPort.accept({hit})` / `acceptBatch({hits})` for normalized output, and `RequestMetricsPort.recordRequest(...)` for request metrics. Add optional object arguments compatibly where needed. Do not introduce another analytics engine, logger, or general-purpose event bus.
- The capture adapter sends to first-party ingress. Public ingress resolves its workspace; authenticated admin ingress assigns trusted workspace/surface. Both use the shared privacy pipeline. Preserve the local sink/read screen and forward asynchronously through a bounded queue; vendor outages must not delay page requests.
- A PostHog adapter maps accepted hits/events to its capture API or SDK. Begin with explicit events; enable autocapture/replay only as separate requirements and consent decisions. PostHog’s event capture is a distinct integration from OTLP traces. [PostHog API](https://posthog.com/docs/api)
- For Datadog, Honeycomb, and Grafana, keep application instrumentation on OTel and route OTLP through a collector. Backend-specific endpoint/auth configuration belongs there or in an adapter, avoiding vendor imports throughout Tovu. [Datadog](https://docs.datadoghq.com/opentelemetry/setup/otlp_ingest/), [Honeycomb](https://docs.honeycomb.io/send-data), [Grafana](https://grafana.com/docs/grafana-cloud/send-data/otlp/send-data-otlp/)
- A Sentry adapter implements exception reporting; browser/React and Electron capture require their respective host wiring. Include release/source-map delivery in that slice. [Sentry source maps](https://docs.sentry.io/platforms/javascript/guides/hono/sourcemaps/troubleshooting_js)
- First ship adapters as reviewed npm packages injected at composition. For installable plugins, add one category-based contribution descriptor to the existing trusted loader—analytics export or error reporting—with enable/disable, destination policy, vault reference, and lifecycle cleanup. Plugins import shared Jini contracts, never another plugin. Arbitrary browser SDK loading needs an approved extension of browser admission.
- Tools remain category-based: configure/test/status/query analytics or errors. Vendor choice is adapter configuration, not a new vendor-shaped core tool family.
