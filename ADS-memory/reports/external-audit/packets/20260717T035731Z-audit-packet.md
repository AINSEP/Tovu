## Threat Model & Scope Contract (frozen)

- **Threat model id:** `TM-adr046-phase3-full-sweep-audit-001`
- **Audit round:** 1 (first full pass — no prior ledger; this is genuinely new, never-before-audited work distinct from the already-merged `TM-adr041-043-044-045-audit-001` and `TM-adr046-phase3-comments-audit-001` series)
- **Intended use / deployment context:** Production admin CMS backend (Node/Express/TypeScript) + its React admin frontend. The backend composition root (`src/server/app.ts`) wires ~40 route-registrar modules into one Express app at boot. This sweep's sole intended effect is moving registrar *call sites* from inline `app.ts` blocks into per-domain `ServerModuleHandle` factory modules, with zero intended behavior change. The frontend changes add real admin-UI surfaces (Comments moderation, plus SEO/Media/Taxonomy/Redirects/Collections editing panels) that call the already-existing (pre-this-session) backend API.
- **Allowed actors & capabilities:** (1) authenticated admin principals holding a specific permission set (e.g. `comments.configure`, `comments.moderate`) acting through the admin API/UI; (2) anonymous public site visitors hitting public routes (site catch-all, SEO sitemap/robots, member-public routes); (3) the boot/composition-root process itself (no external actor — this is where registration-order bugs manifest). No actor in this contract has direct DB/filesystem access outside these two surfaces.
- **In-scope blocking failure domains (ALLOWLIST):**
  1. Route/registrar relocation drops, duplicates, or reorders a registration such that real HTTP behavior changes (a route becomes unreachable, double-registers, or a public route now falls after a catch-all)
  2. A narrowed `RouteDeps` Pick type omits a field its registrar body actually reads, producing a `undefined` runtime error or silently-wrong behavior once composed through the real `createApp()`
  3. Auth/session ordering regression — `registerAuthRoutes` no longer registers strictly before `app.use("/api/admin", requireAdminSession(...))` inside `core.ts`, which would either permanently lock out all admin sessions (login unreachable) or remove the gate's protection (unauthenticated access to `/api/admin/*`)
  4. Storage/recovery `operationInFlight` regression — `recovery/status.ts`'s live read of `core/operation-lock`'s `isOperationInFlight` is broken, stubbed, or made to read a stale/cached value post-relocation (carried-forward invariant from this session's own 7-round `TM-adr041-043-044-045-audit-001` audit, which found and fixed a real bug in a similarly "safe-looking" refactor of this exact code)
  5. SEO public-route-vs-catch-all ordering regression — the 2 public SEO routes (sitemap, robots) register at or after `registerSiteRoutes`'s `/:slug` catch-all, making them permanently unreachable
  6. Any of the 3 deliberately-excluded gated-mutation ceremonies (`registerAdminTaxonomyMergeTermRoutes`, `registerAdminStorageMigrateForwardRoutes`, `registerAdminRecoveryRestoreRoutes`) gets accidentally relocated, duplicated, or dropped
  7. Frontend calls a backend endpoint/method/path/payload shape that does not match the real route handler (invented endpoint, wrong verb, wrong field names) — would 404/400/500 in production
  8. A permission-gated frontend form fires a request for a caller who structurally cannot succeed (missing required permission), rather than declining client-side — wastes a round-trip and produces a confusing failed-request UX, not just an inefficiency (this repo's own AC for Comments settings explicitly requires the client-side decline)
  9. Any relocated registrar body's actual logic changed incidentally during the move (not just its import/type signature) — a "relocation" that quietly became a behavior change
- **Mandatory invariants:**
  - INV-AUTH-ORDER: `registerAuthRoutes(app, deps)` executes before `app.use("/api/admin", requireAdminSession(deps))` inside `createCoreModule`'s single `registerRoutes(app)` call body (source-order guarantee, not a runtime check)
  - INV-OPLOCK-LIVE: `recovery/status.ts` keeps `isOperationInFlight` as a direct module-level import from `core/operation-lock`, queried with the real `workspaceId`, never routed through a stubbable/mockable `RouteDeps` field
  - INV-SEO-PUBLIC-ORDER: `modules/seo.ts`'s `registerRoutes(app)` registers `registerSeoSitemapRoute`/`registerSeoRobotsRoute` at the same relative position (before `registerSiteRoutes`) that they held in the original inline `app.ts`
  - INV-GATED-CEREMONY-UNTOUCHED: all 3 gated-mutation ceremony registrars remain inline calls in `app.ts`, not absorbed into any new module
  - INV-BEHAVIOR-IDENTICAL: every relocated registrar's HTTP-observable behavior is byte-identical pre/post relocation (this is a pure composition-root refactor, not a feature change)
  - INV-COMMENTS-PERM-DECLINE: the Comments settings form component returns `null` (no request fired) when the caller's principal lacks `comments.configure`, rather than firing a request that will 403/404
- **Blocking impact threshold:** any validated instance of an in-scope failure domain occurring under normal actor/capability use as defined above (not a contrived/adversarial-only trigger) meets the bar.
- **Risk tier & score floor:** HIGH → floor 8.5. Rationale: INV-AUTH-ORDER's failure mode is total admin-app lockout (no session obtainable at all); the storage-recovery domain has a documented history of a real bug surviving a similarly "safe-looking" refactor in this exact codebase this session; this diff touches the entire admin route surface (~40 registrars across 9 domains) in one composition-root change.
- **Gate formula (deterministic):** `blocking_gate = FAIL` iff `(count(validated unresolved blockers) > 0) OR (score < 8.5)`. The two terms are independent; neither rescues the other. The coordinator recomputes this from the returned validated blockers + score and rejects any auditor-returned gate that disagrees.
- **Explicit non-goals:**
  - NOT re-auditing `TM-adr041-043-044-045-audit-001` (Storage/Collections/Taxonomy/Recovery core logic) or `TM-adr046-phase3-comments-audit-001` (ADR-046 Phase 3 second slice + Comments backend/ADR-031/035) — both already externally audited and merged to `main` in a prior round this session. This round covers only the NEW work built on top: SPEC-036 through 042.
  - NOT auditing CI/CD (none exists in this repo yet — explicitly deferred by the user to a later, separate piece of work).
  - NOT evaluating the future AG-UI/CopilotKit wiring or a possible automation daemon — informational research only, not yet implemented, out of scope for this diff.
  - NOT a general security penetration test of the whole application — scope is bounded to this diff's 9 listed failure domains.
  - NOT auditing the underlying business logic of features these registrars expose (e.g. whether Collections' content-model design is correct) — that was ADR-043's own accepted design; this audit is about the *relocation*, not the *feature*.
