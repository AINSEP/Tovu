## Design

**Module responsibilities**

- `src/assistant/capability-source-registry.ts` — the generic seam. A module-level ordered list of registered `CapabilitySource` entries, with `register`/`list`/`resetForTests`, cloned line-for-line from `tool-contribution-registry.ts`'s shape (replace-by-id, not append; order otherwise preserved). The one deliberate difference: a source's `list` is `() => Promise<readonly CapabilityCard[]>`, not synchronous — see the async discussion below. No I/O of its own; it holds function references, same as its template.
- `src/features/agent-plugins/capability-source.ts` — the first, and for this slice the only, registrant. Exports a registration function (e.g. `registerAgentPluginSkillsCapabilitySource()`) that calls `registerCapabilitySource({ id: "agent-plugin-skills", list })`, where `list` walks this workspace's installed packages and projects every skill folder of every installed digest into a card. Lives in `features/agent-plugins/`, reaches into `assistant/capability-source-registry.ts`, never the reverse — the same one-directional rule `tool-contribution-registry.ts`'s own header states for tool contributors.
- `src/assistant/capability-catalog-query.ts` — builds and queries a small, purpose-built FTS5 index (its own schema, not `@jini-ai/sqlite`'s tool-shaped one — see the trade-off below) from every registered source's `list()`, folded together. Exposes an async build function and a synchronous `search(query, { kind? }, limit?)` / `get(id)` pair once built.
- `src/assistant/capability-tool-registrations.ts` — `contributeCapabilityTools()`, following the exact shape `tool-contribution-registry.ts`'s own doc points at ("see `comments/tool-registrations.ts` for the shape"): calls `registerToolContributor({ domain: "capability", build, risk })`. `build` returns two `ToolRegistration`s whose handlers lazily build-and-memoize the catalog on first real call (this is where the async/sync boundary actually gets crossed — see below), then call `search`/`get` on it.
- `src/server/tool-catalog-manifest.ts` — one added line in `installFirstPartyToolContributors()`: `contributeCapabilityTools();`, alongside the existing 24. One added line elsewhere in the same file (or a sibling composition call from the same module) to register the Agent Plugin skills source: `registerAgentPluginSkillsCapabilitySource();`. Both are no-argument calls, matching the file's existing convention exactly.

**Card shape** (discovery-only, no execute field at all — the debate's Rule 2 in the packet, "there is no `capability_invoke` and must never be one," applies to the *card* too, not just the tool surface):

```
CapabilityCard {
  id: string            // globally unique — see id scheme below
  kind: string           // "agent-plugin-skill" for this slice; opaque data, never switched on
  source: string         // the registering CapabilitySource's own id, e.g. "agent-plugin-skills"
  name: string           // humanized skill name, same helper capability-projection.ts already has
  description: string    // authored text; folded search vocabulary stripped before any caller sees it
  keywords: readonly string[]
  handle: string          // opaque to everything except the registering source's own get() path
}
```

`handle` is not a raw filesystem path handed to the agent — see `capability_get`'s safety section below.

**Id scheme, resolving the packet's own NOTE directly:** `agent-plugin-skill:<pluginId>:<archiveDigest>:<skillName>`. The packet's NOTE says `listInstalledPlugins` walks every digest, so two installed versions of one `pluginId` both appear, and one real plugin (`ui-ux-design`) has 7 skill folders. Putting the digest in the id makes both facts harmless for *discovery*, where `resolve-agent-plugin-refs.ts`'s ambiguity-refusal logic (needed there because prompt injection must resolve to exactly one binding) simply isn't needed: every skill folder of every installed digest gets its own row, `capability_get(id)` resolves deterministically because the digest is baked into the id, and a duplicate install just shows up as two near-identical search hits rather than a thrown error. This is also a real, if secondary, improvement over the composer-chip path's current limitation: for the *search/get* lane specifically, all 7 of `ui-ux-design`'s skills become individually discoverable and individually retrievable, not only the eponymous one — `install.ts`'s own `indexInstalledRoot` already walks and lists every `skills/<name>/SKILL.md`, confirmed from its walk regex; the eponymous-only limitation lives entirely in `resolve-agent-plugin-refs.ts`'s *resolution* logic, not in the underlying data model, so this slice doesn't inherit it.

**Registry API** — `capability-source-registry.ts`: `registerCapabilitySource({id, list})` (replace-by-id, no throw), `listCapabilitySources()`, `resetCapabilitySourcesForTests()`. Identical shape and identical semantics to `tool-contribution-registry.ts`, on purpose — no new pattern to learn.

**Sync vs. async — direct answer to your question 1.** `capability-source.ts`'s `list()` must be async: it walks `packages/sha256/*` on disk and reads each skill's markdown, exactly the I/O `capability-projection.ts`'s own `readSkillMarkdown: (skillPath) => Promise<string>` already models as async. But `ToolContributor.build`'s declared type (`tool-contribution-registry.ts`) is synchronous, and `buildAssistantToolRegistrations`'s loop calls every contributor's `build` synchronously, once, at boot — so I am **not** proposing making `build` async, and I'm not proposing touching `tool-contribution-registry.ts` or `tool-registrations.ts` at all. The consequence I'm following through, per your instruction: the async boundary has to be crossed inside something that is *already* async by the kernel's own design — and `ToolHandler` already is (`(ctx) => Promise<unknown>`, verified directly in `Jini/packages/daemon/src/tool-executor.ts`). So `build()` returns two fully-formed `ToolRegistration` objects synchronously, same as every other domain; each object's `handler` is an async closure that, on the *first actual tool call* (not at `build()` time, not at boot), builds the catalog from every registered source's `list()`, memoizes the in-flight promise (not just a boolean flag — see the concurrency trap below), and reuses it for every later call within this process's lifetime. This is a genuinely different seeding moment from `tool-catalog-query.ts`'s eager boot-time seed, and that difference is the direct, correct consequence of the sync/async mismatch — not a stylistic preference.

**Where the catalog gets built — direct answer to your question 3.** Nowhere near `agent-daemon-server.ts`, and I don't think it needs to be. Because seeding is deferred into the tool handlers themselves (previous paragraph), this slice never needs boot-time construction at all — the catalog is built lazily, inside `capability-tool-registrations.ts`'s own module, the first time an agent actually calls `capability_search` or `capability_get`. That stays inside the four approved new files plus the one approved edit. **I am flagging explicitly, as you asked:** if a later slice wants this catalog seeded *eagerly* at boot (matching the native tool catalog's exact posture, so the very first call pays no first-call latency), or exposed over HTTP the way `/api/tools/search` is (so `@jini-ai/mcp`'s own proxying mechanism could reach it without Tovu registering a native tool at all), either is a real, separate scope decision requiring a `agent-daemon-server.ts` edit — I am not deciding that here, only naming that the decision exists and that this slice's design does not require it.

**Reuse `@jini-ai/sqlite`'s helpers, or a local schema — direct answer to your question 2.** Define a small, local FTS5 schema in `capability-catalog-query.ts`, not a reuse of `ensureToolCatalogTables`/`reseedToolCatalog`/`searchToolCatalog`. The concrete reason, not reflex: I read the actual schema (`Jini/packages/sqlite/src/db/tool-catalog/tool-catalog.ts:48-65`) — `tool_catalog(id, description, input_schema_json, source, updated_at)`. There is no `kind` column, and the debate's own settled point 1 requires one ("a `kind`/`lane` column so a caller who already knows what it wants can scope the query"). I have two ways to get a `kind` column using the existing helpers: overload `source` to carry both "which source produced this" and "what kind is this" (loses precision — those are two different axes; a single source could in principle ever emit more than one kind), or extend the shared `@jini-ai/sqlite` package's schema (a published, cross-repo package — exactly the kind of blast-radius the debate already ruled out for `ToolRegistration`, for the identical reason). Neither is acceptable, so a small local schema — id, kind, source, name, description, keywords folded into the indexed text, updated_at — following the *same* proven pattern (idempotent `CREATE TABLE IF NOT EXISTS`, FTS5 external-content table, OR'd-terms tokenizer, `bm25()` ranking) costs about 80 lines that are almost a direct copy of the existing ~100-line file, plus one column. This also sidesteps a second, smaller trap: `sourceForToolId` (`tool-catalog-query.ts:36-39`) derives `source` by splitting a tool id on its first underscore — that's a tool-id-shaped assumption (`<domain>_<verb>`) that would silently mis-parse a capability card id like `agent-plugin-skill:ui-ux-design:<digest>:some-skill` (no underscore-delimited domain prefix at all). The capability catalog's `source` column should just be the registering source's own id, passed straight through — not derived.

One more deliberate simplification for this slice: I would **not** reuse `tool-search-keywords.ts`'s `indexedDescriptionFor`/operator-vocabulary folding for capability cards. That vocabulary was tuned against tool search terms specifically (its own module doc: "operators search in theirs" — theirs being tool-domain nouns); nothing says it transfers to skill/content search, and reusing it unexamined risks quietly degrading rather than improving capability search quality. Seed raw, authored descriptions for this first slice; folding a capability-specific vocabulary in is a real, separate, later optimization — exactly the same kind of measured-before-tuned discipline `tool-catalog-query.ts`'s own history already models (40% top-1 before the fold, an explicit benchmark before the swap).

**Workspace scope before ranking.** This is the one place I have a materially different, and I think better-grounded, answer than a generic "add a workspace column and filter before the WHERE clause" design would produce — because I checked whether that's even the right shape for *this* process. It isn't, or at least isn't strictly necessary. `agent-daemon-server.ts:295-296` constructs `routeDeps` via `createSqliteRouteDepsForWorkspace(process.env.TOVU_WORKSPACE)` at module load — a single value, read once, for the entire process lifetime (confirmed by the surrounding comment: `daemon-supervisor.ts`'s `spawnRealDaemonProcessFor` sets `TOVU_WORKSPACE` "on every spawn including every automatic respawn," binding *this process* to *that* workspace). One agent-daemon process serves exactly one workspace, for its whole life. That means the capability catalog this slice builds only ever holds one workspace's Agent Plugin installs to begin with — there is no *other* tenant's row in the same SQLite instance to leak through a result count, because no other tenant's data is ever loaded into this process. The debate's rule ("filter before ranking, never after") is satisfied by construction at the *seeding* boundary, not by a per-query predicate: `capability-source.ts`'s `list()` reads `process.env.TOVU_WORKSPACE` (the same ground-truth env var `agent-daemon-server.ts` itself reads, mirroring `server/deps.ts`'s own `resolveWorkspace({db}).id` fallback for the unset case) to resolve exactly one workspace's `AgentPluginWorkspaceLayout`, and every card it ever produces already belongs to that one workspace. I'd still tag each card with the resolving source's workspace as a defensive, near-free field (cheap insurance matching `install.ts`'s own SECURITY-note discipline about never assuming a layout was correctly scoped just because it type-checked) — but the *design* doesn't depend on a runtime filter to be correct, because the leak this rule guards against structurally cannot occur in this daemon-per-workspace architecture. If that architectural assumption is ever wrong — a future mode where one daemon process serves multiple workspaces — this whole section needs re-deriving, and I'd want that stated as an explicit re-evaluation trigger rather than silently assumed to still hold.

**How `capability_get` returns skill content safely.** The agent never sees a raw path. `capability_get`'s tool argument is the card's opaque `id`; the handler looks the id up in a small in-memory map `capability-source.ts` builds alongside its cards (id → `{packageRoot, skillPath}`), then calls straight into the *already-hardened* read path this codebase already has — `capability-projection.ts`'s own `readInstalledSkillMarkdown(packageRoot, skillPath)`, which itself goes through `package-paths.ts`'s `assertContainedOnDisk`. No new path-safety logic gets written; the one containment guarantee `install.ts` and `capability-projection.ts` already share stays the only one. I'd also set the `capability_get` tool's `ToolDescriptor.maxOutputBytes` (an existing, non-optional-to-use-but-optional-to-set field the kernel's `ToolExecutor` already truncates against, confirmed in `Jini/packages/daemon/src/tool-executor.ts`'s `truncateOutput`) rather than writing a second truncation mechanism for large skill files.

**Composition-root wiring.** `installFirstPartyToolContributors()` (`tool-catalog-manifest.ts`) takes zero arguments today and is called once, from `agent-daemon-server.ts:332`, with no `workspaceId` or layout in scope at that call site (that file is out of scope for this slice). Rather than thread a new parameter through it and its one real caller — which would force editing `agent-daemon-server.ts` — I'd have `registerAgentPluginSkillsCapabilitySource()` follow exactly `mcp-federation/presets.ts`'s own precedent: resolve what it needs (workspace id, layout) from the environment itself, inside the registration function, the same way a federation preset resolver reads `env` directly rather than being handed it. This keeps the edit to `tool-catalog-manifest.ts` a literal two added lines and touches nothing else.

One structural-typing point worth stating plainly since it resolves a scope worry before it comes up: `contributeCapabilityTools()`'s own `build` function can read `routeDeps.workspaceId` without any change to `AssistantToolRegistryDeps`'s 24-type intersection in `tool-registrations.ts`. I checked — `PluginsToolDeps` (`src/features/plugin-runtime/tool-registrations.ts:52-54`) already declares `workspaceId: string` as one of its own fields, and it's already one of the 24 types folded into that intersection, so `AssistantToolRegistryDeps` already structurally carries `workspaceId`. A 25th domain's own narrow `build` signature — typed against a small local interface that names only the few fields it actually needs — is assignable to `ToolContributor["build"]` under ordinary contravariant parameter checking, exactly the same way every other domain's own narrower `*ToolDeps` already works today. No edit to `tool-registrations.ts` is required for this reason, and I want that on the record before anyone assumes it is.

## Defects and traps you predict

1. **`listInstalledPlugins` (the digest-walk-and-index loop) is private, not exported, inside `resolve-agent-plugin-refs.ts`.** `indexInstalledRoot` (the actual manifest-parse-plus-skill-walk) *is* exported from `install.ts` and fully reusable as-is. The ~15-line outer loop that walks `packages/sha256/*`, filters non-digest dirnames, and tolerates a per-digest failure is not exported anywhere. My design duplicates that small outer loop inside `capability-source.ts` rather than requesting an export change to a file outside the approved scope — flagging this explicitly rather than silently picking one: exporting it would be a strictly smaller, lower-risk edit than duplicating ~15 lines of digest-scanning logic that could drift from the original if one copy is fixed and the other isn't, but it does touch a file not on your approved list. Your call.
2. **Primary-key collision if the id scheme is skipped.** If the two-installed-digests case isn't folded into the id (see the id scheme above), a reseed's `INSERT` against an `id TEXT PRIMARY KEY`-shaped schema would either throw on the second row or silently overwrite the first, for exactly the case the packet's own NOTE calls out. This is avoidable entirely by construction (digest in the id) — I'm calling it out specifically because it's the single easiest way to get this wrong by copying `tool-catalog-query.ts` too literally without re-deriving the id scheme for a differently-shaped source.
3. **Concurrency: two near-simultaneous first calls to `capability_search` and `capability_get` must not both pay the full disk-scan-and-seed cost, and must not build two independent `:memory:` instances.** The lazy-build memoization has to cache the *in-flight promise*, shared at module scope between both tool handlers (not per-handler, not a plain resolved-boolean flag) — a boolean-flag-guarded lazy-init is a classic double-build race if two calls land before the first resolves.
4. **`sourceForToolId`'s underscore-splitting logic does not transfer.** Cited above under question 2 — worth restating here as a concrete "don't copy this line" trap for whoever implements from `tool-catalog-query.ts` as a template.
5. **Risk classification is mandatory, not optional.** `tool-registrations.ts`'s own `derivedRiskByToolId()`/`assertRiskMetadataIsWirable` refuses to wire any tool id with no risk entry (verified: "an unclassified id is refused rather than assumed safe" is stated as a hard gate in that file's own doc). `contributeCapabilityTools()` must export a risk map classifying both `capability_search` and `capability_get` as read-only/no-elevated-risk — omitting this isn't a style choice, it's a build-time failure.
6. **The `resolveWorkspace` fallback path.** If `TOVU_WORKSPACE` is unset (the packet's own D10-fix comment names this as a real, handled case — `deps.ts`'s `resolveWorkspace({db}).id` default), `capability-source.ts`'s registration must fall back the same way `agent-daemon-server.ts` itself does, not silently produce zero cards or throw — matching existing behavior rather than inventing a new one for this one source.

## Blind spots the other participants will likely miss

- **The daemon-is-per-workspace architecture** (`agent-daemon-server.ts:288-296`). Anyone working from a staged copy or no in-place access is likely to design a `workspaceId` column with per-query filtering as the tenancy answer — technically safe, but solving a leak that structurally cannot occur in this process model, at the cost of a filter clause and a column nobody needs yet.
- **`workspaceId` is already structurally present on `AssistantToolRegistryDeps` via `PluginsToolDeps`.** Without checking this specific fact, the natural (wrong) conclusion is that a 25th domain needs its own field added to the 24-type intersection in `tool-registrations.ts` — an out-of-scope edit that isn't actually necessary.
- **`ToolHandler` is already `Promise`-returning at the kernel level.** Without reading `Jini/packages/daemon/src/tool-executor.ts` directly, the "obvious" fix for the sync/async mismatch is making `ToolContributor.build` (and `buildAssistantToolRegistrations`'s loop over all 25 domains) async — a much larger, wrong-direction change. The lazy-build-inside-the-handler answer only becomes obviously correct once you've confirmed the handler itself was already async all along.
- **`listInstalledPlugins`'s private/non-exported status.** Easy to assume it's reusable since it's clearly the right logic; only becomes visible as a scope question once you actually go looking for its export.
- **`sourceForToolId`'s tool-id-shaped assumption.** A subtle, quiet bug for anyone who treats `tool-catalog-query.ts` as a copy-paste template rather than a pattern to re-derive per field.

## Strengths to preserve

- `ToolRegistration.handler`'s non-optional invariant, and the decision it drives: capability content never gets a fake handler to sneak into the real `ToolRegistry`. The catalog stays a separate, descriptor-only projection, permanently.
- `tool-contribution-registry.ts`'s replace-by-id/no-throw-on-duplicate-domain semantics — clone them exactly for the capability seam; don't invent new semantics for a pattern that already works.
- The `assistant/` → feature one-directional import rule. `capability-source.ts` reaches into `assistant/`, never the reverse.
- `assertContainedOnDisk` as the *only* path-containment check anywhere near an installed package. Never a second, hand-rolled one.
- The existing native tool catalog (`tool_catalog`, `ToolCatalogQuery`, `/api/tools/search`) — completely untouched. This slice adds a second, separate catalog; it does not modify the first.
- `mcp-federation/trust.ts`'s federated tier and `ToolExecutor`'s native gate — both untouched. Agent-Plugin-declared MCP servers stay unconditionally `unavailable`, exactly as `capability-projection.ts` already decided; this slice doesn't reopen that.

## Risk tier recommendation

**Medium, agreeing with the packet, but for a narrower reason than "new architecture is inherently medium-risk."** The two things that would normally push a slice like this toward "high" — cross-tenant leakage and a shared-kernel-type change — both turn out, on inspection, not to apply here: tenancy is structurally satisfied by the daemon-per-workspace architecture rather than needing new enforcement code to get right, and nothing in this design touches `@jini-ai/core`, `@jini-ai/daemon`, or `@jini-ai/sqlite`. What keeps it at medium rather than low: the digest-duplication id scheme and the lazy-catalog concurrency memoization are both real, non-obvious correctness requirements with a cheap-looking wrong answer (skip the digest in the id; guard with a boolean instead of a shared promise) that would pass a shallow test and fail under the exact conditions — two plugin versions installed, or two near-simultaneous first calls — the packet's own NOTE and this slice's own design specifically anticipate.
