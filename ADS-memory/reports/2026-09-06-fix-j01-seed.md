## Verification of the claim (before any fix)

- **CONFIRMED** (read `seed.ts:326-341`): `seedIdentity` early-returns as soon as
  `users.findByUsername` finds the owner user. No write happens on that path.
- **CONFIRMED** (read `seed.ts:406-441`): the owner `principalRoles.save` is the LAST write of the
  seed — after `principals.save` and `users.save`. Writes are sequential, awaited, and NOT wrapped
  in a transaction (call site `apps/website/src/features/identity/wiring.ts:116` passes bare repos).
  So a process exit between `users.save` and `principalRoles.save` is a reachable state that the
  early-return then makes permanent.
- **CONFIRMED** (read `identity/authorize.ts:69-99`): `resolveEffectivePermissions` reads ONLY
  `principalRoles.listByPrincipalId` and `principalPolicies.listByPrincipalId`. With neither, it
  returns `[]`; `authorize()` finds no `*` row, `candidates.length === 0`, and returns
  `{allowed:false, reason:"no_grant"}` for EVERY permission. The owner can still log in (user row +
  hash exist) but is denied everything — a silent brick.
- **CONFIRMED** (read `apps/website/src/features/identity/wiring.ts:149-175`): the follow-on
  reconciliation does NOT repair the binding. `migrateDeprecatedPermissionGrants` is handed
  `{policyPermissions, policies, idGen, workspaceId}`; `applyBuiltinRoleGrants` is handed
  `{roles, rolePolicies, policies, policyPermissions, idGen, workspaceId}`. Neither receives
  `principalRoles` or `principals`, so neither can write a principal→role link. `command grep -n
  "principalRoles|principal_roles"` over `builtin-role-grants.ts` returned rc=1 (no match) — and the
  pattern is proven able to match, since the same grep hits 5 lines in `wiring.ts`.
- **CONFIRMED**: the dedup check at `seed.ts:435` is unreachable on this replay — control returns at
  `:334` long before it.
- **CONFIRMED** (read `git show 434d781e be29a436`): tonight's fix covered a DIFFERENT window
  (replay collides with its own rows / `UNIQUE constraint failed: roles.workspace_id, roles.name`).
  It made every step converge, but left the early-return guard keyed on the owner user alone.

Verdict: the bug is real. Proceeding to fix.

## The fix (`packages/cms/src/identity/seed.ts`)

New private helper `ensureOwnerRoleBinding`, called from the early-return branch BEFORE it declares
the seed complete. It moves the completion boundary from "the owner user exists" to "the owner user
exists AND holds a role".

- Gated on **"the owner principal holds NO role at all"**, not "it lacks the owner role".
  Deliberate: an operator who moves the seeded owner principal to a lesser role also leaves it
  lacking the owner link, and repairing on that broader signal would re-escalate that principal to
  wildcard authority on the next restart — a privilege escalation shipped as a bug fix. A principal
  with zero roles is never a deliberate state.
- Converges rather than assuming: it goes through the existing `seedBuiltinRoleWithPolicy`, so a
  workspace whose owner ROLE or wildcard grant also never landed gains those here instead of being
  linked to a role that grants nothing. Read-before-write, since `principal_roles` has no unique
  index (the pattern already used at `:435` and for `role_policies`).
- `OWNER_ROLE_NAME` / `OWNER_ROLE_PERMISSIONS` extracted as module constants — two call sites now
  depend on them agreeing exactly, and drift would be a silent authority bug.
- Cost on a healthy boot: **one `listByPrincipalId` read, zero writes.** This matters because
  `seedIdentity` also runs on Tovu's read-only dry-run path
  (`createSqliteIdentityRouteDeps({reconcileGrantsOnBoot:false})`), and a write there throws
  `attempt to write a readonly database`. CONFIRMED green — see the wiring test run below.
- Function doc updated: the old "a completed seed early-returns before any write" claim is now
  stated accurately rather than left silently false.
- 434d781e / be29a436 are untouched — all 5 of their assertions still pass.
