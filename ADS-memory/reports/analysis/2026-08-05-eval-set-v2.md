## Count vs. the ~100 target (flagged, not silently resolved)

Landed at 130, ~30% over target. I chose coverage over trimming: I could write an honest, non-leaking,
realistic query for 130/131 tools, and discarding good cases purely to hit a round number felt like
padding-down for no measurement benefit — the brief's skip rule argues against padding, not against a
larger honest set. If exactly ~100 matters for a fixed scoring budget, the cleanest cut is by domain
size, not arbitrarily: identity (15), newsletter (14), widgets (12), and collections (11) are the four
largest clusters and could each lose 2-4 cases (favor the CRUD-defining verbs over rename/status-edit
variants) without losing domain coverage or breaking any `alsoAcceptable` pair. I did not pre-cut this
myself — I'd rather the scorer choose which ~30 to drop than have me guess which lose the least signal
sight-unseen.

## Pushback on ecological validity (invited by the brief)

Agree with the brief's own stated belief, with a sharpening: this buys statistical precision, not
ecological validity, and the reason is structural, not incidental. Every query is one author's (mine)
guess at operator phrasing, and despite deliberately varying misspellings/run-ons, the underlying
register is suspiciously coherent — I default to casual, mildly complaining, first-person phrasing
across all 130 cases, which no real population of site admins would produce that uniformly. Some real
operators are terser ("comment spam?"), some paste raw error text, some write in their non-native
English with different grammar patterns than the ones I generated. A retrieval system tuned against
this set (or its 20-case predecessor) risks overfitting "how one LLM imagines an admin talks" rather
than how admins actually talk — a failure mode invisible to this set's own scoring, since the set would
score its own blind spot as a pass. The only fix this authoring approach cannot supply itself: real
operator transcripts (support tickets, actual chat logs, even a small hand-collected sample) as a third,
independent check against both held-out sets. Synthetic query sets from any single author, however
disciplined about vocabulary leakage, remain a proxy for register even when they are provably not a
proxy for the answer key.

## Risks

- The `alsoAcceptable` calls are my own judgment about what a "reasonable person" would also accept;
  a scorer disagreeing with 2-3 of these would not surprise me and is not itself evidence the case is
  bad — see per-pair reasoning inline in the cases file's own comments-adjacent list above.
- `settings_get_raw`'s "every layer" phrasing is the one case I'd re-examine first if scores look
  suspiciously good on it specifically.
- I have no way to check whether any of my 130 queries accidentally collide with the *existing* 20-case
  set's phrasing, by construction (I never saw it). If the scorer notices overlap, that is new
  information about how narrow the space of plausible operator phrasing actually is — not evidence I
  peeked.
