## Bugs found and disposition

1. **Widget-host confirmations refused — functional origin-policy drift (fixed).** Cause: `apps/website/src/server/runtime/composition/modules/site-assistant.ts:621` supplies only the canonical-origin predicate; the former route helper never compared Origin to the serving host. The shared policy now checks the actual serving scheme/Host before invoking that predicate. The three preview/localhost/loopback tests reproduced `400 !== 200` before implementation and pass afterward, including absent Fetch Metadata. Fixtures now include the actual serving Host/protocol: metadata alone never supplies trust. Class guard: all three serving origins, foreign origins, wrong ports/schemes and every metadata value go through both mounted handlers.

2. **Frontend-control ignores explicit non-same-origin metadata — security defense gap (fixed; Low for the omission alone).** Cause: original `apps/website/src/assistant/site/visitor-frontend-control.ts:16-24` checks Origin/Referer but never `Sec-Fetch-Site`. Four new credential POST reproductions each returned 200 before implementation; all return 403 afterward and assert that no cookie is minted. The old confirm refusals for cross-site, same-site, none and empty metadata remain green. Class guard: 72 cases assert both expected statuses and identical acceptance, so both routes cannot agree on an incorrect permissive result unnoticed. Human sign-off for a High/Critical exploit is not indicated by the inspected evidence; the compatibility conflict below still blocks release.

3. **Referer can replace missing Origin on credential POST — missing-header policy gap (fixed).** Cause: the same frontend-control block uses `origin ?? referer` without restricting that fallback to GET, despite its comment describing GET. The class table reproduced 200 for a credential POST with a matching Referer and no Origin. Those rows now return 403. Confirm's obsolete missing-Origin acceptance expectation was changed to refusal with a comment citing the Coordinator decision. This strengthens the assertion; it does not remove the test. Normal browser POSTs cannot arbitrarily forge/omit their Origin, so this is not evidence of a standalone foreign-page takeover.

4. **Origin-required everywhere rejects ordinary browser GET streams — compatibility blocker introduced by the literal rule (unresolved).** The browser stream opens through `apps/site-chat/src/visitor-page-control.ts:49`, using Jini's GET stream transport. Same-origin GET normally omits Origin, which is why frontend-control previously used Referer. The shared policy at `apps/website/src/assistant/site/visitor-request-origin.ts:23` refuses that request before owner resolution. A direct probe minted real credentials through the mounted POST handler and used a real publication: `{ issued: 200, validGetOwnerWithOrigin: true, validGetOwnerWithoutOrigin: false }`. Removing only Origin, while retaining the valid cookie, tab credential, publication, matching Referer and same-origin metadata, loses the owner. This is a protocol/implementation inference backed by that owner probe, not a live-browser observation. The [Fetch Origin algorithm](https://fetch.spec.whatwg.org/#origin-header) explains the GET omission. Coordinator was asked whether to keep a GET-only Referer fallback; no answer arrived during implementation. No exception or transport redesign was invented. Required next decision: authorize the narrow GET fallback (still enforcing metadata and validated origin), or change the stream transport so the required browser Origin is available. Do not roll out this patch without resolving this item.

## Production exploitability at main 49127c1dc

**No arbitrary foreign-page control exploit was demonstrated from the missing metadata check alone.** I inspected that revision's frontend-control, guest-scope protections and CORS middleware. A foreign page can send a simple POST, but its browser-controlled Origin fails the existing canonical/serving-host check; forging same-origin metadata does not help. A page on an already allowed canonical origin can submit to another serving origin without the additional metadata veto, potentially minting/refreshing a guest identity where browser cookie rules permit, but cannot thereby read a victim's tab credential or control their page: the guest cookie is HttpOnly and SameSite=Strict, a separate signed tab credential and valid publication are required, and the inspected CORS middleware does not grant credentialed cross-origin reads. CORS limits reading, not whether a simple POST is sent; Strict cookies are withheld on cross-site requests, while same-site cross-origin requests still need Origin/CORS/token analysis. A real takeover would need another condition such as credential disclosure or a broader CORS/XSS defect, which this bounded review did not establish. See the [Fetch credentials/CORS rules](https://fetch.spec.whatwg.org/#cors-protocol-and-credentials) and [SameSite rules](https://httpwg.org/http-extensions/draft-ietf-httpbis-rfc6265bis.html#name-the-samesite-attribute). Treat the confirmed gap as defense in depth, not a proven session takeover.
