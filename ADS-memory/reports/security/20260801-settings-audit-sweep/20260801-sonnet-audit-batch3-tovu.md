## Findings

**[HIGH: Data loss] `useSettingsSlice`'s unmount flush diffs against a stale `persisted` snapshot, silently dropping the operator's true final edit**
- **File:** `apps/admin/src/hooks/use-settings-slice.hooks.ts:168-185` (the unmount cleanup effect), contrasted with the debounce path at `:201-207` which the file's own comment says must read "at RUN time, not at schedule time."
- **What is wrong:** The debounce-triggered save reads `target = latest.current` and diffs against `persisted.current` *inside* the async callback that runs when its turn in `saveChain` arrives — deliberately, per the comment at `:202-204`, because an earlier save may have advanced `persisted` by then. The unmount cleanup does the opposite: it captures `const target = latest.current` and `const base = persisted.current` **synchronously, before scheduling**, then closes over those stale values in the `.then()` it appends to `saveChain`. If an earlier debounced save is still in flight when unmount happens, `persisted.current` has not yet been advanced when the unmount flush captures it, so the flush's `save(target, base)` call diffs against a base that will be out of date by the time it actually runs.
- **Failure scenario:** Using the real `saveLanguage`/`loadLanguage` pair (`apps/admin/src/lib/settings-tabs.ts:247-250`, which computes `changed: next !== previous` and `apps/admin/src/lib/ledger-slice.ts:64-74`'s `saveChangedEntries`, which writes only `changed` keys):
  1. Persisted locale = `"en"`. Operator picks `"es"`. `latest="es"`, debounce timer set (600ms).
  2. Debounce fires: `saveChain` runs immediately, `target="es"`, calls `save("es", persisted.current="en")` → diff says changed → starts a (slow) write of `locale="es"` to the ledger. Still in flight.
  3. Operator immediately picks `"en"` again (reverts). `latest="en"`, a new debounce timer is armed.
  4. Operator closes the settings dialog / navigates away before the new debounce fires and before the in-flight save resolves. Unmount cleanup runs: `timer.current` (the new debounce) is non-null → cleared; `hasUnsavedEdits.current` is true → proceeds. It captures `target="en"`, `base=persisted.current="en"` (**still `"en"`** — the in-flight save from step 2 has not yet run its `persisted.current = target` assignment) and schedules `save("en", "en")` after the in-flight save.
  5. The in-flight save resolves: writes `locale="es"` to the ledger, then sets `persisted.current = "es"`.
  6. The unmount-scheduled call now runs: `saveLanguage(next="en", previous="en")` → `changed = ("en" !== "en") = false` → `saveChangedEntries` writes **nothing**.
  7. Final ledger state: `locale="es"` — the value the operator explicitly reverted away from before leaving the page. Their actual last decision (`"en"`) is never persisted, with no error, no pending-save indicator, and no way for the operator to know it didn't take.
- **Fix:** Make the unmount flush follow the same discipline the debounce path already documents: defer reading `latest.current`/`persisted.current` until inside the `.then()` callback that actually executes (i.e., read them at the point they're passed to `io.current.save(...)`, not before `saveChain.current = saveChain.current.then(...)` is constructed).

**[MEDIUM: Cross-tenant disclosure/amplification] The settings change-feed's ledger poll has no workspace predicate at the SQL layer; disclosure relies entirely on an application-level filter with no defense-in-depth, and it is an observable side channel**
- **File:** `src/features/settings/repo.sqlite.ts:445-469` (`listRevisionsSince`) and `:419-444` (`listRevisions`), consumed by `src/server/routes/admin/settings/events.ts:129-147` (`tick`).
- **What is wrong:** Every other query in `repo.sqlite.ts` filters by `workspaceId` (and `principalId` where applicable) at the SQL layer: `getWorkspaceValue`, `getUserValue`, `listWorkspaceValues`, `listUserValues`, `deleteWorkspaceValue`, `deleteUserValue` all do. `listRevisionsSince`/`listRevisions` are the sole exceptions — they select from `settingRevisions` with only a `seq` predicate, against the *entire* table, which (per the packet's own framing) is shared by multiple workspaces in one `content.db`. The SSE route's disclosure correctness then depends entirely on `change-feed.ts`'s `isRevisionVisibleTo` JS-side filter being right, with no independent check at the query boundary — a defense-in-depth gap inconsistent with the rest of this same file.
- **Failure scenario:** Two workspaces (A, B) share one `content.db` (e.g. two `tovu serve` processes with different `overrides.workspaceId`, as `server/deps.ts:163-187` supports). Workspace A's operator opens `/settings/events`. Every polling tick (`POLL_INTERVAL_MS=1000`), the server issues `listRevisionsSince({sinceSeq: cursor, limit: 200})` — a query over the **whole shared table**, including workspace B's revisions — then discards B's rows in JS. Two consequences, both concretely observable by workspace A's own operator, an authenticated but otherwise unprivileged user with only `settings.read`:
  1. **Amplification:** if workspace B is writing settings fast enough to fill the 200-row page with B's own (invisible-to-A) rows, A's poller needs multiple 1-second ticks to page past them before it can see A's own next visible change — a purely B-driven cost imposed on every other tenant's subscribers.
  2. **Timing side channel:** the delay described above is a function of *another tenant's write volume*, which A's operator can infer by timing how sluggish their own settings-changed notifications become — information no per-tenant authorization boundary is supposed to expose (ADR-007 tenant scoping, cited in `change-feed.ts:61`, is stated to cover exactly this "workspace" boundary).
- **Fix:** Add a `workspace_id = ? OR workspace_id IS NULL` predicate (global rows have `workspace_id IS NULL`, per `types.ts`'s `SettingRevisionRecord.workspaceId`) to `listRevisionsSince`, scoped to the SSE viewer's own workspace, matching the pattern already used by every sibling query in this file. Application-level `isRevisionVisibleTo` can stay as the second (user-scope) layer of the check.

**[LOW: Resource governance] `/settings/events` has no cap on concurrent connections per principal and does not re-check authorization for the life of the (arbitrarily long-lived) stream**
- **File:** `src/server/routes/admin/settings/events.ts:53-163`.
- **What is wrong:** Authentication and `settings.read` authorization are correctly checked once, before the first event is written (lines 60-82) — that part is sound. But nothing bounds how many such connections one principal can hold open simultaneously (no rate limiter is registered for this route in `src/server/modules/settings.ts` or `src/server/app.ts`, unlike e.g. login (`LOGIN_STRICT`) or magic-link routes), and the authorization check is never repeated for the connection's remaining lifetime — a session/permission revoked after connect keeps receiving `settings-changed` frames (namespace names only, not values) until the client disconnects.
- **Failure scenario:** Any authenticated principal with `settings.read` (a low bar) opens many concurrent `EventSource` connections to `/settings/events` (e.g. via a script, or simply many stale tabs). Each holds an open HTTP response plus two `setInterval` timers (`POLL_INTERVAL_MS=1000`, `KEEPALIVE_INTERVAL_MS=25000`) indefinitely. Combined with the previous finding (each tick's query cost is not scoped to the caller's own workspace), a moderate number of concurrent connections from one principal multiplies unscoped table scans across the whole process. Separately, an operator whose session is administratively revoked (role change, forced logout) mid-connection keeps hearing "something changed" notifications for their old workspace until they close the tab.
- **Fix:** Cap concurrent SSE connections per principal (or add a lightweight rate limiter to this route, mirroring the `RateLimiter` pattern already used elsewhere in `server/middleware/rate-limit.ts`), and consider re-validating the session/permission periodically (e.g. once per keepalive tick) for a stream this long-lived.

## Assessed and found clean

**Priority 1 — the agent-callable write's four claimed structural bounds.** Traced `agent-tools.ts` → `tool-registrations.ts` → `write-service.ts` assuming the JSON Schema `enum` is fully bypassed (i.e., assuming an attacker can get any string into `input.setting` and any value into `input.value`, with no schema enforcement at all). All four bounds **PROVEN**, independent of schema enforcement:

1. **Target key is a closed enum, checked before `authorize()`.** `resolveAgentWritablePreference(settingId)` (`agent-writable-preferences.ts:178-180`) looks the id up in a hardcoded `Map` (`BY_ID`, built once from the 7-entry `AGENT_WRITABLE_PREFERENCES` array), and `tool-registrations.ts:273-278` calls it and throws before touching I/O, before `routeDeps.settingsUiTabsReady` is even awaited, and before `write-service.set()` (and therefore its `authorize()` call) is ever reached. An unlisted id — including a value never enumerated, or a Map-safe value like `"__proto__"` (a real `Map`, not a plain-object lookup, so no prototype-pollution vector here) — cannot reach `authorize()` at all, so it cannot be used to probe which grants the caller holds; every reachable id gets the identical `settings.user.self.write` check, so there is no differential signal between the 7 legal ids either.
2. **Scope is the hardcoded constant `"user"`.** `AGENT_PREFERENCE_WRITE_SCOPE = "user" as const` (`agent-writable-preferences.ts:94`) is passed literally at `tool-registrations.ts:313`. The tool's input schema has no `scope` property, and the handler never reads one from `input` — there is no code path for a caller-supplied scope to reach `write-service.set()` for this tool at all.
3. **Target principal is never named.** `tool-registrations.ts:316-319` does not pass `principalId` to `setSettingValue(...)` at all (and the schema has no such property, so there is nothing to read from input even if the handler tried). `write-service.ts`'s `set()` (`:257-263`) then derives `deriveRequiredPermission({scope:"user", targetPrincipalId: undefined, callerPrincipalId})`, and since `targetPrincipalId == null`, `isSelf` is `true` → `settings.user.self.write`. The eventual write (`:325-330`) falls back to `principalId: input.principalId ?? input.callerPrincipalId` — always the caller, for this call path.
4. **The ledger's `actor` is the human operator, not the agent's own identity.** `write-service.ts`'s `set()` records `actor: input.callerPrincipalId` (`:299`), which is `ctx.principal.id` from the tool-execution context. Traced this back through `src/assistant/agent-daemon-server.ts`'s `onStarted` (`:270-298`, `principal = { id: parsed.principalId }`, tracked per-run in `principalByRunId` and returned unchanged by `resolvePrincipal` for every tool call in that run) to where `contextRef.principalId` is actually produced: `src/server/modules/assistant.ts`'s `proxyRunStart` builds it as `JSON.stringify({ ...decoded, principalId: principal.id })` where `principal = getAuthedPrincipal(res)` — the client-parsed `decoded` object is spread **first** and the server-verified session principal is applied **after**, unconditionally overwriting any `principalId` a client tried to smuggle into its own `contextRef` payload. `getAuthedPrincipal` only ever reads `res.locals.principal`, populated exclusively by `requireAdminSession`'s cookie-backed session validation (`dev-auth.ts`) — never from request body/query/headers. There is no path for the agent (or a malicious client) to make this be anything other than the actual signed-in human operator who started the run.

Also checked and found sound for area 1: no `{type:"json"}`/object-shaped values are accepted by any of the 7 agent-writable keys (`validateValueAgainstSchema` requires `string`/`boolean`/`enum` per key), so a nested/prototype-pollution-shaped `value` payload is rejected by schema validation before it is ever persisted or later `JSON.parse`d back out — this closes the "nested/prototype-polluting input" question the packet raised for this specific tool.

**Priority 2 — SSE disclosure correctness (apart from the workspace-scoping finding above).** Auth + `settings.read` authorization enforced before the first byte is written (`events.ts:60-82`). No setting *value* ever reaches the wire — only `{namespaces: string[]}` (`events.ts:143`, `change-feed.ts:70-109`). `isRevisionVisibleTo` is a true allowlist: an unrecognized `scope` falls through to `default: return false` (`change-feed.ts:64-67`), so a future scope is withheld until explicitly handled. `Last-Event-ID` is coerced via `Number(...)` and validated (`Number.isFinite && >= 0`) before use in a parameterized Drizzle `gt()` call (`repo.sqlite.ts:445-451`) — no injection, and a malformed/absent header safely falls back to `maxRevisionSeq()` (current head), never to replaying another workspace's history or an unbounded scan (query is always `LIMIT REVISION_PAGE_SIZE`).

**Priority 3 — resource exhaustion/lifecycle**, apart from the missing-connection-cap finding above: poll interval is fixed server-side (not client-influenced); the ledger query is indexed (`seq` is the autoincrement PK) and bounded (`LIMIT 200`); `pollTimer`/`keepaliveTimer` are cleared via both `req.on("close")` and `res.on("close")` (`events.ts:116-122, 154-157`), so a disconnected client does not leak a running poll loop; `tick()` never throws out of its own `setInterval` callback — a DB error is caught, logged, and the cursor is left unchanged so the same window is retried next tick (`events.ts:129-147`).

**Priority 4 — cache removal correctness.** No remaining code path in the files read assumes a cached per-layer value read: `getEffective` (`settings.ts:322-376`) goes straight to the repo for all three layers, and its own header explicitly documents why (cross-process staleness with the agent daemon). `invalidateWorkspaceSettingsCache` is a documented no-op with nothing left to defeat (no cache exists for a purge to fail to invalidate). The retained definition cache's safety argument holds given what's in scope: `settings_register_definitions` (the only agent-reachable definition-mutation surface) remains in `UNWIRED_SETTINGS_TOOL_IDS` (`tool-registrations.ts:173-185`), confirmed still unwired, so the daemon process cannot write a definition and invalidate this cache out from under the main process.

**Priority 5 — multi-tenant scoping in the repos**, apart from `listRevisionsSince`/`listRevisions` above: every value/definition query and mutation in `repo.sqlite.ts` carries the correct `workspaceId`/`principalId` predicate. `write-service.ts`'s `set()`/`clear()` append the revision and write the value row inside the same `deps.repo.transaction(...)` callback (`:287-334`, `:382-429`), and `SqliteSettingsRepo.transaction` (`repo.sqlite.ts:477-493`) wraps both in a real `BEGIN IMMEDIATE`/`COMMIT`/`ROLLBACK` against the raw connection — no partial-write window found between a value row and its paired revision.

**Priority 6 — daemon authorization.** `requireAgentDaemonToken` (`daemon-auth.ts`) is mounted as the very first `app.use`, ahead of `express.json()` (`agent-daemon-server.ts:354-355`); it fails closed (503) when the token env var is unset, has no loopback exemption, and compares via `timingSafeEqual` after a length pre-check that leaks only the fixed, public token length (`daemon-auth.ts:60-65`). The one exempt route (`/api/delegated-tool-calls`) is justified in-file and independently gated by `resolvePrincipal`'s fail-closed live-`runId` check (`agent-daemon-server.ts:340-344`). `requireRunOwnership` is mounted between the bearer gate and the run routes it protects (`:364-365`), addressing "which admin, not just which process."

**Priority 7 — refresh-vs-unsaved-edits guard.** The `refresh()` function itself (`use-settings-slice.hooks.ts:245-257`) correctly refuses while `timer.current || hasUnsavedEdits.current`, and re-checks both again after its own `await` — the exact discipline its own comment describes, and it holds up. The debounce-triggered save path also correctly defers its reads to run-time. The one place this discipline is *not* followed is the unmount flush, reported as the HIGH finding above.
