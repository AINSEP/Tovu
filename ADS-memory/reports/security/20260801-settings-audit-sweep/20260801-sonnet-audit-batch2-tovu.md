## Findings

**[SEVERITY: MEDIUM] Stale-response race lets a fast navigation cause an editor to silently save the wrong record's data**
- **File:** `apps/admin/src/sections/PostEditor.tsx:138-168` (also present in `CollectionEntryEditor.tsx:180-250`, `WidgetInstanceEditor.tsx:58-111`, `MenuEditor.tsx:222-282`, `FormEditor.tsx:280-318`)
- **What is wrong:** Each editor's data-loading `useEffect` re-fetches on prop-id change (`props.postId`, `props.entryId`, `props.widgetId`, `props.menuId`, `props.formId`) but has no guard (no cancellation flag, no `AbortController`) against a slow earlier fetch's `.then()` callback firing *after* a faster later fetch already populated the screen for the new id. The callback unconditionally calls `setTitle`/`setSlug`/`setEntry`/`setWidget`/`setMenu`/etc. with the stale response.
- **Failure scenario:** Open `/admin/posts/A` (slow network / large post). Before it resolves, click through to `/admin/posts/B` (small, fast). B's editor renders correctly. A's fetch then resolves late and its `.then` callback runs `setTitle(A.title); setSlug(A.slug); setStatus(A.status); editor.commands.setContent(A.bodyJson)` — the screen, still showing the URL/back-link for B, now silently displays A's content. If the operator clicks **Save**, `api.updatePost({ id: props.postId /* = B, correct */ }, { title, slug, status, bodyJson /* = A's stale content, from state */ })` fires — **post B is silently overwritten with post A's title/slug/status/body**, with no error, no conflict, no warning. In `CollectionEntryEditor.tsx`/`WidgetInstanceEditor.tsx`/`MenuEditor.tsx` the effect is worse: `save()` reads the *id* itself from stale state (`entry.id`, `widget.id`, `menu.id`), so the same race causes the update request to target the **wrong record's id** entirely, potentially clobbering an unrelated entry/widget/menu the operator never intended to touch.
- **Fix:** Add a per-effect staleness guard — either an `AbortController` passed into the fetch and checked in `.then`, or a simple `let stale = false; return () => { stale = true }` cleanup, with every `setXxx` in the `.then` callback gated on `if (stale) return;`. Apply the same pattern to all five editors listed.

**[SEVERITY: LOW] Dashboard silently hangs with no error on a failed fetch**
- **File:** `apps/admin/src/sections/Dashboard.tsx:10-16`
- **What is wrong:** The mount-time effect chains `api.listPosts().then(...)` and `api.getPresentation().then(...)` with no `.catch()` on either — the only screen in this codebase's file list that omits it (every sibling list screen sets an error state on failure).
- **Failure scenario:** Load `/admin/dashboard` while the session is on the edge of expiring, or during a transient 500/network blip. Either promise rejects, is never handled (an unhandled promise rejection), and `postCount`/`publishedCount`/`themeId` never update. The dashboard is stuck showing `"…"` placeholders indefinitely with no error banner and no retry affordance, unlike every other screen's `notice error` fallback for the identical failure mode.
- **Fix:** Add `.catch((e) => setError(...))` to both calls and render a `notice error` state, matching `Posts.tsx`/`Menus.tsx`/`FormsList.tsx`'s existing convention.

## Assessed and found clean

1. **Server-side authorization on assistant execution routes** — Verified by tracing the actual middleware wiring, not assumed. `requireAdminSession` is mounted at `src/server/modules/core.ts:40` (`app.use("/api/admin", requireAdminSession(deps))`), registered in `src/server/app.ts` (line ~553) strictly before `createAssistantExecutionModule` registers its 4 routes (line ~708) — no code path reaches `detect-agents.ts`/`test-agent.ts`/`test-connection.ts`/`list-models.ts` without first passing the session gate. Each of the 4 handlers additionally calls `deps.authorize({ principalId, permission: ADMIN_ASSISTANT_PERMISSION, workspaceId: deps.workspaceId, ... })` before doing any work, and `authorize()` (`src/identity/authorize.ts`) is a real, fail-closed, workspace-scoped RBAC check (resolves roles/policies via `principalRoles.listByPrincipalId({ workspaceId, principalId })`), not a stub. All 4 routes also independently 404 if the URL's `:workspaceId` doesn't match the server's own resolved `deps.workspaceId`, and pass the server's own trusted `deps.workspaceId` (never the untrusted URL param) into `authorize()`, so there is no cross-workspace smuggling vector via the URL. Clean.
2. **Credential handling** — `detect-agents.ts` and `test-agent.ts` (the two execution routes actually in this batch's file list) take no `apiKey` in their request bodies at all, so the "unredacted key on a 2xx path" concern doesn't apply to these two files as written. `execution-settings.ts`'s client-side handling is clean on inspection: the API key is read/written only via `localStorage` (never included in `changedLedgerEntries`'s ledger diff, so it never reaches `api.setSetting`), and `writeStoredCredentials` propagates storage-quota failures as thrown errors rather than silently swallowing a lost key. (Note: `test-connection.ts`/`list-models.ts`, which *do* carry `apiKey` server-side, are not in this batch's file list — I read them only as surrounding context per the packet's instructions and did not file findings against them. On inspection they redact the key from all error/response paths I traced, but that is outside this batch's scope to certify.)
3. **Command/argument injection and path traversal** — Neither `detect-agents.ts` nor `test-agent.ts` passes any caller-controlled value to a shell, spawn argument, env var, or filesystem path. `test-agent.ts`'s only body inputs (`agentId`, `model`) are used exclusively as `.find()`/`.some()` lookup keys against the in-memory array `detectAgents()` already returned — never passed into the detection/probing mechanism itself. The actual subprocess-spawning logic lives inside `@jini-ai/agent-runtime` (`detectAgents()`), which is outside this batch's 37 files and outside this audit's scope to certify.
4. **XSS / unsafe rendering** — Full sweep of all 31 `apps/admin/src` files in the list for `dangerouslySetInnerHTML`, `.innerHTML`, `eval(`, `new Function(`, `javascript:` URLs, and `target="_blank"` without `rel`. Only one `dangerouslySetInnerHTML` exists in scope (`components/Sidebar.tsx:15`, rendering `NavItem.icon`), and every `icon` value is a hardcoded static SVG-path string literal in `nav.ts` — no dynamic or user-controlled input reaches it. `PostEditor.tsx`, `CollectionEntryEditor.tsx`, `WidgetInstanceEditor.tsx`, and `FormEditor.tsx` all render rich content exclusively through TipTap's schema-driven `EditorContent` (ProseMirror), never raw HTML injection; the one free-text image-URL entry point (`PostEditor.tsx`'s toolbar "Insert image by URL") is operator-typed via `window.prompt`, not attacker-influenced. All three `target="_blank"` anchors carry `rel="noreferrer"`. Clean.
5. **API client correctness (`api.ts`)** — Every method funnels through the single `request()` helper (line 721), which checks `res.ok` and throws `ApiError` on any non-2xx response — there is no method that swallows a non-2xx as success. The one documented exception (`importRedirects`, always 207) matches the real server contract, verified by reading the corresponding route's DTO comment. Workspace-scoping omissions (`content-types`, `entries`, `taxonomy`, `database`, `recovery` routes not using the `/workspaces/{id}/` prefix) are a documented, deliberate convention (session-derived workspace), consistent with the routes' own server-side handling — not a bug.
