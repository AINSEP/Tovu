- Relates: **ADR-006** (rule-of-two), **ADR-021** (authorization/permission catalog), **ADR-022** (entries/entry_refs), **ADR-027** (`asset_blobs` content-addressing precedent), **ADR-049** (tool-domain assembly). ## Context

The spec (`ADS-memory/specs/047-pages-vibecoding/spec.md`, 11 REQs) is Tovu-side wiring over an already-built, already-tested engine (`@jini-ai/vibecoding/core` + `/html`, read in full — `core/{types,target,apply,history}.ts`, `html/regions.ts`). The engine owns the loop; nothing about it changes. What needs architecture is: where the one missing engine piece (`HtmlRegionParser`) lives and how it's built, how Tovu's schema/store/permission/tool layers plug into the injected ports, and the handful of places the spec left a decision for this stage (§10 undo persistence, §9's enforcement point, the migration mechanism).

The owner's standing instruction — ports over direct dependencies, data passed in over lists owned internally, generic mechanism in Jini and host-specific glue in Tovu, reversible/opt-in over baked-in defaults — is the tie-breaker used below wherever the spec leaves room.

## Decision 1 — `HtmlRegionParser`: parse5, in `@jini-ai/vibecoding/html/node`, Jini-side

Confirmed against the actual port contract (`Jini/packages/vibecoding/src/html/regions.ts:87-112`): `HtmlRegionParser` is two methods — `findRegions(html)` returning every `data-agent-element`-tagged node (including invalid/duplicate handles — the target's own allowlist logic needs to see those to refuse them) with `innerStart`/`innerEnd` offsets, and an optional `checkWellFormed?`. Ratifying the spec's parse5 choice — it is the only spec-compliant, never-throwing option available (§3 evaluation table), and `sourceCodeLocationInfo: true` maps directly onto the offset contract.

**Module boundary.** `Jini/packages/vibecoding/package.json` today declares exactly three entries — `.`, `./core`, `./html` — all `"runtime": "universal"` (verified: no `./node` key exists yet). The README (`Jini/packages/vibecoding/README.md:19-22`) already earmarks `./node` as "planned and deliberately not present yet." Shipping REQ-1 means adding a fourth entry to both the `exports` map and the `jini.entries` manifest, marked `"runtime": "node"` — parse5 becomes this entry's one new dependency, and `./core`/`./html` stay dependency-free. This is the same universal/Node split the package already uses, applied to its one missing adapter.

**Offset validation and malformed-input behavior.** parse5's `sourceCodeLocation.startTag.endOffset` → `endTag.startOffset` gives inner-content bounds for elements with both tags. A node parse5 could not reliably locate (implicit-insertion recovery cases, primarily) has no dependable `sourceCodeLocation`. The obvious implementation — silently drop that region from `findRegions`'s output — is wrong and is called out below as a Critical Internal Constraint: a dropped region isn't "unaddressable," it's a region the target's `validate` will see vanish from `beforeHandles`, and the very next edit to *any* region in that document gets rejected as "removes existing handle" with no way for the model to recover, because the region genuinely is still in the DOM. The adapter must instead treat a location-less tagged element as a structural problem: refuse to complete `findRegions` and let `checkWellFormed?` report it, or (if called outside a well-formed check) surface a thrown error the store layer converts into a rejection rather than a silent omission. This is Jini-side implementation detail this ADR does not code, but it is a decision, not a detail left open — silent omission must be explicitly ruled out in the implementation.

**`checkWellFormed?` is honored as written, not forced.** parse5's own doc position — it cannot always distinguish malformed markup from standards-mandated recovery — means the adapter's `checkWellFormed` surfaces `onParseError` entries verbatim (phrased for the model, per the port's contract), and is genuinely allowed to pass documents parse5 silently repaired. The handle-multiset check in `validate` (engine, unmodified) is the backstop for the security property; `checkWellFormed` is a courtesy diagnostic, not the safety mechanism.

### Article IV rule-of-two

One adapter (parse5) ships now. The spec names `DOMParser` (browser-only, client-side preview parsing) as the rule-of-two second implementation and defers building it — **ratified, not deferred out of the ADR's scope to decide**: the port's *shape* is already right for two implementations independent of rule-of-two, because `"runtime": "universal"` was chosen for the package before this feature existed and the authoritative write path is server-side regardless (a `DOMParser` adapter could never be primary — the DB row is canonical). The near-term trigger for actually building it is named in the spec's own sequencing step 8: the visual-editing tab (D-REV-4). Until that ships, `DOMParser` remains a *named*, not merely *plausible*, second adapter, which is what the rule asks for. **Article IV: COMPLIES.**

### Article I (Library-First)

**COMPLIES.** parse5 is maintained, widely adopted (jsdom's own dependency), no custom implementation proposed.

## Decision 2 — The write path: byte-preserving splice stays entirely in Jini; concurrency is Tovu's to own

`createHtmlRegionTarget` (engine, unmodified — `regions.ts:170-292`) already does everything the spec asks for: the splice (`spliced()`, byte-preserving outside the edited region), the handle-multiset validation (the "a model may not extend its own allowlist" property, `validate()`'s final block), and the not-an-upsert refusal on `replacePart` for a nonexistent region. None of this needs Tovu-side reimplementation or wrapping — the target is handed `{ store, parser }` and used as-is.

**What is genuinely Tovu's: `PagesHtmlDocumentStore`'s concurrency behavior.** `regions.ts`'s own read-then-splice-then-write sequence (`replacePart`, `validate`) reads `store.read()` fresh each call but has no notion of a version — that's fine for the engine, because within one `applyEdits` call edits are sequential (`apply.ts:68-77`, deliberately, so `validate` never judges a state that never existed) and never concurrent with themselves. But **two different admin sessions editing the same page**, or a retried tool call racing a still-in-flight one, are two *separate* `EditTarget` instances layered over the *same* underlying row, and nothing in the engine or the port protects against that TOCTOU. `PostRecord.version` already exists and is bumped on every write (REQ-4's own text says so) — `PagesHtmlDocumentStore.write` must use it as an optimistic-concurrency guard: read the row's current `version` alongside `body_html` in `read()` (stored on the instance, since `HtmlDocumentStore.read()` returns only a string per the port), and `write()` performs `UPDATE ... WHERE id = postId AND version = <version captured at the matching read>`, incrementing `version` and treating a zero-row update as "the document changed underneath this edit" — which the caller surfaces to the model as a rejection reason ("the page was edited elsewhere since this turn started — re-read and retry"), not a silent overwrite. This is a genuine gap neither the spec nor the decision log names (see Concerns #2) and is designated a Critical Internal Constraint below.

## Decision 3 — Schema (REQ-2/REQ-3): additive columns via Drizzle's own `check()` builder, not hand-written SQL

**Ratifying the additive shape, correcting the mechanism.** `body_format text NOT NULL DEFAULT 'doc'` and `body_html text` (nullable) as new columns, `body_json`'s existing `.notNull()` loosened — all confirmed additive/backward-compatible against the live schema (`src/db/schema.ts:32-77`; every existing row already satisfies `body_format='doc' AND body_json NOT NULL AND body_html IS NULL`, so the CHECK below holds with zero backfill).

**The spec's mechanism claim does not hold.** §4 says the CHECK constraint needs hand-written SQL "matching the FTS precedent at `drizzle/0022_posts_fts_search_index.sql`, because Drizzle's builder can't express it." Checked directly: this repo runs `drizzle-orm@0.44.7` (`package.json:55`), which ships `check()` from `drizzle-orm/sqlite-core` (`node_modules/drizzle-orm/sqlite-core/checks.d.ts:22`) — a first-class table-constraint builder, unused anywhere in `schema.ts` today but fully available. The FTS precedent is not analogous: `0022_posts_fts_search_index.sql` is a **virtual table** (FTS5), which genuinely has no Drizzle builder at any version, hence hand-written SQL there. A CHECK spanning `body_format`/`body_json`/`body_html` on an ordinary table is exactly what `check()` exists for.

**Decision:** add the CHECK inside `posts`' own `sqliteTable(...)` third-argument array via `check("posts_body_format_shape", sql\`...\`)`, alongside the existing `uniqueIndex`/`index` entries at `schema.ts:73-76`. `drizzle-kit generate` then emits it into the next numbered migration automatically — `schema.ts` stays the single source of truth for the constraint, rather than splitting it across a generated migration and a hand-maintained SQL file that can drift from the schema it describes. (Also corrects the migration path citation: the real file is `src/db/drizzle/0022_posts_fts_search_index.sql`, not `drizzle/0022...` — same stale-prefix shape as the `src/infra/db/schema.ts` citation the midpoint findings already caught, see Concerns #1.)

**REQ-3's discriminated union — ratified as specced**, with the write-service enforcement point named explicitly: `resolveCreateFields`/`createPost`/`updatePost` in `src/features/post/post.ts` (the confirmed single write chokepoint — `createPost` at line 456, `bodyJson` currently required non-optional on `PostRecord`) is where AC-1 ("a Post can never carry `body_format: 'html'`") is enforced, symmetrically with how `kind` is already enforced there. Concretely: `resolveCreateFields`/its update-side twin gain a branch on `kind` — `kind: "post"` forces `bodyFormat: "doc"` regardless of input (mirroring how `kind` itself already defaults and is never client-overridable into an invalid state) and requires `bodyJson`; `kind: "page"` with `bodyFormat: "html"` requires `bodyHtml` and forbids `bodyJson`. The discriminated-union `PostResponse` type on the read side is a compile-time backstop for the admin route, not a substitute for this write-side gate — a malicious or buggy direct write attempt is a runtime concern the type system cannot catch, which is exactly why AC-1 asks for both a write-service test and the DB CHECK as defense in depth.

## Decision 4 — REQ-5's tool domain: `pages-vibecoding`, a new domain, not an extension of `post`

The spec offers both options ("register a new `pages-vibecoding` (or extend the existing `post`) domain"). **Decision: new domain.** Three reasons, all instances of precedent already in this codebase:

1. **Permission/risk boundary mismatch.** `pages.edit_html` (Decision 6 below) is `admin`-only; the existing `post`-domain write permission is not. `tool-registrations.ts`'s `DOMAIN_SLICES` model (`tool-registrations.ts:186-234`) keys one `DerivedRiskByToolId` map per domain; folding `pages.replace_document`/`pages.edit_region` into `buildPostRegistrations` would mean per-tool permission overrides inside a domain builder that today applies one permission uniformly, muddying a boundary that currently reads cleanly.
2. **Directly mirrors the `themes` precedent.** `THEME_WRITE_PERMISSION`'s own doc (`agent-tools.ts:94-101`) states the exact reasoning this case reuses verbatim: "editing a theme's source files is a different capability with a different worst case... so it gets its own string," which is why `themes` is its own domain distinct from `settings` even though both are presentation-adjacent. Editing raw Page HTML vs. editing a Post's Tiptap body is the same shape of split.
3. **Article III (Simplicity Gate).** A new domain module maps 1:1 to REQ-9's new permission and REQ-5's two new tools — traceable. Folding it into `post` would blur that file's existing, already-well-scoped boundary (Tiptap CRUD only).

**Shape**, following `ThemeToolDeps`/`buildThemesRegistrations`'s exact pattern (`src/features/theme/tool-registrations.ts:52-63,133`): a structurally-declared `PagesVibecodingToolDeps` (never `RouteDeps` imported directly — same back-edge-avoidance reasoning as `ThemeToolDeps`'s own comment states), a `pagesVibecodingDerivedRisk: DerivedRiskByToolId` map (`pages.replace_document`/`pages.edit_region` both `"mutates-durable-state"`), and `buildPagesVibecodingRegistrations(deps)` whose handlers construct `createHtmlRegionTarget({ store: new PagesHtmlDocumentStore(postId, deps), parser })` per call (the parser instance — the `./html/node` export — is a module-level singleton import, stateless; the store is per-request, bound to the specific page being edited) and drive it through `applyEdit`/`applyEdits`/`correctionsFor`, all engine code, unmodified, exactly as REQ-5/REQ-7 specify.

## Decision 5 — REQ-6: daemon-only in v1, with the BYOK seam kept genuinely open

Independently re-verified the spec's grep evidence by reading `agent-daemon-server.ts` in full (595 lines): zero occurrences of `execution.mode`/`byok` in the daemon's own control flow, confirming the spec's claim that the admin's real chat execution has no branch on it today. **Ratified: v1 Pages generation runs exclusively through this daemon path.**

**Why this is a long-term-extensibility decision, not just a scope cut (per the dispatch brief's framing):** the seam that keeps a future BYOK path from requiring a redesign is *already correct by construction*, because of Decision 4's domain shape. `buildPagesVibecodingRegistrations`'s handlers are wired through the same `ToolExecutor`/`ToolHandler` contract every one of the 21 existing domains uses (`tool-registrations.ts`'s own module doc, "the plumbing they share lives in" the kit) — a `ToolHandler` has no opinion about which execution path invoked it; it is called identically whether the calling turn came from the daemon or (hypothetically) a future BYOK dispatcher, because tool-calling in this codebase is normalized *above* the domain layer, not inside it. The gap REQ-6 names — BYOK has no live tool-calling consumer for *any* Tovu feature — is real, but it means the seam that needs building is upstream of every domain (a BYOK-mode tool-turn dispatcher), not a per-domain concern Pages needs to special-case. **Decision: build Pages' tool domain with no reference to execution mode at all** (as REQ-5 already implies), which is what makes "add a BYOK path later" a change to the shared dispatcher, not a redesign of this feature. Nothing here is BYOK-specific plumbing to build now — the extensibility is achieved by *not* coupling this domain to daemon-path specifics, not by adding new abstraction.

## Decision 6 — Permission and rate limit: ratified as specced, with the write-chokepoint tie-in named

`pages.edit_html`, `admin`-only in the built-in seed, follows `THEME_WRITE_PERMISSION`'s exact precedent (REQ-9, corrected citation already folded into the spec via the midpoint findings). `PAGES_GENERATION_PER_PRINCIPAL`, keyed by principal (not IP, since this is an authenticated admin endpoint), reusing `createRateLimiter`'s sweep-on-write eviction (`rate-limit.ts:174-224`, SPEC-046 REQ-8) — ratified as specced; nothing here needed architectural revision. One tie-in worth stating explicitly: `pages.edit_html` gates the *tool-calling* surface (`pages.replace_document`/`pages.edit_region`), while AC-1's Post-lock is enforced independently at the write chokepoint regardless of caller identity or permission — the two are complementary, not redundant: permission answers "may this principal invoke Pages authoring at all," the chokepoint answers "can *any* caller, however authorized, ever produce an invalid `(kind, body_format)` pair." Both are needed; neither substitutes for the other.

## Decision 7 — REQ-11 preview: reuse confirmed, sequencing consequence ratified

Read `SrcDocSandbox.tsx` and its test in full: `sandbox="allow-scripts allow-popups allow-popups-to-escape-sandbox"` with `allow-same-origin`'s absence pinned by an explicit assertion (`SrcDocSandbox.test.tsx:11-12`), exactly as the spec claims. **Ratified: reuse as-is, no new component.** The sequencing consequence the spec draws (D-4 stops being a prerequisite, since an opaque origin is what actually defeats the session-theft threat regardless of URL-vs-srcdoc) is architecturally sound and is adopted — Decision-log D-4's "separate origin, prerequisite for everything" is superseded by this ADR for the same reason the spec gives, restated here so it's not silently dropped: the *property* D-4 protects (no admin-session access from AI-authored script) is fully delivered by the opaque `srcdoc` origin alone; a distinct subdomain would add reload-survivability and shareability, neither a v1 requirement.

## Decision 8 — §9 (OQ-4 guardrail): enforcement is prompt AND structural, at a Tovu-owned decorator over the injected `EditTarget`

The spec's own AC-11 flags this as needing "Architect-level design; this AC records the requirement, not the mechanism." Decision:

**Prompt-level exclusion** (already specced, ratified) is necessary but, per this codebase's own settled lesson (D-6/D-REV-3: prompt severity is not where scope discipline actually comes from — mechanism is), not sufficient on its own.

**Structural enforcement point: a Tovu-owned `EditTarget` decorator, not an engine change.** The engine's `validate` (in `createHtmlRegionTarget`) is deliberately generic — it has no concept of Tovu's Contact-Form-widget policy and per the ownership rule must not acquire one (Jini stays product-agnostic). Tovu therefore wraps the target the domain handler constructs: `withFormGuardrail(target: EditTarget): EditTarget`, a thin decorator whose `validate` first checks the candidate's `content` for a `<form` tag (case-insensitive substring/regex match — deliberately not a second HTML parse; the region-level fragment is small and a false-positive-favoring plain-text check is the right cost/precision tradeoff for a guardrail whose job is "never let a raw form ship," not "parse arbitrary markup") and returns a model-facing rejection if found, before delegating to the wrapped target's own `validate`. This composes cleanly with the port's own contract (`EditTarget` is exactly the seam meant for this — nothing about the port assumes only one implementation wraps `store`+`parser` directly) and keeps the policy in Tovu where it belongs. Both the daemon-path handler (Decision 4) and the future BYOK path (Decision 5) get this guardrail for free, since it lives at the target-construction site, not inside a specific tool handler.

## Decision 9 — §10 undo/redo persistence: **in-memory, keyed per (page id, admin session), not persisted** — a real decision, not an inherited recommendation

The spec is explicit that this is its least-evidenced call (§15 Concerns #3) and asks the Architect to decide rather than inherit. Deciding it now, on the grounds actually available:

- `createEditHistory` (`history.ts`) is engine-owned in-memory state scoped to one `EditTarget` wrapper; nothing about `EditHistoryOptions.limit` (default 50) or the transaction/undo/redo API implies or requires durability — the engine's own module doc states `snapshot`/`restore` is the durable-safety-net tier (D-7's "dependable safety net" framing), and undo/redo is explicitly the *session-scoped convenience* tier layered on top.
- The only durable-safety requirement in the spec (D-7) is satisfied entirely by `body_html` itself being the durable row plus `PostRecord.version` (Decision 2) — every committed state is already durable; only the *stack of intermediate steps* is in question, and losing that stack on a server restart is "the user has to re-describe an edit," not "the user's work vanished."
- Precedent inside this exact codebase, not just an analogy: the site assistant's SSE run state is deliberately not persisted server-side either (spec's own citation), so an editing session's undo stack not surviving a restart is consistent with how this codebase already treats other per-session, non-authoritative assistant state — not a new posture invented for Pages.
- Persisting undo stacks durably would require storing full before/after content pairs per transaction, which is a strictly bigger feature (a real content-history/versioning system) that nothing in SPEC-047's 11 REQs asks for. Building it now would be exactly the "complexity added for a future that isn't in the current spec" Article III forbids without a Complexity Justification entry this ADR would then have to write — and there's no present requirement to justify it against.

**Decision: `createEditHistory` instances are held in an in-memory map keyed by `(postId, adminSessionId)`, created lazily on first edit and evicted on session end or after an idle TTL** (mirroring `rate-limit.ts`'s own sweep-on-write eviction shape rather than inventing a new eviction strategy — SPEC-046 REQ-8's lesson, that an unbounded in-memory key space is a real memory-exhaustion path, applies here too: a page-id+session-id key space is bounded by concurrently-open editing sessions, which is small, but "small today" is exactly the condition SPEC-046 REQ-8 was written to stop being trusted blindly). This is now a settled architectural decision, not a carried-forward recommendation — flag for owner sign-off is no longer needed at the *architecture* level, though the owner may still want to confirm the product framing ("undo doesn't survive a refresh") in UI copy.

## Critical Internal Constraints

Evaluated per the four-part test (unit, plausible wrong implementation, broken property, required constraint). Three units designated Binding; everything else in this feature is either engine code already covered by its own tests or ordinary wiring with no load-bearing internal invariant.

**CIC-1 — `PagesHtmlDocumentStore.write` (Tovu, new).**
- Plausible wrong implementation: unconditional `UPDATE body_html WHERE id = postId` with no version check.
- Broken property: two concurrent editors (or a retried tool call racing an in-flight one) silently clobber each other's write — the second writer's `spliced()` was computed against a document that no longer matches what's in the row by the time the write lands, and byte-preservation is violated for content the writer never saw.
- Required constraint: **write must be conditioned on the `version` captured at the matching `read()`**, incrementing on success and returning a rejection (never a silent no-op or a fallback overwrite) when the row's version has moved. Verification surface: an integration test that reads, mutates the row out-of-band (simulating a concurrent session), then attempts the original write and asserts rejection rather than data loss.

**CIC-2 — the `./html/node` parser's handling of an un-locatable tagged element (Jini, new).**
- Plausible wrong implementation: `findRegions` silently omits any `data-agent-element` node parse5 could not attach a reliable `sourceCodeLocation` to.
- Broken property: the omitted handle vanishes from `beforeHandles` on the *next* validate call for a completely unrelated edit, which the multiset check (correctly, per its own design) then reports as "removes existing handle" — permanently blocking edits to that document with a reason that misdescribes the actual defect (nothing was removed; the parser lost track of something that's still there).
- Required constraint: an un-locatable tagged element must surface as a structural failure (via `checkWellFormed` or a thrown error), **never as a silent absence** from `findRegions`'s result set. Verification surface: a fixture HTML document engineered to trigger parse5 location loss on a tagged node (if such a case is reachable at all — this should be confirmed against parse5's actual recovery behavior before REQ-1 ships, since if the case is unreachable in practice the constraint is moot but should still be asserted as a property, not assumed).

**CIC-3 — the `kind`/`body_format` write-chokepoint gate in `resolveCreateFields`/`createPost`/`updatePost` (Tovu, modified).**
- Plausible wrong implementation: trusting a caller-supplied `bodyFormat` on a `kind: "post"` input, or accepting a `kind: "page", bodyFormat: "html"` write with `bodyJson` still populated (satisfying neither branch of the CHECK cleanly, or worse, satisfying it by accident with stale data).
- Broken property: AC-1's guarantee — "a Post can never carry `body_format: 'html'`" — is a security/data-integrity property (the whole reason D-1/D-2 exist: Tiptap must never be offered HTML-shaped content), not merely a validation nicety.
- Required constraint: `kind` **derives** `bodyFormat` at the chokepoint (never trusts a client-supplied value that disagrees with `kind`), and the branch is exhaustive — every `(kind, bodyFormat)` pair other than `(post, doc)` and `(page, html)` (v1) is rejected before any repo access, mirroring `resolveCreateFields`'s existing "all validation runs before any repository access" invariant. Verification surface: the integration test AC-1 already asks for, at the write-service boundary (Article V).

## Implementation Outline: SKIP

Reason: every unit that would warrant a public/exported-contract outline is already fully specified either by the existing engine contract (`HtmlRegionParser`, `EditTarget` — both pre-existing, documented ports this ADR does not modify) or by a Critical Internal Constraint above (`PagesHtmlDocumentStore.write`, the write-chokepoint gate). The remaining work — a new tool domain following the `buildThemesRegistrations` pattern, a schema migration, a permission string, a rate-limit profile — is ordinary wiring against precedent this codebase already has four-plus live examples of, with no novel public contract shape to design ahead of implementation. Triggers checked: no new cross-module port is introduced (the `withFormGuardrail` decorator in Decision 8 is a private composition of the existing `EditTarget` shape, not a new port), no new public API surface beyond the two tool ids REQ-5 already names in full, no algorithmic complexity beyond what CIC-1/CIC-2 already isolate.

## Migration Safety

Additive-with-one-widening-change, as the spec discloses (§15 Concerns #2) and this ADR accepts without objection: `body_format`/`body_html` are pure additions (every existing row backfills via column default with no script); `body_json`'s `NOT NULL` loosening is backward-compatible (widens what's *allowed*, doesn't invalidate what already exists — every current row keeps a non-null `body_json`, satisfying the CHECK's `doc` branch unchanged). The CHECK constraint itself (Decision 3) is satisfied by every pre-existing row with zero backfill, since every existing row is `(body_format='doc', body_json NOT NULL, body_html NULL)` by construction of the column defaults. No destructive migration anywhere in this feature.

| Port | Adapter 1 (now) | Adapter 2 (named, deferred) | Trigger for building it |
|---|---|---|---|

No other new port is introduced by this feature. `EditTarget`, `HtmlDocumentStore` are pre-existing engine ports with one Tovu-side implementation each (`PagesHtmlDocumentStore`), which is ordinary code, not a candidate for rule-of-two scrutiny — the port was justified when the engine was designed, not by this feature.

## Consequences

- A new Jini package entry (`./html/node`) ships before any Tovu integration test can run — the cross-repo sequencing risk the spec already flagged stands; this ADR does not remove it, only specifies exactly what that entry must guarantee (Decision 1, CIC-2).
- `posts` gains its first-ever Drizzle-native `check()` constraint in this codebase — a small precedent worth noting for future schema changes: multi-column invariants on ordinary tables no longer need a hand-written SQL migration, only virtual tables (FTS5) do.
- Pages generation is a fifth admin capability locked to `admin`-only alongside `theme.edit` — worth the owner's awareness that the permission surface for "authors raw artifact source" is now a small but growing cluster with one shared shape.
- `PagesHtmlDocumentStore`'s version-conditioned write (CIC-1) is new machinery beyond what a naive read of REQ-4 implies ("SELECT... UPDATE... bump version") — flagged here so it isn't implemented as the simpler unconditional write and then discovered broken under concurrent editing later.

## Concerns (pushback, per dispatch instructions)

1. **The spec's Drizzle-CHECK-constraint claim is wrong** (Decision 3) — `check()` exists in the installed `drizzle-orm` version and should be used instead of hand-written SQL. This also corrects the migration file's citation path (`src/db/drizzle/0022...`, not `drizzle/0022...`) — the same stale-prefix pattern the midpoint findings already caught twice elsewhere in this decision chain; a third instance is worth naming as a pattern, not a one-off.
2. **A real, un-named gap: `PagesHtmlDocumentStore` concurrency.** Neither the spec nor the decision log considers what happens when two writers touch the same page concurrently. This ADR closes it (CIC-1, Decision 2) but it is worth the owner knowing this wasn't previously considered anywhere in the input material — it was found during this ADR's own trace of the write path, not carried forward from prior work.
3. **`entry_refs`' widget-dependency tracking does not reach `body_html`.** Read `src/core/entry-refs/extractor.ts:61-123` directly: `extractEntryRefs` walks a Tiptap `bodyJson` node tree looking for `widgetEmbed` atoms. It has no path for raw HTML content at all. REQ-9's guardrail directs the model to embed the Contact Form widget in generated pages instead of raw `<form>` markup — but if that embed takes the form of some HTML marker inside `body_html`, **D-13's own stated protection ("deleting a widget must not silently break pages") does not actually cover html-format Pages**, because nothing extracts a ref from `body_html` into `entry_refs` today. This spec doesn't claim to wire that extraction (§9 only commits to the generation-time prompt guardrail), so this isn't a defect in what was specced — it's a gap in what the feature *appears* to inherit for free but doesn't. **Decision: out of scope for v1, same as REQ-6's BYOK gap** — named explicitly here rather than silently assumed covered, so a future widget-delete on a workspace with generated Pages is a known, accepted risk rather than a surprise. If the Contact Form embed mechanism for generated HTML is designed before v1 ships, this extraction gap should be revisited as part of that design, not discovered later as a bug.
4. **§10's decision (Decision 9) is now settled, but is a judgment call between two reasonable readings** — the alternative (persist undo/redo alongside the document, giving cross-session/cross-restart undo) is not unreasonable, it is simply a bigger feature than anything in SPEC-047's 11 REQs asks for. If the owner's actual product intent is "undo must survive a refresh," that changes this decision and should come back through a spec amendment, not a quiet architecture change.

## What could not be verified

- Whether parse5 can actually produce a tagged element with no `sourceCodeLocation` in practice (CIC-2's premise) — this was reasoned from the port's own doc comment ("parser cannot always distinguish malformed from recovered") and parse5's documented recovery-algorithm behavior, not from running parse5 against a constructed fixture. Should be confirmed empirically before REQ-1 ships; if unreachable, CIC-2 becomes a defensive invariant with no live trigger rather than a real gap, which doesn't remove the requirement but does lower its urgency.
- The exact shape of a Tovu-side `PagesVibecodingToolDeps` interface was reasoned by direct analogy to `ThemeToolDeps` (read in full) but not drafted here — Implementation Outline was SKIPped on the grounds that the pattern is fully precedented, not because the concrete interface was written and checked.
