All four Round 1 participants (codex, gemini-3.6, gemini-3.1, myself) converged on Option C independently — that convergence survives the correction intact, and I think it's now on firmer ground, not shakier ground.

**Did the correction move me? Partly, and it's worth being precise about which part.** My Round 1 argument never rested on "SQLite has no JSON type" — I didn't make that claim at all; my case rested on `mode: "json"` appearing zero times in the schema, on the FTS5 precedent being hand-authored *outside* Drizzle specifically because indexing document-shaped data needs dialect-specific DDL (`files/tovu/schema.ts:15-24`), and on the packet's own F5 (three structurally different indexing mechanisms). None of that depended on SQLite's storage format, so none of it is undermined by learning that format is now real binary JSONB. What *does* move: I now have a concrete, better-specified answer to "should new JSON columns be spelled differently" (see The JSONB Verdict), where in Round 1 I'd have said "text, obviously" without examining the alternative. The correction upgraded a default into a checked default — same conclusion, better-tested.

**Strongest argument against my position, engaged directly:** the corrected asymmetry table (`PACKET-R2.md:42-47`) shows MySQL and SQLite *can* index into JSON via a generated/expression column — so why not treat "declare the JSON column, add an expression index when you need one" as the general strategy instead of "declare a real column up front"? This is the live version of Option A now that the SQLite-has-no-JSON premise is gone. It fails for a mechanical reason the table itself states: on both engines the query path must be known **in advance** (`PACKET-R2.md:44-47`, rightmost column) — the same moment you'd otherwise just declare a column. A MySQL generated column or a SQLite expression index still stores the value twice (once inside the document, once materialized for the index), still can't carry `NOT NULL`/`CHECK`/a foreign key against that member, and still requires the DDL to be written per-dialect by hand, same as a real column would, except worse: now there are two representations of the same fact to keep synchronized instead of one. The escape hatch reduces zero work versus just declaring the column, once you've reached the point of needing to query it — it only reduces work for fields you're still guessing about. That's exactly a document field, not a to-be-indexed one, which is what the Column-vs-Document Rule below encodes.

**Sequencing (Q7):** no code path writes a commerce row in any dialect today. `CommercePaymentRuntimePort` deliberately excludes charge/refund/webhook/credential methods (`files/tovu/commerce/contracts.ts:31-38`), every `CommerceStatus` capability is hardcoded `"unavailable"` (`files/tovu/commerce/status.ts:53-60`), MySQL has zero files, and Postgres's only file is explicitly "evaluation-only — no live `pg` client... per `implementation-outline.md`'s 'Postgres adapter deferred' note" (`files/tovu/db-postgres-ops.ts:7-9`). Designing three physical schemas today means speculatively designing two of them against adapters that don't exist. **Vertical-slice-first**, one dialect (SQLite — the only one with a real adapter), one product → price → order → webhook-dedup path, proven end to end, before the pattern is generalized into two schema trees that currently have nothing running against them.

## The JSONB Verdict

**Answer to the owner, directly, no hedge: partly right, and the two halves need to be pulled apart because "flexibility" is doing double duty.** "JSONB for max flexibility" is correct about *storage* flexibility — a document with fields that grow and change without a migration — and that half is now genuinely portable: real binary JSONB on Postgres, functionally-binary JSON on MySQL (`PACKET-R2.md:45`), real `jsonb()` BLOB on SQLite (`PACKET-R2.md:17-27`). It is wrong about *query* flexibility — "store it as JSONB so we can filter/sort/aggregate on whatever field turns out to matter later" — because that half is Postgres-only. Postgres indexes the document; MySQL and SQLite index one named, pre-declared scalar pulled out of it (`PACKET-R2.md:53-55`). The owner's MySQL instinct was right per the packet's own note (`PACKET-R2.md:59`) — that's exactly why the trap is subtle: two of the three engines really do give you JSONB-grade *storage*, which makes it easy to over-infer JSONB-grade *querying* everywhere. It doesn't transfer.

**Storage spelling (Q3): no, don't change it — for either the 37 existing columns or new commerce ones, and this is a case where I checked the tempting answer and rejected it.** The repo's own header already anticipated exactly this question — "Content is stored as normalized columns + JSON text (`body_json`) so it stays portable to Postgres `jsonb` later" (`files/tovu/schema.ts:12-13`) — written when "later" meant "when Postgres exists," not "right now, in SQLite, via a new binary encoding." Converting existing columns costs a reviewed migration per table for zero present benefit, since none of the 37 are indexed or hot-path-parsed — the "faster to reparse" advantage of `jsonb()` only pays off under repeated `jsonb_extract` calls, which is precisely the access pattern the Column-vs-Document rule says shouldn't be happening to an unindexed field. It also costs readability: a `BLOB` isn't legible in a plain `sqlite3 db.sqlite3 "select col from t"` dump or most DB browsers the way `TEXT` is, which matters in a codebase this densely commented for debuggability. One thing I'd flag rather than assert as settled: whether `jsonb()`'s on-disk encoding is guaranteed byte-stable across `better-sqlite3`/SQLite version bumps isn't something the packet verified either way — worth a quick check before anyone adopts BLOB storage anywhere, independent of this decision. Net: keep `text("*_json")` as the spelling for new commerce escape-hatch columns too. If a field ever earns an expression index, that's the signal it should have been promoted to a real column instead (see next section) — the BLOB detour mostly evaporates once the rule is applied correctly.

**MariaDB (Q4): out, explicitly, not folded silently into "MySQL support."** Its `JSON` is "an alias for `LONGTEXT COLLATE utf8mb4_bin`" (`PACKET-R2.md:47`) — genuinely text, not binary — and MySQL↔MariaDB row-based replication fails on JSON columns for exactly that reason (`PACKET-R2.md:49`). If Tovu ever documents "MySQL-compatible" as covering MariaDB — a common self-hoster assumption — the JSONB storage-portability claim silently stops being true for that fourth target. Supporting MariaDB for real is a fourth adapter and a fourth migration tree, not a footnote on the MySQL one.

## The Column-vs-Document Rule

A rule to apply at review time, not a principle to remember:

**Would any planned or plausible-within-two-releases query filter, join, sort, aggregate, or uniquely constrain on this field?**
- **Yes** → it is a column, added across all three dialect migration trees in the same PR, no matter how "metadata-shaped" it looks going in.
- **No, but it's read back whole by primary key and only ever rendered or passed through** → it is JSON, stored as `TEXT`, never indexed, per the existing convention (`files/tovu/schema.ts:12-13`, 44 occurrences of the pattern, zero use of `mode: "json"`).
- **"Maybe later"** is not a third answer — it's "No," recorded with a comment naming what would trigger promotion.

The FTS5 precedent is the concrete cost of getting this wrong once: a hand-authored, single-dialect migration living outside `drizzle-kit generate`'s normal diffing because Drizzle's sqlite-core has no builder for a virtual table or trigger (`files/tovu/schema.ts:15-24`). Under the corrected facts, the near-identical failure mode for commerce would be reaching for a MySQL generated column or a SQLite expression index over a JSON path that was declared as "just metadata" — same category of hand-maintained, per-dialect, diff-invisible DDL, just phrased as an index instead of a virtual table. A second occurrence of that pattern should be read as "the rule wasn't applied," not as "this is now how Tovu does indexed metadata."

## Remaining Disagreements

**Products vs. `member_tiers` (Q6) — I side with codex's Round 1 framing, against the two "fold it in" readings.** `member_tiers` carries `welcomePagePath` and `visibleInPortal` (`files/tovu/schema.ts:493-494`) — access-grant concepts with no meaning for, say, a one-time digital download. A generic `commerce_products`/`commerce_prices` pair with a `product_kind` discriminator (the unified-catalog reading) would leave most rows with several structurally-required-but-semantically-null columns and a `check()` per kind to keep the invariants straight, to save one join. Extending `member_tiers` directly to carry general commerce fields (SKU, tax class, inventory) pushes the pollution the other way and touches an existing live, migrated table for capabilities it was never scoped for. The cost of keeping them separate is exactly one FK: a new `commerce_products`/`commerce_prices`/`orders` domain, with `member_tiers` optionally referenced as the entitlement target a given price grants — commerce owns financial truth, `member_subscriptions` stays the access-entitlement projection. That's a real, named cost (one bridge to keep in sync), but it's smaller than the schema-pollution cost of either merge direction.

**Idempotency ordering (Q5) — converged on the diagnosis, want to sharpen the mechanism.** Round 1 agreed `UNIQUE(provider, event_id)` stops duplicate *processing* but not out-of-order *delivery*, and agreed `version` doesn't fix it — confirmed again reading the actual columns: `version: integer("version").notNull()` on both `memberTiers` (`schema.ts:502`) and `memberSubscriptions` (`schema.ts:522`) is a local optimistic-concurrency counter with no relationship to a provider's event timestamp; `updatedAt` records local write time, not source-of-truth time. What Round 1 didn't fully settle: the check-then-write needs to be one atomic statement, not a read-then-decide round trip in application code — `UPDATE ... SET ... WHERE id = ? AND provider_event_at < ?`, gated on a new column that stores the provider's own event timestamp/sequence, using plain `WHERE`, which is identical DDL and identical semantics on all three dialects. A second read-then-write in app code reopens exactly the race the unique index was there to close.

## What Would Change My Mind

- Tovu commits to Postgres-only for the commerce subsystem specifically, dropping C4's SQLite-first-class requirement for this one domain — GIN-indexed `jsonb` (Option A) becomes the straightforward answer the moment there's only one engine's indexing semantics to satisfy.
- A concrete, present-tense filtering/reporting requirement lands against a specific provider-metadata field — that promotes the named field to a column per the rule above; it wouldn't change the overall shape, just trigger it correctly.
- A real MySQL or Postgres adapter lands before commerce ships — Q7's sequencing answer changes materially, since "prove tri-dialect equivalence" would already be two-thirds discharged instead of zero.
- Someone shows `jsonb()`'s SQLite encoding is byte-stable across driver versions **and** a commerce JSON field is large/hot enough for the reparse savings to matter — that's the specific, narrow case where BLOB storage for new columns would be worth the readability cost I'm otherwise declining to pay.
