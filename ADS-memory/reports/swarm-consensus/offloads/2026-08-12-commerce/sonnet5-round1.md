## Position

**Option C — relational core, JSON only as a narrow, never-indexed escape hatch — with one addition not on the list: a portable idempotency primitive built from a UNIQUE index, not from JSON.** This is not a novel proposal for Tovu; it is the schema's own existing convention, just not yet applied to commerce.

The evidence is in `files/tovu/schema.ts` itself. Every one of its 63 tables that needs to carry variable or provider-owned data does it the same way: a plain `text("*_json")` column, written and read at exactly one chokepoint, never filtered or joined on in SQL — `bodyJson` (`schema.ts:49`), `seoExtJson` (`:80`), `ext` (`:88`), `fieldsJson` on `members` (`:477`), plus `dataJson`, `stateJson`, `payloadJson`, `evidenceJson`, `countersJson`, `topicsJson`, `constraintJson` and more (`schema.ts:178-942`, 20+ occurrences). Not one of them is a Drizzle `mode: "json"` typed column — the grep count for that mode across the entire file is zero (F3) — and not one of them is indexed. The team already had the JSONB-first idea available in the tool they use and declined it, everywhere, every time. Commerce would be the first table set in this codebase to break that pattern.

More telling: the two commerce-adjacent tables that already exist and are load-bearing — `memberTiers` and `memberSubscriptions` (`schema.ts:485-525`) — contain zero JSON. Price (`monthlyPriceCents`, `yearlyPriceCents`, `currency`, `:497-499`), status, and the subscription lifecycle (`status`, `source`, `startedAt`, `currentPeriodEnd`, `canceledAt`, `:514-519`) are all plain typed columns. This is the team's own working answer to "how do we model a priced, recurring thing," produced under the same three-dialect aspiration (`schema.ts:9-13`), and it is not JSONB.

## Option Assessment

**A — JSONB-first: reject.** The packet's own F5 is the refutation: GIN (Postgres), generated-column-plus-B-tree (MySQL), and expression index (SQLite) are three structurally different DDL mechanisms, not three configurations of one mechanism. This codebase has exactly one existing precedent for "index into semi-structured content" — full-text search — and it is *not* expressed in the shared Drizzle schema at all. The file header says so explicitly: the FTS5 virtual table and its sync triggers live only in a hand-written `drizzle-kit generate --custom` migration, "because drizzle-orm's sqlite-core has no builder for a virtual table or a trigger" (`schema.ts:15-24`). That is the one case where this team already needed a dialect-specific index over document-shaped data, and the answer was "step outside the declarative schema and hand-author it, once, for one dialect." A JSONB-first commerce model would need that escape hatch on every query path that filters into the document, times three dialects — which is not "the right index generated per dialect" (as Option A's framing implies), it's three parallel hand-maintained migration trees wearing one JS type as a costume.

**B — fully relational LCD: reject as stated, but closest to proven.** `memberTiers`/`memberSubscriptions` *are* this option already, successfully. Where it breaks is provider payloads: a Stripe or PayPal event body is owned by the provider, not Tovu, and it grows fields on their schedule. Modeling the full raw payload as named columns means a schema migration every time a provider adds a field Tovu hasn't decided to care about yet — strictly worse than the `*_json` convention this codebase already runs 20+ times for exactly this shape of externally-owned, opaque data.

**C — relational core + narrow JSON, never indexed: accept.** See Position. The discipline that makes this work is mechanical and already enforced elsewhere in the file: `posts_body_format_shape` (`schema.ts:131-134`) uses Drizzle's `check()` builder — confirmed present in the pinned `drizzle-orm@0.44.7` (`schema.ts:124-125`) — to enforce shape invariants at the DDL level without ever reaching into a JSON column to do it. The same discipline (typed columns for anything a query, a constraint, or a join will ever touch; JSON only for what is read back whole, by id, never sliced) is exactly what commerce needs for provider payload capture.

**D — per-dialect schemas behind a repository port: partially accept, but premature at the schema layer, and arguably already true at the port layer.** Two of the three required dialects have no real adapter to diverge on purpose from: MySQL has zero files anywhere in this repo (F3), and Postgres's only file, `db-postgres-ops.ts`, is pure evaluation logic with an explicit comment that this is "deliberately evaluation-only — no live `pg` client... per `implementation-outline.md`'s 'Postgres adapter deferred' note" (`db-postgres-ops.ts:9-11`). Designing three physical commerce schemas today means speculatively designing two of them against adapters that don't exist, which risks tripping C5 ("nothing may present unproven capability as working") the moment any of that unexercised schema is described as ready. Where D is already right: `CommercePaymentRuntimePort` (`contracts.ts:37-39`) is exactly this pattern — a narrow port, with F1 confirming "no provider runtime is composed in either composition root" — extend that same shape to a `CommerceRepositoryPort`, but keep the *schema itself* as one Drizzle definition, matching all 63 existing tables, until a second dialect adapter is real enough to justify diverging.

**E:** not choosing wholesale; my answer is C plus one addition, detailed in Unlisted Option.

## Failure Modes And Sacrifice

**Failure mode 1 — the escape hatch gets reached into.** The moment someone needs "find all orders where `metadata.campaign_id = X`" for a dashboard, the temptation is to index into the JSON column — which is precisely the FTS5 trap (`schema.ts:18-24`): a hand-authored, per-dialect, out-of-band migration outside `drizzle-kit generate`'s normal diffing. The guardrail has to be a review-time rule ("needs to be queried" → promote to a real column, never index the bag), not a technical one — Drizzle will happily let someone write a raw-SQL expression index against a TEXT column in one dialect and forget the other two.

**Failure mode 2 — idempotency-by-unique-index doesn't solve ordering.** A `processed_webhook_events(provider, event_id)` UNIQUE table (portable identically across all three dialects — a plain unique index, no dialect-specific DDL) stops double-processing the *same* event, but Stripe/PayPal deliveries can also arrive *out of order* — an older `customer.subscription.updated` after a newer `.deleted`. Open SaaS's own handler demonstrates the failure mode directly: `updateUserSubscription` (`opensaas/payment/user.ts:47-66`) is an unconditional last-write-wins `update`, and `updateUserCredits` (`user.ts:74-91`) does `credits: { increment: numOfCreditsPurchased }` on every delivery with no stored event id at all — a Stripe retry (which Stripe's at-least-once delivery guarantee makes a certainty, not an edge case) would double-credit the user. My own recommendation isn't complete on this point either: event-id dedup needs to be paired with an event-timestamp/sequence check against the target row (`if incoming.eventCreatedAt <= row.updatedAt: skip`) — the existing `version` column pattern (already on `posts`, `members`, `memberTiers`, `memberSubscriptions` — `schema.ts:71,480,502,522`) gives optimistic concurrency for concurrent writers, but not chronological ordering of externally-timestamped events; that's an additional column, not something `version` gives for free.

**The genuine sacrifice: analytics.** If provider payload and any genuinely open-ended commerce metadata live as opaque JSON, then ad-hoc reporting queries against the primary OLTP database ("revenue by campaign," "refund reasons breakdown") become impossible without promoting specific fields to columns first. That's a recurring tax on future feature requests, not a one-time cost, and it's the real price of Option C. The standard mitigation — a downstream analytics export/warehouse — is out of scope for this data-model question, but it should be named now rather than discovered later as a surprise when the first "just add a JSON field" reporting request lands.

## What Would Change My Mind

- If Tovu commits commerce to Postgres-only (explicitly dropping C4's "SQLite must remain a first-class production target" for the commerce subsystem specifically) — the three-dialect indexing problem disappears for the one subsystem that needs it, and GIN-indexed `jsonb` (Option A) becomes defensible on its own terms.
- If a concrete, present-tense reporting requirement surfaces needing ad-hoc queries over specific provider-metadata fields — that pulls those *named* fields out of JSON into real columns; it doesn't change the overall shape, but it's the kind of evidence that should be actively sought before the schema is written, not treated as a hypothetical.
- If a real, tested MySQL or Postgres adapter lands before commerce ships (contradicting F3's current state) — the "prove tri-dialect equivalence" precondition (Q7) would already be partly discharged, which changes the sequencing answer (Q8) materially: the first commerce migration could then legitimately run against two real engines instead of needing to build that harness from zero.

## Unlisted Option

A decomposition not on the A–E list: **split the schema question by concern, not by dialect.** Give the money/idempotency ledger (payment events, balances) dialect-portable, always-relational, always-indexed treatment — a `processed_webhook_events(provider, event_id) UNIQUE` table costs nothing extra per dialect, because a unique index is one of the few DDL shapes that *is* identical across Postgres, MySQL, and SQLite. Give catalog/browsing data (product descriptions, display metadata) the loose, JSON-friendly, read-mostly treatment, because it tolerates eventual consistency and never needs a transactional guarantee. This resolves the A-vs-D tension directly: instead of arguing "one schema for everything" vs "one schema per dialect for everything," split by whether the data needs a portable transactional guarantee (ledger: yes, relational, small) or not (catalog metadata: no, JSON-tolerant, can stay loose). This is a refinement of C, not a genuinely different option — if the packet's framing already covers this inside C, "no, the listed options cover it" is also a fair reading.

## Blind Spots

**(a) A viable option not listed:** the concern-split described above — treat "does this data need a cross-dialect transactional guarantee" as the axis, rather than choosing one physical strategy for the whole commerce domain.

**(b) A question we should be asking but isn't:** does Tovu commerce need to support an unauthenticated/guest purchaser, or is every purchaser necessarily an existing `members` row first? Nothing in F1 or F2 mentions a cart or checkout session that exists before a member record does, and Open SaaS's own checkout path requires `context.user` to be set before `generateCheckoutSession` runs at all (`opensaas/payment/operations.ts:26-31`). If Tovu commerce needs to support one-time guest purchases (very common for digital/physical goods, less so for membership), that implies an identity/ordering model that doesn't route through `member_id` the way `memberSubscriptions` does (`schema.ts:512`) — and it isn't addressed by open questions 1-8 at all.

**(c) The framing assumption most likely wrong:** that "portability strategy" is chiefly a schema/indexing design problem to solve up front. F1 shows the live constraint is architectural, not physical: `CommercePaymentRuntimePort` deliberately excludes charge/refund/webhook/credential methods, `CommerceStatus` hardcodes every actual capability as `"unavailable"` (`contracts.ts:57-62`), and F1 states plainly that "no provider runtime is composed in either composition root." There is currently no code path that would ever write a commerce row of any kind, in any dialect. Given that, and given F3 (MySQL: zero code; Postgres: evaluation-logic only, `db-postgres-ops.ts:1-51`), the higher-leverage question is "what's the smallest vertical slice — port, one composed adapter, one table — that proves checkout works end-to-end for the one dialect that's actually real," not "what schema is simultaneously correct for three dialects with no adapters." Over-designing physical portability against a constraint (C1) that has zero exercised adapters behind two of its three legs risks locking in assumptions before real usage patterns exist to test them — which is the same reasoning the schema file itself already uses when it defers Postgres to "the rule-of-two second adapter" (`schema.ts:9-10`) rather than designing for it now.
