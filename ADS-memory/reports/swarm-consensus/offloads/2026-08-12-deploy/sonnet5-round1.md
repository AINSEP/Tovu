## Position

**What is being deployed:** I assume reading #1 — *the rendered site/content of a workspace*, pushed to an external hosting target so it goes live — not "Tovu the instance" and not theme/plugin packaging.

- "Deploying Tovu itself" would mean provisioning/managing the host Tovu runs on — a hosting control plane. Nothing in F2's 32 route groups manages infrastructure lifecycle (no `hosts`, no `provisioning`, no `environments`), and building that now would directly violate C1 (no proprietary hosted control plane) by turning Tovu into one. I reject this reading.
- "Theme/plugin deployment" is packaging and distribution — that's what `marketplace` (F2) is already the route group for. Conflating it with "deployment" mixes two features that don't share a data model.
- The owner's own example — GitHub — only makes sense under the "rendered site / content" reading: you don't deploy a Tovu instance to GitHub, you push *output* there.

Given that reading, my position: **the right general integration surface is a provider-neutral port with direct HTTP adapters (Option B), not MCP.** The smallest honest first slice is closer to Option D (push to a git remote, let the operator's own CI do the rest) than to a full multi-provider deploy-status system. **MCP is the wrong primary transport**, for reasons specific to what this codebase has already decided about MCP, not in the abstract.

The owner's hypothesis — "just MCP, tokens and base URLs" — is **partly right, partly wrong**: right that the credential shape is "sealed token + base URL" (that's already built, see below); wrong that MCP-the-protocol should be what carries it.

## Option Assessment

**A — MCP-only. Reject.** Three codebase-specific reasons, not generic MCP skepticism:

1. `mcp-federation/ports.ts:139-142` states plainly that only the stdio transport is implemented and the hosted-HTTP transport was "deferred rather than half-built." So "MCP" in this repo today means: Tovu spawns a local child process per third-party server (`adapter.stdio.ts:307-370`, `spawnMcpStdioChannel`). For GitHub that means either running a third-party GitHub MCP binary as a subprocess — which is mechanically Option C with a JSON-RPC skin on top — or Tovu writing its *own* first-party MCP server that internally wraps GitHub's REST API, which is Option B wearing a costume. Neither path gives a deploy feature anything MCP-the-wire-format actually buys, because the trigger here is a human clicking "Deploy" or a scheduled job, not an LLM choosing among tools.
2. `mcp-federation/trust.ts:36-42` names the exact class of operation deploy sits in — it lists Supabase's `execute_sql`, `apply_migration`, `delete_branch`, and **`deploy_edge_function`** as the kind of "strictly larger and less reversible surface" Tovu's native tier "deliberately withheld... on purpose." The federated trust tier (R1–R8, `trust.ts:56-107`) is built to admit a small, DEMOTE-ONLY, mostly-read surface to an LLM — R3 (`trust.ts:70-74`) lets a remote's self-declared hints only *remove* a tool, never add one, and does not default an *unset* `destructiveHint` to refused. A deploy tool that just doesn't declare `destructiveHint: true` sails through R2's allowlist untouched. Routing deployment through federated MCP either reproduces the exact hole this file was written to avoid, or forces deploy tools to bypass federation and become *native* Tovu tools instead — at which point you're not doing "MCP," you're doing native tool registration with an MCP-shaped afterthought.
3. `external-mcp/put.ts:22-24,57` and `delete.ts:30` both return `restartRequired: true` — an MCP server registration change (i.e., adding a deploy target) does not take effect until the agent daemon restarts. In a multi-workspace single process (C2), that means configuring workspace A's GitHub connector requires a restart that also interrupts every other tenant's live site. That's a bad cost for what should be as cheap as saving a row.

**B — Direct HTTP adapters. This is the core of my answer.** `integrations-ports.ts` already has the exact seam a provider-neutral deploy port needs: `KeyringPort`/`SecretSealerPort` (`integrations-ports.ts:59-97`) for sealing tokens, `IntegrationSecretRepoPort` (`integrations-ports.ts:158-163`) for persisting them workspace-scoped, and `HttpClientPort`/`EgressPolicy` re-exported from the shared `../http` core (`integrations-ports.ts:28,40`) satisfying C4 directly. I did not receive a commerce-payments file in this set, so I can't independently confirm the packet's claim that commerce already uses this exact pattern — but everything I *can* verify is consistent with it: this is infrastructure built for "provider-neutral port, N adapters," not for "everything speaks one third-party protocol." GitHub's deployments/checks/workflow-run APIs map cleanly onto it.

**C — CLI subprocess adapters. Narrow fallback only, not a default.** The hardening this needs already exists as a worked example: `adapter.stdio.ts:372-386`'s `INHERITED_ENV_VARS` allowlist (`PATH`, `HOME`, `TMPDIR` only — explicitly NOT the daemon's own `TOVU_AGENT_DAEMON_TOKEN`, per the comment at `adapter.stdio.ts:298-302`) is precisely the discipline a `gh`/`vercel`/`wrangler` subprocess adapter would need to reuse. But it costs more than B per provider: a per-workspace scoped `GH_TOKEN` env has to be constructed and injected on every invocation (no ambient `gh auth login` is safe in a multi-tenant self-hosted process), stdout has to be parsed instead of a typed JSON response consumed, and the operator's installed CLI version becomes an unpinned variable Tovu doesn't control. I'd reserve C for providers whose primary interface genuinely has no REST equivalent (e.g., `wrangler` has operations without a documented API surface) — not use it as the default GitHub path when GitHub's REST/GraphQL API is directly reachable through the already-guarded `HttpClientPort`.

**D — Git-push-as-deploy. Right-sized as the *first slice*, not as "the design."** It's the cheapest way to satisfy C5 (no unproven capability): Tovu's job stops at "the commit landed," and it inherits F7's change-set/recovery machinery for the Tovu-side content that produced the push. But it only works for git-integrated hosts. A target that deploys from a direct asset upload rather than a CI-watched repo gets nothing from D — so D can't be the whole story, only the honest opening move.

## Failure Modes And Sacrifice

- **The real sacrifice of rejecting A:** MCP's actual appeal — pointing at a well-known third-party server with zero Tovu-side code — is given up. Every provider Tovu doesn't write a B-adapter for gets no deploy support at all. That's a real ongoing maintenance cost this position accepts.
- **B's guarded client is tuned for the wrong shape for some providers.** `EgressPolicy`'s response caps and redirect revalidation (F4) are safety-first, but deploy status sometimes needs streaming build logs or long-lived connections that a cap-oriented client wasn't built for — likely needs an explicit policy carve-out, which is a hidden design cost, not a free reuse.
- **The credential story is less unified than it looks.** `external-mcp/deps.ts:14-16` reuses `siteAssistantSecretSealer`/`siteAssistantSecretKeyring` — a *separate* named instance from the generic `KeyringPort`/`SecretSealerPort` in `integrations-ports.ts`. There are already two parallel places sealed secrets can live in this codebase. A deploy feature needs a decision about which one it uses, not an assumption that "the sealed secret store" is singular.
- **No long-running-job primitive exists to reuse.** `module-status.ts:7-16` is boot-lifecycle-only (a readiness snapshot), not per-run job tracking. The closest analog is `WebhookDeliveryRepoPort`'s claim/markDelivered/markFailed/backoff shape (`integrations-ports.ts:121-155`) — but that's for *outbound* webhook fan-out (Tovu notifying others), the wrong direction for "GitHub calls Tovu back when a build finishes." A deploy-run tracker with inbound-callback handling is new work either way.
- **Change-sets don't rollback the live artifact.** F7's reversibility is for what Tovu wrote to its own `content.db`; it cannot un-deploy a build already promoted on a provider. Presenting a change-set rollback as "undoing a deploy" would violate C5 — it would look like it worked while the external site stayed on the bad build.

## What Would Change My Mind

- If the hosted-HTTP MCP transport referenced in `mcp-federation/ports.ts:139-142` actually landed (not just stdio), the subprocess/restart objections to A would mostly dissolve, and a well-maintained third-party GitHub MCP server over HTTP would become a much stronger contender against hand-rolling a B adapter.
- If I saw the commerce payments adapter the packet references and it turned out to *not* follow the port+adapter shape I'm inferring from `integrations-ports.ts`, I'd need to revisit whether B is actually this codebase's established convention or just what the ports file happens to suggest.
- If `trust.ts`'s R3 rule were revised so an *unset* `destructiveHint` on a mutating tool defaulted to refused (rather than only `true` demoting), the specific objection to federated deploy tools would be substantially weakened.

## Unlisted Option

A genuine sub-option worth naming on its own: **provider deploy-hook URLs** (Netlify/Vercel/Cloudflare Pages "build hook" pattern — a POST to a pre-issued opaque URL triggers a rebuild of whatever's already git-connected on their side). This needs no token, no per-provider API client, no version tracking — just `EgressPolicy`-guarded `fetch` on a stored URL through `HttpClientPort`. It's smaller than either B or D as described in the packet, and for a large fraction of real "push my site live" cases it may be the actual smallest honest slice, ahead of git-push. I'd call it a decomposition of B rather than a wholly separate letter, but it changes the sequencing answer enough (Q9) that it deserves naming rather than folding silently into B.

## Blind Spots

**(a) A viable option not listed:** an **operator-authored deploy script** — Tovu execs one operator-provided command per workspace (stored, run with a sealed/scoped env, sandboxed and timeout-bounded, using the exact hardening `adapter.stdio.ts` already proved out) rather than Tovu shipping N first-party provider adapters. This pushes protocol knowledge onto the operator entirely — which is arguably *more* aligned with a self-hostable, technical-operator product (C1) than either a curated adapter list (B) or a curated CLI list (C), since GitHub Actions and Netlify's own build system are themselves just script runners under a thin UI.

**(b) A question we should be asking but aren't:** *who initiates a deploy, and does it need to be event-driven rather than request/response?* C6 asks whether the assistant can drive this, but nobody asks whether deploy should fire on a Tovu-side event (e.g., "redeploy whenever a post publishes") rather than always being manually triggered. Tovu already has outbound webhook fan-out infrastructure (`WebhookSubscriptionRepoPort`/`WebhookDeliveryRepoPort`, `integrations-ports.ts:104-155`) built exactly for "notify something when a Tovu event happens." Deploy-on-publish might not need a bespoke trigger mechanism at all — it might just be one more webhook topic. Nobody in the packet asks this, and it changes the shape of "the frontend surface" (Q8) considerably.

**(c) The framing assumption most likely wrong:** that there is one correct answer to "MCP vs CLI vs HTTP vs git" *at all*, as a global choice. Every existing external boundary in this codebase — `KeyringPort`, `SecretSealerPort`, `HttpClientPort`, even `McpSessionPort` itself — is one narrow **port** with a small number of interchangeable **adapters** behind it (ADR-006's rule-of-two, visible everywhere I read). The packet's own four lettered options are framed as mutually exclusive choices for "the" transport. The architecturally consistent move, given what this codebase already does everywhere else, is a single `DeploymentTargetPort` where each provider adapter is free to pick HTTP, a deploy-hook URL, a CLI subprocess, or (later) MCP — transport becomes a per-adapter implementation detail, not a product-wide decision. Insisting on one global transport is very likely the wrong-shaped question, not just a hard one to answer.
