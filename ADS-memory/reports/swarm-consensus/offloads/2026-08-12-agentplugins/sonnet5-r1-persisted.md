## Position

The question as posed — "how should Agent Plugins become invokable commands" — presupposes that "invokable command" is one coherent thing. It isn't. The spec defines exactly two portable component types, and they are different in kind, not just in trust level:

- A **Skill** (`skills/<name>/SKILL.md`) is markdown. It has no arguments, no return value, no side effects, no capability surface. "Invoking" one can only ever mean "inject this text into the model's context for this turn." That's confirmed by what's already shipped: `tovu/agent-plugin-catalog.ts:76-82` has a `skill:ui-ux-design` composer entry whose entire behavior is `insertText: "UI/UX Design skill"` — text insertion, nothing more, because there is nothing more a Skill can do.
- An **MCP server** is a subprocess with real inputs/outputs (`tools/call` takes `arguments`, returns `content`) and, on a self-hosted box, is genuine local code execution.

A design that answers "how do commands work" with one mechanism for both (which is what Options A, C, and D each do, read literally) is answering the wrong-shaped question. My position is a decomposition, not a pick from the slate:

1. **Skill invocation = context composition only, with no new trust model**, because a Skill executes no code — the only "grant" a user makes is *bundling the plugin at all* (already gated by `AgentPlugins.tsx:64-67`'s catalog, which is explicit that these are "catalogued as installed" and "not execute[d]"). This is very close to what exists today and should stay honest about being exactly that: a labeled context nudge, not an action.
2. **Command *metadata* (label, description, argument shape) lives in a Tovu reverse-domain extension namespace** (`extensions["org.tovu.commands"]`, Option B) — because the spec explicitly sanctions this ("Client-specific data uses reverse-domain namespaces under `extensions`... Each client defines the semantics of its own namespace," per the packet's Extension Mechanism section) and F2 already locked this as the intended home for Tovu-specific UI metadata. This is packaging, not execution.
3. **MCP-backed command *execution*, when it ships, must go through `mcp-federation`'s existing trust tier (Option C's substrate), not a new one** — because that tier is the only adversarially-designed answer in this codebase to "a local subprocess I don't control is about to run" (`tovu/mcp-federation/trust.ts:1-107`). But reusing it is not free (see Failure Modes) — the tier's core assumption, an *independent* allowlist author, doesn't hold for plugin-supplied MCP servers the way it holds for `supabase-mcp-plugin.ts`.
4. **The first-party `.tovu-plugin` system (Option D) is not a viable substrate for either of the above**, and should be rejected outright as the reuse target — not merely deprioritized. See Option Assessment.

On adversarial task item 5 (should Agent Plugins be the command surface at all, or the first-party system): neither, as currently scoped, is actually competing for that job. The first-party system's only hook point is `content.entry.beforeSave` (`tovu/plugin-runtime/hook-registry.ts:125`, `VALID_HOOKS = new Set(["content.entry.beforeSave"])`) — it extends the *content save pipeline*, not the *composer*. Its own manifest carries a forward-compat `adminSurfaces` field that is explicitly "UNUSED in v1" (`tovu/plugin-runtime/manifest.ts:59-60`) — even its own designers haven't claimed the UI-surface space yet. So open question 4 ("should the two systems converge") is partly a false dilemma: they don't currently solve the same problem, they're both labeled "plugin system" and that's what makes them look like they're competing. That said — a sharper version of item 5 is worth asking, and I raise it in Blind Spots: is *any* explicit user-typed slash command the right paradigm for MCP-tool invocation, given Tovu's own precedent (federated MCP tools are registered into `ToolRegistry` and called autonomously by the model — `tovu/mcp-federation/registrations.ts:90-132` — never through the slash palette)?

## Option Assessment

**A — Skills-as-commands.** Not wrong, but it's not "a design" so much as the already-shipped 80%: `agent-plugin-catalog.ts:71-84`'s `skills` discovery group already does exactly this (label, description, text-insertion). Its failure as a *complete* answer is that it says nothing about MCP servers at all — a plugin that ships `mcp.json` (unlike the one real plugin in this repo, which doesn't) gets no invocation story under A. Necessary, insufficient.

**B — Reverse-domain extension namespace.** Structurally sound and spec-sanctioned, but be honest about what it buys: it makes Agent Plugins a portable *packaging* format that Tovu-only command metadata rides inside. A plugin published for another agent-plugins.org client gets zero command behavior in Tovu unless it also carries Tovu's private namespace, and vice versa — Tovu's commands mean nothing to any other client. That's fine (the spec's extension mechanism exists for exactly this), but it should not be sold as "we adopted an open standard for commands." We adopted an open standard for packaging and bolted proprietary commands onto it, which is the correct and honest move, not a compromise to apologize for.

**C — MCP-tools-as-commands.** The strongest of the four as a pure execution model, because MCP is the only portable component type with actual invocation semantics, and `mcp-federation/trust.ts` R1-R8 is a genuinely hardened answer to "an external subprocess wants to expose tools" (namespacing by construction, default-deny allowlist, one-way self-declared-hint demotion, frozen-at-connect, untrusted-data-boundary wrapping, single coarse permission gate). But C as stated ("commands are projections of `tools/list`, executed through the existing federation and trust layer") glosses over a load-bearing mismatch: `trust.ts` R2's allowlist is meant to be authored by someone *other than* the thing being classified (`ports.ts:114-119`: "a DEFAULT is a per-vendor judgement and therefore belongs to a vendor preset... authored from that server's real, inspected tool surface, which is what makes it an independent classification rather than a restatement of the remote's own claims"). A plugin-supplied `mcp.json` is authored by the plugin, not by a Tovu operator or vendor preset — there is no independent author unless Tovu invents one. "Just reuse the federation layer" undersells this as a wiring exercise when it's actually a missing trust-design piece.

**D — Reuse the first-party plugin runtime.** Reject this as the substrate, not just deprioritize it. `loadPlugin()`'s pipeline (`tovu/plugin-runtime/loader.ts:8-20`) is: verify per-file SHA-256 against `manifest.integrity`, check `sdkRange` against `@tovu/sdk`, dynamically `import()` a `server/index.mjs` ESM entry, call `setup()` with a capability-scoped SDK, attach hooks. Agent Plugins has no `integrity` field, no `sdkRange`, no code entry point at all for a Skill, and an MCP server is a subprocess, not an ESM module to `import()`. The three-member capability vocabulary — `content.read`, `content.extend`, `hooks.attach` (`manifest.ts:36`) — has no natural mapping to either portable component: a Skill has no SDK call surface to gate (it's not code); an MCP server's surface is whatever tools it exposes, which `mcp-federation` already governs with its own (better-fitted) permission model. Forcing D through here means either fabricating capability strings that mean nothing (capability theater, directly against C6) or forking the loader to understand a second, third manifest shape, which stops being "reuse" the moment it happens. The only thing worth salvaging from D is the *tier-1/2/3 vocabulary as a shared UX label* across both systems' admin screens — a copy decision, not a runtime decision — and even that is undercut by the fact that Agent Plugins v1 has no signing story (open question 7), so it can't honestly earn anything above a tier-3-equivalent label regardless of which system displays it.

## Failure Modes And Sacrifice

**Failure mode 1 — allowlist collapse.** If C ships without solving the allowlist-authorship gap, the path of least resistance is auto-admitting whatever `mcp.json` declares on plugin enable. That silently reintroduces exactly the failure `trust.ts` R2/R3 were built to refuse: a remote (here, a plugin author) self-declaring its own trustworthiness. Concretely, a compromised or malicious Agent Plugin's `mcp.json` tool could set `destructiveHint: false` on something destructive, and R3's one-way demotion rule (`trust.ts:70-74`, "SELF-DECLARED HINTS DEMOTE ONLY, NEVER PROMOTE") only protects against a lie *within* an already-independently-vetted allowlist — if the allowlist itself came from the plugin, there's nothing left for R3 to demote from.

**Failure mode 2 — silent partial plugins.** The spec's own `extensions` handling is designed to fail silently: "An unknown top-level field or a non-object `extensions` field is non-fatal" (packet, Client conformance). If Tovu's commands live in `extensions["org.tovu.commands"]`, a malformed or misnested block means a plugin installs looking fine (Skills load) while silently carrying zero commands, with no error surfaced anywhere by the spec's own conformance rules. Tovu has to actively manufacture a loud warning for this or it becomes an invisible half-broken install — this is a cost of B specifically, not solved by adopting it.

**Failure mode 3 — mislabeled affordance (A).** If "Skill as command" isn't clearly labeled as context-injection-only, users will read a command-palette entry as "this does something" and get a silent prompt nudge instead — a transparency problem adjacent to C6. The current UI already gets this right (`AgentPlugins.tsx:65-67`'s explicit "not executed" copy); the risk is losing that discipline once a *general* command mechanism ships and the specific plugin-by-plugin honesty gets abstracted away.

**The one genuine sacrifice:** committing to this decomposition means Tovu does **not** get a unified "install a plugin, get a working command" experience soon. Skills get context-nudges; MCP-backed commands wait on a real allowlist-authorship answer that doesn't exist yet. That's a visible, feel-able product gap next to any client that ships a single generic "commands" abstraction — and the alternative (faking uniformity by auto-trusting plugin-declared MCP surfaces, or overselling what a Skill "execution" does) is precisely what C6 forbids. The sacrifice is a slower, honestly two-tier command UX in exchange for not lying about what's proven.

## What Would Change My Mind

- A future Agent Plugins spec version adding a native `commands` component type with a declared argument/output shape would remove the need for B's private namespace and change how I'd weight "propose upstream" in the namespace-risk question.
- A product decision that the composer's slash palette is *only* ever for context/skill insertion, never for triggering side-effecting tool calls, would dissolve the C-vs-"agent tool" tension I raise in Blind Spots — that's arguably already implied by `jini/composer-discovery.ts:38-46`'s current behavior (draft-text manipulation only, no execution stub anywhere), so if that's confirmed as intentional rather than incomplete, my "wrong invocation paradigm" concern about C becomes the settled answer rather than an open challenge.
- A second real Agent Plugin (beyond `ui-ux-design`) that ships an `mcp.json` would raise the urgency of the allowlist-authorship gap from theoretical to immediate — right now `agent-plugin-catalog.ts:23-33` shows the only bundled plugin has no MCP server at all, so this is forward-looking, not blocking today's slice.
- If `mcp-federation`'s trust tier turns out to be less battle-tested than it reads (I evaluated it from source only, not from its test suite), that would weaken my confidence in "reuse it for C" specifically — worth a quick check before committing.

**Source-material flag:** the packet's spec summary doesn't specify whether `extensions` values must be flat JSON or may nest arbitrary structure, and doesn't describe any future/draft command-type proposal. That materially limits how precisely I can assess B's schema-design risk — I'm treating "extensions is a free-form object namespace" as the working assumption, consistent with the quoted "non-object `extensions` field is non-fatal" language, but a byte-verbatim spec read could narrow or widen that.

## Unlisted Option

**F — Ship nothing beyond today's catalog display; treat "commands" as explicitly out of scope until the allowlist-authorship design exists.** This is stricter than "phasing" (open question 8) as usually meant — it's not "smallest honest slice of commands," it's "zero command execution, full stop, until the MCP admission-authorship problem in Failure Mode 1 has an actual answer." Given C5/C6 (must not fake capability, must not regress the Installed/Marketplace screen) and given the one real plugin in the repo is skill-only anyway, this is arguably the most defensible v1 posture: keep `AgentPlugins.tsx`'s current "catalogued, not executed" honesty exactly as-is, ship Skills-as-context-insertion (already 90% done) as the only "invocation," and explicitly *not* build MCP-tools-as-commands until there's a real per-plugin operator-approval design — rather than shipping C with a fabricated or absent allowlist story under schedule pressure. I list this separately from A because A implies "and MCP comes next, mechanism TBD"; F says the MCP half is a full stop, not a follow-up sprint.

## Blind Spots

**(a)** F above — the "solve nothing for MCP yet, on purpose" option — is a viable answer the packet's four options don't really allow for, since C, D, and even the phasing question all assume MCP-backed commands are a "when," not an open "whether now."

**(b)** The question we should be asking but the packet doesn't: **should MCP-backed plugin capabilities be slash commands at all**, versus ordinary agent tools the model invokes autonomously the way already-federated MCP tools work today (`mcp-federation/registrations.ts:90-132` registers them straight into `ToolRegistry`, called by the model's own reasoning, never via the composer)? If the answer is "agent tool, not slash command," then Option C's entire framing ("commands are projections of `tools/list`") is solving a UX problem Tovu hasn't actually decided it wants, and the real work is just "federate an Agent Plugin's `mcp.json` the same way `supabase-mcp-plugin.ts` federates Supabase's" — which sidesteps the slash-command question entirely and inherits `trust.ts` far more cleanly (still needs the allowlist-authorship answer, but doesn't also need a new command-palette-to-tool-call dispatch mechanism).

**(c)** The framing assumption most likely wrong: that "how do Agent Plugins become invokable commands" is one design question with one answer. It's at least two orthogonal questions — "how does a Skill's context get into a turn" (already mostly solved) and "how does an MCP server's tool get called safely when a plugin, not an operator, chose to bundle it" (largely unsolved, and arguably not a *composer* question at all per (b)) — and the four listed options each implicitly answer only one of the two while sounding like they answer both. Treating this as "pick A or B or C or D" produces a design that's silently incomplete for whichever half it didn't address, and that incompleteness would be far more visible if the packet had asked "how does a Skill get invoked" and "how does an MCP tool get invoked" as two separate questions instead of one merged one.
