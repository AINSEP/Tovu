## Sequencing Verdict

**Q1 (precondition or parallel):** Precondition for anything to be called *done*, but narrow and fast, not a phase gate. The fix is composition-root glue over already-built, already-tested pieces (capture `loadPlugin`'s import result → `buildCapabilityScopedSdk()` → call `setup(sdk)`, with `coreDeps.attachFilter` wired to `attachLoadedPlugin`/`hookRegistry.attach`). That's on the order of the wiring ADR-057 already did once for Site Glue. Hook-catalog *design* and Tier-1 primitive *design* don't need to wait on it. But no PR in either track should be merged as "shipping" ahead of it, because every one of them rides the same activation→`onEnabled`→`setup()`→`addFilter` path, and until AC-01 is provably closed there is no integration test proving that path exists at all — building on top of an unconfirmed foundation risks discovering the gap is systemic rather than this one narrow miss.

**Q2 (trust or surface):** Surface — more lopsidedly than Round 1, not less. In Round 1 I argued a fully-trusted Tier-3 plugin still can't do much because only one hook exists. Now: a fully-trusted Tier-3 plugin can't do *anything* through the documented enable path, and that's not a trust gate at all — it's one missing function call. Tier-2/Rung-1 sandbox work (Option B) would be hardening a boundary around a loop that doesn't run yet. Trust-tier investment is solving a problem the system hasn't reached.

**Q3 (EC-10 urgency):** Ship in the same batch as the wiring fix, not after it. ADR-024's own binding invariant (`ADR-024-plugin-execution-and-trust-model.md:115-116`): "no feature ships whose failure mode exceeds the current recovery rung." `traceability.spec.md:99` shows EC-10 still `PENDING`, and `feature.spec.md:233` confirms today's only recovery is a manual `PATCH .../plugins/:id {enabled:false}`. Right now EC-10 is *latent* — no filter can attach through the SPEC-005 path, so nothing can brick a save via it yet. The wiring fix is exactly what makes it *live*: the first real attached filter (word-count) can now throw and block every save in that workspace. Shipping the wire without EC-10's auto-disable in the same change violates the ADR's own invariant the moment the fix lands. Treat as one work item.

**Q4 (Tier-1 primitives):** The finding doesn't change this one directly — Tier-1's manifest-declaration→core-mediated-behavior translation is a different mechanism from `setup()`/`addFilter` (Tier-1 is zero-code by definition) and remains its own, still-entirely-unverified wiring question. But the grep result above means don't credit the 60–73% number yet: "webhook dispatch has visible backing infra" (Round 1, mine and codex's) is true of the *port*, not of any caller. Before this number does more sequencing work, someone should do for the Tier-1 primitives what the Coordinator just did for the hook path — find (or confirm the absence of) the actual caller.

**Q5 (background/scheduled work):** Still out, reinforced rather than reopened. Designing a hook contract for scheduled work before confirming the one hook that exists fires end-to-end is premature squared.

**Q6 (per-hook discipline cost, and does it move Q2):** The cost math changes in one respect: ADR-024 §7's discipline (explicit priority, phase, order, failure behavior) has only ever been exercised inside `hook-registry.ts`'s own unit — a real, working implementation, but one that has never yet been fed a filter attached through the real enable path. "Per-hook cost" is currently a design-time estimate, not an operationally-validated one. That doesn't change the Q2 verdict — if anything it reinforces surface-over-trust, since the blocker on validating even the existing hook is a wiring gap, not an isolation gap.

## Remaining Disagreements

With both Gemini responses (`gemini-3.6-flash-high[-round1]`, `gemini-3.1-pro-high[-round1]` — textually identical to each other in both rounds): "Reject C — expanding the in-process hook catalog creates ecosystem lock-in / breaks the ABI freeze" conflates hook-*catalog breadth* with Tier-3's *in-process execution model*. Hooks here are delivered through the capability-scoped SDK (`capability-sdk.ts:107-117`) regardless of which tier executes the code; the ABI freeze (ADR-024 §3) is what governs safety, and it applies identically whether there's one hook or twenty. Rejecting catalog growth on execution-model grounds is a non sequitur given what's actually in these files. Also, if Rung-1 process isolation is worth engineering now (as both Gemini responses and my own Round 1 carve-out argue), note it doesn't address EC-10 at all: an isolated process still blocks its own workspace's saves when its one attached filter throws. Don't let Rung-1 work read as if it's addressing the more urgent gap — it isn't.

With codex's Option E (capability-broker: converge Tier-1 and Tier-2 into one core-owned registry/protocol now): codex's own Round 1 already named the loader gap as real (`codex-round1`: "the current loader does not yet complete setup or registration") but treated it as a caveat on Option B rather than the actual next action. I'd sharpen that: designing a converged broker architecture before the one-hook loop is proven wired front-loads architecture ahead of a one-function fix that would tell us far more about what the real integration constraints are.

## Strongest Counter-Argument

Steelman: the wiring fix is small enough to be a fixed cost, not a real sequencing decision — the actual constraint on velocity is parallel design work (hook-catalog discipline, Tier-1 primitive infra, EC-10's quarantine design, Rung-1 isolation), which several people can design and partially build concurrently, landing behind one integration PR that wires everything at once. Under that view, my "precondition" framing is theater around glue code.

Rebut: I'd accept "design in parallel," but not "implement and merge without the wire landing first as its own PR." The reason isn't that the code is hard — it's that until it lands, there is no way to write or run the one integration test that proves AC-01 (word-count's `ext.word-count.count` write) end-to-end. Every other workstream this round — new hooks, EC-10's throw-detection, Tier-1 primitives if they turn out to reuse `setup()`/`addFilter` — needs that green test as its regression harness. Landing the fix first isn't about difficulty; it's about unblocking the project's only current end-to-end proof point, which every later PR should be reviewed against.
