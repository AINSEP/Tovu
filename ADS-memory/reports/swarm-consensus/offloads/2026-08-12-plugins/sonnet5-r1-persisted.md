## Position

ADR-024's tier model is the right frame at the trust axis, and I don't think Round 2 needs to re-litigate A vs B — that fight already happened (unanimous 4/4, `ADR-024-plugin-execution-and-trust-model.md:124-128` names B "rejected... mis-sequences cost before learning") and was empirically checked (`:148-160`, the demand audit puts Tier-1 at 60–73% of real demand). Re-opening "sandbox first" without new evidence would be worse than what the packet already has. But the packet's A/B/C framing hides a more important fact: **the current bottleneck on "ecosystem in the WordPress sense" is not trust, it's hook-catalog breadth, and there's an unresolved question about whether the loaded runtime even completes the one loop it claims to.**

Two grounded reasons:

1. **One hook point gates everyone, at every tier, today.** `feature.spec.md`'s own title is "One Hook" (`feature.spec.md:1`), and `content.entry.beforeSave` is the *only* declared point (`behavior.spec.md:81`, `state.spec.md:112`). A fully-trusted, sideloaded, first-party Tier-3 plugin — no sandbox required, ADR-024 already permits this today — still can't touch admin menus, rewrite `title`/`slug` (blocked by design, `feature.spec.md:109`, deferred as OQ-09), run on delete/publish/trash, or filter a query. That's not a trust gap, it's a *surface* gap, and it's orthogonal to whether Tier-2 ever ships. Options A and C aren't really alternatives — A's own vindication is *conditioned* on core shipping "core-mediated primitives" (webhook dispatch, snippet/asset injection, mail adapter, redirect executor, form-submission sink — `ADR-024-...md:155-157`), and every one of those is itself a hook. Growing Tier-1 *is* growing the hook catalog, just scoped to declarative consumers. So "hooks vs capability SDK" (how C is framed at line 95 of the packet) is a false choice in this codebase: hooks here are already delivered *through* the capability-scoped SDK (`capability-sdk.ts:107-117`; `hook-registry.ts:70-85`), not an alternative to it. The real decision isn't A-or-C, it's "how fast and how disciplined" to grow the one axis both depend on.

2. **The walking skeleton may not actually close the loop it's credited with.** `loader.ts:147-158`'s own comment says steps (4)-(5) of BR-01 — invoking `setup()` with the capability SDK and attaching the hook — "are still NOT called from inside this function," and `hook-registry.ts:11-20` independently confirms (by grep) that `loadPlugin()` "has never called `.attach()`" and that the only real production caller of the newly-extracted `attachLoadedPlugin()` is something called "Site Glue" (ADR-057), which is outside SPEC-005's scope and outside my staged files. I can't see the composition root, so I can't confirm this is still broken — but two independent, self-disclosed comments in the given files say the SPEC-005 enable path (`activation.ts`'s `setPluginEnabled` → `onEnabled` hook) has no shown wiring to either `loadPlugin` or `attachLoadedPlugin`. If that's still true, AC-01 (`word-count` writes `ext.word-count.count` on save) is not actually provable end-to-end through the documented path. This is worth confirming *before* anyone invests in hook-catalog breadth or Tier-1 primitives, because both build on top of "the one hook already works."

Given that, my position: don't spend Round-1-adjacent energy re-fighting isolation-first; spend it confirming the one hook actually fires end-to-end, then grow the hook catalog under the same discipline `content.entry.beforeSave` got (typed signature, one capability token, ABI-freeze audit) as the primary lever — with Tier-1 primitives as the first, most disciplined consumers of that growth, not a separate track.

## Option Assessment

**A — Grow Tier-1 first.** Real, audited support (`:148-160`) — I'd keep this, but flag it's conditioned on 5 unbuilt primitives, of which only one (webhook dispatch) has visible backing infrastructure: `integrations-ports.ts:104-114`'s `WebhookSubscriptionRepoPort`/`WebhookDeliveryRepoPort` already provide claim/retry/backoff plumbing, and `:59-87`'s `KeyringPort` already provides HKDF signing (`deriveSigningSecret`). Snippet/asset injection, a mail adapter, a redirect executor, and a form-submission sink have zero visible infrastructure in this packet. Treating A as "cheap and next" without checking those four is an unverified assumption baked into a vindication number. Also: A alone caps the ecosystem at "no WooCommerce-class plugin, ever" — the audit says so itself (`:158`, "the highest-value single plugin... is squarely Tier-2").

**B — Build the Tier-2 sandbox now.** Reject wholesale; already rejected with reasons I find sound (`:124-128`), and nothing in this packet supplies new evidence to reopen it. But I'd carve out **Rung 1 (per-site process isolation)** as legitimately separable: ADR-024 itself calls it "a near-free runtime swap *because of* the §3 ABI freeze" (`:74-75`). It doesn't unlock the marketplace (Rung 2's capability enforcement is what third-party code needs, `:76-77`), but it's a live risk-reduction for *today's* Tier-3 reality under the Electron multi-site topology (`:21-27`, one unsandboxed plugin can read every site's `content.db` on the same machine) — worth doing on its own merits, independent of the marketplace timeline, and not equivalent to "isolation-first."

**C — Expand the hook surface.** I'd rate this the single highest-leverage lever available *right now*, for the reasons in Position — but the packet's framing of it ("go wide on hooks... staying at Tier-3 for first-party and Tier-1 for third-party") undersells the discipline cost. ADR-024 §7 (`:95-99`) already specifies the bar every new hook must clear: explicit priority, declared phase, deterministic order, defined failure behavior, no cross-plugin deps in Phase-0. INV-06 (`feature.spec.md:207`) is explicit anti-hook-soup. Going wide fast, without that per-hook rigor, reproduces exactly the WordPress failure mode (undocumented ordering, silent side-effect chains) this architecture was designed to avoid. C is right in direction, risky in execution speed.

**D — Converge the three extension systems.** Reject full convergence. Agent Plugins is explicitly "not an install/permission/sandbox/trust model" (packet F5) — it packages Skills/MCP servers for an agent runtime, a different consumer and a different risk shape entirely; forcing it into one artifact with CMS plugins conflates unlike things. Themes and plugins already share the thing worth sharing — tier vocabulary, by direct design (`ADR-024-...md:5,31`, "generalizes ADR-020's theme tiers to plugins") — without sharing an artifact format, because a theme's renderer contract and a plugin's hook/capability contract are genuinely different shapes. I'd keep vocabulary/admin-surface convergence (already happening) and reject artifact convergence.

## Failure Modes And Sacrifice

- **Hook-catalog growth without per-hook ABI-freeze audits** compounds the thing ADR-024 §3 called "nearly irreversible once third-party plugins exist" (`:63-65`) — every new hook signature and every new capability token is now permanent SDK surface under the ADR-005 deprecation ladder. Growing width is not free; it's compounding weight on a promise that can't be retracted.
- **The ABI freeze may already be unaudited on the one hook that exists.** `feature.spec.md:109` and `state.spec.md:80` both write the `beforeSave` filter's type as `(entry, ctx) => ExtPatch` — no `Promise` in the documented return type — while `hook-registry.ts:170` actually does `await attachment.filter(snapshot, ctx)` at runtime. Awaiting a non-promise is harmless in JS, so nothing is broken today, but it's exactly the kind of drift ADR-024 §3 demanded be checked now ("SPEC-005's single existing hook... must be audited against this rule now, while there are zero third parties to break," `:68-69`) — and I see no evidence in the frozen public type that the audit happened. Separately, `hook-registry.ts:165`'s snapshot is a *shallow* spread (`{ ...entry, ext: {...} }`); nested fields like `bodyJson` remain shared references across invocations, in tension with §3's "no live core objects... serializable payloads only." Neither is proven broken from what I have — both are unverified and worth checking before hook-catalog growth multiplies the surface.
- **Tier-1's four unbuilt primitives may not be cheap.** If a mail adapter or redirect executor turns out to need real new infra (not just wiring what `integrations-ports.ts` already provides), Tier-1's 60–73% number degrades toward the audit's own stated collapse condition (`<~20%` → "B regains urgency," `:150-151`).
- **The genuine sacrifice:** committing to hook-catalog-first plus a conditional Tier-1 push means the actual WordPress-style promise — install executable code from a stranger — stays unavailable for an unbounded period. There is no dated Rung-2 commitment anywhere in ADR-024's Open section (`:140-147`). I'm naming that as a real cost, not hiding it: third-party ecosystem growth is capped at "declarative only" for the whole period this sequencing covers.

## What Would Change My Mind

- Seeing the composition-root wiring that proves `loadPlugin()`/`attachLoadedPlugin()` *is* actually called on SPEC-005's own enable path — that would remove my biggest reservation about building anything on top of "the loop already works," since I only have `loader.ts`/`hook-registry.ts`'s own comments, not the wiring itself.
- Evidence that the four unverified Tier-1 primitives require substantial new infrastructure — that would shift real weight back toward B/Rung-2 sooner, exactly per ADR-024's own stated collapse condition.
- Evidence of real, current operator demand for third-party executable plugins specifically (not declarative content packs) — the audit measured plugin-catalog demand in the abstract; if the actual near-term ask is dominated by code-requiring integrations, sequencing should reflect that rather than the aggregate percentage.
- A red-team pass on the `beforeSave` type signature confirming the async/serializable ABI-freeze rule was actually checked (not just asserted as a requirement) — would remove that specific concern.

## Unlisted Option

**Recovery/quarantine as its own workstream, not folded into A/B/C/D.** ADR-024 §9 names a *second*, coequal ladder — change-set gateway → snapshot → attribution → safe-mode quarantine → compat doctor → kill-switch (`:112-117`) — and states the binding invariant "no feature ships whose failure mode exceeds the current recovery rung" (`:115-116`). Right now the only recovery primitive that exists is change-set revert. `feature.spec.md`'s own EC-10 (`:233`) shows the gap directly: a throwing filter "blocks *all* content saves while the plugin is enabled," and the only recovery is an operator manually calling `PATCH .../plugins/:id {enabled:false}` — automatic quarantine is explicitly deferred (OQ-06, `:268`). None of A–D touch this. Given ADR-024's own promise is "an update or plugin must never brick your site" (`:10-11`), and the one plugin that exists today can already brick every save, I'd rate closing this gap as comparably urgent to hook-catalog growth — and cheaper than either Tier-1 primitive-building or Rung-1 process isolation, since the mechanism (detect a plugin repeatedly throwing, auto-disable via the same gateway path REQ-07 already uses) doesn't require new trust infrastructure at all.

## Blind Spots

**(a) Viable option not listed:** the recovery/quarantine workstream above — every listed option (A–D) is about what a plugin can safely *do*; none is about what happens when an already-permitted plugin (at any tier, including today's Tier-3) *fails*.

**(b) A question we should be asking but aren't:** what is the execution model for a plugin's background/scheduled work? `feature.spec.md`'s manifest explicitly parks `contentTypes` as "parsed-and-stored, UNUSED in v1" (`state.spec.md:48`) and ADR-024's Open section defers "background jobs (Electron sleep/catch-up semantics)" (`:145`) without discussion. WordPress-plugin-ecosystem expectations lean heavily on custom post types and cron-like background work; under ADR-011's desktop topology a site can simply not be running when a job would fire. None of the eight open questions in the packet ask this, and it's structurally harder here than in a normal server deployment.

**(c) The framing assumption most likely wrong:** the packet frames the live tension as trust-tier-breadth vs hook-surface-breadth (A/B vs C) — but per Position, the actual near-term gate is neither: it's whether the one hook that exists is provably wired end-to-end (`loader.ts:147-158`, `hook-registry.ts:11-20`). Debating how fast to widen an extension surface is premature if the single existing point on that surface isn't confirmed to fire through its own documented enable path. I'd want that resolved as a precondition, not a parallel workstream, before treating "grow the hook catalog" as shovel-ready.
