## Position And Movement

R1's core position — reject A and D, accept B+C as one design (compile to `static` at build time, hydrate islands for interactivity) — is now unanimous and I'm not moving off it. What moves this round is that R2 forces the seven things R1 left as "disclose to the owner" into actual verdicts. I'll take them in order, correcting one of my own R1 claims along the way.

**Self-correction first.** My R1 cited the marker vocabulary as `data-embed-type="menu"/"widget"/"post"/"media"` (guide §6.2–6.4). That's the vocabulary the packet's corrections say is wrong, and I re-verified it directly against `static-render.ts` rather than trusting either the guide or my own R1 text: the real marker form is the unified `{"type":"<kind>"}` JSON marker — `{"type":"content"}` for the entity slot (`static-render.ts:78-83`, filled by `injectCurrentEntityContentId`), `{"type":"menu"}` for nav (`static-render.ts:251-262`, `injectMenuEmbeds`), `{"type":"partial"}` for slots (`static-render.ts:338-349`, `resolveSlots`). Codex was right in R1 and I was wrong. This doesn't change my conclusion — the point ("dynamic content arrives through markers the route layer resolves, not through per-request framework execution") survives with the corrected vocabulary — but the citation was wrong and I'm not going to keep citing it wrong.

**#2 Source-vs-artifact reset.** The authored source (TSX/SFC/component source, lockfile, build config) **must** ship in the package, unconditionally — a compiled-only bundle is unrepairable by an agent and unauditable by a human, which fails C6 outright regardless of what we decide about #1. `marketplace.ts`'s catalog/editable split (`marketplace.ts:257-270`: `cpSync` into `THEME_CATALOG_DIR` plus a separate editable copy, each independently stamped) already works at the *file* level with zero assumption about file content, so per-file reset on the **source tree** needs no new mechanism — it's the existing behavior, unchanged. The **generated tree** is where "file" stops being a coherent reset unit: restoring one generated `pages/index.html` in isolation can desync it from a `components.js` bundle the same build emitted, if the two were compiled together. So the verdict is a narrowing, not an invention: source keeps full C5 (per-file reset, today's mechanism, unmodified); the generated tree gets one operation — atomic whole-tree restore from the catalog's last-known-good artifact — and the editor UI must visibly distinguish the two trees so a user is never offered a per-file reset control on a file that structurally can't honor it.

**#3 AI-authorability.** `theme_write_file` today is one contract: full-file overwrite, immediate whole-theme revalidation, and the result **becomes what the live site serves** (`agent-tools.ts:200-206`, and per-write it's capped at `MAX_THEME_FILE_BYTES = 1_000_000` bytes, `theme-files.ts:68`). That single contract has to split in two for a build-tier theme, and the split has to be disclosed to the calling agent in the tool's own return value, not left implicit: a write to a **source** file gets syntax/schema validation but does *not* become what's live until the next build lands (under my #1 verdict, that build is external — see below); a write to a **generated** file should be refused outright, not silently accepted and then eaten by the next build. The current tool description's promise — "the re-validated theme also becomes what the live site serves" — is simply false for source writes under this design, and shipping the split without updating that sentence recreates exactly the silent-degrade failure class the packet's corrections already caught twice in this codebase (the stale `data-embed-type` guide text, the dead `pages` manifest field).

**#4 One class or two.** It's the design, not an admission of failure, but I want to sharpen how Opus framed it. Every tier already has an authored-file/served-file relationship — for `static` themes specifically, `theme.pages[pageId]` (the file an author edits) and what `renderStaticPage` serves are the *same bytes*, just passed through mechanical rewrites (`static-render.ts:389-413`). A build-tier theme is not a new kind of object; it's the first tier where "authored" and "served" can diverge in *content*, not just in rewrite passes applied to identical content. So: two classes, but named as **single-source** (declarative/templated/handlebars/static — edited file is served file) versus **compiled** (source tree and generated tree can diverge) — an axis every theme sits somewhere on, not a quality tier where compiled themes are lesser citizens. Opus's language ("opaque, versioned, replaced wholesale, editor-read-only") risks implying the compiled class loses AI-authorability altogether; it doesn't — the source tree keeps it, per #3.

**#5 Conformance.** Three literal/regex rewrites currently gate the entire live-traffic path: the exact-string `<link rel="stylesheet" href="../css/styles.css" />` match for token injection (`static-render.ts:402–406`), the `../css/`/`../js/` prefix regex for asset rewriting (`static-render.ts:31–35`), and the bare-`.html`-href regex for page-link rewriting (`static-render.ts:45–46`). Nothing stops a bundler that minifies attribute order, hashes the stylesheet filename, or inlines styles from silently producing a page where none of these fire — same failure shape as `parseTier`'s silent coercion of an unknown tier to `"declarative"` (`theme.ts:249–252`), which the packet already flags as needing to become a hard error. My verdict: don't touch `static-render.ts` to fix this — it's the file serving 100% of live traffic, and Round 1 was unanimous that regression risk there is the highest in the system. Instead, add a **separate, new** build/install-time conformance check that scans generated output for the exact anchor strings these three passes depend on and **fails the build closed** if any is missing, before the artifact is ever accepted into the catalog. That keeps the fix in a new, low-blast-radius gate rather than in the high-blast-radius rewrite pipeline itself, and it's a real, currently-unbudgeted deliverable, not a policy statement.

**#6 Web Components.** Settling this one decisively: **islands only, not whole-page.** The reason isn't a preference, it's the same constraint #2 and #5 both turn on — Tovu's marker substitution and token injection operate on visible, string-addressable HTML between build and serve. A whole-page custom-element root with declarative shadow DOM hides its internal structure from exactly that pipeline (I flagged the token-injection interaction as a real, unresolved cost in my own R1 unlisted-option writeup, and Codex independently rated Web Components "weaker... for whole-page authoring" in R1). Keep the page shell as ordinary light-DOM HTML — where markers and token injection already work unmodified today — and confine any custom element to interactive leaf components that don't need to intersect the rewrite pipeline. Web Components is therefore the **compiler output format for islands**, not a format Tovu's server needs to understand structurally; React, Vue, or Angular compiling to a custom element is invisible to `static-render.ts` either way.

**#7 Three frameworks or one first.** One first: **React**. Not on ideology — on the two things that actually matter here: (a) the most mature "compile whole app to static HTML + selective hydration" tooling exists for React today (Astro's React integration, Next static export, `vite-plugin-ssr`) — the exact pattern I named in R1 as the precedent this design already follows, so shipping React first means adopting an existing pattern rather than inventing one; (b) the conformance suite from #5 has to be hand-verified against real compiled output before it's trusted, and doing that once, well, against one framework beats doing it three times shallowly. Angular is explicitly last, on the point every R1 participant converged on independently (Opus: "an order of magnitude heavier per request"; Codex and Gemini: its own compiler + DI container, "heavier, more opinionated build model") — that's an engineering-cost argument for sequencing, not an architectural exclusion; Angular output that passes the same conformance suite is just as acceptable as React's. Vue is the natural second, for the reason I gave in R1: it already has the closest existing precedent to this exact design (`vite-ssg`) at the lowest incremental distance from React's islands model.

## The Build-Lifecycle Verdict

**Verdict: author builds locally for v1. Tovu does not execute a theme's build.** Tovu-runs-build is not rejected permanently, but it does not ship as part of "code tier v1," and I want to be explicit about why this isn't me splitting the difference the packet told me not to split.

The reasoning: R1's unanimous rejection of Option A/D rested on one load-bearing fact — the thing that makes `templated`/`handlebars` safe today isn't `worker_threads`, it's the AST allowlist that runs *before* the worker ever sees the input (`liquid-allowlist.ts`), because Liquid is a restricted DSL that admits allowlisting and arbitrary JS structurally does not. The repo's own reasoning for *why* it uses `worker_threads` instead of `vm2`/`isolated-vm` — "`vm2` carries known sandbox-escape CVEs while `isolated-vm` needs native compilation" (`liquid-sandbox.ts:18–20`) — is itself evidence of how carefully this team has already reasoned about, and rejected, execution sandboxes that turned out weaker than they looked. "Tovu runs `npm install && npm run build` on stranger-supplied source" is not a smaller version of that same problem moved to build time — it's the *same* problem: arbitrary code execution with no allowlist, just relocated from render-time (Option A, already rejected) to build-time. A `postinstall` script or a compromised transitive dependency has just as much access to the host as an SSR adapter would, and unlike SSR's output-is-a-string mitigation, a build step's entire job is to execute code — there's no "wall it off with regex" answer available afterward.

Codex specified real containment for this (`disposable OS process or container, no server credentials, no writable host filesystem beyond staging/output, strict CPU/memory/disk/time limits, constrained network access`), and that's the right spec *if* Tovu is going to run builds at all. But it is a **separate, standalone piece of security infrastructure** — the repo has zero of it today, and the closest analog it does have (a sanitizer for the much smaller trust surface of raw CSS, ADR-010) hasn't shipped either (per the packet's own correction bullet: "having not even shipped the CSS sanitizer ADR-010 asked for"). That's not a rhetorical point, it's the actual evidence I'm weighing: this team's track record on a strictly smaller, strictly better-understood trust surface is "not yet," and "code tier" would be asking for a *harder* one (process/container isolation with credential and filesystem containment, not string sanitization) to materialize as a side effect of shipping a theme-authoring feature. Gating the feature "behind" containment that doesn't exist yet, in a single release, means shipping without the gate in practice — the containment work will lose to the feature's own deadline pressure, the same way ADR-010 apparently has.

So: v1 ships with the build living outside Tovu's server entirely — the author's own machine, or the marketplace publisher's own CI, producing the versioned artifact the way `marketplace.ts`'s catalog/editable copy mechanism already expects to receive one. This does cost the in-product live-editing UX for source, and I'm not going to undersell that (see Strongest Counter-Argument below) — it's a real, named sacrifice, not a free win. If and when a genuinely audited, separately-shipped build sandbox exists — built, tested, and load-bearing on its own before any theme feature depends on it — Tovu-runs-build for self-hosted local rebuilds becomes the right v2, and I'd support Codex's spec for it at that point without changes.

## Remaining Disagreements

- **Against Codex's scoping, specifically:** Codex's R1 position folds "marketplace/publisher CI produces the artifact" and "a self-hosted installation must be able to rebuild locally, out of process" into one v1 design, both gated by the same containment spec. I'd split these — publisher-CI-produced artifacts need no new Tovu-side execution at all (Tovu just validates and accepts an artifact, which is #5's job, not a build sandbox), while self-hosted local rebuild is the piece that actually requires the unbuilt containment infrastructure. Bundling them makes the whole feature look blocked on one piece of work that's really only needed for the harder half.
- **Against reading "two classes" as a quality hierarchy:** Opus's R1 language for the compiled class ("opaque, versioned, replaced wholesale, editor-read-only") is correct for the *generated* tree but, read as a description of the whole class, understates that the *source* tree keeps full AI-authorability under my #2/#3 verdicts. I'd rather the split be described as which tree you're looking at, not which theme you're looking at.
- **Against treating Web Components as a general-purpose answer:** Gemini's R1 "why this is superior" framing (zero server changes, framework-agnostic, preserves AI-authorability) is true for islands and reads as broader than that in the writeup. I'm narrowing it to islands-only per #6, for the marker/shadow-DOM reason above, which Codex already flagged as a real weakness and I now think should be a hard scope boundary, not a noted cost.

## Strongest Counter-Argument

The strongest case against my build-lifecycle verdict is Codex's own point, and I don't think it fully dissolves: **restricting v1 to author-builds-locally may make this feature not worth building at all for the persona Opus's R1 blind-spot named** — "a site owner tweaking their own site through the admin editor," the same persona copy-not-inherit and per-file reset exist for in the first place. That persona's entire relationship to Tovu today is: open the in-admin editor, change something, see it live. Under my verdict, using a framework means leaving the product, running a toolchain, and re-uploading — which isn't a smaller version of today's UX, it's a **worse** one than `declarative`/`static` already deliver *without* a framework. If the real demand is coming from that persona rather than from professional marketplace developers who were always going to run their own build regardless of what Tovu does, then "author-builds-locally" isn't a responsible v1 — it's a v1 that ships to nobody who actually asked for it, and the honest move would be to say so rather than ship a feature scoped for a customer that doesn't exist. I don't have evidence either way on which persona is driving the request (Opus named this as an open question in R1 and it's still open); I'm holding my verdict because the security case for it stands on its own regardless of who's asking, but this is the argument most likely to actually change the recommendation, not just the sequencing.

## What Would Change My Mind

- **A build sandbox that ships as its own audited deliverable before the code tier depends on it** — concretely, a disposable-container build execution path with no server credentials, no writable host filesystem outside staging/output, and enforced CPU/memory/disk/network limits, tested and load-bearing on its own. At that point Tovu-runs-build (with self-hosted local rebuild specifically) becomes my v1 recommendation, not v2.
- **Evidence on who's actually asking**, resolving Opus's still-open persona question. If it's professional/marketplace authors who'd run their own build regardless, the Strongest Counter-Argument above loses its force and author-builds-locally stops being a controversial call at all. If it's the self-hosted site-owner persona, I'd want to revisit whether shipping v1 at all (versus the JSX-to-declarative-tier compiler I proposed in R1, which preserves live in-admin editing with zero build step) is the right answer before revisiting the lifecycle question.
- **A demonstrated, loud-fail conformance check** for #5 that reliably catches non-conforming bundler output in practice (not just in principle) would let me stop insisting the check must live in a wholly separate gate — if it's proven robust, it could reasonably move closer to `static-render.ts` without inheriting that file's blast-radius risk.
