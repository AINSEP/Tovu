## Position

The literal ask — "let theme authors build Tovu themes using React, Vue, or Angular" — does not require Tovu's server to execute React, Vue, or Angular at all. It requires a **compiler**, not a new runtime tier. My chosen design is **Option B and Option C treated as one design, not two**: authors write components in their framework of choice, a build step (the author's own toolchain, run on their machine or their own CI — not Tovu's server) compiles that source to the existing `static`-tier contract — `pages/*.html` documents, `css/styles.css`, `js/*.js`, `tokens.json` — with interactive pieces shipped as ordinary client-side JS that hydrates designated mount points. This is exactly how the mainstream "bring your own framework" static-site tooling already works (Astro, Next static export, Vue's `vite-ssg`), so it is not a novel mechanism Tovu has to invent, only a documented + tooled authoring convention layered on top of a tier that already ships **100% of real Tovu traffic** (F1) and needs **zero changes to `render.ts`, `pages.ts`, or any sandbox** to support it.

The reason I reject the other three options is not "less flexible" — it's that each one either (a) claims a security property it cannot actually deliver, or (b) is honest about giving up more constraints than it discloses. I lay that out in detail below, but the one-sentence version: the thing that makes `templated`/`handlebars` safe today is a **non-Turing-complete, AST-allowlisted DSL** running inside `worker_threads` used purely for *resource* isolation (CPU/memory), not *code* isolation. A React/Vue/Angular component is, by definition, arbitrary JavaScript/TypeScript with an arbitrary `npm` dependency graph — there is no equivalent allowlist for "a well-behaved subset of JavaScript," and `worker_threads` was explicitly *not* chosen for code-sandboxing in this codebase (the repo's own `liquid-sandbox.ts:18-20` rejects `vm2`/`isolated-vm` on CVE/native-dependency grounds and picks `worker_threads` specifically because Liquid is a restricted DSL it can pre-lint, not because `worker_threads` sandboxes arbitrary code — it doesn't; a worker thread can `require('fs')`, `require('child_process')`, or make network calls exactly as freely as the main thread, because it shares the same OS process). Options A and D both, in different ways, try to reuse a security story that was purpose-built for a DSL that admits allowlisting, against a target (real component-framework code) that structurally does not admit it.

## Option Assessment

**Option A — per-framework SSR adapters in `worker_threads`, rejected.** The packet frames this as "mirroring the templated/handlebars posture," but that posture has three load-bearing legs: (1) an AST-walked, load-time tag/filter allowlist (`liquid-allowlist.ts:44-143`, `handlebars-allowlist.ts` per the guide's §2.4) that rejects anything outside ~17 tags / ~68 filters; (2) a defensive re-lint immediately before render (`liquid-worker.ts:123-130`); (3) `worker_threads` isolation used for wall-clock/heap **resource** limits (`liquid-sandbox.ts:50-55`, `liquid-worker.ts:65-75`'s `memoryLimit`/`renderLimit`/`parseLimit`), not for code-execution containment. Leg (1) is what actually makes leg (3) safe to build on — you can *only* trust the worker with a restricted language because you already verified, statically, that the language it's about to run cannot do file/network/process I/O. There is no analogous static check for "this React component tree is safe" — JSX compiles to arbitrary function calls, an author's `import` statement can pull in anything on npm, and `fetch`/`fs`/`child_process` are one `require()` away inside the very worker Option A proposes to trust. Building this "properly" would mean inventing a real JS sandbox from scratch (think a WASM-hosted restricted JS engine with a hand-built capability surface) — a materially larger and riskier engineering bet than "one more tier like the last two," and exactly the kind of bet the codebase's own header comment in `liquid-sandbox.ts` shows this team is already wary of (rejecting `vm2` over sandbox-escape CVEs). Option A as stated oversells its own safety.

**Option D — trusted signed-plugin JS in-process, rejected as scoped.** This is the most *honest* option (it doesn't pretend to preserve C4), but the packet's own framing understates what else it gives up. Signature verification proves provenance, not safety — a signed artifact from a legitimately-compromised or merely buggy trusted author still executes with full privilege. More importantly: running it "in-process" with real capability means it can no longer be terminated the way `renderLiquidInSandbox` terminates a hung worker (`liquid-sandbox.ts:132-138`) — the file's own comment explains *why* a `Promise.race` around synchronous work doesn't help ("synchronous CPU-bound work on the main thread can't be pre-empted by a timer running on that same thread"). A hung or malicious in-process plugin therefore either hangs the *whole server process* (breaking C2, degrade-never-500, for every visitor, not just this theme's) or, if it's wrapped in its own worker to avoid that, it's back to Option A's problem (a worker with real Node capability is not meaningfully more contained than the main thread). So Option D quietly reopens **C2 and C3**, not just the C4 the packet names — a plugin bug takes down more than "one broken theme." That is a materially bigger blast radius than the packet's own framing discloses.

**Option B and Option C, accepted as one design.** Treating them as separate options (as the packet does) obscures that real theme authors want both static marketing pages *and* interactive widgets in the same theme — which is precisely what B (compile to static) plus C (hydrate islands) together provide, and neither alone does cleanly. Static-only output undersells "why would I use React for this" (you get JSX ergonomics but no interactivity); islands-only undersells the marketing-page reality (a `pages/pricing.html` doesn't need a client framework mounted just to be static prose). Combined, this needs **zero new server code paths, zero new sandbox, zero change to the route/render split (C7, F4), and zero change to the 7 live static themes (C8)** — it is entirely additive tooling on the author side.

## Failure Modes And Sacrifice

This is not a free win — three real costs, one of which I'd call the genuine sacrifice:

**The genuine sacrifice: no live, per-request dynamic component rendering.** `templated`/`handlebars` themes can do real per-request logic — `{% for product in products %}` reads *this request's* resolved data (`render.ts:1349-1377`'s `buildTemplateRenderData`). A compiled-to-static React page cannot: its JSX ran once, at the author's build time, against whatever data (or none) the build had. The only per-request dynamism this design gets is exactly what the *existing* static tier already gets — Tovu's own `data-embed-type="menu"/"widget"/"post"/"media"` resolvers splicing content into the static HTML at request time (guide §6.2–6.4). If the actual product need is "a React component that queries live posts and re-renders server-side on every hit," this design does not deliver that, and no option short of A/D would — that has to be said plainly rather than discovered later.

**Hidden cost: the mechanical-rewrite pipeline is literal-string/regex, not a DOM parser, and it is unusually brittle.** `renderStaticPage` injects design tokens by matching one exact literal string — `'<link rel="stylesheet" href="../css/styles.css" />'` (`static-render.ts:402-406`) — and rewrites asset paths by regexing the literal prefixes `../css/` and `../js/` (`static-render.ts:31-35`). If a bundler emits that tag with different quoting, attribute order, a hashed filename, or an inlined `<style>` block instead, the token-injection `.replace()` silently finds no match and just... doesn't inject tokens — no error, no warning, same silent-degrade failure class this codebase has already shipped twice (the `fuel` theme's un-embedded nav, guide §8.3; the dead `pages` manifest field, §8.6). The menu-embed substitution is explicitly described in the guide's own words as regexing "the whole `<tag ...>...</tag>` span" (guide:312) — again string-shaped, not tree-shaped. Any build tool an author picks has to be constrained to emit byte-compatible output, which means this design needs a companion `tovu theme verify` lint (or, longer-term, upgrading `static-render.ts` from string-replace to a real parser like `parse5`) — real, currently-unbudgeted work, and it touches the one code path serving 100% of live traffic (C8), which raises the regression stakes of touching it at all.

**Hidden cost: build-lifecycle ownership either breaks AI-authorability for source, or reintroduces an execution-trust problem in a different shape.** `theme_write_file` today is powerful because a write is a full-file overwrite immediately re-validated by the same deterministic, load-time validators every other write path uses (`agent-tools.ts:200-206`) — cheap, synchronous-ish, safe. If an agent edits a `.tsx` source file, nothing rebuilds `pages/*.html` from it — the write-then-validate loop simply doesn't apply to source under this design. Two ways to close that gap, both costly: (a) leave source author-only and let `theme_write_file` continue to only touch already-compiled output (C6 is preserved for output, quietly *dropped* for source — an agent can polish a shipped page but can't meaningfully co-author the component tree); or (b) have Tovu run the author's build (`npm install && npm run build`) itself, which does not avoid "executing someone else's code" — it just moves the execution from render-time (Option A's worry) to build-time and changes its shape to **software-supply-chain risk** (arbitrary `postinstall` scripts, a compromised transitive dependency) — a well-documented, high-frequency real-world attack class, arguably more dangerous in practice than an SSR sandbox escape, and one this repo has no machinery for at all today (it hasn't even shipped the CSS sanitizer ADR-010 called for on the *much smaller* trust surface of raw stylesheets — `theme.ts:145`, guide §8.4). I'd disclose this to the owner as a real fork in the road, not paper over it: self-hosted build (safe, but source becomes edit-locally-then-upload, a genuinely different authoring UX from every other tier) vs. Tovu-run build (keeps the UX, imports a new and currently-unmitigated risk class).

## What Would Change My Mind

- **Evidence the actual product need is live, per-request dynamic component rendering** (not build-time composition) — e.g. a concrete theme requirement like "inventory must reflect real-time stock inside a server-rendered React tree on every request." That would force reconsidering Option A, but even then I'd want a real audited JS-sandboxing investment (e.g., a WASM-hosted, capability-restricted JS engine, evaluated as its own spike) before endorsing "worker_threads + an adapter," because the latter's security claim doesn't hold up under the reasoning above.
- **Evidence the ask is narrower than it sounds** — e.g. "authors just want JSX-like ergonomics for composing our existing block vocabulary," not full framework runtime/ecosystem access. That would point toward the JSX→declarative compiler I describe below instead of B+C.
- **A working, tested, in-repo counter-example** showing `worker_threads` *can* safely contain arbitrary Node-capable code (i.e., that my read of `liquid-sandbox.ts:18-20`'s own reasoning is wrong, or that Node has since added an in-process capability-restriction primitive I'm not accounting for) — I'd want to see that verified against the same CVE-class the repo already rejected `vm2` for.
- **A committed decision to accept a materially different self-hostability shape** — e.g., the owner explicitly deciding a hosted build service is acceptable product surface (flagged per C1) — would reopen whether Tovu should own the build pipeline rather than leaving it to authors.

## Unlisted Option

**A JSX/Vue-SFC-syntax compiler targeting the `declarative` tier's JSON, not the `static` tier's HTML.** Instead of compiling to a complete `<!doctype html>` document, compile framework-shaped author syntax down to the `{"type":"doc","content":[...]}` block tree the `declarative` tier already consumes, referencing the exact same fixed `COMPONENTS` registry (`render.ts:1000-1013`: `tovu/site-header`, `tovu/hero`, `tovu/section`, `tovu/feature-grid`, `tovu/nav`, `tovu/cta`, `tovu/footer`, etc.). An author writes `<Hero title="..." actions={[...]} />`-shaped JSX; a small build step (or even a hand-rollable Babel/SFC-compiler plugin) emits the equivalent JSON node. This is strictly narrower than B+C — it only lets authors *compose Tovu's existing building blocks* with framework-familiar syntax, not ship arbitrary custom components or real interactivity — but it is also strictly *safer and cheaper*: it targets the tier the codebase itself already documents as the one with zero code-execution risk, installable from strangers with zero review (ADR-010, guide §2.2), fully implemented and tested today, just presently unused (F1: 1 theme, "reference only"). If what's actually driving the request is developer *familiarity* rather than a demand for arbitrary component capability, this is a better-shaped answer than either B+C or A/D, and it's cheap enough to prototype in isolation from this whole debate. I'd present both this and B+C to the owner rather than picking one blind, because they answer two different readings of the same sentence.

## Blind Spots

**(a) A viable option the packet failed to list:** richer built-in `COMPONENTS`/declarative vocabulary as the actual fix. "Authors want React/Vue/Angular" may really mean "authors want the visual/compositional flexibility that framework-based site builders are known for," not the frameworks themselves. Expanding the fixed 12-component registry (`render.ts:1000-1013`) with more layout primitives, section variants, and richer props could deliver that experience without any author ever touching JSX/SFC syntax or a build step at all — cheaper than every option in this packet, including my own recommendation, if the underlying complaint is really "our themes all look the same," not "I specifically want to author in React."

**(b) A question we should be asking but aren't:** *who* is "theme authors" here? The packet's own constraints pull in two different directions — C4 (installable from strangers, marketplace-shaped) implies professional/third-party developers who'd be perfectly happy to run `npm run build` locally and upload output; C6 (AI-authorability via `theme_write_file`, a live in-app file editor) implies a much less technical persona co-authoring with an agent inside the product itself. "Build themes using React" sounds like a request from the first persona; the packet's own emphasis on C6 suggests the second. The right design is genuinely different for each (B+C serves the first well and the second poorly, per the AI-authorability cost above), and the packet never resolves which one is actually asking.

**(c) The assumption most likely to be wrong:** that this is a *rendering/runtime* question at all — that "support React" implies "Tovu's server must run React somewhere in the request path." Every concrete fact in this packet points the other way: the pure route/render split (F4, `render.ts:1577` `renderSite()` takes resolved data and returns a string), the total absence of any framework runtime in `src/` today (F9 — only the *separate* admin SPA has React, and that's the CMS's own control panel, not theme rendering), and the fact that the tier carrying all real traffic (`static`) is defined precisely by having *no* runtime language to speak of (F5). Four of the five candidate designs in this packet (A, C partially, D, and even the "code" tier's own doc-comment framing at `theme.ts:30-34`) implicitly assume the answer belongs inside the request path. If that assumption is wrong — and I think it is — most of the engineering weight this packet is implicitly asking about (sandboxing strategy, per-framework adapters, worker isolation) is solving a problem the actual ask never had, and the real work is a compiler and an authoring contract, not a fifth theme tier.
