## Position And Movement

My position is **Host-Resolved Intent with Async Draft Middleware** (an evolution of the Option E / Option B camps). The package (`@jini-ai/chat`) must own the argument-aware trigger grammar, accessibility, and preview surface, but remain utterly ignorant of execution, tool catalogs, and confirmation state.

**Movement:** In Round 1, I viewed dispatch ownership as the main gap. The new requirements for arguments (N1) and whole-draft destruction permanently alter the equation. The trigger grammar (`^\/([^\s/]*)$`) and the synchronous draft replacement (`replaceComposerSlashTrigger(draft, "")`) are fatally coupled. The moment we accept arguments, the package can no longer blindly mutate the draft synchronously on selection, because it does not know if the host will successfully execute the command or abort via confirmation. The package must yield control of draft mutation to the host's asynchronous response. 

## Solution Slate

**Option 1: The Tokenized AST & Package-Owned Execution (The "Rich Shell" approach)**
- **Concept:** The package builds a full tokenizer for the composer. `/command arg` is parsed into an AST. The package executes the command directly by importing a standardized agent-transport library and managing its own confirmation modals.
- **Trade-offs:** Provides a rich, terminal-like experience out of the box with syntax highlighting.
- **Sacrifice:** Utterly violates N4 and C1 (package neutrality). The package becomes permanently coupled to a specific execution backend, permission model, and host taxonomy.
- **Falsification test:** Attempt to mount the composer in a lightweight support-chat host that has no agent backend; the package would drag in massive unused dependencies and fail to compile or run.

**Option 2: Host-Resolved Intent with Async Draft Middleware (Recommended)**
- **Concept:** The package expands the trigger grammar to capture arguments. On selection, the package freezes the draft, transitions to an executing state, and yields the `{ item, args }` payload to the host's `onDiscoverySelect` promise. The host executes the action (including managing the two-phase `PendingConfirmationStore` UI) and returns a draft-mutation directive.
- **Trade-offs:** Maintains strict package neutrality, solves the draft-destruction bug, and natively handles confirmation sequences without package involvement.
- **Sacrifice:** The package can no longer guarantee the "instant" feel of a text macro if the host implementation introduces latency. The host must explicitly return a mutation directive (or the package gracefully falls back) even for trivial macros.
- **Falsification test:** Write a command that opens a modal confirmation. If the draft vanishes before the modal opens, or if cancelling the modal leaves the user with an empty draft, the async-draft contract is broken.

**2. The Trigger Grammar (`files/jini/composer-discovery.ts`)**
```typescript
export interface ComposerSlashQuery {
  command: string;
  args: string;
  hasSpace: boolean;
}

/** Matches `/command` or `/command args...`. */
export function parseComposerSlashQuery(draft: string): ComposerSlashQuery | null {
  if (!draft.startsWith('/')) return null;
  const match = draft.match(/^\/([^\s/]+)(?:\s+(.*))?$/);
  
  if (!match) {
    return draft === '/' ? { command: '', args: '', hasSpace: false } : null;
  }
  return {
    command: match[1],
    args: match[2] ?? '',
    hasSpace: draft.includes(' '),
  };
}

export function filterComposerDiscovery(
  groups: readonly ComposerDiscoveryGroup[],
  query: ComposerSlashQuery,
): ComposerDiscoveryMatch[] {
  const normalizedCommand = query.command.toLowerCase();
  const matches: ComposerDiscoveryMatch[] = [];

  for (const group of groups) {
    for (const item of group.items) {
      // Normalize item label to support triggers like "/mcp" or "Word Count"
      const itemCommand = item.label.startsWith('/') 
        ? item.label.slice(1).toLowerCase() 
        : item.label.replace(/\s+/g, '-').toLowerCase();

      if (query.hasSpace) {
        // N1: Argument-aware lockstep. Filter isolates the single active command.
        if (item.acceptsArguments && itemCommand === normalizedCommand) {
          matches.push({ groupId: group.id, groupLabel: group.label, item });
        }
      } else {
        const searchable = [itemCommand, item.description, item.kind, ...(item.keywords ?? [])]
          .filter((value): value is string => typeof value === 'string')
          .join(' ')
          .toLowerCase();
        if (normalizedCommand === '' || searchable.includes(normalizedCommand)) {
          matches.push({ groupId: group.id, groupLabel: group.label, item });
        }
      }
    }
  }
  return matches;
}

/** Draft is strictly replaced via host directive; fallback macro replacement is safe via query state. */
export function replaceComposerSlashTrigger(draft: string, insertText: string): string {
  return draft.startsWith('/') ? insertText : draft;
}
```

## Strongest Counter-Argument

The strongest counter-argument against this async-middleware approach is that it forces the host to explicitly own the return value for draft-clearing, adding boilerplate for simple macros, and it risks locking the composer input (during `executing: true`) if a host handler hangs indefinitely without rejecting the promise.

## What Would Change My Mind

If telemetry revealed that users frequently chain multiple slash commands inside a single draft text block (`Hello /command1 and /command2`), then whole-draft assumptions shatter. I would immediately abandon this design and pivot to a token-range AST parser, accepting the C1 penalty to allow partial inline execution.
