## Position

The registry-ownership question (open Q2) is already answered by the code and isn't where the real design gap is. `TOVU_COMPOSER_DISCOVERY_GROUPS` lives entirely in `files/tovu/agent-plugin-catalog.ts:42-99`, is typed only against the package's `ComposerDiscoveryGroup` (`files/jini/slots.ts:92-96`), and the package never imports Tovu. That's a clean, working host-owned registry, and C1 is already honored. Don't spend debate energy re-deciding it.

The real gap — and the thing that should drive the choice among A/B/C/D — is that **one real execution effect has already leaked into this "text-macro-only" system, through the side door, and it exposes a type-contract bug rather than a missing mechanism.** `agent-plugin-catalog.ts:86-98` wires `mcp:settings` with `insertText: ""`, and `AssistantDock.tsx:270-273`'s `handleComposerDiscoverySelect` calls `navigate("/settings?tab=external-mcp")` off `slots.onDiscoverySelect`. So today, selecting `/mcp` already **executes** something client-side — Option B already exists and already ships. But because `ComposerDiscoveryItem` has no way to say "this item has no text outcome," `replaceComposerSlashTrigger(draft, "")` (`composer-discovery.ts:38-40`) runs anyway and silently blanks the draft (`Composer.tsx:95`: `match.item.insertText ?? match.item.label` — `??` doesn't catch `""`, so the empty string wins). That's not a hypothetical; it's the one live non-macro command in the repo, and it's already misbehaving in a small, specific way.

My position: **B (client-side command dispatch), narrowed to fixing that contract gap, not building new machinery.** Reject C for this phase on architectural grounds, not just maturity grounds. Reject D as framed — it either collapses into B or violates C1.

## Option Assessment

**A — text macro only.** Already insufficient as a description of the current system: `/mcp` already does more than insert text (F1's own claim — "the entire outcome... is: the draft becomes some text" — is contradicted by `AssistantDock.tsx:270-273`). A stays relevant only as the *default* behavior for items that genuinely are just a canned phrase (e.g. `agent-plugin:ui-ux-design`, `insertText: "UI/UX Design agent plugin"` at `agent-plugin-catalog.ts:67`) — but it is not "the design," it's one case of a design that needs a second case.

**B — client-side command dispatch.** Already the load-bearing mechanism (`onDiscoverySelect`, `slots.ts:124`, is literally typed `(selection) => void | Promise<void>` — an effect slot, not a notification slot, despite F2 calling it "currently used only for notification"). The fix isn't adding dispatch, it's letting an item opt out of the forced draft mutation that currently runs unconditionally in `selectSlashItem` (`Composer.tsx:92-99`) and `selectPlusItem` (`Composer.tsx:101-106`) before the host effect ever fires. That's a small, backward-compatible type change (e.g. items default to macro behavior when `insertText` is a non-empty string; an item can declare it has no draft outcome at all), not a new subsystem.

**C — server/agent tool invocation.** Reject for this phase, and reject the framing, not just the timing. Per `AssistantDock.tsx:114-119`'s own doc comment: "Tool execution is not a prop here — it happens server-side: the spawned coding-agent CLI gets `.mcp.json`-injected access to Tovu's registered tools... and calls them through the daemon's `/api/delegated-tool-calls` gate." There is no entry point anywhere in the staged files for the *UI* to directly trigger a tool call — every tool call in this system originates from the agent CLI's own reasoning, not from a user click. Option C's own phrasing ("selecting builds a structured tool call executed through the existing tool pipeline") describes a pipeline that doesn't exist in this direction. Building it means either (a) fabricating a synthetic `tool_use` that bypasses the agent's own decision loop — a materially new, security-relevant capability requiring its own consent model (see Blind Spot a) — or (b) just sending the agent a prompt asking it to use the tool, which is Option A wearing a costume. C3 ("command execution has to work in that [CLI] model") is usually read as a constraint C needs to satisfy; I'd read it the opposite way — it's evidence C's premise doesn't fit this architecture at all right now.

**D — hybrid with declared command kind.** Collapses into one of the other two depending on who evaluates the kind. If the *package* switches on `kind: 'macro'|'client'|'tool'` and, say, auto-builds a tool call for `'tool'`, the package now has to know what a tool call is and how to reach the transport — that's exactly the host-concept leakage C1 forbids, and it contradicts a design law already written into this codebase: `slots.ts:77-80` — "`kind` is intentionally an open string: Jini filters and renders the value but never switches on a host-owned taxonomy such as `'plugin'` or `'skill'`." If instead the *host* switches on kind internally, that's just B with an extra label. D isn't a fourth option; it's A/B relabeled or a C1 violation depending on where the switch statement lives.

**E — something else.** See Unlisted Option.

## Failure Modes And Sacrifice

- `Composer.tsx:89` — `void slots?.onDiscoverySelect?.({ item, source });` explicitly discards the promise. Today this is harmless because the only wired effect (`navigate`) can't meaningfully fail. The moment any host wires a fallible async effect into this seam — which is the whole point of formalizing B — a thrown/rejected handler vanishes with no user-visible failure at all. This has to be fixed before B is "the design," not treated as a later polish pass.
- The `insertText: ""` bug (cited above) is a second, narrower instance of the same root cause: the type can't express "no text outcome." Fixing draft-mutation opt-out fixes both at once.
- Real sacrifice: this position explicitly does **not** give Agent Plugins (C5) real command execution. A plugin-contributed slash command under this design can navigate, open a panel, or run some client-only effect — it cannot invoke a tool, run agent work, or do anything requiring new consent, because I'm rejecting C's premise for this phase. If Agent Plugins' actual ask turns out to be "let a plugin run a tool from the palette," this position defers that indefinitely rather than half-building it now.
- Second sacrifice: no argument grammar. `parseComposerSlashQuery`'s regex (`composer-discovery.ts:11`) rejects any whitespace outright, and nothing in this position touches that. Any command needing a parameter has to open its own follow-up UI (a dialog, a second prompt) rather than accept `/command arg`. That's a real UX ceiling I'm accepting rather than solving.

## What Would Change My Mind

Two concrete things. First, if the Agent Plugins debate (C5) lands on a design where plugin trust is closed the same way the *current* catalog closes it — bundled-with-Tovu, source-vetted, not dynamically installed (`agent-plugin-catalog.ts:18-19`: `"Bundled with Tovu — catalogued, not executed"`) — then the security objection to C mostly evaporates, because the trust boundary is "ships in the Tovu repo," not "arbitrary user-installed code," and I'd reconsider a narrow, explicitly-gated tool-invocation path modeled on the MCP-UI confirmation flow rather than rejecting C outright. Second, if there's real evidence (not speculation) that users are typing `/command argument` and hitting the dead end of the regex rejecting the whole token — that's a signal the macro/dispatch question is secondary to fixing the trigger grammar first, and I'd reorder the priority.

## Unlisted Option

Not a sixth letter — a reframe of B: **reuse the slot-injection pattern this exact file already uses twice**, rather than inventing new "command execution" machinery under the letter C. `AssistantDock.tsx:71-73` (`registerMcpUiSurfaceRenderer({ onToolCall: createMcpUiToolCaller(...) })`) and `AssistantDock.tsx:90-91` (`registerExtEventRenderer("a2ui", ... onAgentAction={postA2uiAction})`) are both instances of "package renders/owns the UI and keyboard model, host supplies the actual network call as one injected function." That's precisely the shape a future tool-invoking slash command should take *if it's ever built*: the package doesn't grow tool-call knowledge, it takes one more optional injected caller function, exactly like it already does for MCP-UI and A2UI. This means C, if it's ever justified, doesn't need a new architectural pattern invented — it needs this one applied a third time. I'd rather name that now than have someone re-derive it as a "novel" design later.

## Blind Spots

**(a) A viable option this packet didn't list:** confirmation-gated commands. Tovu has already built, in this exact file, a full consent-before-execute pattern for consequential actions — `PendingConfirmationStore` plus the redemption route (`AssistantDock.tsx:53-64`), used when an MCP-UI dialog's "Delete" needs a real human click before anything happens server-side. None of A/B/C/D/E has a notion of "selecting this doesn't execute — it opens a confirmation step." If any slash command is ever destructive or consequential (e.g., a hypothetical `/reset-workspace`), it needs this two-phase shape, and neither `ComposerDiscoveryItem` nor the select handlers have anywhere to put it today.

**(b) A question we should be asking:** not "what does a command do on select" (the packet's framing) but **when** an item's effect fires relative to the compose→send lifecycle, and whether that timing is declared per item or hardcoded per host. Today there are already two different timing models sharing one contract with no declared rule distinguishing them: draft-mutating items are edit-then-send (the user can still change their mind before hitting Send), while `/mcp`'s navigate fires instantly on select, before Send is ever pressed, with no way to undo it. Nothing in `ComposerDiscoveryItem` says which behavior a given item gets — it's implicit in what the host's `onDiscoverySelect` happens to do for that item's id. That's a bigger architectural question than "text vs. tool," and it's currently answered by accident.

**(c) The framing assumption most likely wrong:** that registry ownership (Q2) is the crux tension needing debate. The evidence says it's already solved — cleanly, host-owned, C1-compliant, uncontested by any of the staged files. Spending the debate's energy re-litigating "package-owned vs. host-owned vs. contributed registry" risks missing that the actual unresolved problem is narrower and already half-built: the `ComposerDiscoveryItem` type can't express "no text outcome" or "needs confirmation," and that gap is what produced the one concrete bug in the system (`insertText: ""` blanking the draft). A debate that resolves registry ownership but leaves that contract gap untouched will have solved the easy 90% and left the actual paused-work blocker exactly where it is.
