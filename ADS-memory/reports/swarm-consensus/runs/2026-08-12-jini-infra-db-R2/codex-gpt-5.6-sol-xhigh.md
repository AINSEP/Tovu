## D1. Dual dialects

I recommend strategy (b): a small Tovu-owned schema IR, not 63 hand-maintained twins.

```ts
type Scalar =
  | { kind: "id"; representation: "text" }
  | { kind: "int"; bits: 32 | 64; generated?: "identity" }
  | { kind: "bool" }
  | { kind: "json" }
  | { kind: "instant"; precision: 3 }
  | { kind: "localDateTime" }
  | { kind: "text"; collation: "binary" | "unicode-ci" }
  | { kind: "bytes" };

interface TableSpec {
  name: string;
  scope: "global" | "workspace";
  columns: Record<string, {
    type: Scalar;
    nullable?: boolean;
    default?: Literal;
  }>;
  primaryKey: string[];
  indexes: IndexSpec[];
  checks: Expr[];             // typed AST, never SQL strings
}

interface SearchSpec {
  projectionTable: string;
  sourceTable: string;
  fields: Array<{ name: string; weight: number }>;
  tokenizer: "english-stemmed" | "unicode";
}

interface LogicalMigration {
  id: `${number}_${string}`;
  operations: SchemaOp[];
  verify: Invariant[];
}

emitDrizzleSchema(schema, "sqlite"): GeneratedSource;
emitDrizzleSchema(schema, "postgres"): GeneratedSource;
compileMigration(migration, "sqlite" | "postgres"): DdlPlan;
```

`schema.ts` already admits that FTS5 cannot be represented by its SQLite Drizzle declarations, and keeps it in custom migration 0022 ([schema.ts](/Users/la/Programming/Tovu/src/db/schema.ts:15), [0022 migration](/Users/la/Programming/Tovu/src/db/drizzle/0022_posts_fts_search_index.sql:54)). The new IR makes search a first-class logical projection and emits FTS5 plus triggers for SQLite, versus a `tsvector` projection, GIN index, and PostgreSQL maintenance trigger.

Keep migrations `0000–0034` immutable for existing SQLite installations. After Drizzle verifies that legacy head, bootstrap `_tovu_schema_migrations` at `0034`. PostgreSQL begins from a generated `0034` baseline. Migration `0035+` is authored once as `SchemaOp[]` and compiled twice. SQLite’s compiler performs unsupported changes by create/copy/drop/rename inside a write freeze, with pre-snapshot, FK revalidation, and index/trigger recreation. PostgreSQL takes an advisory lock and executes ordinary DDL and verification in one transaction. Nontransactional operations such as `CREATE INDEX CONCURRENTLY` require an explicitly journaled multi-phase operation; they cannot silently appear in an atomic migration.

Mappings that need explicit codecs:

- Text UUID-like IDs stay `TEXT`/PostgreSQL `text` initially; changing them to `uuid` would reject legacy or plugin IDs.
- Generated integer keys become SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` and PostgreSQL `bigint GENERATED BY DEFAULT AS IDENTITY`; imports must reseed identities.
- Boolean becomes checked `INTEGER 0/1` versus `boolean`.
- JSON becomes validated canonical JSON text versus `jsonb`; checksums operate on canonical parsed JSON, not bytes.
- `instant` becomes UTC ISO text versus `timestamptz`; offset-less values are rejected. `localDateTime` uses `timestamp without time zone`.
- `BLOB` becomes `bytea`.
- SQLite FTS5 `porter unicode61` is not ranking-equivalent to PostgreSQL `english` `tsvector`.
- Identifier comparisons use SQLite `BINARY` and PostgreSQL `COLLATE "C"`; case-insensitive keys get explicit normalized columns rather than ambient database collation.

CI runs codegen and requires a clean diff, creates both databases from scratch, introspects them into normalized `TableSpec` form, and requires equality to the canonical manifest. It also upgrades previous-release fixtures and runs every repository/search contract against both engines. The first check proves structural non-drift; the contracts prove only the documented behavioral equivalence, not identical FTS ranking.

This design does **not** depend on resolving Drizzle’s nominal-type collision. Generated schemas, helpers, and adapters remain in Tovu. Jini ports expose plain interfaces, values, and row streams, following the current structural `DbOpsPort` boundary ([ports.ts](/Users/la/Programming/Jini/packages/infra/src/db/core/ports.ts:49)). Still run the decisive `pnpm pack` consumer fixture; a green result may permit later helper extraction, but cannot be a release prerequisite.

## D2. Live SQLite → PostgreSQL

```ts
prepareTransfer(input: {
  source: SqliteRef;
  target: PostgresRef;
  instanceSchema: string;
  workspaceIds: string[] | "all";
}): Promise<TransferRun>;

copySnapshot(runId: string): AsyncIterable<BatchReceipt>;
replayChanges(runId: string, throughSeq?: bigint): Promise<DeltaReceipt>;
verifyTransfer(runId: string): Promise<VerificationReport>;
approveCutover(input: {
  runId: string;
  planHash: string;
  reportHash: string;
  cutoffSeq: bigint;
}): Promise<ApprovalToken>;
cutover(runId: string, approval: ApprovalToken): Promise<CutoverReceipt>;
```

Flow:

1. Provision `tovu_i_<instanceId>` plus a role restricted to that PostgreSQL schema. Lock core migrations and plugin activation for the run.
2. Enable deterministic change-log triggers recording table, operation, stable key, and sequence; then take the existing WAL-safe online backup. Tables without stable keys force full write downtime.
3. Apply the official PostgreSQL baseline, activate every installed plugin declaration, then bulk-copy the snapshot in dependency order while the site remains writable.
4. Replay keyed changes idempotently. Freeze writes briefly, record cutoff sequence, drain through it, and validate row counts, canonical per-key hashes, constraints, workspace ownership, and sampled repository reads.
5. Human approves the exact cutoff and routing change. Switch configuration, boot PostgreSQL read-only for health checks, then enable writes. Retain SQLite read-only until the retention deadline.

`__drizzle_migrations` is never copied. It remains legacy evidence in SQLite; PostgreSQL records its own official baseline and subsequent `_tovu_schema_migrations`.

FTS5 tables and shadow state are never transferred. Copy or regenerate `post_search_document`, then build PostgreSQL `tsvector`/GIN state and test query acceptance. The current projection is intentionally separate from source posts ([0022 migration](/Users/la/Programming/Tovu/src/db/drizzle/0022_posts_fts_search_index.sql:14)).

Every transferred row retains its `workspaceId`; selection is an approved allowlist, never agent inference. Core media tables contain storage keys and hashes rather than payload bytes ([schema.ts](/Users/la/Programming/Tovu/src/db/schema.ts:1140)); blobs move through storage ports, stream-hash verified by SHA-256. Plugin `BLOB` columns stream as `bytea`.

For tables absent from `schema.ts`, inventory both transitional `p_*` and final `plgn_*` names, require a matching installed declaration/provenance fingerprint, create them through the PostgreSQL data-module engine, and copy them generically. Unknown or orphaned plugin tables block cutover. Snapshot paths, plugin DDL journals, and migration control rows are reconstructed, not copied.

## D3. Plugin-declared PostgreSQL tables

The present grammar exposes SQLite storage classes and skips an existing table without comparing its columns ([data-module.ts](/Users/la/Programming/Tovu/src/features/plugins/data-module.ts:70), [reconciliation](/Users/la/Programming/Tovu/src/features/plugins/data-module.ts:213)). Replace it with:

```ts
interface DataModuleDeclV2 {
  pluginId: string;
  schemaVersion: number;
  tables: LogicalPluginTable[]; // logical types, key, scope, indexes
  provenance: PluginProvenance;
}

interface PluginSchemaExecutor {
  inspect(pluginId: string): Promise<InstalledManifest>;
  plan(decl: DataModuleDeclV2): Promise<SchemaPlan>;
  apply(plan: SchemaPlan): Promise<{ planHash: string; committed: boolean }>;
}
```

Plugins remain dialect-blind. Tovu core owns namespace validation, desired-state comparison, and SQLite/PostgreSQL compilers; Jini supplies transaction, introspection, locking, and connection mechanics.

SQLite keeps whole-file snapshot and boot restore. PostgreSQL uses a transaction-scoped advisory lock and transactional DDL; a server crash causes PostgreSQL itself to roll back. The Tovu-owned journal stores `strategy: "file-snapshot" | "transactional-ddl"` and nullable `recoveryRef`, rather than mandatory `snapshot_path`, which is currently file-specific ([migration-journal.ts](/Users/la/Programming/Tovu/src/features/plugins/migration-journal.ts:26)). V1 plugin declarations prohibit nontransactional PostgreSQL DDL, so no `pg_dump` is required for routine plugin activation.

## D4. First-party and agent plugins

The first-party transfer plugin owns connectors, manifests, checkpoints, correspondence records, staging, execution, reconciliation, and its `plgn_transfer__*` tables. The agent plugin is a stateless typed facade:

```ts
source_profile({ sourceRef, sampleLimit }): SourceProfile;
target_contract({ targetInstance, workspaceId }): TargetContract;
plan_submit({ sourceFingerprint, targetContractVersion, mapping }): PlanValidation;
dry_run({ planHash }): DryRunReport;
approval_request({ planHash, reportHash, operation: "execute" | "cutover" }): ApprovalStatus;
run_start({ planHash, approvalId }): RunReceipt;
run_status({ runId }): RunStatus;
run_pause({ runId }): RunStatus;
run_resume({ runId }): RunStatus;
run_verify({ runId }): VerificationReport;
cutover_request({ runId, reportHash, cutoffSeq }): ApprovalStatus;
```

The agent literally receives bounded, injection-wrapped JSON: table/column metadata, counts, redacted samples, anomalies, target entity JSON Schemas, and allowed named transforms. It returns `MappingPlanV1` JSON containing selectors, target entities/fields, transform IDs and arguments, conflict policies, and exclusions. The schema rejects SQL, JavaScript, templates, and unknown transforms. Deterministic code compiles that plan into domain ingestion calls for WordPress imports, or fixed-schema bulk operations for backend transfer.

Approval binds the canonical plan hash, source fingerprint, target instance/schema/workspaces, exclusions, conflict/delete policy, identity/password handling, media scope, plugin inventory, estimated rows/bytes, dry-run report hash, and maintenance/rollback boundary. Execution and cutover are separate approvals; any bound change invalidates approval.

## D7. Bugs in this design

1. A plugin activates after change capture inventory: its table and writes vanish from the target. Trigger: activation lock missing; symptom: successful counts omit the table.
2. A plugin table has no stable key: update/delete replay cannot identify rows. Symptom: duplicates or undeleted target rows; live transfer must block.
3. `jsonb` changes key order and numeric formatting: raw hashes fail despite equal data. Canonical semantic hashing is mandatory.
4. An offset-less timestamp is interpreted in the migration host’s timezone. Symptom: scheduled content shifts hours; reject rather than guess.
5. Identity reseeding is omitted after preserving imported IDs. Symptom: first new PostgreSQL insert hits a duplicate key.
6. PostgreSQL writes begin and an application defect appears. SQLite rollback now loses new writes; cutover must state this irreversible boundary explicitly.
7. A pooled connection leaks or loses `search_path`. Symptom: one Tovu instance queries another schema or “table not found.” Use schema-qualified SQL plus per-instance roles, never session-only `SET search_path`.
8. FTS5 and `tsvector` return different orderings. Symptom: brittle parity tests fail or users see changed ranking; contract exact inclusion/filtering, not identical rank.
9. Prefix migration scans only `plgn_*`. Symptom: legacy `p_*` tables are silently abandoned; inventory both until an explicit compatibility cutoff.

## Ranked slate

Criteria: semantic parity, safe upgrades, drift prevention, solo-maintainer cost, and Supabase operability.

1. **Tovu schema IR + generated dialect schemas — recommended.** Highest up-front compiler cost, but one definition, paired migrations, inspectable drift proof, and room for MySQL.
2. **Hand-maintained `sqliteTable`/`pgTable` twins plus paired migration review.** Fastest initial PostgreSQL demo, but permanent 63-table review burden and weakest drift defense.
3. **Replace Drizzle with a dialect-neutral ORM/schema tool.** Avoids codegen ownership but forces a broad repository rewrite while still not eliminating FTS, DDL, timestamp, or collation differences.

The cheapest decisive test is a three-table vertical slice—`posts` with JSON/boolean/checks, `post_search_document` with search, and one plugin table—generated and migrated on both engines, round-tripped with hostile timestamp/JSON/blob fixtures, then normalized and compared.

I would change my mind toward twins if that slice shows the IR/compiler becoming a second ORM or cannot express existing checks without raw escape hatches. I would postpone MySQL-target work if PostgreSQL production conformance exposes substantially more adapter divergence than the schema inventory predicts. A successful packed-consumer experiment would change only where reusable Drizzle helpers may live, not the Tovu/Jini ownership boundary.
