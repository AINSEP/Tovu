### 2. Changes from Round 1 and Influential Arguments

My position has changed on all four points after reviewing the peer and Coordinator arguments:

*   **A (`src/` → `render/`):** I yield my Round 1 `src/` position to **Codex's argument** (adopted by the Coordinator). I originally argued `src/` was universally understood. However, Codex correctly pointed out that `src/` is an "everything bucket" in modern frameworks. A component-tier author will instinctively put `src/utils/`, `src/styles/`, or `src/assets/` in it, muddying the strict separation of `scripts/`, `css/`, and `assets/` that we all agreed upon. `render/` establishes a precise, unambiguous boundary: *only* what the renderer adapter interprets lives here.
*   **B (`data-agent-element` → `data-tovu-agent`):** I yield to **Codex and the Coordinator**. My Round 1 argument was based on DRY principles (one resolver for both layers). But the security argument is paramount: `data-agent-element` implies trusted, authenticated single-tenant admin operability. Reusing it for multi-tenant, untrusted third-party visitor-facing markup is a dangerous conflation of trust boundaries. A distinct namespace (`data-tovu-agent`) cleanly separates these scopes to avoid future privilege-escalation bugs.
*   **C (`entrypoints.slots` → `partials`):** I yield to **Fable**. Fable correctly observed that "slot" collides terribly with component framework semantics (Vue, Svelte, Web Components), where slots receive content *from* the parent rather than resolving a *named shared unit* from the theme. Renaming it to `partials` avoids this collision and perfectly aligns with the `partial` type in the newly revealed 6-type embed system.
*   **D (`ai/instructions.md` → `AGENTS.md`):** I yield to **Fable and Codex**. I previously argued for grouping all machine-readable context to avoid root pollution. But Fable correctly distinguished the audience and lifecycle: `ai/` is for the *published site's* runtime AI capabilities, while `AGENTS.md` is for *dev-time* coding agents editing the source. `AGENTS.md` at the root is an existing cross-tool industry convention, making discovery automatic.

### 3. Steelmanning the Opposing Sides (The Strongest Arguments Against My Current Positions)

*   **Against `render/` (Steelman for `src/`):** Ecosystem friction. Every modern JS framework (Next.js, Vite, Astro) defaults to `src/`. Forcing a framework tier author to configure their bundler to use `render/` instead of `src/` adds immediate friction and goes against established muscle memory. `src/` with a strict linter could theoretically enforce the boundary without the config overhead.
*   **Against `data-tovu-agent` (Steelman for `data-agent-element`):** Maintainability and toolchain duplication. The host must now maintain two parsers, two registries, and two attribute injection helpers. If the admin UI and the visitor UI ever share a capability (e.g., "trigger global search"), the theme has to map two different attributes to the exact same underlying action, which is fragile.
*   **Against `partials` (Steelman for `slots`):** The new ground truth states the manifest field `slots` is *already wired and read at render time*. Renaming it to `partials` introduces a breaking change requiring migration tooling. Furthermore, the 6-type embed system includes `partial`, `menu`, `widget`, `form`, `media`, and `post`. If the manifest field is named `partials`, it only accounts for one of the six embed types. The term `slots` acts as a generic bucket for *all* embed injection points, not just partials.
*   **Against `AGENTS.md` (Steelman for `ai/instructions.md`):** Theme roots are already crowded (`theme.json`, `tokens.json`, `package.json`, `NOTICE.md`, `LICENSE`). Co-locating *all* AI-related files under `ai/` ensures that a theme consumer (or marketplace platform) can strip a single directory to remove all AI surface area entirely, rather than having to hunt down `AGENTS.md` and `ai/` separately.

### 5. Ranked Solution Slate: Render-Layer Source Folder (Question A)

**Criteria for Ranking:**
1.  **Ambiguity / Boundary Protection:** How likely is an author to place non-render files (CSS, utilities, global scripts) here?
2.  **Tier Compatibility:** Does the name accurately describe the contents across all existing/planned tiers?
3.  **Friction:** How much configuration is required to make standard tooling work with it?

**Option 1: `render/` (with `pages/`, `partials/`, and `components/` interiors) — [RECOMMENDED]**
*   **Trade-offs:** High precision, low ambiguity. Component-framework authors will need to slightly adjust default bundler configs (e.g., Vite/TS aliases) to point to `render/` instead of `src/`.
*   **Why it wins:** It strictly enforces the "only what the adapter interprets" rule. It definitively solves the overlap with `css/`, `scripts/`, and `assets/`. When an agent or human looks at `render/`, they know it contains exclusively view-layer outputs.

**Option 2: `src/` (with `pages/`, `partials/`, and `components/` interiors)**
*   **Trade-offs:** Zero ecosystem friction. Every framework expects it. However, it *highly* attracts non-render files. Authors will instinctively put `src/styles.css` or `src/utils.ts` in it, which breaks the invariant structure. Requires heavy linting to enforce the boundary.
*   **Why it's ranked second:** It's structurally sound and developer-friendly, but relies entirely on documentation and active linting to fight developer muscle memory.

**Option 3: `templates/` (with `pages/` and `partials/`)**
*   **Trade-offs:** Accurate for `templated` and `declarative`, but factually incorrect for `static` (they are full HTML pages, not templates) and the component-framework tier (they are executable components, not templates).
*   **Why it's ranked last:** It fails the tier-compatibility test completely and will confuse authors writing TSX/Svelte components.

### 6. Incorporating New Ground Truth (Final Proposal Adjustments)

The new ground truth drastically tightens the required schema and clarifies the implementation details:

1.  **The 5-value `ThemeTier`:** The schema must explicitly type `tier` as `"declarative" | "templated" | "handlebars" | "static" | "code"`. `handlebars` is fully built and tested, making it a first-class citizen. `code` is explicitly reserved for trusted JS plugins, keeping it wholly distinct from the unbuilt component-framework tier (the 6th concept).
2.  **Wired Fields (`slots`, `modes`, `defaultMode`) & The `regions` Field:** Because `regions` is fully implemented and tested for widget placement, our schema *must not drop it*. `modes` and `defaultMode` must also be preserved structurally. While `slots` is wired, it must be mechanically migrated to `partials` to avoid the Vue/Svelte collision, leaving `regions` intact to handle dynamic widget placements.
3.  **The 6-type Embed System:** The embed mechanism is definitively **one attribute**: `data-embed-config`. It carries a JSON blob (e.g., `{"type":"partial","id":"nav","current":"signin"}`). The fact that `partial` is just one of 6 types (`menu`, `widget`, `form`, `media`, `post`) validates that generalizing this as a logical request with an id + params is the correct architectural path.
4.  **`theme_write_file` Hot-Reload in `AGENTS.md`:** The `AGENTS.md` file should explicitly inform coding agents that they can use the `theme_write_file` tool to hot-reload edits instantly. Knowing that no full server restart is required will drastically speed up an agent's dev-time reconciliation loops.
5.  **Documentation Discipline:** The two-artifact split (human guide + machine spec) will strictly follow the proven `theme-authoring-guide.md` pattern: two-table field splits ("read vs. dead"), path:line verified citations, explicit gotchas, and a minimal worked example.
