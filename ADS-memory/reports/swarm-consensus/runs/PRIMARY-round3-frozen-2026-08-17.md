# Primary (Claude Opus 5, host) — Round 3 frozen position

Frozen before dispatching or reading any Round 3 peer response. Scope: correcting Decisions 5 (build output) and 13 (tier taxonomy) against the real, shipped `ADR-020 §5` architecture, and working out how it interacts with everything else Round 1/2 already converged on.

## Position

**No new tier. `build.source: "compiled"` stays gated to `tier: "static"`, exactly as shipped.** The gate isn't an artificial constraint to relax — it's correct by construction: whatever framework produced the output (React/Vue/Angular/Svelte/Astro), the OUTPUT itself is static HTML/CSS/JS once built. There is no server-executing "framework tier" to invent because nothing framework-specific survives to runtime. `build.framework` stays purely descriptive (editor/marketplace UI only), never branched on.

**The `sourceDir`/generated-tree split resolves the render/css/scripts/assets question cleanly, and I think it's the right design:** `build.sourceDir` is a author-declared, freely-shaped subfolder holding the pre-build project (could be a whole Vite/Next.js/Angular CLI project with its own `package.json`, its own arbitrary layout — Tovu doesn't and shouldn't constrain it, since it's never consumed directly). Everything OUTSIDE `sourceDir` is the generated tree, and I believe it should be required to conform to the exact SAME `render/`/`css/`/`scripts/`/`assets/` shape Round 1/2 already converged on for authored themes — `code-tier-asset-normalizer.ts`'s job (relocate/rewrite a raw bundler output into Tovu's asset-path conventions) is direct evidence this normalization step already exists for exactly this purpose. That means a consumer (the render pipeline, the validator, a coding agent) never needs to know or care whether a theme is authored or compiled — same shape either way, `build` is purely metadata about provenance layered on top.

**`build` (the whole `ThemeBuildInfo` shape) carries forward into schema v2 unchanged in spirit**, the same way Round 2 already decided to preserve `regions` as-is rather than redesign it blind. It's real, tested, shipped three days before this debate started — there's no reason to touch it, only to make sure the new schema's `apiVersion`/`$schema` versioning story doesn't accidentally orphan it.

**What I'm least sure of, and want the panel's read on:** whether `sourceDir` should be allowed to sit INSIDE the invariant tree (e.g., as a special case of `render/`, or its own reserved top-level folder) or whether it's cleaner as a completely separate, unconstrained subfolder the validator explicitly exempts from every other rule (no `dist/`-ban, no `render/`-only requirement, nothing — because it's pre-build author source, structurally unrelated to the runtime shape). I lean toward the latter (fully exempt, own arbitrary layout) since constraining it would just re-invite the exact ecosystem-friction argument (`src/` conventions, bundler defaults) Round 1/2 already fought about for authored themes — a compiled theme's author is going to use whatever their framework's own scaffolding produces, and fighting that is a losing, low-value battle Tovu doesn't need to pick.
