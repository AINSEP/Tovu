Here are the answers to the five open questions, correcting the trajectory based on the shipped code constraints from `ADR-020 §5`.

### 1. Confirm or Refute: Should `build.source: "compiled"` be permanently restricted to the `static` tier?
**Confirm.** The static-only gate is permanently correct by construction. Regardless of how complex the author's chosen framework is (React, Vue, Astro), the output that Tovu consumes and serves is ultimately a static bundle of HTML, CSS, and JavaScript. Because Tovu does not execute a server-side Node.js environment (or similar SSR runtime) for third-party themes, there is no "server-executing tier" for a compiled theme to map onto. The framework's build step resolves all dynamic templating and component logic into static files *before* Tovu serves them. Therefore, runtime execution is exclusively `static`.

### 2. The `sourceDir`/Generated Tree Split vs. Invariant Shape
**Same shape; it is the normalizer's job to get it there.** The generated tree (everything outside of `sourceDir`) must conform to the exact same `render/`, `css/`, `scripts/`, `assets/` invariant shape as an authored theme. 

If compiled output were allowed to have a different shape, every downstream consumer—the Tovu render pipeline, validation systems, and coding agents—would have to implement branching logic (`if (theme.build.source === 'compiled') { ... }`) just to locate basic assets. Relying on the existing `code-tier-asset-normalizer.ts` to relocate the framework's raw output into Tovu's canonical shape guarantees that at runtime, Tovu only needs to understand a single, universal structure.

### 3. Constraints on `sourceDir`
**Fully exempt.** I strongly agree with the Coordinator. The `sourceDir` should be a completely unregulated sandbox. Since this directory represents the author's pre-build source code—which Tovu never directly consumes or serves at runtime—imposing Tovu's naming conventions here would actively fight the native conventions of frameworks like Next.js, Nuxt, or Astro. By declaring `sourceDir` explicitly in the manifest, Tovu knows exactly which folder to ignore during serving and runtime validation.

### 4. Widening `build.framework`
**Yes, it must widen, but purely additively.** Since the field is "purely descriptive, never branched on," there is zero risk in expanding the string literal union to include `"svelte" | "astro" | "solid" | "qwik" | "web-components"`. This is highly valuable metadata for the marketplace, human developers, and AI agents trying to understand the source code inside `sourceDir`. Because the normalizer enforces the invariant shape on the output regardless of the framework, adding new string literals has no systemic side effects.

### 5. Ranked Solution Slate for the `build` object in Schema v2

*   **Rank 1: Option B (Evolve and Align)** — Keep the exact semantic shape of `ADR-020 §5`, but align its naming and organization with v2 conventions. Specifically, expand the `framework` enum, and consider grouping the heavy cryptographic fields (`lockfileHash`, `artifactHashes`) into a dedicated `integrity` object. This maintains the shipped constraints while improving schema hygiene. *(Recommended)*
*   **Rank 2: Option A (Verbatim Carry-Forward)** — Keep the object exactly as it is in `ADR-020 §5`. This requires zero migration effort and perfectly matches the currently shipped validation gates, but it misses the opportunity to standardize the schema during the v2 transition.
*   **Rank 3: Option C (Manifest Split)** — Extract the build provenance data entirely out of `theme.json` into a sibling `theme.build.json` or `theme.lock`. The `artifactHashes` dictionary can get massive for large framework builds. Moving it out keeps the core `theme.json` highly readable for humans and agents, though it requires updating `loadTheme()` and `checkBuiltThemeConformance()` to read multiple files.

### Concrete Examples

Below are the sketches for how this looks in practice, assuming **Rank 1 (Option B)** where we keep the same semantics but ensure it fits the v2 schema.

#### Authored Theme Example (`theme.json`)
```json
{
  "$schema": "https://tovu.dev/schemas/theme-v2.json",
  "apiVersion": "2.0.0",
  "name": "simple-authored-blog",
  "tier": "static",
  "partials": { ... },
  "build": {
    "source": "authored"
  }
}
```

#### Compiled Theme Example (`theme.json`)
```json
{
  "$schema": "https://tovu.dev/schemas/theme-v2.json",
  "apiVersion": "2.0.0",
  "name": "complex-astro-blog",
  "tier": "static",
  "partials": { ... },
  "build": {
    "source": "compiled",
    "framework": "astro",
    "sourceDir": "author-src",
    "builderVersion": "4.15.0",
    "integrity": {
      "lockfileHash": "sha256-abc123...",
      "artifactHashes": {
        "render/index.html": "sha256-def456...",
        "css/bundle.css": "sha256-ghi789..."
      }
    }
  }
}
```
