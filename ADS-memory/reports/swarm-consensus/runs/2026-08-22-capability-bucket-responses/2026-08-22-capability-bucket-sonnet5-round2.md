## DP1

**Position:** One discovery surface — a single search index, one `capability_search`/`capability_get` pair — with activation kept in strictly separate, per-lane adapters that the search surface itself has no way to reach. Not "two indexes" anymore.

**Changed this round? Yes, and I should say plainly why rather than paper over it.** My Round 1 Position literally said "two lanes... build the missing READ lane as a second FTS5/BM25 index." My own Blind Spot (a) named the one-index answer and I filed it as a blind spot instead of my position — that was me not noticing my own contradiction, and the Coordinator's DP1 is right to call it out directly.

**Why the change:** I was attributing a trust benefit to *index-splitting* that actually belongs to *activation-splitting*, and the Coordinator's between-round finding #2 is what exposed that. An FTS5 table is inert data — a row of `{id, kind, name, description, keywords}` cannot execute anything regardless of which physical table it sits in or how many other tables exist beside it. Concatenating N sources' listed cards into one seed call costs about the same as concatenating two (finding #2: any object with a `.list()` returning descriptor-shaped data can back the existing catalog machinery — no core type change either way). So splitting the *index* bought nothing for trust and cost roughly nothing to avoid. What actually protects trust is that the search/get surface has no `activate`/`invoke` method on it at all — a card's `handle` field is opaque to everything except the one adapter that registered it, and reaching an adapter's real execution gate (`ToolExecutor` for native tools, `mcp-federation/trust.ts`'s 8 rules for federated ones) requires a call the search surface cannot make itself.

**Direct answer to the Coordinator's real question:** refusing an execute path on the facade is what addresses my trust-collapse concern. Splitting the index only ever addressed cost, and per finding #2 that cost argument doesn't survive scrutiny — it's close to free either way. I was solving the wrong layer.

**What I still hold from Round 1, restated correctly:** a single flat merge with no way to distinguish kinds at query time is a real ranking-quality risk — Codex and Primary both flag this, and it's legitimate: a first-party tool's one-line description and a Skill's long markdown abstract have very different term-frequency statistics, and BM25 mixing them can hurt both. The fix for that is a `kind`/`lane` metadata column on one shared table (so a caller who already knows it wants only Skills can scope the query), not a second physical index. That's a real nuance the "just one flat index" reading of Primary/Codex/Gemini Flash's position glosses over, and it's the one piece of my Round 1 argument worth keeping.

**Strongest argument against the position I'm now rejecting (pure flat single-table, no scoping column, no distinction at all):** if ranking degrades as more, dissimilar kinds are added, an operator has no lever to pull short of re-architecting into separate tables later — a `kind` column costs one field now and avoids that.

**What would change my mind back toward two physical indexes:** evidence that one FTS5/SQLite instance cannot hold two structurally different `description` distributions without measurable rank degradation even with a `kind` filter available (i.e., that filtering doesn't fully solve what splitting would) — I have no such evidence and don't expect it at Tovu's current or near-term scale.

Bundling it into "the primary axis" produces categories like "workspace-scoped mutating RPC" vs. "global read-only resource," as if tenancy were as fundamental as operation shape, when it's really a required field on every record regardless of operation shape (this is exactly how Codex's own record keeps `scope` alongside `operations` rather than folding it into the protocol union — I'm endorsing that structural choice explicitly). Modality-plus-trust is a reasonable two-facet summary, but stapling tenancy on as a third co-equal axis dilutes what a "primary axis" is supposed to buy: a clean discriminator for "what does this thing need in order to be safely activated," not "what does this thing need, period."

**What would change my mind:** evidence that tenancy actually correlates with operation shape in this codebase in some way I'm missing — e.g., if every job-submission capability turned out to always be global/cross-tenant while every synchronous call was always workspace-scoped, tenancy would stop being orthogonal and Gemini Flash's bundling would be justified. Nothing in the 12 files or the sibling-repo reads I did suggests that correlation exists; `external-mcp-store.ts` and `install.ts`'s workspace scoping apply regardless of what kind of tool the server or plugin exposes.

Improving ranking quality, adding sources, or tuning result shape over time is additive and non-breaking to an existing generically-named tool in a way that a rename never is — callers that already call `capability_search(query)` keep working as more sources register behind it and as ranking improves; they would NOT keep working if the tool itself were renamed. ## Ranking criteria

Stated before the ranking, so the order is auditable against them rather than against my own preference:

1. **Schema-migration avoidance, measured concretely** — does adding a new capability kind touch anything outside that kind's own new files? (Primary's "two-file property," which I'm adopting as the literal falsification test below.)
2. **Preserves the two trust boundaries this codebase already built** (native `ToolExecutor`/`authorize()` gate; federated `mcp-federation/trust.ts`'s 8-rule gate) rather than flattening or duplicating them.
3. **Time-to-first-value** — the owner asked for a working outline now, not a five-year plan; a criterion that only rewards maximal generality would misread the ask.
4. **Falsifiability** — per DP4's lesson, an architecture with no attached measurement plan risks solving a problem nobody measured; I'm penalizing options that can't state a cheap test of their own central claim.
5. **Does not block on, or paper over, the lifecycle/tenancy gaps already found in source** (the digest-ambiguity gap in `resolve-agent-plugin-refs.ts`; the workspace-stitching bug class documented in `install.ts`'s SECURITY note).

## Slate

**Option 1 (recommended) — Unified discovery seam + strictly separate per-lane activation + immediate wording fix, shipped independently of everything else.** One capability-card catalog (single FTS5 table, `kind` column for scoped queries), fed by a pluggable source-registration seam with exactly one real source (Agent Plugin skills) at first; native tools and federated MCP keep their existing, separate activation gates untouched; a lightweight content-read adapter for skills that deliberately stays outside the real `ToolRegistry` (per the verified `handler`-is-required finding) rather than faking a handler. **Genuine sacrifice:** more up-front work than a bespoke fix — the seam, the `kind` column, and the reseed-on-event wiring all have to exist before the first commit is "real," which is slower to ship than Option 2 below. I am not pretending this is free.

**Option 2 — Literal Option C: a bespoke `agent_plugin_search`/`agent_plugin_read_skill` pair, no generic seam underneath.** **Genuine sacrifice:** ships fastest, but per DP5, both the name and the implementation become debt the moment a second READ-ish kind appears — a second bespoke implementation is a near-certainty, not a risk, since the packet's own §1 says more kinds are expected, not merely possible.

**Option 3 — Full generic activation router (literal Option B, or Codex's `capability_activate` dispatcher in front of every lane), built now rather than deferred.** **Genuine sacrifice:** this adds one more piece of infrastructure — a dispatcher every activation call must pass through — that nothing today demonstrably needs, since every lane already has a correct, direct entry point (`ToolExecutor.execute`, the federated adapter, a plain file read) that callers already know how to reach without indirection. Building the router now means debugging and securing a new layer against a hypothetical future need (a job/async protocol, a trigger) that doesn't exist in the repo yet.

**Ranking: Option 1 > Option 2 > Option 3.** Against criterion 1, Option 1 and Option 3 both pass and Option 2 fails outright (it's the definition of the schema-migration cost). Against criterion 2, Option 1 and Option 2 both preserve the existing gates untouched; Option 3 risks becoming the "confused deputy" router Codex himself warns about if it ever trusts a capability-supplied hint instead of re-deriving admission per lane. Against criterion 3, Option 2 wins outright and Option 1 is close behind (the seam is small); Option 3 loses badly — it's the most work for the least currently-demonstrated benefit. Criterion 5 is where Option 2 loses decisively: a bespoke Agent-Plugin-only implementation has no natural place to also fix the digest-ambiguity lifecycle gap generically, since it isn't built as a reusable seam. Net: Option 1 wins on the criteria that matter most (1, 2, 5) at an acceptable cost on criterion 3; Option 3 is rejected for now specifically because criterion 3 and criterion 4 (no attached falsification target — there's no second protocol yet to test a router against) both fail it, not because it's wrong in principle.

## BUILD OUTLINE

**Phase 0 — Fix the Agent-Plugin injection wrapper's wording. Ship immediately, gated on nothing else.**
*What:* change the wrapper text in `resolve-agent-plugin-refs.ts` that currently hedges pinned-plugin content as optional, to the non-hedging phrasing already measured to produce the 4-of-4 result.
*Why it exists, specifically:* per DP4, this is the only piece of the entire packet with a real before/after measurement behind it, and it targets the failure that was actually observed (directive non-compliance under hedged wording), not a hypothesized one (poor findability). It costs a wording change, not an architecture change, and there is no reason for it to wait on Phases 1 through 5.

**Phase 1 — A pluggable capability-source registration seam. No new persistent store.**
*What:* a module, shaped like the existing `tool-contribution-registry.ts` / `mcp-federation/presets.ts` / `page-head.ts` pattern this codebase already has four instances of (register / list / reset-for-tests, replace-by-key), that lets any part of the codebase register an object whose only job is to list its own capability cards — discovery-only metadata: an id, a kind label, a name, a description, keywords, a scope/workspace tag, a source label, and an opaque handle meaningful only to the registering source. At first, exactly one source registers: Agent Plugin skills.
*Why it exists:* this is the one piece that has to be real, not simulated, before any "unification" claim is credible. Primary's two-file property — register a source, write its own activation adapter, touch nothing else — is the actual falsifiable definition of "no structural change per new kind," and it can only be tested if the seam is generic from day one rather than built to fit one kind and generalized later. This directly answers DP5: without this phase, a generically-named tool is cosmetic.
*Why no new datastore:* the packet's own soft constraint prefers not adding one if an existing mechanism suffices, and `tool-catalog-query.ts` already proves a disposable, rebuild-from-nothing SQLite FTS5 table is sufficient for exactly this shape of data. Reuse it rather than justify a second one.

**Phase 2 — One discovery index, one search surface.**
*What:* the same seeding pattern `tool-catalog-query.ts` already uses, generalized to seed from every registered capability source (Phase 1) rather than from the tool registry alone, into one table carrying a `kind`/`lane` column. Agent-facing surface: `capability_search` and `capability_get`, descriptor-only — no execute path exists on this surface, ever.
*Why one table, not two:* per DP1, splitting the physical index bought no trust protection (an FTS5 row is inert regardless of table count) and cost roughly the same either way once Phase 1's seam exists (concatenating N sources' listings costs about what concatenating two does). The `kind` column gets scoped queries for free without the cost or drift-risk of a second table.
*Why this has to follow Phase 1, not stand alone:* without the seam, this phase degenerates into exactly DP5's trap — a rename with no generality underneath it.

**Phase 3 — Reseed on install/enable/disable events, not boot-only, for sources whose change-cadence is runtime-driven.**
*What:* wire the same seed function Phase 2 built to fire again on Agent Plugin install/uninstall/enable/disable (and later, MCP connection add/remove), in addition to firing at boot.
*Why it exists:* per DP3, boot-only seeding matches the native tool lane's change-cadence (code-deploy time) but not the plugin-install lane's (a user action that can happen mid-conversation, which the packet's own flagship workflow requires supporting). This is deliberately scoped as a small wiring addition, not a new mechanism, because the index Phase 2 built was already disposable and rebuildable by design — the only new thing is a second trigger calling an already-existing function.

**Phase 4 — Activation stays split by lane. No shared router.**
*What:* native tools keep going through `ToolExecutor` and `tool-registrations.ts`'s existing risk/permission machinery, untouched. Federated MCP tools keep going through `mcp-federation/trust.ts`'s 8-rule admission tier, untouched. Agent Plugin skill content gets one new, deliberately minimal adapter: resolve a card's handle, read the underlying bytes, return text — nothing resembling a `ToolExecutor` handler, and deliberately never registered into the real `ToolRegistry`.
*Why it exists as three separate things rather than one dispatcher:* per the verified finding that `ToolRegistration.handler` is required (non-optional) at the type level in the shared Jini kernel, forcing the skill-read lane through anything resembling the real tool-registration path means either faking a handler (which quietly turns "non-callable content" into "just another ordinary tool," undermining the reason a separate lane exists at all) or changing a cross-repo published package's types (out of scope for a Tovu-side feature). Keeping the three lanes as three plain, direct call paths sidesteps both costs and needs no new kernel-level concept.

**Phase 5 — Resolve the digest-ambiguity lifecycle gap before discovery traffic increases.**
*What:* a workspace-scoped record of which installed digest is "the" current install for a given plugin id, replacing `resolve-agent-plugin-refs.ts`'s current scan-every-digest-and-refuse-on-ambiguity behavior with a real lookup.
*Why it has to land here, not later:* Phase 2's search surface makes more capabilities discoverable, which makes hitting this existing, already-documented gap (a plugin installed twice under one workspace) more likely to actually occur in practice, not less — shipping better discovery before fixing this converts a rare, already-known failure into a common one.

**Deliberately parked, not built now:** a generic activation router across all three lanes (Codex's `capability_activate` dispatcher, or literal Option B). Revisit specifically once a second genuinely different operation protocol exists in this repo — an async job, a trigger, a hook — that a hand-rolled per-lane call path can no longer accommodate cleanly. Nothing in the current 12-file set or the sibling-repo reads shows that need existing today.

## What I would NOT build, and why

- **A universal `capability_invoke`/activation router spanning all three lanes, built now.** Covered above as Slate Option 3 and Phase 4's "deliberately parked" item — no second operation protocol exists yet to justify it, and it risks becoming the confused-deputy dispatcher Codex himself warns his own design against if it ever trusts capability-supplied metadata instead of re-deriving admission per lane every time.
- **A new persistent datastore for the discovery catalog.** The existing disposable, boot-seeded (now also event-reseeded) FTS5 pattern is sufficient and already proven at 131 tools; a durable store is needed only for Phase 5's lifecycle/activation-record table, which is genuinely stateful (an install decision that must survive a restart), unlike the catalog, which is a derived index that can always be rebuilt from source-of-truth data.
- **MCP as the universal substrate (Option D).** Unchanged from Round 1: it erases the native/federated trust asymmetry this codebase built on purpose, and it fits Agent Plugin skill text (non-executable markdown) badly — modeling static content as a fake remote tool call is a worse mismatch than a plain read adapter.
- **SHAPE and RENDER as first-class capability kinds inside this bucket.** Reaffirmed from Round 1's §4 attack: SHAPE items configure the agent rather than being discovered and used by it (a different axis entirely), and RENDER is a property of an activation *result*, not a capability kind in its own right. Building index/search support for either now would be solving a problem outside this packet's actual named scope (Agent Plugins, MCP, first-party tools) on spec.

## Cheapest test that falsifies my own recommendation

Register a second, deliberately unrelated capability source through Phase 1's seam — something structurally different from Agent Plugin skills, e.g. a synthetic "project docs" source, built as a fake/test double before any real second kind exists in production — and count how many files outside that new source's own module had to change to make it appear in `capability_search` results correctly scoped and ranked. If the answer is anything other than "the new source's own files, plus one registration call at a composition root" — if seeding, the tool definition, the composer, or any core file had to change — my central claim (discovery genuinely unifies behind one seam, with no structural change per new kind) is falsified, and Option 2's bespoke-per-kind approach was the honest answer all along. This is cheap specifically because it needs no real second capability kind to exist yet — a throwaway test double is sufficient to run it.
