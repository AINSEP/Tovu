## What this tested

`2026-08-21-coverage-layer2-order-dependency-experiment.md` pinned the file list (built once, reused)
and got 6/6 clean — no layer-2 flip. That left an obvious confound: the 7 historical runs that DID
flip (3 full-corruption / 4 clean) each rebuilt their list with an unsorted `find`, whose enumeration
order is unstable on this filesystem.

This control reproduces the historical condition: same 16 files (12 `src/server/http/**` + 4
`src/media/**`, both counts verified before starting), `--test-concurrency=1`, same `test:cov` command
shape, lcov to scratch — but the file list is **regenerated by unsorted `find` immediately before each
of the 6 runs**. `ps -eo args | grep -c '[e]xperimental-test-coverage'` confirmed `0` as its own
command before every run.

## Finding 1 — file order is NOT the lever, and this is now proven directly

Only **2 distinct file-list hashes** appeared across 6 runs, not 6 — `find` held stable for runs 1-4,
flipped once, then held for 5-6. (The two orderings differ by the position of exactly one file,
`plugins-dto.unit.test.ts`, 3rd vs last in the http group.) So the control only weakly varied the
thing it set out to vary.

**But it produced a stronger result by accident.** Run 3 corrupted while running a **byte-identical
file list** to runs 1, 2 and 4, which were clean. Same input order, different output. That is direct
evidence of nondeterminism *within* a fixed order — order cannot be the cause.

This refutes **both** branches the prior handoff pre-registered:
- "6/6 clean → it was the machine" — did not happen; one run flipped on an idle machine.
- "Flips again → the file list matters after all" — the flip happened on an identical file list.

## Finding 2 — the Coordinator's memory-pressure hunch is NOT supported

The prior handoff recorded, explicitly labelled as an untested hunch, that the historical flip-flop
was caused by machine memory pressure. Run 3 flipped on a quiet machine with the coverage slot
verified free and no concurrent coverage process. **That hunch should now be treated as unsupported,
not merely untested.** It is not positively refuted — 1 event cannot separate a load effect from a
baseline rate — but it no longer has anything pointing at it.

Rate across the idle machine so far: **1 corrupt in 12 runs** (this control's 1/6 plus the pinned
experiment's 0/6). Historical busy-machine rate: 3/7. These are too small to distinguish; do not
quote a "rate went down" claim from them.

## Finding 3 — CORRECTED: layer 2 is the SAME bug as layer 1, not a separate one

**A first version of this report claimed run 3 contained a "third instantiation image" (21 extra
`FN:` lines). That was WRONG and is retracted.** It came from a diff that compared only the first
comma-field of each record, i.e. line numbers with the function names cut off, so a reordering read
as an insertion. Recorded here rather than silently deleted, because the register of proven-false
claims in this repo exists precisely because inferences like that get promoted to facts.

The blocks are structurally **identical**. Both are 523 lines with the same count of every record
type: `FN:` 43, `FNDA:` 43, `FNF:` 43, `FNH:` **29 in both**, `BRDA:` 72, `DA:` 357. There is no
third image and no extra function entry.

What actually differs is **which of the two known images supplies the numbers**:

| | run 1 (clean) | run 3 (corrupt) |
|---|---|---|
| distinct `DA:` hit-count values | 14 — `1, 2, 6, 27, 28, 30, 31, 34, 37, 42, 44, 48, 49, 105` | **3** — `0, 32, 128` |
| `DA:1` | `6` | `32` |
| `assertValidEntry` | `FNDA:105` | `FNDA:0` |
| `buildProviderUpsertRow` | `FNDA:31` | `FNDA:0` |
| `getMediaProviderCredentials` | `FNDA:13` | `FNDA:0` |
| `resolveSealedKeyPair` | `FNDA:31` | `FNDA:0` |

Run 3's only three possible hit counts — `0`, `32`, `128` — are **exactly the esbuild CJS wrapper's
own counts**, visible in both runs' function tables as `FNDA:128,__export`, `FNDA:128,__copyProps`,
`FNDA:32,__toCommonJS`.

**So run 3 is reporting the CJS wrapper image, and run 1 is reporting the real ESM module image.**
The dual instantiation is present in 100% of runs — that is layer 1, and `FNF:43` against a clean
scoped `FNF:20` proves it every time. Layer 2 is not a second defect. **Layer 2 is the coin-flip over
which of those two images wins the lcov merge.** When the wrapper wins, real functions report
`FNDA:0` and 66 lines drop to unhit.

This is why no static cause was ever found for layer 2: there isn't one to find. It is a merge-order
race downstream of a single upstream defect.

## Finding 4 — the corruption is not binary, and `294` was never a signature

Run 3 read `LH:291`; every prior record of "full corruption" read `LH:294`. `291` had never been
recorded. Given Finding 3, the magnitude is simply however many lines happen to be unhit in the
wrapper image on a given run — so treating `294` as *the* corruption signature was a mistake, and any
analysis that matched on it would have scored run 3 as clean. **Detect on the shim markers and on
`FNF:` exceeding the scoped baseline, never on an `LH:` value.**

## Layer 1 is unchanged and fully deterministic

6 shim markers and `FNF:43 FNH:29` in **6 of 6** runs, no exceptions — consistent with all prior
rounds. Layer 1 has now reproduced in every single run ever recorded against this cluster.

## What this changes for the next step

The prior handoff said "do not ship a layer-1 fix while layer 2 is unexplained." That instruction was
written on the assumption layer 2 had a findable static cause (order, concurrency). Order is now
ruled out by direct evidence, concurrency was already ruled out, and load is unsupported. Layer 2
looks like the same instantiation bug as layer 1, surfacing intermittently.

**Recommendation: the blocker should be lifted.** Fix layer 1 (the `spawnSync` children that inherit
`NODE_V8_COVERAGE`, per `2026-08-21-coverage-dual-instantiation-root-cause.md`), then re-measure. If
layer 1's fix also drops layer 2's rate to zero, they were one bug. This is a decision for the owner.

# Addendum — the fix scope, measured (Coordinator, same day)

## Before-fix baseline, captured on an unfixed tree

Scoped coverage run of **one** test file, `src/cli/__tests__/integration/export-command.integration.test.ts`
(`TEST_CONCURRENCY=2`, exit 0, coverage slot verified free as its own command):

- **679 of 703** first-party `SF:` blocks contain esbuild CJS-wrapper functions — **96.6% contaminated
  by a single test file.** This independently confirms (and slightly exceeds) the previously-quoted
  "~89% of source files" figure.
- Artifacts: `…/scratchpad/before-after/before-export-cmd.lcov.info`, `before-corrupt-files.txt`.

The contamination is overwhelmingly *from the spawned child*: the parent test itself only loads the
CLI surface, while the child boots the whole app. This is the measurement the post-fix run must be
compared against.

## There are TWO routes to dual instantiation, not one

Confirmed by direct check — **this materially changes the fix scope and was not in the prior reports.**

**Route B — spawned child inherits `NODE_V8_COVERAGE`.** 12 test call sites. This is what the
`CovLeakFix` work closes. Verified by probe today: `delete env.NODE_V8_COVERAGE` does NOT work (Node
re-injects it into descendants); redirecting the variable to a scratch dir is the only fix that holds.

**Route A — an in-process `require()`.** `src/server/deps.ts:1048-1050`, `createSiteAppLazily`, does
`require("./app.js")` synchronously. That pulls `server/app.ts` and its transitive graph through
tsx's **CJS** hook while the same modules are already loaded as ESM — two images, same process, **no
child needed.**

**Evidence that Route A is independent:** the 12 `src/server/http/**` + 4 `src/media/**` cluster shows
`FNF:43` and 6 shim markers in 6 of 6 runs, and **not one of those 16 files spawns any child process**
(verified by grepping all 16 for `spawnSync`/`spawn(`/`execFileSync`/`execSync`/`fork(` — zero hits).
Its corruption cannot be Route B. Closing Route B alone will NOT clean that cluster.

## Route A is deliberate and its justification is still valid — do not "fix" it casually

The `require` carries a doc comment justifying itself by an eager module-scope side effect in
`server/app.ts`. **That justification was checked, not assumed, and it still holds:**
`src/server/app.ts:1222` really does contain `export const app = createApp();`, so a plain `import`
would run the entire app-boot graph as a load side effect. Converting the call site to `await import()`
would also make `ExportEngine`/`createSiteApp` async — the repo-wide blast radius the earlier handoff
warned about.

Route A is therefore an accepted architectural tradeoff, not a defect to patch under time pressure.
The correct treatment is to make it **visible rather than silent** — which is what
`check:coverage-integrity` does. The long-standing tribal rule ("shim markers present → use the
scoped number") stops being tribal knowledge and becomes an enforced gate.

**Genuinely fixing Route A means removing the eager `export const app = createApp()` at
`app.ts:1222`** so the `require` can become a normal import. That is a separate, scoped piece of work
and should not be bundled into this one.

## Revised expectation for the post-fix measurement

- The export-command run should drop sharply from 679/703. That is Route B's contribution.
- The 16-file http/media cluster should be **unchanged** at `FNF:43`. That is Route A, still open by
  decision. If it *does* change, one of the conclusions above is wrong and needs re-deriving.

# Addendum 2 — "clean" in this report means LINE-clean only. No run was actually clean.

Surfaced when a dispatched agent validated a detector spec against the six real blocks and found the
proposed primary signal fired on all six. Verified by the Coordinator directly:

| run | wrapper-FN entries | FNF | LH |
|---|---:|---:|---:|
| 1 | 3 | 43 | 357 |
| 2 | 3 | 43 | 357 |
| 3 | 3 | 43 | **291** |
| 4 | 3 | 43 | 357 |
| 5 | 3 | 43 | 357 |
| 6 | 3 | 43 | 357 |

**The true clean baseline for `src/media/provider-credential-store.ts` is `0 shim markers,
FNF:20 FNH:20, LH:357 LF:357`** — reproduced by two independent scoped runs recorded at
`2026-08-21-coverage-dual-instantiation-root-cause.md` lines 254 and 262.

So **all six runs are contaminated.** Every one reports `FNF:43 FNH:29` against a true `20/20` — the
function coverage is wrong in 6 of 6. What is clean in 5 of 6 is only the *line* coverage. Anywhere
this report says "clean," read "line-clean."

Consequence, and the reason this is worth its own addendum: quoting `29/43` for this file gives **67%
function coverage for a file that is actually at 100%**. A detector that gates on the line signal
alone would pass five contaminated runs as healthy. The `check:coverage-integrity` gate therefore
reports two severities — CONTAMINATED (wrapper images merged; function coverage untrustworthy;
expected on all 6) and SEVERE (wrapper image also won the line merge; expected on run 3 only) — and
gates on the first. It is expected to FAIL on today's repo, because today's repo genuinely is
contaminated via Route A. That is the honest signal, not a bug in the gate.

number.

wanted, it needs the child's profile collected and merged deliberately as a separate image — not by
letting it silently overwrite the parent's.
