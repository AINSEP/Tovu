# Zana: two-way contract between the vibecoded app and the admin

Date: 2026-09-29 · Status: DISCUSSION ONLY (owner: "not coding right now, save this")
Builds on: `2026-09-24-zana-admin-adapter-plan.md` (owner direction: app talks ONLY to Zana; versioned
JSON manifest + standard REST; no Jini types in the app).

## Owner framing
Zana = Tovu with a vibecoded front end (React, Angular, React Native, iOS, Android…) instead of posts/pages.
Needs a two-way street: admin builds/saves things the app uses; the app sends data back to the admin.
Example: build a form in the admin, the app renders it, and submissions come back to the admin.

## Shape
- **The Zana server is the one hub.** Admin and app both talk only to it. The admin is just another client.
- **The contract is HTTP + JSON, described by a published spec** (OpenAPI for endpoints, JSON Schema for
  definitions such as forms). That is what makes it work with any language or stack.
- **Admin → app (read / "delivery API"):** forms, menus, media, collections, settings, flags, AI prompts.
  e.g. `GET /api/forms/contact` returns fields, validation and labels as JSON.
- **App → admin (write):** form submissions, app entity data (bookings, orders), events (`order.created`),
  sign-ups. e.g. `POST /api/forms/contact/submissions` shows up in the admin inbox and triggers email, AI or integrations.
- The server enforces the admin's rules (validation, spam checks, permissions). Auth is an app key plus per-user sessions/tokens.

## Packages per platform (three tiers)
1. **Spec** (required, one source of truth): OpenAPI + JSON Schemas.
2. **Thin clients** (cheap, generated from the spec):
   - `@zana/client` in TS. It works in web and in React Native, since both have fetch.
   - Swift and Kotlin clients are generated later, only if needed.
3. **UI helpers** (optional convenience, not required):
   - Headless hooks such as `useZanaForm("contact")`. These return fields, state and submit, and work in both React and React Native because they render no UI.
   - Drop-in components (`<ZanaForm/>`) per framework only where demand shows.
   - **No separate Swift/Kotlin form UI packages for now.** The vibecoding agent can generate native form UI
     from the JSON definition, so the schema is enough.

## UI components (owner follow-up, same day)
Owner wants installable UI pieces (e.g. a Zana form) that are easy to style, adapt to any stack (including Flutter),
and that the AI can install and hook up. The admin hides the backend complexity.
- **Recommended: a shadcn-style component registry, not a compiled package per platform.** `zana add form` (a CLI or
  an MCP tool the vibecoding agent calls) copies the component SOURCE into the app for its detected stack.
  The app owns the code, so it takes the app's own styling. There are no version upgrades to chase.
- **Each stack's component is a thin renderer over the shared JSON definition.** Validation rules live in that JSON
  (JSON Schema), so any platform can check them locally with a stock validator. The server re-validates anyway.
- **Styling:** components use design tokens (colors, radius, spacing, fonts). Tokens can come from the app's
  theme or from the admin's theme settings.
- **Hand-maintain only React + React Native** at first. Vue, Angular, SwiftUI, Jetpack Compose and Flutter versions are
  generated by the AI from the React reference, then checked by a shared conformance suite (a set of form-JSON
  fixtures plus the expected behavior) so all stacks behave the same.
- Prior art to study: shadcn registry (copy-in), JSON Forms (one schema, renderers per framework),
  react-jsonschema-form, SurveyJS / Form.io, server-driven UI (Airbnb, Shopify).

## Gaps for "a non-technical person builds a complex app by speaking" (owner asked, same day)
Owner's list so far: front end, hooks/SDK, server, admin, agentic runtime, outside integrations.
Missing, highest leverage first:
1. **Safety net:** undo/rollback of code AND data, automatic backups, a preview before publish, separate
   draft/live environments. With this, the user never has to be afraid to say "change it".
2. **Data model evolution:** the AI changes entities and the DB migrates safely without losing data (renames, splits).
3. **Self-verification + self-healing:** the agent tests its own work (E2E + visual checks), watches errors and logs in
   production, and fixes problems before the user ever sees them.
4. **Product memory:** a living plain-language spec of what the app does and why. It is updated from conversations, so
   change #200 doesn't break change #12. It comes with a plain-language changelog.
5. **End-user identity:** sign-up/login/social login, roles and permissions for the app's own users, and teams/multi-tenant.
6. **Ship it:** domains, SSL, hosting, and for mobile the App Store / Play Store signing, TestFlight and review
   submission (this is the hardest part for non-technical people), plus OTA updates.
7. **Automations:** scheduled jobs, workflows ("every Monday email me a report"), background tasks.
8. **Common building blocks as admin modules:** payments/subscriptions, notifications (email, SMS, push), file storage,
   search, realtime (chat/live updates), analytics, i18n, SEO, accessibility.
9. **Guardrails for the AI:** approvals for destructive or costly actions, budgets for AI and vendor spend, an audit log.
10. **Trust & compliance:** secrets vault, rate limits, GDPR export/delete, HIPAA-ready mode (care apps).
11. **Starting points:** domain templates (booking, CRM, shop, care) so the user starts at 70%, not 0.
12. **No lock-in + upgrades:** export the code at any time, and a way to migrate existing apps when the Zana contract
    or components change.
13. **Collaboration:** invite teammates or clients, with roles in the admin.
14. **Mobile specifics:** offline mode + sync, and push notification certificates (APNs/FCM).

## Build-quality system prompt (owner asked, same day)
The coding agent needs a standing system prompt so generated apps follow good architecture by default.
It must cover the concepts in the owner's screenshot (`2026-09-29-zana-concepts-checklist.png`): *"Despite switching
from programming languages to natural (human) languages, the underlying technology concepts do not change":*
security, stability, efficiency, privacy, code reuse, encapsulation, modularity, version control, automated
testing, multi-tenancy, capacity planning, release management, backups, disaster recovery, observability,
secrets management, API reverse compatibility, input sanitizing, dependency management, schema evolution.

Owner-named additions:
- **Observability extension points:** one telemetry port (OpenTelemetry as the neutral standard: traces,
  metrics, logs), with exporters for Datadog, Grafana (Loki/Tempo/Prometheus), Sentry (errors), Honeycomb, etc.
  These are selected in the admin, not hard-coded in the app. Front end and mobile report errors and performance through the same port.
- **Dependency injection:** ports/adapters everywhere (storage, email, payments, telemetry, AI provider,
  auth), so vendors are swappable and tests use fakes.

- **Caching:** layers (CDN/edge, HTTP cache headers, server cache e.g. Redis, client/query cache, mobile
  offline cache), with invalidation rules tied to admin writes/events. The cache is a port so its backend can be swapped.
- **AI observability:** traces of agent runs (prompts, tool calls, tokens, cost, latency, errors), evals and quality
  scores, a prompt/model version history, guardrail and approval events. Uses OpenTelemetry GenAI conventions, with exporters to
  Langfuse / LangSmith / Helicone / Datadog LLM Observability / Arize Phoenix, etc.
- **Systems design basics:** statelessness + horizontal scaling, load balancing, queues/async, idempotency,
  consistency vs availability trade-offs, read replicas, sharding/partitioning when needed, backpressure, timeouts,
  retries with jitter, circuit breakers, graceful degradation, SLOs.

Other items the prompt should enforce (Claude's additions, for review):
- Config and environments (dev/preview/prod), feature flags, 12-factor config, no secrets in code.
- An error-handling contract (typed errors, user-safe messages), structured logging with request IDs, health checks.
- API versioning + contract tests; idempotency keys on writes; rate limits; pagination; caching rules.
- Background jobs + queues with retries and dead-letter handling; webhooks signed and verified.
- Authz on every endpoint (deny by default), tenant isolation tests, audit log.
- Supply chain: pinned dependencies, vulnerability audit, license check, SBOM.
- Accessibility, i18n, performance budgets, offline behavior on mobile.
- Code-quality gates: types, lint, complexity ceiling, tests before merge, ADRs for decisions, a plain-language changelog.
- Data: migrations that are reversible or expand/contract, seed data, PII tagging, retention/deletion.

## Infrastructure: invisible to the user (owner question, same day)
Reference diagrams saved: `2026-09-29-zana-sysdesign-ref-video-platform.svg`, `-ref-1.png`, `-ref-2.png`
(DNS, CDN, load balancer, stateless app servers, DB + cache, job queue + workers, full-text search, cloud storage,
media processing, event firehose, data warehouse/BI, push/SMS/email, monitoring).

Question: build our own platform that abstracts this, or set it up on AWS (IaC) per app? Either way the user never sees it.

Claude's recommendation (for discussion):
- **Both, using one mechanism.** The app's manifest declares what it needs. Zana picks and provisions the infrastructure through IaC
  (OpenTofu/Pulumi, run in CI, never a vendor CLI on a laptop). "Zana Cloud" is just that IaC pointed at Zana's
  own account (multi-tenant, simplest for users). "Bring your own cloud" is the same IaC pointed at the customer's
  AWS/GCP/Fly account (no lock-in, enterprise).
- **Every piece in the diagrams is a port with swappable adapters** (the same DI rule as the system prompt), so the app code never changes
  when infrastructure is upgraded.
- **Tiers, switched on automatically:**
  - Tier 0, every app from day one: DNS+SSL, CDN, one stateless app server, Postgres, object storage, email,
    backups, error/metrics monitoring.
  - Tier 1, turned on when the app needs it: job queue (Postgres-backed first, e.g. pg-boss), cache (in-process → Redis),
    search (Postgres full-text → Meilisearch/OpenSearch), push/SMS, media processing/video transcoding.
  - Tier 2, turned on by measured load: load balancer + autoscaled servers, read replicas, an event firehose, a warehouse + BI.
- **"Just use Postgres" first:** one database covers data, queue, search and a basic cache for most small apps. That keeps
  cost and moving parts low. Upgrades happen when monitoring crosses thresholds, and the agent proposes them (see
  Codex: propose, don't auto-apply in prod).

## State in Zana today (cbm reindex 2026-09-29)
- Admin already has forms, menus, widgets and media features (ported from Tovu), but it runs on `lib/mock-backend.ts`
  (855 lines, in memory). `lib/api.ts` hard-codes `/api/admin/v1` + `workspace-local`.
- The server (`apps/server/src/admin-routes.ts`) only proxies `/admin/*` to Vite. It has no data API yet.
- The entity registry (`apps/admin/src/entity-registry.ts`) generates screens from descriptors, but the only data is the dummy recipes, stored in memory.
- The agent can do only one thing to the admin: take a screenshot (`App.hooks.tsx:744`). Entities and actions aren't exposed as agent tools.

- The server's deps (`apps/server/package.json`) are agent-runtime, core, daemon, http-kit, protocol, sandbox, server, sidecar
  and sqlite. **No `@jini-ai/cms` or `@jini-ai/admin`.** Its routes are only the admin proxy, sandbox, vibecoding and auth.
- The vibecoding studio (`apps/vibecoding`) has chat, a workbench, a sandbox file tree and a preview. It still has a `data/mock.ts`.
