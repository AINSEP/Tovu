## Architecture map

bolt.diy is a **Remix app** (React Router v7 conventions: `app/routes/*`, `loader`/`action`) that runs partly server-side (Node or Cloudflare Workers — see `wrangler.toml`, `functions/[[path]].ts`) and partly in-browser (WebContainer). Also ships as an Electron desktop app (`electron/`).

Core pipeline, by directory:
- `app/routes/api.chat.ts` — the chat POST endpoint. Receives messages, calls the LLM, streams back a text/event-stream of message chunks plus custom annotations (usage, progress).
- `app/lib/.server/llm/stream-text.ts` — builds the actual `streamText()` call (Vercel AI SDK) against whichever provider, with the system prompt, files context, and tool defs.
- `app/lib/common/prompts/` — the system prompt library (`prompts.ts` = legacy/optimized, `new-prompt.ts` = current default "discuss"/"code" mode prompt, `discuss-prompt.ts` = discussion-only variant).
- `app/lib/runtime/message-parser.ts` + `app/lib/runtime/enhanced-message-parser.ts` — the streaming parser that turns the LLM's raw markdown+custom-tag output into structured `BoltArtifact`/`BoltAction` events as tokens arrive.
- `app/lib/runtime/action-runner.ts` — takes parsed actions (`file`, `shell`, `start`) and executes them against the WebContainer (write file / run shell command), tracks status (pending/running/complete/failed/aborted).
- `app/lib/stores/workbench.ts` (`WorkbenchStore`, 77 edges — the top non-utility god node) — the central client-side orchestrator: owns `FilesStore`, `EditorStore`, `PreviewsStore`, `TerminalStore`, wires the parser's callbacks to the action runner, tracks unsaved changes / artifacts / selected file.
- `app/lib/stores/files.ts` (`FilesStore`) — in-memory + WebContainer-backed file map, watches the container FS for external changes (e.g., npm install writing files) and reconciles.
- `app/lib/stores/previews.ts` (`PreviewsStore`) — listens to WebContainer `port` events, tracks live dev-server URLs, feeds the `<iframe>` preview.
- `app/lib/webcontainer/index.ts` — boots the singleton `WebContainer` instance (StackBlitz's in-browser Node runtime), mounts the initial file system.
- `app/lib/persistence/` — IndexedDB-backed chat history (`db.ts`, `useChatHistory.ts`, `chats.ts`) that snapshots the whole conversation + file map per message (this is bolt's "versioning").
- `app/components/workbench/Workbench.client.tsx`, `Preview.tsx`, `EditorPanel.tsx`, `FileTree.tsx` — the IDE-like UI: file tree, CodeMirror editor, iframe preview, terminal.
- `app/components/chat/Artifact.tsx`, `Messages.client.tsx`, `AssistantMessage.tsx` — renders the parsed artifact/action stream as collapsible "Bolt built X" cards in the chat transcript.

Import-cycle note (from Graphify): `app/lib/persistence/index.ts ↔ useChatHistory.ts ↔ app/lib/stores/workbench.ts` is a 3-file cycle — persistence and the workbench store are mutually coupled (chat history save-on-change reads live workbench state; workbench restores from persistence on load). Relevant to Q8 (versioning).

## Q1. Generation loop — user prompt → LLM call → parsed output → files written → preview updated

End-to-end trace, file:line at each hop:

1. **Client submits** — `Chat.client.tsx` posts to `/api/chat` (Remix resource route).
2. **Server entry** — `app/routes/api.chat.ts:18` `action()` → `chatAction()` at `app/routes/api.chat.ts:42`. Parses `{messages, files, promptId, contextOptimization, chatMode, designScheme, maxLLMSteps, supabase}` from the request body (`api.chat.ts:51-68`).
3. **Optional context-optimization pre-pass** (`api.chat.ts:108-207`, only when `contextOptimization` is true and there are existing files): calls `createSummary()` then `selectContext()` — two *extra* LLM calls that produce a running chat summary and a filtered file subset, streamed to the client as `progress` annotations (`type: 'progress'`) so the UI can show "Analysing Request" / "Determining Files to Read" while this happens. This is the context-management mechanism for Q7.
4. **Main LLM call** — `streamText()` is invoked at `api.chat.ts:310` (and again at `api.chat.ts:269` inside `onFinish` for the "continue" case — see below). Implementation is `app/lib/.server/llm/stream-text.ts:54`.
   - Builds/looks up the model (`LLMManager.getInstance()`, `stream-text.ts:108-141`), resolves a token budget (`getCompletionTokenLimit`, `stream-text.ts:29`), builds the system prompt via `PromptLibrary.getPropmtFromLibrary()` (`stream-text.ts:152-163`), appends a "context buffer" of selected files and chat summary when in build+optimization mode (`stream-text.ts:165-196`), appends a locked-files block if any files are locked (`stream-text.ts:198-220`).
   - Calls the Vercel AI SDK's `_streamText()` (aliased import, `stream-text.ts:1`) with `system`, `messages: convertToCoreMessages(...)`, and the mcp tool defs passed through from the route (`stream-text.ts:276-290`).
5. **Streaming back to client** — `api.chat.ts` iterates `result.fullStream` to detect provider errors (`api.chat.ts:326-346`) and separately calls `result.mergeIntoDataStream(dataStream)` (`api.chat.ts:347`) to pipe the raw token stream into a Vercel AI SDK `DataStream` response. A `TransformStream` (`api.chat.ts:383-419`) post-processes the wire format to wrap "thinking"/reasoning chunks (prefix `g`) in a `<div class="__boltThought__">` for the client to render distinctly.
6. **Auto-continue on truncation** — if `finishReason === 'length'` (model hit its token cap mid-artifact), `onFinish` (`api.chat.ts:221-299`) pushes the partial assistant content plus a synthetic user turn containing `CONTINUE_PROMPT` (`prompts.ts`) back onto the message list and re-invokes `streamText()` (`api.chat.ts:269-283`), merging the continuation into the same `dataStream`. This is how bolt survives responses that exceed `MAX_TOKENS` without corrupting the artifact — see Q2 for how the parser's own state machine tolerates the resulting split.
7. **Client-side parse** — the raw stream lands in `useMessageParser` (`app/lib/hooks/useMessageParser.ts`), which feeds each incremental chunk into `StreamingMessageParser.parse()` / `EnhancedStreamingMessageParser` (`app/lib/runtime/message-parser.ts`, `enhanced-message-parser.ts`) — see Q2.
8. **Actions dispatched to the store** — parser callbacks (`onArtifactOpen/Close`, `onActionOpen/Stream/Close`) are wired in `WorkbenchStore` (`app/lib/stores/workbench.ts`) to `ActionRunner` (`app/lib/runtime/action-runner.ts`), which executes each action against the live `WebContainer`: `file` actions write to the container FS via `FilesStore`, `shell`/`start` actions run in the container's spawned shell.
9. **Preview updates** — `WebContainer` fires a `server-ready`/`port` event when the dev server inside the container binds a port; `PreviewsStore` (`app/lib/stores/previews.ts`) catches it and sets the iframe `src` in `Preview.tsx` — this is push-based (event-driven), not polled.

## Q2. Output protocol — the artifact/action format (most reusable piece for Tovu)

**Format.** The LLM is instructed (see Q3 system prompt) to emit ordinary markdown prose interleaved with exactly one custom-tag block per response:

```
<boltArtifact id="kebab-case-id" title="Human title">
  <boltAction type="file" filePath="src/App.tsx" contentType="...">
    ...full file contents...
  </boltAction>
  <boltAction type="shell">npm install</boltAction>
  <boltAction type="start">npm run dev</boltAction>
</boltArtifact>
```
Four action `type`s: `file`, `shell`, `start`, `supabase` (with a `operation="migration"|"query"` sub-attribute) — parsed at `message-parser.ts:341-380` (`#parseActionTag`). There's also a separate, simpler `<bolt-quick-actions>...<bolt-quick-action type=... message=... path=... href=...>Label</bolt-quick-action>...</bolt-quick-actions>` mini-format for suggested follow-up buttons (`message-parser.ts:103-131`), unrelated to code generation.

**Parser.** `StreamingMessageParser` (`app/lib/runtime/message-parser.ts:76`) is a **hand-rolled single-pass character scanner with resumable position state**, not a full XML/HTML parser (deliberately — the content inside `<boltAction type="file">` is raw source code that may itself contain `<`, `>`, or look like a tag, so a generic parser would misfire). Key design points:

- **State is keyed by `messageId`** and persisted across calls (`#messages = new Map<string, MessageState>()`, `message-parser.ts:77`). Each call to `parse(messageId, input)` is handed the **entire accumulated text so far** (not just the new delta — confirmed by the caller pattern in `useMessageParser.ts`), and the parser resumes from `state.position` (`message-parser.ts:83-99`), so it never re-emits output for content it already processed. This is the key mechanism for Q2's "how does it handle partial/streaming output without corrupting state."
- **Partial-tag handling**: when scanning for `<boltArtifact` and the input ends mid-tag-name, it just `break`s out (`message-parser.ts:312-314`) and leaves `state.position` at the start of the ambiguous prefix, so the next call re-scans from there once more text has arrived — never mis-classifies a truncated tag as plain text.
- **Partial file-action streaming**: while inside a `file` action, if the closing `</boltAction>` hasn't arrived yet, it doesn't wait — it emits an `onActionStream` callback with a live "content so far" every time `parse()` is called (`message-parser.ts:181-203`), letting the file editor/preview show content growing in real time. Only on the close tag does it fire `onActionClose` with the *fully accumulated, trimmed, markdown-fence-stripped* content (`message-parser.ts:141-180`).
- **Markdown-fence stripping** (`cleanoutMarkdownSyntax`, `message-parser.ts:60-71`) strips a wrapping ```` ```lang\n...\n``` ```` if the model ignored instructions and fenced the file content anyway — defensive against model non-compliance with the raw-tag format.
- **Escaped-entity cleanup** (`cleanEscapedTags`, `message-parser.ts:73-75`) unescapes `&lt;`/`&gt;` that some models produce inside file content when they (incorrectly) think they need to escape angle brackets for the surrounding "XML".
- Everything **outside** an artifact block is passed through unchanged as `output` (`message-parser.ts:320-321`) — that's the assistant's visible chat prose, rendered as markdown; artifact/action tags are replaced with placeholder `<div class="__boltArtifact__" data-...>` elements (`createArtifactElement`, `message-parser.ts:389-398`) that a React component (`Artifact.tsx`) later hydrates by reading the corresponding parsed data out of a store, not by re-parsing the DOM.
- `EnhancedStreamingMessageParser` (`app/lib/runtime/enhanced-message-parser.ts`) wraps/extends this with extra heuristics — e.g. `_wrapInShellAction` (`enhanced-message-parser.ts:214-222`) auto-detects shell commands that arrive as fenced code blocks outside a `<boltAction>` and synthesizes a shell action for them, for defense against models that partially forget the tag format.

**Why this matters for Tovu**: the resumable-position, delta-safe design is the reusable core — an equivalent single-artifact-with-actions grammar (even simplified to just `file` actions, since Tovu doesn't need `shell`/`start`/`supabase`) would let a streaming HTML+CSS response render incrementally in a live preview without re-parsing from scratch on every token, and without the classic streaming-JSON/XML corruption bugs (mid-tag truncation, double-counting, escaping).

## Q3. System prompt architecture

Lives in `app/lib/common/prompts/`: `new-prompt.ts` (current default, `getFineTunedPrompt`, read above — **~300 lines / roughly 2,500-3,000 tokens** as one giant template literal), `prompts.ts` (an older/alternate `getSystemPrompt`, used as fallback via `?? getSystemPrompt()` at `stream-text.ts:163`), `discuss-prompt.ts` (a much shorter prompt used instead of the full build prompt when `chatMode !== 'build'` — see `stream-text.ts:283`: `system: chatMode === 'build' ? systemPrompt : discussPrompt()`). Selection is via `PromptLibrary.getPropmtFromLibrary(promptId, {...})` (`app/lib/common/prompt-library.ts`), i.e. there's a registry of named prompt variants and the client picks one by `promptId` (a Settings option), not just one hardcoded prompt.

Structure of `getFineTunedPrompt` — a single large XML-tag-delimited template string composed of named sections, each independently interesting:

- `<response_requirements>` — global tone/format rules, explicitly forbids HTML tags in prose ("except for artifacts").
- `<system_constraints>` — **hardcodes the exact shape of the WebContainer sandbox**: no native binaries, no pip, no C/Rust compiler, no git, an enumerated shell command allowlist (`new-prompt.ts:36`). This is the part that is entirely N/A for Tovu (no WebContainer) but is the pattern to imitate: tell the model the *precise, closed* execution environment so it doesn't hallucinate capabilities.
- `<technology_preferences>` — opinionated defaults (Vite, Supabase, Pexels for stock photos, "never downloads images, only links").
- `<running_shell_commands_info>` — a striking directive: **never reveal to the user that the model is being fed a live process list / terminal output** — "act as if you inherently know this." This is a prompt-injection-shaped instruction for hiding tool/context plumbing from the end user; worth noting as a UX pattern, not necessarily one to copy.
- `<database_instructions>` — heavily conditional (interpolates live connection state) block enforcing Supabase-specific migration conventions (always full file, never diff, always RLS) — a good model for "domain-specific structured-output contract embedded in the system prompt," which Tovu would replace with its own HTML/CSS contract (e.g. "always full document," "always inline `<style>`," "no external script tags," whatever the Tovu policy becomes).
- `<artifact_instructions>` — the actual output-format contract matching the Q2 parser: **max one `<boltArtifact>` per response**, ordering rules (files before shell, package.json before install, start command last), "ALWAYS use latest file modifications, NEVER fake placeholder code," explicit ban on binary/base64 content. This section is the prompt-side half of the artifact protocol and is directly portable to a Tovu prompt (minus the shell/start/package.json-specific rules).
- `<design_instructions>` — ~60 lines of aesthetic direction ("breathtaking," "Apple/Stripe-level," concrete technical requirements like 4.5:1 contrast, 8px grid, Pexels-only stock imagery, font-pairing guidance, a self-check checklist at the end). This is **the single most directly reusable section for Tovu's use case** — Tovu pages are exactly the kind of single-document, design-forward output this section is written for, and it needs zero adaptation for the WebContainer-specific stuff since it's all pure design taste.
- `<mobile_app_instructions>` — React Native/Expo scaffolding rules. Not applicable to Tovu — LEAVE.
- `<examples>` — one worked few-shot example showing the literal artifact tag output for a trivial request.

Notable prompt-engineering details: it opens with `The year is 2025.` (a training-cutoff anchor, common pattern to prevent the model from citing stale framework versions) and repeats "CRITICAL"/"NEVER"/"ALWAYS" emphasis heavily — a blunt-instrument style rather than structured constraints, worth noting as a trap (see TRAPS).

**How the parser is actually driven (confirms the Q2 mechanism precisely):** `app/lib/hooks/useMessageParser.ts:60-77`. On every render, `parseMessages(messages, isLoading)` is called with the Vercel AI SDK's `useChat` full `messages` array. For every assistant/user message it calls `messageParser.parse(message.id, extractTextContent(message))` — **passing that message's entire accumulated text on every call**, not a delta. The parser's own `state.position` cursor (keyed by `messageId`, `message-parser.ts:83`) is what makes this cheap and correct: it slices from where it left off. This is the load-bearing detail — the calling convention (always pass full text, let the parser dedupe) is as important as the parser's internals, and it's the piece Tovu must replicate exactly to reuse this pattern.

## Q4. Follow-up edits — whole files or diffs?

**The model always emits complete files, never diffs**, for both new and modified files — `<artifact_instructions>` in the system prompt is explicit: *"NEVER use diffs for new files or SQL migrations"* and *"ALWAYS use latest file modifications, NEVER fake placeholder code"* (`new-prompt.ts:164,175`). There is no diff-based edit protocol in the LLM's output format at all.

Where diffing *does* exist is the other direction — **compressing what gets sent back to the LLM as context**, and it's a genuinely interesting design (see also TRAPS: it looks partially dead):

- `app/utils/diff.ts:17` `computeFileModifications(files, modifiedFiles)` — walks a `Map<filePath, originalContent>` of "files that changed since we last snapshotted," diffs each against current content via `diffFiles()` (`diff.ts:61`, unified diff via the `diff` npm package with the header stripped to save tokens), and for each file picks **whichever is smaller, the diff or the full file** (`diff.ts:38-44`) — a token-budget optimization, not a correctness mechanism.
- `fileModificationsToHTML()` (`diff.ts:101`) would wrap that into a `<bolt_file_modifications><diff path="...">...</diff></bolt_file_modifications>` block for injection into context.
- **However**, tracing actual call sites: `FilesStore.getFileModifications()` (`app/lib/stores/files.ts:519`, calls `computeFileModifications`) is only reachable via `WorkbenchStore.getFileModifcations()` (note the typo — `workbench.ts:280`), and **that typo'd method has zero callers anywhere in the app.** The code path that's actually wired into the chat send flow is different and simpler (see Q9): `WorkbenchStore.getModifiedFiles()` → `filesToArtifacts()` (`app/utils/fileUtils.ts:107`), which sends **full file content**, not diffs, wrapped in a synthetic `<boltArtifact title="User Updated Files">` block. So the diff-compression code in `diff.ts` is exercised only by its own unit tests (`diff.spec.ts`) — it is not on the live path. See TRAPS.

**How bolt avoids regenerating unchanged files on a follow-up prompt**: it doesn't rely on the model choosing not to — the `<artifact_instructions>` say *"Only include new/modified files"* in a response, i.e. compliance is prompt-enforced, not structurally enforced. The actual token-saving lever is upstream: the **context-optimization pass** (Q7) filters which files are even shown to the model in the first place, so files outside the selected context buffer are simply invisible to the model on that turn and can't be "regenerated" because they were never in context.

## Addendum (MSG-01): constrained-output vs. prompt-nagging — tested against open-lovable's hypothesis

**Hypothesis under test** (from the open-lovable analyst, relayed by team-lead): open-lovable's default prompt (~900 lines) nags repeatedly, in ALL-CAPS threat language, about staying in scope ("only edit what was asked," restated 5+ times, "VIOLATION = FAILURE"), because its edit mechanism (whole-file regeneration) has no structural guarantee against scope creep. Its optional Morph Fast Apply mode uses a constrained `<edit>` snippet format and its prompt is shorter and calmer. Predicted mechanism: **constrained output format substitutes for prompt nagging.**

**Verdict: not supported as literally stated, but a related, narrower version of it holds — at a different layer than expected.**

**Evidence — tone and redundancy, with counts:**

bolt.diy actually ships *three* prompt variants in `PromptLibrary` (`app/lib/common/prompt-library.ts:30-45`), and they diverge sharply on exactly this axis:

| Variant | File | Lines | Default? | `CRITICAL`/`NEVER`/`FORBIDDEN` count | Scope-discipline lines |
|---|---|---|---|---|---|
| `default` (`getFineTunedPrompt`) | `new-prompt.ts` | 305 | **Yes** (`prompt-library.ts:30-34`) | 7 / 11 / 5 | **1** — "Only include new/modified files" (`new-prompt.ts:173`), stated once, plain bullet, no threat framing |
| `original` (legacy `getSystemPrompt`) | `prompts.ts` | 714 | No (selectable) | 11 / 13 / — | 0 found by grep for scope/unrelated-file language |
| `optimized` ("experimental... for lower token usage") | `optimized.ts` | 563 | No (selectable) | 12 / 11 / 4 | **Yes, and nag-heavy** — see below |

**The shipped default is calm and does not nag about scope.** Every `CRITICAL`/`NEVER`/`FORBIDDEN` in `new-prompt.ts` is doing *content* work, not *scope* work — quoting representative lines: `NEVER downloads images, only links to them` (:43), `NEVER mention XML tags or process list structure in responses` (:48), `NEVER use diffs, ALWAYS provide COMPLETE file content` (:96, Supabase-specific), `NEVER create binary files or base64-encoded assets` (:148), `CRITICAL: React Native and Expo are ONLY supported mobile frameworks` (:252). None of these police "don't touch files the user didn't ask about." The closest thing to a scope instruction actually points the *opposite* direction from open-lovable's nag — `new-prompt.ts:154-160`: *"CRITICAL RULES - MANDATORY: 1. Think HOLISTICALLY before creating artifacts: Consider ALL project files and dependencies, Review existing files and modifications, Analyze entire project context, Anticipate system impacts."* That's an instruction toward broader consideration, stated once, not a repeated warning against overreach.

**But bolt.diy's own non-default `optimized` variant is exactly the nag-heavy pattern the open-lovable analyst described**, almost line-for-line: a `# CRITICAL RULES - NEVER IGNORE` numbered checklist (`optimized.ts:250-286`) including rule 3, *"For modifications, ONLY alter files that require changes - DO NOT touch unaffected files"* (`optimized.ts:255`) — the direct scope-discipline nag — capped off with *"CRITICAL: These rules are ABSOLUTE and MUST be followed WITHOUT EXCEPTION in EVERY response"* (`optimized.ts:285`), which is functionally identical in register to open-lovable's "VIOLATION = FAILURE."

**The critical control**: `optimized.ts` uses the **same edit mechanism** as `new-prompt.ts` — always full-file rewrite, never a diff (`optimized.ts:16`: *"WebContainer CANNOT execute diff or patch editing so always write your code in full no partial/diff update"*; repeated again at `optimized.ts:283`). So within bolt.diy's own prompt library, **edit-format is held constant (full-file rewrite, in both the calm and the nag-heavy variant) while nagging tone varies** — which directly falsifies the hypothesis's literal causal claim ("full-file rewrite requires heavy scope nagging to compensate"). If edit format were the deciding variable, both bolt variants should nag equally; they don't.

**Tie to Q4 (per the ask):** bolt.diy rewrites whole files in *every* variant (confirmed in the Q4 answer above — the model never emits diffs; `computeFileModifications`/diff-based context-compression exists but is dead code, see TRAPS). Given that, the hypothesis predicts uniformly heavy nagging. Instead we see one shipped-default variant that's calm and one non-default experimental variant that's nag-heavy, with identical edit mechanics. **So the variable that actually predicts tone in bolt.diy is not "diff vs. full-file," it's something else — and the something else appears to be a different structural constraint that the calm default has and that doesn't require a diff format at all: per-file explicit addressability.** In bolt's artifact grammar, the model can only write to a file by emitting an explicit `<boltAction type="file" filePath="X">` for it (`action-runner.ts:311-339`, `#runFileAction` — there is no "resync whole project" step; `ActionRunner` only ever executes actions the parser actually extracted from the response, per Q2). A file the model doesn't mention is structurally never touched, full stop — not because the model was told not to touch it, but because there is no mechanism by which an unaddressed file could change. Combined with the context-buffer scoping in Q7 (at most 5 files are even visible to the model on a given turn when context-optimization is on), the *set of files that can possibly be affected* is structurally narrow before the model writes a single token — which plausibly removes the *need* for the "only touch what's relevant" nag that `optimized.ts` and (per the analyst) open-lovable's default both carry. This is a **narrower, refined version of the original hypothesis**: not "constrained edit-*format* (diff/patch) reduces nagging," but **"constrained edit-*addressability* (explicit per-unit selection, whether that unit is a file or a diff hunk) reduces nagging — and diff/patch format is only one way to get that constraint, not the only way."**

**What this means for Tovu, and why it's not a clean transplant:** bolt's actual discipline mechanism operates at the *file* granularity — "which of N files gets touched." Tovu's page-generation scope has already collapsed that axis to N=1 (per the brief: one HTML+CSS document, not a multi-file project) — so bolt's mechanism doesn't transfer, because the thing it constrains (file selection) doesn't exist as a problem in Tovu's design. Tovu's actual analog of "user asks for a blue button, AI restructures the page" is a **within-document** scope-creep problem (touching unrelated *regions* of the one document), which is precisely the axis open-lovable's Morph Fast Apply `<edit>` snippet format addresses and that neither of bolt.diy's prompt variants has any mechanism for (bolt never needs within-file diffs since its files are typically small, component-sized units — the whole point of "one file = one artifact action" is that files stay small enough that full-rewrite-per-file is cheap and low-risk). **This is a genuine, actionable revision to the TAKE list**: for the "stay in scope" problem specifically, open-lovable's Fast Apply constrained-snippet mechanism is the more relevant reference than anything in bolt.diy, precisely because Tovu's single-document scope makes it structurally analogous to editing *one file* in a multi-file tool — which is exactly the case bolt.diy's own file-level addressability trick can't help with (there's nothing to sub-select if there's only one file). Recommend evaluating a within-document constrained-edit format (e.g., a `<boltAction type="edit" selector="...">` region/selector-scoped patch, distinct from `type="file"` full-document replacement) as an addition to TAKE item 3, rather than assuming the calm-prompt-plus-full-rewrite combination bolt.diy ships will transfer as-is.

**On Q2 (per the ask — is the resumable parser the constrained-output mechanism, or independent?):** **Independent.** The `StreamingMessageParser`'s resumable-position scanning (Q2) is a *streaming-correctness* mechanism — it makes sure partial/truncated tag boundaries don't corrupt state while tokens arrive. It has no opinion on *what* the model chooses to write or how many files/regions it touches; it would parse a response that rewrites one file exactly as readily as one that rewrites fifty. The mechanism actually bearing on the nagging-vs-constraint question is the *action-addressability* property of the artifact grammar (one explicit tag per touched unit) discussed above, which lives in the prompt's `<artifact_instructions>` contract and in `ActionRunner`'s execution model (Q2/Q4), not in the parser's streaming-state-machine internals. Both are part of "the output protocol" broadly, but they answer different questions — one is about *robustness to partial data*, the other is about *scope of effect* — and it's worth keeping them conceptually separate when Tovu designs its own format, since Tovu will need the streaming-robustness property regardless of which scope-discipline mechanism (or none) it picks.

## Q5. Preview — generated code to live pixels

Preview is **WebContainer-native, not iframe-srcdoc**: `app/lib/webcontainer/index.ts:26` boots a singleton `WebContainer.boot({coep: 'credentialless', workdirName, forwardPreviewErrors: true})` — StackBlitz's actual in-browser Node.js runtime (a WASM-based Linux-like VM with a real filesystem, process spawner, and network stack), not a sandboxed script evaluator. `action-runner.ts` writes files into this VM's FS (`#runFileAction`, `action-runner.ts:311-339`, via `webcontainer.fs.writeFile`) and spawns the `npm run dev` (or whatever `start` action specifies) as a real child process inside the VM (`#runStartAction`, `action-runner.ts:282-309`).

- **Port discovery is event-driven**: the WebContainer instance emits a `port` event when the dev server inside the VM binds a port; `PreviewsStore` (`app/lib/stores/previews.ts`) listens and maintains `previews: atom<PreviewInfo[]>` with `{port, ready, baseUrl}`.
- **The iframe** (`Preview.tsx:981-1004`) points its `src` at the WebContainer's per-preview subdomain (`*.local-credentialless.webcontainer-api.io`, matched via regex at `Preview.tsx:380,790`) — genuinely cross-origin from the host app, not same-origin.
- **Cross-tab sync**: `PreviewsStore` also wires a `BroadcastChannel('preview-updates')` (`previews.ts:18,34-51`) so multiple browser tabs of the same bolt session stay in sync on file changes and localStorage.
- Update latency is bound by the dev server's own HMR (Vite in bolt's default templates), not by bolt's own machinery — bolt doesn't reload the iframe on every file write, it lets Vite's HMR do that inside the container and only force-reloads the iframe (`iframeRef.current.src = iframeRef.current.src`, `Preview.tsx:122`) on explicit user action (refresh button) or when a completely new preview URL/port appears.
- An `inspector-script.js` (`public/inspector-script.js`) is injected into every preview via `webcontainer.setPreviewScript()` (`webcontainer/index.ts:37-39`) — this is the element-inspector-in-preview feature (click an element in the live preview to jump to its source), unrelated to the core generation loop but a nice UX pattern: **this is the closest bolt.diy analog to what Tovu would need for "click an element in the live HTML preview to tell the AI what to change," since Tovu has no WebContainer to inject a script into a Node dev server — but it could inject the same idea directly into a static HTML preview iframe.**

Not applicable to Tovu at all: the WebContainer boot, port-binding, HMR reliance — Tovu's "preview" is trivial by comparison (render one HTML+CSS document into an iframe via `srcdoc`, no process, no server, no port).

## Q6. Error feedback loop — is it autonomous self-repair?

**No — it's human-in-the-loop, not autonomous.** `webcontainer/index.ts:42-57` listens for the WebContainer's `preview-message` event (`PREVIEW_UNCAUGHT_EXCEPTION` / `PREVIEW_UNHANDLED_REJECTION`, forwarded from the sandboxed iframe because `forwardPreviewErrors: true` was passed to `WebContainer.boot`) and sets `workbenchStore.actionAlert` with the error/stack. Shell/build failures set the same alert type from `action-runner.ts` (`onAlert?.({type: 'error', ...})`, e.g. `action-runner.ts:205-210`, `238-243`).

That alert renders as `ChatAlert.tsx` — a dismissable card with **two buttons: "Ask Bolt" and "Dismiss."** Clicking "Ask Bolt" (`ChatAlert.tsx:71-76`) calls `postMessage(`*Fix this ${preview|terminal} error* \n\`\`\`...\n${content}\n\`\`\`\n`)`, which pre-fills/submits a new user chat turn quoting the raw error/stack trace. There is **no automatic retry loop, no autonomous multi-turn self-repair** — the model only sees the error if the human clicks the button (or manually pastes the error themselves). This is a meaningfully simpler mechanism than "agentic self-healing" and is directly and cheaply portable to Tovu: catch a client-side JS error or CSS render issue in the preview iframe (via `window.onerror`/`postMessage` from the iframe), surface it as a dismissable "Ask AI to fix this" card, and on click send the same "fix this error" synthetic turn.

## Q7. Context management — what gets sent to the model

Multi-layered, and this is a meaningful cost/complexity center of the codebase:

1. **Baseline**: on every turn, the last-3-messages window is enforced when history is long (`messageSliceId = processedMessages.length - 3` when `processedMessages.length > 3`, `api.chat.ts:104-106`) — this only takes effect downstream when `contextOptimization` triggers a summary/slice (`stream-text.ts:186-194`); otherwise the SDK sends the whole `messages` array as-is (no default truncation).
2. **Opt-in "context optimization" pipeline** (`contextOptimization` flag, a Settings toggle) runs, when there are existing files, **two extra full LLM calls before the real generation call**:
   - `createSummary()` (`app/lib/.server/llm/create-summary.ts`, not fully read but invoked at `api.chat.ts:121-136`) — produces a running natural-language summary of the conversation so older turns can be dropped from the literal message list while their gist survives in the system prompt (`stream-text.ts:177-184`).
   - `selectContext()` (`app/lib/.server/llm/select-context.ts:15-234`) — **a dedicated LLM call whose only job is to pick which files belong in context.** It's given the full list of file *paths* (not contents) plus whatever's already in the "context buffer," and must respond in a constrained tag format: `<updateContextBuffer><includeFile path="..."/><excludeFile path="..."/></updateContextBuffer>` (`select-context.ts:140-153`). The prompt hard-caps this at **5 files in the buffer at a time** (`select-context.ts:167`) and explicitly tells the model "context buffer is extremely expensive." Parsed via regex (`select-context.ts:180-193`), not a structured-output API — if the model doesn't wrap its answer in the exact tag, `selectContext` throws (`select-context.ts:183`).
3. **Building the actual context text**: `createFilesContext()` (`app/lib/.server/llm/utils.ts`, referenced at `stream-text.ts:166` and `select-context.ts:105`) renders the selected `FileMap` into a fenced-code-block context buffer appended directly to the system prompt (`stream-text.ts:168-175`), plus the running summary appended below it (`stream-text.ts:177-184`) — at which point, if a summary exists, **all older messages are collapsed to just the single most recent one** (`stream-text.ts:186-194`: `messageSliceId` slices the array, or if unset, only the last message is kept). So context optimization is a real trade — it buys token savings at the cost of the model literally not seeing prior turns verbatim, trusting the summary instead.
4. **Locked files**: any file flagged `isLocked` in the incoming `files` map is listed in a dedicated system-prompt block telling the model not to touch it (`stream-text.ts:198-220`) — a user-controlled scoping mechanism (see `app/lib/persistence/lockedFiles.ts`, `app/components/workbench/LockManager.tsx`, not read in depth) that constrains generation without removing files from context entirely.
5. **Ignore patterns**: `IGNORE_PATTERNS` (`app/lib/.server/llm/constants.ts`) filtered via the `ignore` npm package (gitignore-style) strip `node_modules`, lockfiles, etc. from ever being considered (`select-context.ts:12,82-85`, `getFilePaths`, `select-context.ts:236-244`).
6. **Sanitization before sending**: every message's text is run through `sanitizeText()` (`stream-text.ts:46-52`) which strips the `__boltThought__` reasoning wrapper, `<think>` blocks, and (interestingly) **strips any `package-lock.json` file action entirely via regex** (`stream-text.ts:49`) — presumably because lockfiles are large, noisy, and never something the model needs to re-read.

This is the most Tovu-relevant "system smell": it shows that once a corpus is more than a handful of files, naive "send everything" breaks down and needs its own LLM-mediated selection step. **Tovu's page-generation scope (one HTML+CSS document) makes almost all of this unnecessary** — there's no multi-file selection problem when there's only one file — but the *summary-for-old-turns* idea might still be worth keeping for very long edit sessions on one page.

## Q8. Versioning, snapshots, rollback, undo

Two separate, non-overlapping history mechanisms exist:

**A. Chat-level snapshot/rewind (the real "version control")** — IndexedDB, two object stores (`app/lib/persistence/db.ts`): `chats` (full message array per chat) and `snapshots` (keyed by `chatId`, storing `{chatIndex: <messageId>, files: <FileMap>, summary}` — `db.ts:305-333` `getSnapshot`/`setSnapshot`/`deleteSnapshot`). A snapshot is **a full copy of the entire file map at a point in time**, not a diff chain. Rewind is a URL-param-driven read path in `useChatHistory.ts:79-119`: `?rewindTo=<messageId>` finds that message's index, finds the closest snapshot at-or-before it, slices the message array into `archivedMessages` (everything before/at the snapshot, kept but hidden) and the active `initialMessages` (everything from the snapshot to the rewind point), and reconstructs the file tree by replaying `detectProjectCommands`/`createCommandActionsString` (`useChatHistory.ts:116-119`) against the snapshot's saved files rather than replaying every LLM action historically. Additional git-like verbs: `forkChat()` and `duplicateChat()` (`db.ts:225,245`) branch a chat at a given message into a new chat id.

**B. Per-file `.history/` JSON (separate, editor-facing, not sent to the LLM)** — `ActionRunner.saveFileHistory`/`getFileHistory` (`action-runner.ts:347-374`) write a `FileHistory` JSON blob to `.history/<filePath>` **inside the WebContainer's own filesystem** (via `#runFileAction`) every time a file changes. This backs the in-editor diff view (`DiffView.tsx`, `app/styles/diff-view.css`) so the user can see a red/green diff of the current file against its last saved version in the code editor UI — a local undo/diff-view feature, unconnected to the chat/snapshot system and unconnected to what the LLM sees.

For Tovu (single document, no filesystem to write `.history/` into): the *chat-level snapshot* pattern (IndexedDB, full-content snapshot per turn, rewind-by-message-id) is the one to port — it's already file-count-agnostic and would collapse trivially to "snapshot the one HTML/CSS string at each turn." The `.history/`-in-VM mechanism is WebContainer-specific plumbing with no Tovu equivalent need (Tovu can just diff two DB rows for an in-editor diff view, no separate history files required).

## Q9. User hand-edits — direct editing and reconciliation with the AI's view

Yes — `EditorPanel.tsx` (CodeMirror) lets the user edit any file directly; edits flow through `WorkbenchStore.setCurrentDocumentContent()` (`workbench.ts:176`) which updates `unsavedFiles` (`workbench.ts:50,191-205`) and, on save, `FilesStore`.

**Reconciliation with the LLM's next turn** is the interesting part and is a **full-file resend, not a diff or silent merge**: right before the user's next chat message is actually sent, `Chat.client.tsx:511` calls `workbenchStore.getModifiedFiles()` → `FilesStore.getModifiedFiles()` (`app/lib/stores/files.ts:522-541`), which walks the store's internal `#modifiedFiles: Map<path, originalContent>` (populated whenever a file's live content diverges from its last-known-to-the-LLM content) and returns only the files whose current content differs from that baseline. Those are wrapped by `filesToArtifacts()` (`app/utils/fileUtils.ts:107-121`) into a **synthetic `<boltArtifact id=".." title="User Updated Files"><boltAction type="file" filePath="...">...full content...</boltAction></boltArtifact>` block**, prepended to the user's actual new message text (`Chat.client.tsx:516-517`), then `workbenchStore.resetAllFileModifications()` clears the diff baseline (`Chat.client.tsx:531`). So from the model's point of view, a hand-edit shows up as if *it* had just written that file — the LLM literally reads its own artifact tag format back, describing what the human changed, immediately before the human's new instruction. This is an elegant unification: the "context injection format" and the "model's own output format" are the same grammar, so there's only one artifact/action parser+renderer needed in the whole app, used in both directions.

**FilesStore also watches the WebContainer FS directly** (not shown in depth here, but referenced by the god-node ranking and by `npm install` writing `node_modules`/lockfiles) to reconcile tool-driven changes (e.g. `npm install` rewriting `package-lock.json`) that didn't come from either the LLM's artifact or the user's editor — a third source of file mutation the store has to track.

## Q10. Security posture — isolation of generated/untrusted code

- **Execution isolation**: WebContainer itself is the primary boundary — it's a WASM-sandboxed Node runtime running client-side, and it serves live previews from a **separate, dynamically-generated subdomain** (`*.local-credentialless.webcontainer-api.io`, confirmed at `Preview.tsx:380,790`), i.e. genuinely cross-origin from the host `bolt.diy` origin, not same-origin. `coep: 'credentialless'` (`webcontainer/index.ts:27`) is required for the SharedArrayBuffer-based WASM VM to work under cross-origin isolation.
- **Iframe sandboxing**: the preview `<iframe>` carries `sandbox="allow-scripts allow-forms allow-popups allow-modals allow-storage-access-by-user-activation allow-same-origin"` (`Preview.tsx:992,1003`, also a copy at `Preview.tsx:523` for a downloaded-static-export preview). **Worth flagging**: `allow-scripts` + `allow-same-origin` together is a widely-known sandbox-weakening combination (a same-origin sandboxed document with script execution can, in principle, remove its own `sandbox` attribute via the parent's DOM or otherwise interact with same-origin state) — mitigated here only because "same-origin" for that iframe is the *webcontainer-api.io* subdomain, not the host app's origin, so the practical blast radius is contained to the preview's own throwaway origin, not bolt.diy's session. Still worth a second look if Tovu copies this sandbox string verbatim onto an iframe that's genuinely same-origin with the admin app.
- **Host app CSP / headers**: `app/lib/security.ts:83-121` defines a real CSP (`default-src 'self'`, `frame-src 'none'`, `object-src 'none'`, HSTS in prod, `Permissions-Policy` disabling camera/mic/geolocation/payment) plus rate limiting (`checkRateLimit`, `security.ts:24-65`, in-memory per-IP-per-endpoint sliding window) — **but see TRAPS: this is not applied to the LLM-calling routes.**
- **API key handling**: user-supplied provider API keys travel as a `Cookie` header (`apiKeys` cookie, parsed at `api.chat.ts:70-74`), not sent to the LLM provider through any server-persisted secret store — i.e. bolt.diy is architected for **BYOK (bring your own key), client-held**, not a server-side credential vault. `validateApiKeyFormat()` (`security.ts:126-144`) does only a crude length/placeholder check, no real verification.
- **Generated-file restrictions**: the system prompt forbids binary files and base64-encoded assets outright (`new-prompt.ts:148-150,176`) — a content-level (prompt-enforced, not structurally-enforced) restriction that keeps the artifact format text-only, incidentally simplifying the parser and reducing what a malicious/compromised model output could smuggle through the pipe.
- **No sanitization of file content before writing to the container FS** — `#runFileAction` (`action-runner.ts:311-339`) writes `action.content` verbatim; nothing in the traced path HTML-escapes or validates file contents. This is fine in bolt's model (the WebContainer sandbox is the trust boundary, not the file writer), but **is the one place Tovu's design must diverge hard**: Tovu pages are rendered server-side into real end-user-facing HTML (`src/server/http/site/render.ts`) with no per-page sandboxed execution environment, so `action.content`-equivalent (the LLM's generated HTML/CSS) must be sanitized/validated before it ever reaches that render path — bolt.diy has no equivalent mechanism to borrow here because it has never needed one (its "production" output is the user's own deployed app, deployed by the user's own action, not served live from bolt's origin).

## TAKE — ranked, with why / what it replaces / port difficulty

1. **The resumable streaming artifact parser** (`app/lib/runtime/message-parser.ts`, driven per Q3's note as `parser.parse(messageId, fullAccumulatedText)` every render). **Why**: this is the one piece of genuinely hard-won engineering in the repo — a hand-rolled scanner that tolerates arbitrary truncation mid-tag, mid-attribute, or mid-file-content without special-casing, and streams partial file content before the closing tag arrives. **Replaces**: naive "wait for the full response then regex it" approaches, which either block the preview until generation finishes or corrupt on truncation. **Port difficulty: Low-Medium.** Strip it down to one action type (`file`, maybe `style`/`script` as sub-kinds) since Tovu doesn't need `shell`/`start`/`supabase`; keep the `messageId`-keyed resumable-position state machine and the "always pass full accumulated text" calling convention verbatim — that discipline is the actual invention, not the tag grammar.
2. **The `<design_instructions>` block of the system prompt** (`new-prompt.ts:190-249`). **Why**: ~60 lines of concrete, opinionated, WebContainer-agnostic design direction (contrast ratios, spacing grid, font pairing rules, a self-check checklist) — exactly the shape of guidance Tovu needs for "AI generates a bespoke page," and it needs zero adaptation since none of it references the sandbox. **Replaces**: writing this from scratch. **Port difficulty: Trivial** — copy near-verbatim, swap the `designScheme` interpolation point for whatever brand/theme input Tovu collects.
3. **The `<artifact_instructions>` contract shape** (max one artifact per response, explicit ordering rules, "always full content never diffs," binary-file ban). **Why**: it's the prompt-side half of item 1's parser and is what actually keeps model output structurally predictable. **Replaces**: ad hoc "please output HTML" instructions that invite prose-wrapped or partially-fenced output. **Port difficulty: Trivial-Low** — rewrite the action-type list down to Tovu's single `file` (or a `document` action containing `<style>`/body markup), drop all shell/package.json/Supabase-specific ordering rules. **Revision per MSG-01 (see the constrained-output-vs-nagging addendum after Q4)**: bolt.diy's calm default prompt gets away with almost no scope-discipline nagging because its artifact grammar constrains scope at the *file* level (explicit per-file action addressing — an unaddressed file is structurally never touched). Tovu's single-document scope collapses that axis to nothing, so this specific benefit does not transfer as-is. For the "user asks for a blue button, AI rewrites the page" failure mode specifically, evaluate a **within-document constrained-edit action** (a selector/region-scoped patch action, distinct from a full-document-replace action) modeled on open-lovable's Morph Fast Apply `<edit>` snippet format rather than assuming bolt's file-level trick solves it — bolt.diy has no equivalent mechanism at the sub-file level to borrow, because it has never needed one.
4. **Full-content resend for reconciling user hand-edits** (`getModifiedFiles()` → `filesToArtifacts()`, Q9). **Why**: it's a strikingly simple solution to "the AI's model of the file may be stale after a human edit" — reuse the exact same artifact-tag grammar to describe the diff-since-last-turn to the model, so there's only one grammar in the whole system, used bidirectionally. **Replaces**: a bespoke "describe what changed" prompt-engineering problem. **Port difficulty: Low** — Tovu only has one file, so this degrades to "if the user hand-edited the HTML/CSS in the code view since the AI's last turn, prepend the current full HTML/CSS wrapped in the same artifact tag before the user's next instruction."
5. **Snapshot-based chat/version history with rewind** (`app/lib/persistence/db.ts`, Q8: `chats` + `snapshots` IndexedDB stores, `?rewindTo=<messageId>` URL param). **Why**: gives "undo to any prior AI turn" for free once you're already storing full-document snapshots per turn — and Tovu's use case (one document) makes each snapshot cheap (a single HTML+CSS string, not a whole file tree). **Replaces**: needing to build versioning from scratch; this is a good reference shape even though Tovu will use its own SQL tables (posts already have revisioning precedent to check against) rather than IndexedDB. **Port difficulty: Low** — the pattern (snapshot per AI turn, keyed by message/turn id, rewind by replaying from nearest snapshot) transfers; the storage engine does not.
6. **Human-in-the-loop error-to-repair flow** (`ChatAlert.tsx`, Q6: catch a preview JS error, show a dismissable "Ask AI to fix this" card, on click resend the error as a quoted chat turn). **Why**: cheap, safe, avoids the failure modes of autonomous multi-turn self-repair (runaway loops, silent wrong fixes) while still closing the loop for the common case. **Replaces**: either no error feedback at all, or an over-engineered autonomous retry loop Tovu doesn't need yet. **Port difficulty: Low** — Tovu's preview iframe can catch `window.onerror`/console errors the same way (or, since Tovu has no live JS execution requirement necessarily, at minimum catch HTML/CSS validation issues) and reuse the same "quote it back to the model" pattern.
7. **The "make the model choose its own context" pattern for scaling** (`select-context.ts`, Q7) — **lower priority for Tovu now** (single document = no file-selection problem) but worth keeping in mind **if** Tovu's page-gen scope ever grows to "generate/coordinate multiple related pages" — the tagged-response file-selection call is a reusable pattern for that future, not something to build today.

## LEAVE — deliberately not taking, and why

- **WebContainer entirely** (boot, FS, process spawning, port events, HMR reliance) — Tovu has no multi-file project, no npm install, no dev server per page. A Tovu page is one rendered document; the "preview" is just injecting the generated HTML+CSS into an iframe via `srcdoc`, not booting a VM.
- **`shell` / `start` / `build` action types and their entire executor branch in `action-runner.ts`** (`#runShellAction`, `#runStartAction`, `#runBuildAction`, `#validateShellCommand`, `#createEnhancedShellError`) — no shell exists to run commands in; none of this logic has a Tovu analog.
- **`supabase` action type and the whole `<database_instructions>` prompt block** — Tovu is not provisioning a database per page; if Tovu pages ever need dynamic data it'll be through Tovu's own existing Drizzle/SQLite layer, not a client-authored migration system.
- **The context-optimization LLM-selects-files subsystem** (`createSummary`, `selectContext`, the whole "context buffer," the `<updateContextBuffer>` tag protocol) — solves a many-files problem Tovu's single-document scope doesn't have. Revisit only if scope expands (see TAKE #7).
- **`<mobile_app_instructions>`** — React Native/Expo scaffolding, wholly irrelevant.
- **Electron packaging, GitHub/GitLab/Netlify/Vercel deploy integrations, MCP tool-calling support** (`mcpService`, `api.mcp-*` routes) — all real engineering effort in the repo but solving "bolt is a whole dev environment" problems Tovu's single-page-generation feature does not have.
- **The `.history/`-inside-the-VM per-file diff mechanism** (`saveFileHistory`/`getFileHistory`) — Tovu already has a database; an in-editor diff view can just diff two DB-stored revisions instead of writing history files into a filesystem that doesn't exist for Tovu.
- **Cross-tab `BroadcastChannel` preview sync** — solves a "same session open in two browser tabs, both looking at the same live dev server" problem; low priority unless Tovu explicitly wants multi-tab editing of the same page.

## TRAPS — fragile spots, dead code, and design regrets visible in the source

1. **Rate limiting is defined for the LLM endpoints but never applied to them.** `app/lib/security.ts:12` explicitly configures `/api/llmcall`: 10 requests/minute — but `app/routes/api.llmcall.ts:12`, `app/routes/api.chat.ts:18`, and `app/routes/api.enhancer.ts:8` **never call `withSecurity()` or `checkRateLimit()`.** `withSecurity` is applied only to the OAuth/integration routes (GitHub, GitLab, Netlify, Vercel, Supabase user/stats endpoints — confirmed by grep across `app/routes/`). The most expensive, most abuse-prone endpoints in the app (the ones that actually call an LLM provider and cost real money per request) are the *only* ones with no rate limiting at all. This is the sharpest finding in the codebase and a direct warning for Tovu: **wire the rate limiter to the generation endpoint from day one**, don't let it become a "we configured it but forgot to apply it" gap.
2. **The token-saving diff-compression mechanism for context (`app/utils/diff.ts`, `computeFileModifications`/`fileModificationsToHTML`) looks like dead code on the live path.** It's fully implemented and unit-tested (`diff.spec.ts`), and `FilesStore.getFileModifications()` calls into it — but the only caller of that method, `WorkbenchStore.getFileModifcations()` (note the typo in the method name itself, `workbench.ts:280`), has **zero call sites anywhere in the app** (confirmed by repo-wide grep). The actual live path for both user-hand-edit reconciliation and (per the prompt, though not verified beyond the prompt claim) follow-up-diff-avoidance is the simpler full-content `filesToArtifacts()` mechanism (Q9). Left-behind refactor — a real engineering investment (diff-vs-full-content token optimization) that isn't wired up. Worth grepping bolt.diy's git history/issue tracker before assuming this is intentional vs. abandoned, but from source alone it reads as regret. Don't port the diff-compression idea without first deciding whether Tovu actually needs it (a single HTML+CSS document is rarely large enough to make diff-vs-full-file token savings matter).
3. **`allow-scripts allow-same-origin` together on the preview iframe** (`Preview.tsx:992,1003,523`) is a textbook sandbox-weakening combination that security linters flag by default. It's *probably* fine here because "same-origin" resolves to the WebContainer's own throwaway subdomain, not bolt.diy's real origin — but it's exactly the kind of pattern that becomes a real vulnerability if copied onto an iframe that ends up same-origin with the parent app (which is a live risk for Tovu, since a Tovu preview iframe embedded in the *admin* app is much more likely to end up same-origin-ish than bolt's cross-subdomain WebContainer preview). **If Tovu copies this sandbox string, re-derive it from scratch for Tovu's actual origin topology — don't copy-paste.**
4. **`selectContext()`'s output parsing is regex-over-freeform-text, not structured output**, and throws on any deviation (`select-context.ts:180-183`: `if (!updateContextBuffer) throw new Error('Invalid response...')`) — a single malformed model response (missed closing tag, wrapped in markdown fences, etc.) hard-fails the whole context-optimization pass with no retry/fallback visible in the traced code. Low priority for Tovu (this subsystem isn't being ported per LEAVE), but a general lesson: any Tovu-side "ask the model to emit a control-format response" step should have a fallback path, not a bare throw.
5. **Two independent, overlapping "what changed" trackers** exist simultaneously: `FilesStore.#modifiedFiles` (baseline-diff tracking for the Q9 hand-edit reconciliation) and the per-file `.history/` JSON files (`action-runner.ts`, Q8-B, for the in-editor diff view). They're never reconciled with each other and serve different consumers (LLM context vs. editor UI) but track conceptually the same fact ("has this file changed since X"). Not a bug, but a maintenance smell worth avoiding in Tovu's simpler single-document design — one "has the document changed since the AI's last turn" boolean/timestamp should suffice for both the reconciliation-on-send logic and any in-editor diff view.
6. **The auto-continue-on-truncation mechanism re-invokes `streamText()` recursively inside its own `onFinish` callback** (`api.chat.ts:221-299`, calling `streamText()` again at line 269 and merging into the same `dataStream`) with a hard cap `MAX_RESPONSE_SEGMENTS` (`api.chat.ts:252-254`) but no exponential backoff or circuit breaker beyond the flat cap — on a model that reliably hits its token ceiling every turn (e.g. a small `maxTokens` misconfiguration), this could chain up to that cap on every single response, multiplying latency and cost silently. Worth a bounded-retry-with-visible-cost-warning pattern if Tovu adopts a similar continuation mechanism for long HTML documents.

## Addendum: prevention vs. reversal (MSG-02)

**Question tested**: given the earlier finding that bolt.diy's calm default prompt breaks the "heavy nagging compensates for weak edit mechanism" correlation, team-lead's working theory is that bolt.diy's real answer to "the AI wrecked my page" is a *third strategy* — not prompt-level prevention, not a constrained diff/patch format, but **cheap reversal**: snapshot-per-turn plus rewind-to-message, backstopped by streaming visibility that lets the user watch generation happen and stop it early. Three sub-questions: (1) quantify the tone difference precisely — is bolt just as nagging per line, only shorter overall; (2) confirm/refute that reversal (not prevention) is doing the real work, including whether anything actually constrains edit scope at the prompt/runtime level versus rewind being the whole answer; (3) git-archaeology `diff.ts` — was a diff mechanism tried and abandoned, with evidence, not inference.

### 1. Is the tone difference real, or just proportionally shorter?

**Real, and it is not a uniform "shorter but equally shouty" story — it's concentrated almost entirely on the specific scope-discipline axis.**

Overall "shouting density" (count of `CRITICAL`/`NEVER`/`ALWAYS`/`MUST`/`FORBIDDEN` divided by line count) is actually *comparable* across all three of bolt's own prompt variants — so if the question were "does bolt shout as much per line, generically," the answer would be close to yes:

| Variant | Lines | Shouting words (`CRITICAL`+`NEVER`+`ALWAYS`+`MUST`+`FORBIDDEN`) | Density (words/line) |
|---|---|---|---|
| `default` (`new-prompt.ts`) | 305 | 7+11+10+1+5 = 34 | 1 per ~9 lines |
| `original` (`prompts.ts`) | 714 | 11+13+15+0(not counted)+0 = ~39+ (undercounted, FORBIDDEN not searched) | roughly similar order |
| `optimized` (`optimized.ts`) | 563 | 12+11+14+8+4 = 49 | 1 per ~11 lines |

But **on the specific axis the hypothesis is actually about — "don't touch unrelated code/files" — the default has essentially none, and the numbers above are almost entirely doing *content*-restriction work, not *scope*-restriction work.** Exhaustive re-grep of `new-prompt.ts` for scope/isolation language (`unrelated|unaffected|untouched|unchanged|isolated|scope|only.*file|preserve|don't touch`, etc.) turns up exactly:
- `new-prompt.ts:173`: *"Only include new/modified files"* — one plain bullet inside `<artifact_instructions>`, no capitalization emphasis, no threat framing, not repeated anywhere else in the file.
- `new-prompt.ts:24`: *"Focus on addressing the user's request without deviating into unrelated topics"* — this is about conversational/topical focus in prose replies, not code-editing scope; it's the wrong axis and shouldn't be counted as a scope-of-edit nag.
- `new-prompt.ts:151`: *"Split logic into small, isolated parts (SRP)"* — architecture-quality guidance (single-responsibility), not "don't touch files you weren't asked about."

Zero instances of `VIOLATION`, `FAILURE`, `ABSOLUTE`, `WITHOUT EXCEPTION`, or `NEVER IGNORE` anywhere in the default prompt. Contrast with bolt's own non-default `optimized.ts`, which wraps its equivalent scope rule in exactly that register: `# CRITICAL RULES - NEVER IGNORE` (header, `optimized.ts:250`) → `3. For modifications, ONLY alter files that require changes - DO NOT touch unaffected files` (`optimized.ts:255`) → `CRITICAL: These rules are ABSOLUTE and MUST be followed WITHOUT EXCEPTION in EVERY response` (`optimized.ts:285`, closing the whole checklist). **So: not "equally nagging, just shorter." The default's overall emphasis-word budget is spent on content rules (Pexels-not-Unsplash, no binaries, Supabase safety); the scope-discipline nag specifically is present in only one bolt.diy variant (`optimized`, non-default) and absent (bar one calm bullet) in the shipped default.**

### 2. Is reversal doing the real work, or is there real prevention too?

**Confirmed, with an important asymmetry the theory didn't anticipate: the "watch it stream and stop early" half of the reversal story is a UI affordance sitting on top of an admittedly unfinished mechanism, while the snapshot/rewind half is fully built and robust.**

- **Ex-ante scoping does exist** (already established in the MSG-01 addendum above) — per-file explicit action addressing (`action-runner.ts:311-339`, a file can only change if the model emits an explicit `<boltAction type="file" filePath="X">` for it) and the optional context-buffer cap (`select-context.ts`, max 5 files visible). These are real, if modest, prevention mechanisms — they constrain *which* files can possibly be touched, not what happens within a touched file.
- **Mid-stream stop is real at the UI level**: `Chat.client.tsx:221-228` defines `abort()`, calling the AI SDK's `stop()` (halts the token stream), sets `chatStore.aborted = true`, and calls `workbenchStore.abortAllActions()`; it's wired to a visible Stop button via `handleStop={abort}` (`Chat.client.tsx:634` → `BaseChat.tsx:452`). So yes, the user can watch generation happen and click Stop mid-stream — that part of the theory is confirmed as a real, present feature.
- **But the action-cancellation half of that button is an explicit stub**: `WorkbenchStore.abortAllActions()` — the method actually responsible for cancelling in-flight or queued WebContainer actions (file writes, shell commands already dispatched) — is, verbatim:
  ```ts
  abortAllActions() {
    // TODO: what do we wanna do and how do we wanna recover from this?
  }
  ```
  (`app/lib/stores/workbench.ts:460-462`). Clicking Stop halts the LLM from emitting *further* tokens, but there is no implemented mechanism to roll back or even cleanly cancel WebContainer actions that were already dispatched from tokens received before the click — despite `ActionState` having a per-action `AbortController`/`abort()` (`action-runner.ts:102-113`) that `abortAllActions()` could call and simply doesn't.
- **Snapshot/rewind, by contrast, is fully implemented and is the one mechanism in this whole area with no TODOs or dead paths**: the IndexedDB `chats`+`snapshots` stores, `?rewindTo=<messageId>`, full-file-map-per-turn snapshotting, and replay logic (all cited in the original Q8 answer above) work end-to-end.

**Net conclusion for Q2: confirmed, but refine the theory** — it's not "streaming+early-stop *and* snapshot/rewind" as two co-equal legs of a reversal strategy. It's: **prevention is present but thin (file-level addressability + optional context capping); the "stop mid-stream" affordance is visibly wired in the UI but its actual damage-control logic was never finished (a literal TODO); and rewind-to-snapshot is the only fully-realized, robust safety net in the system.** If Tovu builds a similar "watch it stream, can stop" UI, budget for the action-cancellation logic explicitly — bolt.diy's own code is a documented example of that part being harder than it looks and getting left unfinished.

### 3. `diff.ts` archaeology — tried and abandoned, or never live?

**Tried, live, and later abandoned by drift rather than deliberate reversal — confirmed with dates and PRs, but no commit explicitly states a rationale.**

- **2024-07-25, commit `2cb3f09` "feat: submit file changes to the llm (#11)"** (author: Dominic Elm) — this is the commit that introduced `diff.ts` (`computeFileModifications`/`fileModificationsToHTML`, +108 lines) as a new file, in a PR that *also* touched `Chat.client.tsx` (+45 lines), `action-runner.ts`, `files.ts`, `workbench.ts`, `api.chat.ts`, and — tellingly — `app/lib/.server/llm/prompts.ts` (+74 lines). That last file is today's `original`/legacy prompt variant (`prompts.ts`), and it still carries the diff-aware language this PR evidently added: *"Review ALL previous file changes and user modifications (as shown in diffs, see diff_spec)"* (`prompts.ts:323`), *"ALWAYS use the latest file modifications... applied to the most up-to-date version of the file"* (`prompts.ts:329`), *"Include ALL code, even if parts are unchanged"* (`prompts.ts:376`). This is strong evidence the diff mechanism **was live and paired with a prompt written to consume diff-tagged context**, not dead on arrival.
- **2025-02-27, commit `b98485d` "feat: make user made changes persistent after reload (#1387)"** (author: Anirban Kar — different person, ~7 months later) — adds a **new, parallel** method, `getModifiedFiles()`, inserted directly next to the untouched old `getFileModifcations()` in `workbench.ts` (diff shows the new method added right below the old one — old one not removed, not refactored, not called from anywhere by this or any later commit), and wires the new full-content `filesToArtifacts()` path into `Chat.client.tsx` and `fileUtils.ts`. The PR's own sub-commit messages — *"save user made changes persistent," "remove artifact from user message on the UI," "message Id generation fix"* — frame this as solving reload-persistence, not as "replace the diff mechanism." Nothing in the commit body says why the old path was dropped instead of extended; it just goes unused from this point on.
- **No commit ever modifies `computeFileModifications` again** — a full-history `git log -S "computeFileModifications"` returns only commit `2cb3f09`, i.e. the function was written once (2024) and never touched since, consistent with quiet abandonment rather than an active, maintained alternative.
- **Timeline context**: `new-prompt.ts` (today's calm default) was added **2025-04-24**, commit `3cafbb6` — roughly two months *after* the code had already moved to full-content resend. So by the time the calm prompt was written, the live mechanism no longer used diffs, which is at least consistent with (though not proof of) why the calm prompt never mentions a diff format at all — there was nothing left to instruct the model about.

**Conclusion for Q3: confirmed that a diff-based context mechanism was built and genuinely used, then displaced by a full-content mechanism added independently ~7 months later for an ostensibly different reason (reload persistence) — but I found no commit message or PR description that explicitly states "we're moving away from diffs because X."** That specific causal claim is inference from the code+timeline evidence, not a sourced fact, and should be reported to Tovu stakeholders with that caveat attached.

### Answering the three questions as requested — confirmed / refuted / mixed

1. **Tone difference is real — confirmed**, and it's concentrated specifically on the scope-discipline axis (near-zero in the shipped default, present with threat-register framing in bolt's own non-default `optimized` variant), not a uniform "shorter but equally shouty" pattern.
2. **Reversal-over-prevention theory — confirmed, with a refinement**: prevention exists but is thin (file-addressability + optional context cap); the "watch and stop early" leg of the theory is a real UI feature sitting on top of an explicitly unfinished (TODO-stubbed) cancellation mechanism; rewind-to-snapshot is the one genuinely complete, robust safety net.
