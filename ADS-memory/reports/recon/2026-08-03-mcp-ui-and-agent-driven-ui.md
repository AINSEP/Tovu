- Date: 2026-08-03
- Author: Claude Sonnet 5 (dispatched software-architect recon), on request from team-lead
- Status: COMPLETE — all three parts done. Written incrementally; treat later sections as more provisional than earlier ones (see "Scope honesty" at the end for exactly what's verified vs. judgment).

## SECURITY FINDING (confirmed by static trace, 2026-08-03) — the confirmation token leaks to the model in the real pipeline

**`content_post_delete`'s confirmation token, which the code and its tests assert never reaches model-visible text, does reach model-visible text on Tovu's actual call path.** The design is sound; a generic proxy two layers away flattens it. Static trace only — no live delete was run against the dev server, per instruction.

**Reachability: confirmed live, not dead code.** `content_post_delete` is one of Post's "6 of 6" wired tools (`src/assistant/tool-registrations.ts:13-19` domain manifest), registered into `registry` at daemon boot (`src/assistant/agent-daemon-server.ts:143-146`). That same `registry`-backed `toolExecutor` is the one wired into `/api/delegated-tool-calls` (`agent-daemon-server.ts:383`, `registerDelegatedToolRoutes(app, { toolExecutor, ... })`) — the one and only route `@jini-ai/mcp`'s `execute_delegated_tool` tool calls (`packages/mcp/src/server/tools/delegated-tool.ts:98`, `POST /api/delegated-tool-calls`). This is the tool the spawned Claude Code CLI is actually given via `.mcp.json` injection. No gap in the chain; every hop verified by reading the code that performs it, not by inference.

**The leak, hop by hop:**

1. `content_post_delete`'s first call (no token supplied) returns `buildUIToolResult({ modelText, ui })` — an object shaped `{ content: [{type:"text", text: modelText}, {type:"resource", resource:{uri, mimeType, text: htmlContainingToken}}] }` (`src/features/post/tool-registrations.ts:446-453`, building on `delete-confirmation-ui.ts`'s HTML, which embeds the raw token in an inline `<script>` as `var TOKEN = "...";`). This return value is exactly what the code's own comment says it is: the token is genuinely absent from `modelText`.
2. `@jini-ai/daemon`'s `ToolExecutor.execute` sets `rawOutput = await handler(...)` — the object above, completely unmodified — and returns it as `ToolExecutionResult.output` (`packages/daemon/src/tool-executor.ts:357-361`). `truncateOutput` is a no-op here because it only slices strings (`tool-executor.ts:161-165`); the resource object passes through whole.
3. `/api/delegated-tool-calls` sends `{ result: ToolExecutionResult }` back to the calling MCP tool. `execute_delegated_tool`'s handler returns `data.result` **verbatim** — the whole `{status, output, ...}` object, `output` still containing the resource block with the token inside it (`packages/mcp/src/server/tools/delegated-tool.ts:98-99`).
4. `@jini-ai/mcp`'s generic tool-call wrapper converts that return value to the actual MCP `CallToolResult` via `okResult()`: **`const text = typeof payload === 'string' ? payload : JSON.stringify(payload, null, 2); return { content: [{ type: 'text', text }] }`** (`packages/mcp/src/server/tool-protocol.ts:73-76`). `payload` here is the whole `ToolExecutionResult`, not a string, so the entire thing — text block, resource block, HTML, embedded token — is `JSON.stringify`'d into **one plain MCP text content block**. This is the generic proxy every Jini-registered tool goes through; it has no special case for a resource-bearing result and no way to know one is present.
5. That text block is `execute_delegated_tool`'s tool result, as seen by the calling agent (Claude Code CLI). Per Part 1's trace, `claude-stream.ts`'s `content: stringifyToolResult(block.content)` is what turns *any* tool result — this one included — into the plain string that becomes part of the model's own conversation context for its next turn, and separately what Tovu's SSE bridge forwards to the browser transcript.

**Net effect: the model receives the full HTML, including the literal confirmation token, as an ordinary tool result it can read.** There is nothing in this call path resembling an MCP-UI-aware host that withholds `resource.text` from the model — `execute_delegated_tool` is a content-blind JSON-stringify proxy. A model that noticed the token in its own tool-call history could call `execute_delegated_tool({toolId:"content_post_delete", input:{id, kind, confirmationToken:"<the token>", decision:"confirm"}})` on its very next turn and complete the delete with zero human involvement — exactly the outcome `pending-confirmations.ts`'s own module doc says the design prevents ("the agent must not be able to complete the delete on its own").

**Why the test didn't catch this.** `fake-mcp-ui-host.ts`'s own header is explicit about what it does and doesn't model: it "deliberately does NOT model showing the HTML to the model — that is the point." It asserts the token is absent from `buildUIToolResult`'s `modelText` field, which is true and never in question. It never exercises `execute_delegated_tool`/`okResult`'s `JSON.stringify`, because that code lives in a different package (`@jini-ai/mcp`) that the fake host stands in for, by design. The test certifies the wire-shape contract Tovu's own code is responsible for; it was never positioned to catch a leak introduced by the generic MCP proxy sitting between that contract and the real model. Structurally the same failure shape as a jsdom-certified dialog that's visibly broken in a real browser: the test is correct about what it tests, and what it tests isn't the full path.

**What would prevent this (not proposing a fix — flagging what the actual gap is):** `okResult` would need to special-case a `{content: [...]}`-shaped payload and pass its content blocks through as the `CallToolResult`'s own `content` array (preserving the `type: "resource"` block as a genuine resource rather than JSON-stringifying it into text), the way an MCP-UI-aware relay is supposed to. Today it treats every non-string handler return as opaque data to narrate, which is the right behavior for the other ~140 wired tools and the wrong one for exactly this one.

**Status: live, not theoretical.** Not fixed here per instruction — reporting only.

### Follow-up finding: fixing the proxy bug above would not fix the underlying property — the transport is unsound at a deeper layer

Team-lead's second question was whether headless Claude Code CLI withholds MCP-UI HTML from its own model context — the thing that would need to be true for MCP-UI's security model to hold here even in principle. Two independent lines of evidence, converging:

**The structural argument, which needs no external research and is the most certain point in this whole finding:** MCP-UI/MCP Apps' security model requires a HOST — an entity that renders the iframe *to a human* and waits for *that human* to act. Tovu's daemon spawns Claude Code CLI in headless/`-p`/stream-json mode specifically because there is no human watching that process at all — its output is captured programmatically by `claude-stream.ts` and relayed as structured events, not displayed to anyone. A process with no display and no human attention cannot play the host role, independent of whether the CLI's code technically implements the MCP Apps extension. This isn't a bug to fix; it's what headless mode means. The three actors in this pipeline are: the model (inside the CLI process), the CLI's own stdout parser (mechanical, headless), and Tovu's browser (has a human, but is not the MCP client and never receives the raw MCP result — Part 1's finding). None of the three is simultaneously "the MCP client" and "has a human in front of it," which is the one precondition MCP-UI's whole design assumes.

**The documentary evidence, checked rather than assumed, and pointing the same direction:** I found no evidence Claude Code (the CLI product, `code.claude.com` / `anthropics/claude-code`) implements MCP Apps/MCP-UI at all, in any mode. Its complete official MCP reference page (fetched and searched in full) mentions MCP's older, separate "resources" primitive (`resources/list`/`resources/read`, referenced via `@server:protocol://path` mentions) and never once mentions `ui://`, MCP Apps, SEP-1865, sandboxed iframes, or `text/html;profile=mcp-app` — the exact vocabulary that would be present if it did. Every MCP Apps-related bug report I found in a repeated, targeted search is filed against `anthropics/claude-ai-mcp` (claude.ai, the web product) or names "Claude Desktop" explicitly — never `anthropics/claude-code`. One search result states plainly that "Claude Desktop advertises MCP Apps capability with the MIME type text/html;profile=mcp-app" — Desktop, a different product with its own MCP client, not the CLI Tovu spawns. This is consistent, convergent absence across every source checked, not one missing mention — I'm treating it as high confidence, not proven by a single explicit "Claude Code does not support X" statement, in keeping with this report's evidence standard.

**Correction on sequencing, from team-lead's review — confirmed correct.** The CLI-capability question is moot as an explanation of *today's* leak: by the time anything crosses the actual MCP JSON-RPC wire into the Claude Code CLI process, `okResult()` has already reduced it to a single opaque text block — there is no `{type:"resource"}` block on the wire for the CLI to receive, withhold, or mishandle in the first place. My original framing ("the one open item that could undercut the security story") implied a parallel, alternative risk; it's actually a **second, deeper barrier standing behind the first one**, not an independent question. Both must be true — data must reach the CLI as a genuine resource (it doesn't, today), *and* something must then withhold that resource from the model (nothing would, even if it arrived) — for MCP-UI's security model to hold on this transport. This matters for the "make it work" question below, not for explaining the current leak: fixing `okResult()` alone would surface the CLI-capability gap as the *next* failure, not close it.

Sources: [Claude Code MCP reference](https://code.claude.com/docs/en/mcp) (fetched in full, searched for `ui://`/MCP Apps/SEP-1865/iframe — zero matches outside the unrelated `resources/list` primitive); MCP Apps host-adoption and bug-report pattern across [anthropics/claude-ai-mcp issues](https://github.com/anthropics/claude-ai-mcp/issues/165) (iframe handshake, Claude Desktop), [modelcontextprotocol/ext-apps#671](https://github.com/modelcontextprotocol/ext-apps/issues/671) (Claude Desktop/claude.ai)

### Blast-radius sweep — is the confirmation token the only withheld-by-design payload going through this leak?

Team-lead's framing correction, and it's right: the defect isn't in `mcp-ui.ts`, it's in `okResult()` — a **generic** wrapper that `JSON.stringify`s any non-string handler return into model-visible text. MCP-UI is just the first thing that put a secret through it. So the real question is whether anything *else* wired into the delegated-tool surface returns a payload meant to be withheld from the model — credentials, signed URLs, session material, raw tokens.

Swept every domain's `tool-registrations.ts` (Tovu's `src/**` and Jini's `packages/cms/src/**`, 21 domains) for secret-shaped identifiers and return statements. Findings, each checked at the return site, not assumed from the field name:

- **`content_post_delete`'s confirmation token — the only live leak.** Confirmed above.
- **Magic-link sign-in (`members_request_magic_link`)** — safe by construction. `requestSignInLink` (`src/members/write-service.ts:96-99`) is typed `Promise<{ delivered: true }>` — a **constant** response, deliberately, per its own doc: "the anti-enumeration mitigation ADR-030 OQ-8 flags as a launch-gate precondition." The raw token is minted, hashed, stored, and mailed — it never appears in any value the handler returns.
- **Newsletter confirmation (`newsletter_resend_confirmation`)** — same shape. Calls `issueConfirmationToken` (which returns `{tokenId, expiresAt}` — an opaque id, not the raw secret) and **discards that return value entirely**, returning a hardcoded `{ delivered: true }` instead (`src/newsletter/tool-registrations.ts:427-444`).
- **Webhook signing secrets (`integrations`)** — no secret field exists on the record to leak. Only `secretVersion`/`previousSecretVersion` (integers) are exposed (`src/integrations/tool-registrations.ts:96-97`); rotation/generation is explicitly out of scope for this pass per the file's own header.
- **Password hashes (`identity`)** — explicitly excluded from every model-facing projection. `src/identity/tool-registrations.ts:251`: "The load-bearing omission is `UserRecord.passwordHash`: INV-05 keeps hashed secrets server-side."
- **Media, workspace, plugins** — no token/secret/credential-shaped identifiers found in any handler at all.

**The more important finding is *why* the sweep comes back this clean.** This codebase already has an established, load-bearing convention for exactly this class of problem, and it predates and is unrelated to MCP-UI: `packages/cms/src/core/tools/registration-kit.ts`'s `ACTOR_CLASS_RULES_REQUIRING_CONFIRMATION_TRANSPORT` (a `Set(["confirmer-must-equal-own-delegatedBy"])`) makes `assertToolIsWirable` **refuse to build** any tool whose catalog entry declares that actor-class rule, with an explicit, on-the-nose error message: *"requires a human-confirmation transport this host has not wired — leave it unwired until one exists."* Three tools in this codebase carry that rule today and are, correctly, **not wired at all**: `collections_execute_cleanup`, `database_execute_migrate_forward` (`src/features/database/tool-registrations.ts:110-115`), and `backup_execute_restore`. A fourth — a "destructive token-gated ceremony" in content-types — is unwired the same way (`src/features/content-types/tool-registrations.ts:11`). Every one of them is a genuinely destructive, hard-to-undo action that needs a human in the loop, and every one of them is excluded until a real confirmation transport exists, exactly matching what team-lead floated as the "uncomfortable" third option below — except it's not a new idea, it's this codebase's own existing default.

**`content_post_delete` is the one tool that didn't follow that convention — not because anyone decided the convention didn't apply, but because it used a *different* confirmation mechanism (the MCP-UI token protocol) that `assertToolIsWirable`'s gate has no knowledge of.** The gate checks `actorClassRule`; `content_post_delete` doesn't set that field (its `sideEffects` is `"deletes-durable-state"`, a different axis entirely — confirmed by reading its catalog entry, `src/features/post/agent-tools.ts`). So the gate correctly found nothing to object to, and the one tool in the repo that invented its own bespoke "safe until a real host exists" mechanism is the one tool that ended up shipped without one.

**Clean, reassuring answer for the record:** one leak, in a generic wrapper that will leak the next secret anyone routes through it the same way, and a codebase that already has the right instinct (refuse to wire until a transport exists) applied everywhere except the one place that built its own parallel version of that instinct and didn't get the "refuse" part connected to anything.

### Making MCP-UI actually work — user decision received: this is now a build target, not an open question

Everything below assumes the goal is a genuinely working MCP-UI confirmation, not whether to build one.

**What has to change, concretely.** Tovu's browser (`ChatPane`/`AssistantDock`) has to become the real MCP-UI host. It's the only actor in this whole pipeline with a human in front of it (Part 1's structural argument). `@jini-ai/ui/mcp-ui` — `McpUiHost`, `useMcpUiHost` — already exists, is protocol-correct (its own comments cite verifying its handshake against `@modelcontextprotocol/ext-apps`' generated zod schema), and is unimported anywhere in Tovu. That part of team-lead's hunch is right. Two things stand in the way of "just import it," found by reading the actual protocol code rather than assuming compatibility:

1. **Protocol mismatch — Tovu's existing dialog speaks the wrong dialect.** `delete-confirmation-ui.ts`'s inline script posts a raw `{type:"tool", messageId, payload:{toolName,params}}` object and listens for `ui-message-received`/`ui-message-response` — the older, ad hoc `mcp-ui` community-SDK convention. `@jini-ai/ui/mcp-ui`'s `useMcpUiHost` implements the newer, standardized MCP Apps/SEP-1865 protocol: a real JSON-RPC 2.0 handshake (`ui/initialize` → `ui/notifications/initialized` → ready), then `tools/call` JSON-RPC requests for the confirm/cancel actions. These are genuinely different wire shapes; wiring `McpUiHost` into `ChatPane` today and pointing it at `content_post_delete`'s existing dialog would not work — the host would sit in `awaiting-initialize` forever because the dialog never sends `ui/initialize`.
2. **The fix for (1) already exists, unused, in the same package.** `@jini-ai/ui`'s `features/mcp-ui/surfaces/confirmation.ts` module doc states this outright: *"Generalized from the reference implementation's `delete-confirmation-ui.ts`, which is the same dialog hardcoded to one domain... Everything domain-shaped there is a parameter here."* Someone already took Tovu's exact dialog and rebuilt it, protocol-correct and domain-generic (title/description/`{label,value}` details/destructive flag/named confirm-and-cancel tool actions), against the same security property (`confirmation-store.ts`'s token-only-in-`confirm.params`-never-elsewhere rule, verbatim). This is the direct replacement for `delete-confirmation-ui.ts`, not a new build.

**The follow-up call needs a new path, because the browser isn't an MCP client.** `useMcpUiHost`'s `onToolCall` is a plain `(call) => Promise<unknown>` callback — it does not require going back through MCP at all. That's good news: it means the "second `content_post_delete` call" the design always intended doesn't have to round-trip through the CLI/MCP server a second time. It needs one new admin-session-authenticated HTTP endpoint that redeems the token and invokes the same handler logic `content_post_delete`'s step 2 already contains (`src/features/post/tool-registrations.ts:456` onward is unchanged) — reached directly, not via `/api/delegated-tool-calls` (that route's own comment says its only legitimate caller is "this run's own spawned `jini-mcp`," gated accordingly; widening its trust boundary to also accept a browser session is a choice to make deliberately, not a side effect of routing through it).

**Getting the resource payload to the browser at all is a separate, real problem — don't reuse the tool-result/SSE pipe for it.** Even with `okResult()` fixed, the payload would still have to survive Claude Code CLI's own stream-json relay (no evidence either way that an unrecognized `resource` content block survives it faithfully — genuinely unknown, not tested) and then Tovu's own `claude-stream.ts`, which flattens tool-result content to a plain string for the *transcript* by design — that flattening is correct for ordinary tool narration and shouldn't be weakened just to let one payload type through. **Recommendation: don't send the resource through that channel at all.** The daemon already owns a direct event stream to the browser for this run (the same SSE connection `assistant-transport.ts` subscribes to). When `content_post_delete`'s handler mints a confirmation, have it push the UI resource to the browser over that channel as its own distinct event, in parallel with — not instead of — the ordinary, minimal, model-safe text acknowledgment that still goes back through the normal tool-result path unchanged. Two outputs from one handler call: text for the model, resource for the browser, over two different channels, neither one a repurposed version of the other.

**A closely related, but different, mechanism already exists in this transport and is worth knowing about even though it isn't literally MCP-UI — flagging, not substituting.** `@jini-ai/protocol`'s event vocabulary already has `{type:'surface_request', surfaceId, surfaceKind:'form'|'choice'|'confirmation'|'oauth-prompt', payload}` / `{type:'surface_response', ...}` — a generalization of Open Design's own `genui_surface_request`/`genui_surface_response`, unrelated to MCP-UI/`ui://`/iframes (ADR-013's research is explicit that OD's GenUI Surfaces and MCP-UI are two different things — see Part 1). Tovu's own `assistant-transport.ts` already has a comment reserving space for it ("routed through the `ext` escape hatch... so a future renderer can opt in without a transport change") — meaning this event type already flows through Tovu's wire protocol today, unrendered. It solves the same *user-facing* problem (ask the human something without flattening it into transcript text) via a native, non-iframe, non-MCP-UI-spec mechanism, and it's less work than the real thing. **Not recommending it as a substitute** — the user's decision was specifically "make MCP-UI work," and swapping in GenUI Surfaces instead would be answering a different question than the one asked. Naming it because if the team ever revisits "does it have to be literally MCP-UI," this exists and is closer to done than either of us knew before this pass.

**Precise fork point, since this is the crux of the whole design.** Anywhere *downstream* of `content_post_delete`'s handler returning — inside `okResult()`, inside the CLI's own relay, inside `claude-stream.ts`, in the browser — is provably too late to separate what the human sees from what the model sees, because a tool call's return value is, by definition, what the calling model receives. There is no point after the handler returns where a value can be shown to a human but hidden from the model; past that point both are reading the same thing. So the handler itself must emit two separate outputs at mint time: an ordinary, minimal, model-safe text acknowledgment as its actual return value (unchanged path, unchanged risk — it carries no secret), and the UI resource as a *distinct* event pushed directly onto the run's own event log, which the daemon already owns and already streams to the browser over the same SSE connection — a channel the CLI never touches at all for this second output.

**This requires no `AgentEvent` type widening and no `ChatPane` source change — confirmed by reading the mechanism, not assumed.** `AgentEvent` already ships a `kind:'ext'` escape hatch built for exactly this ("host-specific event kinds chat-core doesn't know about"), and Tovu's own `translateRunAgentPayload` already defaults any unrecognized wire event into it. `@jini-ai/ui/chat` ships a working, precedented per-name renderer registry for it (`registerExtEventRenderer`), with a live example doing the same shape for a different protocol (`A2uiSurfaceCard`, registered against `kind:'ext', name:'a2ui'`) — and that component's own header names the more direct precedent: Jini's own `McpUiLab.tsx` registers `show_mcpui_widget` this same way already. One nearby mechanism I checked and ruled out: `registerToolRenderer` (the sibling registry `McpUiLab.tsx` actually uses) looked more direct, but its `ToolRenderProps.result` is typed `string | undefined` (`packages/chat-core/src/tools.ts:24`) — the same flattened constraint as `tool_result.content`, because it derives from the same value the model itself received. Right tool for rendering a tool call's own non-secret result; structurally wrong tool for content that must never be part of that result.

**Smallest useful first step, in order:**
1. Redesign `content_post_delete`'s step-1 handler to stop including the UI resource in its own tool-call return value at all — return only the model-safe text ack there, and emit the resource as the new side-channel event described above. This is where the security property actually gets re-established; everything else is rendering plumbing around it.
2. Swap `delete-confirmation-ui.ts`'s hand-rolled HTML for `@jini-ai/ui/mcp-ui/surfaces`' `confirmation` builder — protocol-correctness for free, no new design.
3. Register a `McpUiHost`-backed component against the new event name via `registerExtEventRenderer` — an additive call in Tovu's own app code, not a `ChatPane` change.
4. Add the one new admin-session-authenticated redemption endpoint the registered component's `onToolCall` calls.

Steps 2-3 are genuinely small — reusing two already-built, already-tested components with a documented registration pattern. Steps 1 and 4 are the real new work.

**Fixing `okResult()` turns out to be independent of this, not a prerequisite — worth stating precisely since I said otherwise before working out the fork point.** Once step 1 lands, `content_post_delete`'s own return value never carries a resource block again, so `okResult()` never sees one for this tool either way. It remains worth fixing regardless — it is still the generic wrapper any *other* future tool would leak a secret through the same way — but it can proceed in parallel rather than gating the four steps above.

**Sequencing, and how the security fix and the working path interact.** Team-lead asked directly, and my answer changed once I worked out the fork point precisely: **do the "exclude until a real host exists" stopgap now, immediately — build the four steps above as the real fix — and fix `okResult()` in parallel, on its own timeline, as unrelated defense-in-depth rather than a blocking prerequisite.** Reasoning:

- The stopgap (declare `content_post_delete`'s destructive path unwired, or gate it behind the same `ACTOR_CLASS_RULES_REQUIRING_CONFIRMATION_TRANSPORT` mechanism the codebase already uses for the other four token-gated tools) is not a detour from the real fix — it's the same shape the real fix ends in, just without steps 2-4 done yet. It costs nothing to build twice, because it isn't a separate design.
- `okResult()` is not on this critical path, once the fork point is precise — the redesigned handler (step 1) never routes a resource through the return value `okResult()` sees, so nothing downstream of the handler needs fixing for this tool specifically. It stays worth doing, in parallel, because it's the generic wrapper any other tool would still leak a secret through today, and because a second tool building the same confirmation pattern before it's fixed would reintroduce this exact bug independently.
- Between "stopgap shipped" and "the four steps shipped," the honest state is: Posts/Pages delete has no agent-facing confirmation UI at all (same as three other domains' destructive tools today). That's a worse user experience than a working dialog and a better one than a dialog the model can click through itself. Team-lead's own framing — "a confirmation gate the model can self-approve is worse than no gate" — is the reason this ordering isn't optional. **Direct answer to the direct question: agreed, disable rather than leave live.** I don't see a reason to leave it running that outweighs that framing — the only case for "leave it alone" would be if the leak were somehow already mitigated by something else in the path, and the trace found nothing that does.

## Executive summary (read this first)

**MCP-UI is not vaporware, and it is not missing. It exists, half-built, disconnected, and pointed at the wrong host.**

- The wire-protocol half (token minting, resource construction) is real, well-researched, and tested — but scoped to exactly one feature (Posts/Pages delete), not a platform capability.
- The rendering half (a React host that shows the dialog to a human) also exists — as a separate, general-purpose package — but nothing imports it.
- Even if the two were wired together, Tovu's actual chat pipeline runs a **headless CLI subprocess** as the MCP client, and headless CLIs are not MCP-UI hosts anywhere in the ecosystem. The rendering surface that needs to exist is Tovu's own browser chat pane, which today receives tool results as plain strings, several layers upstream of where the UI resource gets flattened.

None of this was one team's mistake — it's three independently-reasonable engineering decisions (a domain feature built its own confirmation gate; a platform package built a generic host; the transport layer was designed before either existed) that never got reconciled because no ADR owns the reconciliation.

### The gap, precisely

Tovu's `apps/admin/src/components/AssistantDock.tsx` mounts `@jini-ai/chat-react`'s `ChatPane` against a transport (`apps/admin/src/lib/assistant-transport.ts`) that reduces every wire event into a `@jini-ai/chat-core` `AgentEvent`. That type is a closed union (`packages/chat-core/src/events.ts` in Jini) and its `tool_result` variant is:

```ts
{ kind: 'tool_result'; toolUseId: string; content: string; isError: boolean }
```

`content` is `string`. Traced to the actual source: `@jini-ai/agent-runtime`'s `claude-stream.ts` does `content: stringifyToolResult(block.content)` the moment a tool result leaves the spawned Claude Code CLI's stream-json output — before it ever reaches the daemon, before it reaches Tovu's SSE endpoint. An MCP-UI `EmbeddedResource` (the `{ type: "resource", resource: { uri: "ui://...", mimeType: "text/html;profile=mcp-app", text: "<!doctype html>..." } }` object `mcp-ui.ts` constructs) would be flattened into that string — i.e. dumped as JSON-with-embedded-HTML into the chat transcript as text. Confirmed by grep: no `iframe`, `EmbeddedResource`, `ui-message-received`, or `ui://`-handling code exists anywhere in `apps/admin`.

Separately, `@jini-ai/ui/mcp-ui`'s `McpUiHost` component — the thing that *would* render this correctly — is never imported by `ChatPane`, `AssistantDock`, or anything else in Tovu's admin app (confirmed by grep across both repos).

**Both pieces that would need to connect are real. Neither imports the other.**

### The deeper problem: even wired together, the host is wrong

MCP-UI's whole security model (see `pending-confirmations.ts`'s own module doc) depends on a HOST that (a) renders the UI resource to a human, (b) does **not** feed that HTML to the model, and (c) can itself issue the follow-up tool call when the human clicks, bypassing the model entirely. That's why the confirmation token is safe: it lives only in HTML the model never sees.

Tovu's actual runtime: `AssistantDock` → daemon → spawns **Claude Code CLI in headless/`-p`/stream-json mode** (`initialSelection={{ agentId: "claude" }}` in `AssistantDock.tsx`, confirmed against `@jini-ai/agent-runtime`'s `claude-stream.ts`). I confirmed via web search (spec check below) that current MCP-UI/MCP Apps host support is **Claude Desktop, ChatGPT, Cursor, VS Code, Goose — interactive GUI clients**, not headless CLI automation. A headless subprocess scraping its own stdout cannot be the human-facing host the protocol assumes; there is no separate "human" surface in that process at all. The human-facing surface in Tovu's architecture is the **browser** (`ChatPane`), not the CLI — which means the CLI, the actual MCP client, is the wrong place to terminate the "host" role, and the browser, which could be the host, is not the MCP client and has no direct channel back to the running tool call.

This is not a small wiring gap. It's a structural mismatch between where MCP-UI expects the host to sit (co-located with the MCP client) and where Tovu's only human-facing surface actually sits (across a daemon/SSE boundary from the MCP client). **Update, verified in a follow-up pass (see the SECURITY FINDING at the top of this document): Claude Code CLI's headless mode does not withhold UI-resource HTML from the model's own context — there is no evidence it implements MCP Apps at all, and headless mode has no human present to render UI to regardless.** The confirmation token is confirmed to leak into model-visible text on Tovu's actual call path, via a generic MCP proxy layer that flattens the whole tool result to JSON text before Claude Code CLI's own (non-)support for MCP Apps even becomes relevant.

### Is the spec itself unstable? No — checked, and this cuts the other way

Per the team-lead's instruction, I checked current state rather than relying on training data (mine or the model's that wrote `mcp-ui.ts` could both be stale).

**MCP Apps (SEP-1865) is Final, not evolving.** It shipped as the first official MCP extension on 2026-01-26, and was folded into the base MCP spec's 2026-07-28 release candidate (published six days before this recon). `@mcp-ui/server`/`@mcp-ui/client` (the community SDK Tovu's `mcp-ui.ts` also cites) are at 6.1.0/7.1.1, last published ~6 months ago — stable, not churning. Host adoption is real: Claude, ChatGPT, Goose, VS Code have shipped support; Shopify/Hugging Face/ElevenLabs are shipping MCP-UI servers.

**Conclusion: the spec risk the team-lead asked me to flag is not present.** If anything, the timing argues for building on it now rather than waiting — it wasn't a moving target when `mcp-ui.ts` was written on 2026-07-30, and it's more settled now. The literals `mcp-ui.ts` hardcodes (`RESOURCE_MIME_TYPE`, `RESOURCE_URI_META_KEY`, the `UIActionType` union) match the now-Final spec. The problem this recon found is entirely integration, not spec risk.

Sources: [SEP-1865 spec](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp), [2026-07-28 MCP spec release](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/), [@mcp-ui/server npm](https://www.npmjs.com/package/@mcp-ui/server)

## Part 2 — the agent opening UI on the user's behalf

### Headline finding: most of the hard part is already built. It's just never been used.

Tovu's daemon already wires `@jini-ai/agentic`'s `PAGE_CAPABILITIES` into the tool registry (`src/assistant/agent-daemon-server.ts:148-201`, `createFrontendControl`). That gives an agent seven verbs today: `page.find_elements`, `page.highlight`, `page.scroll_to`, `page.click`, `page.fill`, `page.select_option`, `page.navigate`. The relevant two for this problem:

- **`page.find_elements`** — lists every control a page has *explicitly published* by rendering it with a `data-agent-element="<handle>"` attribute, optionally filtered by `role` (`button`/`checkbox`/`field`/`form`/`list`/`status`/`region`/`link`) or a case-insensitive substring `query` against the handle and its label. Nothing is scanned or inferred; a control is discoverable only if a component author tagged it.
- **`page.click`** — activates one control by the exact handle `find_elements` returned. It does not accept a CSS selector or any caller-supplied locator.

I checked whether this is real infrastructure or an unused stub: `page.click`'s handler (`@jini-ai/agentic`'s `page-executor.ts:332-335`) delegates to a DOM driver whose `find(handle)` (`dom-page-driver.ts:294-299`) throws `no element published as "${handle}" on this page` on zero matches and a distinct ambiguous-handle error on more than one. This is fully built, unit-tested without a browser (the executor is DOM-free by design — "does it refuse to type into a password box is a unit test, not an integration test"), and already flows through the same `ToolExecutor` authorize → confirm → execute → audit pipeline every other tool call does.

**And it is currently used by zero elements in Tovu's admin app.** `grep -rn "data-agent-element" apps/admin/src` returns nothing. `App.tsx` sets `data-agent-page` (the page-level tag `page.navigate` targets), but no component anywhere tags an individual button, field, or dialog trigger. The capability is live and reachable through the daemon; the admin frontend has simply never adopted the convention.

### What this means for "open the attributes modal for the email field"

Concretely, opening a field's attributes dialog is: tag that row's "attributes" button with `data-agent-element="field-attributes:{fieldId}"` and a label that includes the field's name (e.g. `Open attributes for "Email" field`). Then:

1. `page.find_elements({ query: "email", role: "button" })` — the agent locates the exact handle, reading only what the page chose to publish.
2. `page.click({ element: "field-attributes:f_abc123" })` — the agent clicks it. The button's existing `onClick` opens the dialog exactly as it would for a human click; no new dialog-opening code path is needed on the frontend at all.

I want to be direct about what this does to the team-lead's framing: the "hard part" as posed — *"that is not navigation and does not fit the existing allowlist"* — is correct that it doesn't fit `page.navigate`'s allowlist, but that's because it was never a navigation problem. It's a **click** problem, and Tovu already has a click capability with exactly the allowlist property being asked for.

### Where real navigation gaps still exist

`page.navigate`'s allowlist is deliberately panel-level only (`agentReachable`, `AdminPanel`), and the package's own doc is explicit that detail routes are excluded on purpose: *"they need an id the agent has to look up first, and the tool for that is a content catalog, not a navigation allowlist that would have to enumerate every row in the database."* So getting the agent onto a **specific, not-yet-loaded** row's page — "open the attributes dialog for the email field in the Contact form" when the human is sitting on the Dashboard — is genuinely unsolved today, but it decomposes into two already-anticipated, separately-scoped problems:

1. Navigate to a specific entity's detail route by id. Not built. The package comment names the shape it should take (a content-catalog lookup, id → route), not a bespoke per-panel hack.
2. Once there, discover and click the trigger. Built, per above.

This recon's recommendation is **not** to invent a route-fragment DSL (`forms/:formId#field/:fieldId/attributes`) or a typed `openDialog(panelId, dialogId, params)` command to solve problem 1. Both would create a second, parallel addressing/permission system next to `page.navigate`'s existing one, and Part 2 was asked to check whether this belongs in the tool-registration infra that already exists rather than as a bespoke mechanism — it does. If problem 1 needs solving, the shape should be an extension of `page.navigate` (or a sibling capability with the same allowlist discipline) that accepts an id for panels that opt into declaring a resolver — still an explicit per-panel opt-in, still fails closed for an id that doesn't resolve — not a new command bus. That is a real, separate design task; flagging it as out of scope for this pass rather than thinning it out here.

### Answering the four design questions directly

**Addressing scheme.** Compose two existing, independently-scoped mechanisms rather than inventing one: `page.navigate` for "get to the right panel" (already built, already an allowlist) and `data-agent-element` + `page.find_elements` + `page.click` for "trigger the specific control on that panel" (already built, already an allowlist, currently zero-adoption). A dialog is addressed by *what a human would click to open it*, not by a synthetic id namespace someone has to invent and keep in sync with the UI.

**Deny-by-default, structurally.** Not by convention — by construction, the same way `agentReachable: false` works. `page.find_elements` can only ever return elements a developer explicitly rendered with `data-agent-element`. There is no scan, no derivation from component registration, no "everything with an `onClick` is reachable." A dialog trigger becomes agent-openable exactly when, and only when, a developer adds one attribute to that one button — identical shape to `agentReachable`, and consonant with the precedent in `@jini-ai/cms/settings`'s tool wiring, where the one agent-writable settings path is bounded by "a fixed enum, so 'write a key outside the list' is an unrepresentable input, not merely an unauthorized one" (`packages/cms/src/settings/tool-registrations.ts:8-12`). Same discipline, same shape, different layer.

**Target doesn't exist.** Already enforced, not merely designed for: a deleted field or wrong form means the tagged element genuinely isn't in the DOM, so `find_elements` returns no match, and `page.click` against a stale/guessed handle throws `no element published as "<handle>" on this page` (verified in the driver source, not asserted from the doc comment). There is no code path that opens a dialog without an exact, currently-published handle — a "blank dialog" isn't a failure mode this mechanism can produce.

**Interruption policy — this one is a real, currently-unaddressed gap, not just for dialogs.** `createFrontendControl`'s own doc says the plainest possible thing about this: `invoke` "executes a capability on a real admin's real screen with no policy check, no timeout." That's true today for `page.navigate` and `page.click` on ordinary buttons, not just future dialog triggers — an agent can already redirect a user's tab or click something mid-session with no focus-awareness at all. Opening a modal raises the stakes (it can seize keyboard focus away from an input the user is mid-typing into), but it doesn't introduce a new category of problem so much as make an existing one visible. **Recommendation, needs product sign-off, not decided here:** before wiring any dialog-opening handles, add a lightweight interruption check to the DOM driver's `click` path — if the currently-focused element is an editable field outside the target dialog, defer execution behind a small non-blocking "Assistant wants to open X" affordance instead of clicking through; if there's no such focus, execute immediately. This is scoped narrowly (one guard in one shared code path, `@jini-ai/agentic`'s DOM driver, benefiting every future dialog-opening handle, not per-dialog logic) but is a UX/product decision, not an engineering default I should silently pick.

## Part 3 — synthesis: one mechanism or two?

### My answer: two mechanisms, and the evidence argues against merging them — but they share one discipline

The team-lead framed Parts 1 and 2 as possibly "the same problem viewed from two ends." Having traced both all the way to their actual runtime behavior, I don't think that framing survives contact with what's actually built. They solve genuinely different problems with genuinely different trust boundaries:

- **MCP-UI (Part 1) is the agent rendering content the *tool author* controls**, shipped over the wire as untrusted HTML from a tool result, sandboxed in an iframe, rendered by whatever generic host the MCP client happens to be connected to. The tool author writes HTML at tool-authoring time; the host has no idea what that HTML contains until it arrives.
- **The click mechanism (Part 2) is the agent operating a control the *page author already built and shipped***, addressed by a handle the page itself published, executing the page's own existing `onClick`. Nothing is rendered from a wire payload; nothing is sandboxed because nothing untrusted is being displayed — the dialog is exactly the dialog a human clicking the same button would get, running Tovu's own React code with Tovu's own CSP, not injected HTML in an iframe.

Collapsing these would mean either (a) making the click mechanism go through a UI-resource round-trip it doesn't need — the dialog already exists as real, trusted, first-party React; wrapping it in an MCP-UI resource would mean *serializing Tovu's own UI into HTML strings to redisplay it*, which is strictly more code for identical output — or (b) making MCP-UI resources somehow "trusted" because they came from the same registry as click targets, which quietly erases the sandboxing MCP-UI's own security model exists for. Both directions are worse than keeping them separate. **These are unrelated mechanisms that happen to rhyme at the "deny-by-default, addressable target, fails closed" level — that's a shared architectural discipline, not a shared implementation.**

### What they do share, and where it actually belongs

Both need: an explicit per-target opt-in (never derived from existence), a resolvable handle/id (never a raw selector or freeform string), and a defined failure for "target doesn't exist" rather than a silent no-op. That's a pattern, not a component — worth writing down as a short cross-cutting principle (e.g. a governance-ADR note: "any new agent-facing addressing surface follows the `agentReachable`/`data-agent-element` shape: explicit opt-in, resolvable handle, fail-closed on miss") so the *next* one of these — and there will be a next one — doesn't reinvent either allowlist model from scratch or, worse, invent a third shape. That belongs in governance, not in unifying the two mechanisms' code.

### The grounding example: widget delete confirmation

The team-lead's question: is the in-flight widget-delete confirm dialog (built with "whatever confirm pattern the admin already has") a stopgap MCP-UI should replace, or the permanent right answer for an in-app action?

Tovu already has an established, human-initiated in-app confirm vocabulary, unrelated to MCP-UI and predating it: `ConfirmButton` (an in-place two-click control, used for lower-stakes actions) and dedicated confirm dialogs for higher-stakes ones — e.g. Posts' delete-to-trash flow deliberately avoids both `ConfirmButton` and `window.confirm` in favor of a real dialog stating the observable consequence (`apps/admin/src/sections/Posts.tsx:58-65`). This predates Part 1's MCP-UI work entirely and has nothing to do with it.

**My answer: the in-app confirm is the correct permanent mechanism for a human clicking Delete in the browser. MCP-UI is not a replacement for it, ever** — not a stopgap for it, a different thing entirely:

- When a **human** clicks Delete in the widget library, there is no "host" in the MCP-UI sense at all — no tool call happened, no wire boundary was crossed, there's nothing for MCP-UI's iframe-sandboxing to protect against. The confirm dialog is just React state. Replacing it with an MCP-UI resource would mean routing an ordinary UI interaction through a tool-call round-trip it doesn't need, for a component whose HTML MCP-UI would have to sandbox from *itself*.
- MCP-UI's actual, correct future job is the case Part 1 investigated: an **agent**, acting through the chat surface, wanting to delete something *on the human's behalf* — where the tool result crossing the MCP boundary genuinely does need a host to render untrusted-ish content and a token to keep the agent from confirming its own action. `content_post_delete` is exactly this case, correctly identified, correctly built at the protocol layer — just not yet connected to a host that exists in Tovu's actual runtime (Part 1's finding).

So: **if/when an agent gets a `widgets_delete` tool, that tool's confirmation should be MCP-UI** (reusing `mcp-ui.ts`/`pending-confirmations.ts`, generalized past the one Posts/Pages use they were written for). **The human-facing Delete button in the Widgets admin screen should keep using the same in-app confirm vocabulary every other destructive human action in this admin already uses.** Two different actors crossing two different trust boundaries; the "stopgap vs. permanent" framing in the question assumes they're on the same replacement timeline, and the evidence says they aren't — the widget confirm dialog isn't waiting for MCP-UI to mature, it's a permanently different mechanism for a permanently different actor.
