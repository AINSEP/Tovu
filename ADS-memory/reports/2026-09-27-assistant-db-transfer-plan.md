# Assistant "move my data to Supabase": plan

Date: 2026-09-27. Author: Software Architect + Database subagent (read-only; nothing implemented, nothing committed).
Ask: a user on built-in storage says "can we transfer all the SQLite stuff to Supabase?" and the assistant just does it.

---

## 0. Headline

- **Copying is close. Running the site on Postgres is not.** Everything a copier needs to know about the schema already
  exists (copy order, column classes, identity reseed, verification checks, a generated 90-table Postgres schema). What
  is missing is the copier itself, a Postgres driver, and an assistant tool. That gets built in days, not weeks.
- **Tovu cannot run a site on Postgres today.** There is no Postgres driver in the repo and no runtime adapter. 52
  `*.sqlite.ts` adapters and 38 files importing `better-sqlite3` would each need a Postgres version. That is the
  "Layer 1" project scoped on 2026-07-30, and it is still unbuilt.
- **So v1 = "copy", not "switch".** The assistant copies the whole site database into a private schema in the user's
  Supabase project, checks every table, and can refresh the copy on request. The site keeps running on built-in
  storage, so there is nothing to roll back and no downtime. "Switch" comes later, behind Layer 1, and uses the same
  copier. Owner question Q1 confirms this.
- **The password problem goes away.** Tovu never needs the project's `postgres` password. Core generates a password
  for a new, dedicated login role, and hands the model only its SCRAM-SHA-256 hash. The plugin's skill then runs one
  `CREATE ROLE ... PASSWORD '<hash>'` through the Supabase MCP's `execute_sql`. Postgres accepts a SCRAM hash as the
  password, and the actual password never leaves Tovu. No Management API code, no password reset, and the user's
  other apps are untouched.

**Completeness gaps a copier must close (checked against the live `sites/tovu-dev` files today):**

1. **Plugin tables are invisible to the copy order.** `content.db` holds `p_comments__*`, `p_newsletter__*`, `p_store__*`
   (8 tables). They come from `declareDataModule`, not `schema.sqlite.ts`, so `collectCoreTables()` never sees them.
   The copier must take their declarations from the plugin data modules and build their Postgres DDL with
   `classifyPluginColumn`.
2. **Chat is a separate file.** `ai_chats`, `ai_chat_messages`, `assistant_agent_sessions` now live in `chat.db`
   (`platform/db/sqlite/chat-db.ts` header; `sqlite3 sites/tovu-dev/chat.db` lists exactly these three). They are in
   `RAW_SQL_MANAGED_TABLES` (`platform/db/__tests__/schema-migration-drift.test.ts:134`), which excuses them from the
   drift guard without making anything copy them. The memory note saying they are in `content.db` is out of date.
3. **Other files:** `ops/database-journal.db` and `ops/storage-journal.db` hold operational journals, not site
   content. Leave them out, and say so in the plan result.
4. **Bookkeeping and derived tables are skipped:** `__drizzle_migrations`, `sqlite_sequence`, `_plugin_*`, and the
   FTS objects. Postgres gets its own migration bookkeeping.
5. **Sealed credentials copy verbatim.** Their AAD is built only from logical ids (`features/custom-credentials/aad.ts:23`,
   `features/vendor-credentials/aad.ts:34`, `features/publish-content/peer-aad.ts:38`, and others), never from
   anything specific to a database file. The bytes open the same way from Postgres as long as the site keeps its
   Site Token (the root key). Nothing needs re-sealing.
6. **Media bytes are not in the database.** `asset_blobs` holds `storage_key` and `sha256`. The bytes live under
   `uploads/` (99 MB for tovu-dev, against a 42 MB `content.db`). The copy carries rows only, so file links stay valid
   for as long as the site keeps its `uploads/` folder.

## 2. What the assistant can do with a database today

- **Site DB, read-only introspection:** `database_get_health`, `database_get_schema_state`,
  `database_list_pending_migrations`, `database_query_timeline`, `database_list_restore_points`,
  `database_plan_migrate_forward` (`features/database/tool-registrations.ts:105-123`).
- **Site DB, the one write:** `database_execute_migrate_forward`, a token-gated schema upgrade, not a data copy
  (`tool-registrations.ts:127-130`; state machine at `features/database/migrate-forward/state-machine.ts`, which already
  models a Postgres blue/green `CUTOVER` phase that nothing drives).
- **Content CRUD** goes through each domain's own tools (posts, entries, media, forms, ...). There is **no generic SQL
  tool on the site database, and no copy/export/import-data tool.** The only data export is `site_backup_*`, and it
  only writes to GitHub.
- **Supabase side:** the plugin allows `execute_sql`, `apply_migration`, `list_tables`, and more
  (`content/agent-plugins/supabase/mcp.json`). However, `assistant/mcp-federation/trust.ts:352` still refuses every
  `destructiveHint: true` tool, and there is no override. `execute_sql` and `apply_migration` therefore cannot reach
  the model today. That is gap G3 in `2026-09-27-supabase-agent-plugin-plan-v2.md` §1 and is not yet landed. This plan
  needs one `execute_sql` call (§3.4), so **G3 is a prerequisite**.
- Even with G3, having the model push rows through `execute_sql` is not a workable copier: 42 MB of rows would pass
  through model context, cost tokens, and could be altered on the way. The copy must run host-side, over a direct
  Postgres connection.

## 3. The generic capability (core) and what the Supabase plugin adds

### 3.1 Shape

One core feature, `features/database-transfer/`, vendor-blind (it never learns the name "Supabase"):

- **A sealed "database connection" record.** The connection string is stored through `SecretSealerPort` with AAD
  (`workspaceId`, `id`). It is never returned in a tool result, log line, or card, and only its host and database
  name are shown. It fills in one of two ways:
  - (a) **Pasted** into the existing masked in-chat secret form, the same pattern as `custom_credential_set_token`
    (`features/custom-credentials/custom-credential-set-token-ui.ts:1-15`: the keystrokes never reach the model). This
    works for any Postgres (Neon, RDS, self-hosted) and needs no plugin.
  - (b) **Prepared by a plugin** through the minted role (§3.4).
- **`database_transfer_plan` (read-only).** It connects, then checks TLS, the Postgres version (14 or later), the
  target schema's state, and privileges. It counts source rows per table, estimates bytes and duration, and lists
  what is included and excluded (journals, derived search, and, depending on Q2, secret tables). It returns a plan id
  and holds the snapshot, like `site-backup/plan-store.ts`.
- **`database_transfer_run` (human-confirmed card).** It raises the held-open in-chat confirmation that
  `resolveConfirmationDecision` handles (`contracts/core/tool-surface-exchanges.ts:411`). The card shows the destination
  host, the table and row totals, "your site keeps running on its built-in storage", and **Copy** / **Cancel**. It
  then runs the pipeline below and reports per-table counts.
- **`database_transfer_status`** (read-only) for the last run.
- **Permission** `database-transfer.run`, owner-only (`*`), same pattern as `site-backup.push`.

### 3.2 Pipeline (copy mode)

1. **Snapshot.** `captureRestorePoint` gives a consistent `content.db` copy, and the same online backup runs on
   `chat.db`. The copier reads **only the snapshots**, so the live site is never locked or paused. The copy is exactly
   "the site as of HH:MM", and the result says so. That is honest, and it avoids the watermark trap
   (`manifest.ts:922`).
2. **Stage.** In one Postgres transaction: `CREATE SCHEMA tovu_staging_<run>`, then apply **generated Postgres
   migrations** (a new committed `platform/db/drizzle-postgres/` produced by drizzle-kit from `schema.postgres.ts`, not
   hand-written), then plugin-table DDL from their declarations.
3. **Copy** in `computeCoreTableCopyOrder()`, then plugin tables, then chat tables. Rows go through
   `COPY ... FROM STDIN` (binary-safe CSV), or batched `INSERT ... OVERRIDING SYSTEM VALUE` if COPY is not permitted.
   Every value is converted by its manifest class: boolean 0/1 to bool, JSON text to jsonb, timestamps left as text.
4. **Reseed** identity sequences (`reseedSequenceSql`).
5. **Verify.** Row counts per table, plus a per-table checksum. Rows are streamed from both sides in primary-key
   order, each value normalised by its column class using `verifyClassifiedValue`, and the result hashed. Any mismatch
   fails the run.
6. **Swap, atomically, in the same transaction:** `ALTER SCHEMA tovu RENAME TO tovu_prev_<run>`, then
   `ALTER SCHEMA tovu_staging_<run> RENAME TO tovu`, then drop `tovu_prev_<run>`. If anything fails, the transaction
   rolls back and the previous copy (if any) stays untouched. Postgres DDL is transactional, so this is one commit.
   (Size check: tovu-dev is 42 MB, so one transaction is fine. If a site is ever larger than about 2 GB, switch to a
   staging schema that is not transactional and do only the swap as a transaction. Not needed now.)
7. **Marker.** Write `tovu._tovu_transfer` with site id, run id, source snapshot time, table counts, and Tovu schema
   version. **The copier refuses to replace a `tovu` schema without a marker that names this site.** It never touches
   `public` or any other schema.

"Refresh" is the same tool run again. Its card says "replaces the copy from <time>".

### 3.3 Decisions I made (not owner questions)

- **Private schema `tovu`, never `public`.** Supabase exposes some schemas through its Data API, and its docs say:
  "A table in an exposed schema without RLS is readable and writable by any role with a grant on it"
  ([RLS docs](https://supabase.com/docs/guides/database/postgres/row-level-security)). A copy holds members, form
  submissions, and admin accounts, so it must not land anywhere the anon key can reach. The dedicated role gets
  `USAGE, CREATE` on `tovu` only.
- **Driver `pg` (node-postgres), with `drizzle-orm/node-postgres`.** It is mature, TLS works, its migrator already
  ships inside drizzle-orm, and Layer 1 would use the same driver. It goes in `dependencies`, and the Docker build
  must include it. That is a supply-chain change, so it goes through the normal review.
- **Session-mode pooler (port 5432) is the default Supabase target.** It works over IPv4, supports prepared
  statements, and suits a long-lived server. Direct connections are IPv6 unless the project buys the IPv4 add-on.
  Transaction mode (6543) does not support prepared statements
  ([connecting to Postgres](https://supabase.com/docs/guides/database/connecting-to-postgres)).
- **Journals and derived search are never copied.** Search is rebuilt only in switch mode (Layer 1).
- **The copier is dialect-generic from day one:** a `source` reader and a `target` writer behind ports. The same
  engine later runs Postgres→SQLite, which is exactly the "switch back" of §4.3.

### 3.4 What the Supabase plugin adds (content only, no code, matching the v2 ruling)

**The password problem.** `create_project` generates the database password internally and never returns it
(`2026-09-27-supabase-agent-plugin-plan-v2.md` §1 table). The options, checked against current Supabase docs:

| Option | Verdict |
|---|---|
| **A. Tovu mints a dedicated role and sends only its SCRAM hash** | **Recommended.** Core generic tool `database_connection_prepare {label}` generates a 32-byte random password, seals it, and returns `{roleName, scramVerifier, connectionId}`. The **verifier** is a salted SCRAM-SHA-256 hash, not the password: it cannot log in, and brute-forcing a 32-byte random secret offline is infeasible. The plugin skill has the model run, through the MCP: `execute_sql: CREATE ROLE tovu_site LOGIN PASSWORD '<verifier>'; CREATE SCHEMA IF NOT EXISTS tovu AUTHORIZATION tovu_site;`. Postgres stores a verifier passed as the password as-is. The password never leaves Tovu, the user's `postgres` password is untouched, and the role can be revoked alone. |
| B. Reset the project password: `PATCH /v1/projects/{ref}/database/password {password}`, OAuth scope `database:write` ([reference](https://supabase.com/docs/reference/api/v1-update-database-password)) | Rejected. It **breaks every other app** the user connected with the old `postgres` password, it needs Supabase-specific HTTP code (the MCP has no such tool), and the new password would have to travel in the request. |
| C. Build the connection string from the pooler config: `GET /v1/projects/{ref}/config/database/pooler` returns `connection_string`, `db_host`, `db_user`, `db_port`, `pool_mode`, scope `database:read` ([reference](https://supabase.com/docs/reference/api/v1-get-pooler-config)) | Useful for the **exact host**, but it still has no password, and the Supabase MCP has no tool for it. Keep as a later refinement (U2). |
| D. The user pastes the connection string (§3.1a) | Always-available fallback, and the only path for non-Supabase Postgres. |

**Host.** A plugin cannot run code, so it declares its connection templates in `mcp.json`, next to `tovuAuthMode` and
`tovuDefaultTools`, as a new generic key:

```json
"tovuDatabaseTarget": {
  "candidates": [
    "postgres://{role}.{ref}:{secret}@aws-0-{region}.pooler.supabase.com:5432/postgres?sslmode=require",
    "postgres://{role}.{ref}:{secret}@aws-1-{region}.pooler.supabase.com:5432/postgres?sslmode=require",
    "postgres://{role}:{secret}@db.{ref}.supabase.co:5432/postgres?sslmode=require"
  ]
}
```

Supavisor usernames are `<role>.<project_ref>` ([Supavisor FAQ](https://supabase.com/docs/guides/troubleshooting/supavisor-faq-YyP5tI)).
The model fills in `ref` and `region` from `get_project` (both non-secret) by calling `database_connection_finish
{connectionId, vars}`. Core fills in `{secret}` itself, tries each candidate with TLS plus `select 1` against a
5-second timeout, and saves the first one that works. Core never learns a vendor name; it only knows "a plugin
declared templates".

**Plugin skill text** (in `content/agent-plugins/supabase/skills/supabase/`): the steps are pick or create the project
(existing flow), `database_connection_prepare`, `execute_sql` (role and schema), `get_project`,
`database_connection_finish`, `database_transfer_plan`, `database_transfer_run`. Warn the user once, in plain words,
that free projects pause after a week without use (see §4.2).

**Generic host capabilities this adds** (named G-DB*, and none of them mention a vendor):
G-DB1 sealed database-connection record and paste form; G-DB2 `database_connection_prepare` / `_finish` and the
`tovuDatabaseTarget` manifest key; G-DB3 the transfer plan/run/status tools; plus **G3 from plan v2** (destructive-hint
operator override), which must land first.

## 4. Zero-concept chat journey

### 4.1 Happy path (copy mode)

> **User:** can we transfer all the SQLite stuff to Supabase?
>
> **Assistant:** Yes. I'll copy your site's data into your Supabase database. Your site keeps running as it is while I
> do it. *(If Supabase is not connected yet: the existing Connect card, then pick or create a project, per plan v2 §4.)*
> *(Silently: prepare, execute_sql, get_project, finish, plan.)*
>
> **[Card]** Copy site data to Supabase, project "my-site" · 94 tables · 18,402 rows · about 20 seconds · Photos and
> files stay where they are · Your site keeps running · **Copy** / **Cancel**
>
> **Assistant (after):** Done. All 94 tables were copied and checked, as of 3:41 pm. It's in a private area called
> "tovu" in your Supabase database. Say "refresh the Supabase copy" any time to update it.

No terms like schema, role, connection string, pooler, or SCRAM appear anywhere. The only thing the user decides is
**Copy**.

### 4.2 Failures (each one is a plain sentence plus one action)

| Failure | What the user sees |
|---|---|
| Supabase not connected, or sign-in expired | Connect card (existing S-G1) |
| Project paused (free projects pause after 1 week without use; [project pausing](https://supabase.com/docs/guides/platform/free-project-pausing)) | "Your Supabase database is asleep. Wake it up?" The model calls `restore_project`, polls `get_project`, then continues |
| `execute_sql` refused (G3 not landed, or the user turned it off in Settings) | "I need permission to set up a login on your Supabase database." Link to the plugin's tool settings |
| No candidate host connects | "I couldn't reach your Supabase database from here." Offer the paste form (§3.1a) with a one-line "where to find it" |
| Target `tovu` schema exists without this site's marker | Refuse: "There's already different data there. I won't overwrite it." Nothing is written |
| Verify mismatch or a mid-copy error | "The copy didn't match, so I threw it away. Your earlier copy is untouched." The transaction rolls back, and the table name goes in the log |
| Database full (free-tier storage cap) | The plan's size estimate triggers a warning before the card; if it happens mid-copy, rollback as above |

### 4.3 Rollback, downtime, media

- **Copy mode:** the site never changes, so there is nothing to roll back. A failed run leaves the previous copy
  intact (§3.2 step 6). "Delete the Supabase copy" drops the `tovu` schema and the role (confirm card, since it cannot
  be undone). Downtime is zero.
- **Switch mode (later, needs Layer 1):** the same engine, plus (1) maintenance mode that refuses writes with a
  friendly message while the final copy runs (seconds at tovu-dev's size), (2) a config flip from
  `database: {kind: "sqlite"}` to `{kind: "postgres", connectionId}` and a restart, and (3) the SQLite files **kept
  untouched and marked inactive**. "Switch back" runs the copier Postgres→SQLite so writes made after the switch are
  kept, then flips the config back. Downtime equals the final copy plus a restart.
- **Media:** photos and files stay in `uploads/` in both modes, and only their rows move. The card says so. Moving
  file bytes to Supabase Storage is a separate, later feature.

## 6. Owner questions (2)

**Q1. For now, should "transfer to Supabase" mean "copy my data there", while the site keeps running on its built-in
storage?**
What: v1 copies everything into your Supabase database and checks it. It can be refreshed any time, and nothing about
the site changes.
Why: actually running the site on Supabase needs about 50 storage files rebuilt first (weeks). The copy can ship in days.
Effect: yes = ship copy now and treat "switch" as its own project later; no = start the big project first, and
nothing ships soon.
*Recommend: yes.*

**Q2. Should the copy include logins and saved keys?**
What: admin and member accounts (password hashes), and saved encrypted credentials. Temporary things like sessions and
sign-in links are always left out.
Why: a copy that the site doesn't run on has no use for them. They stay encrypted, but they would be one more place
holding them.
Effect: yes = a complete copy, ready for a later switch; no = a safer copy, and a switch would copy them at that moment.
*Recommend: no for copy mode, and yes at switch time.*

## Owner decisions (2026-09-27, tovu-7a)
- Q1: COPY now (site keeps built-in storage); running the site on Supabase/Postgres is a later, separate project.
- Q2: a plain copy EXCLUDES logins and saved keys (password hashes, sealed credentials); include them only at switch time.
