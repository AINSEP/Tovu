## DESIGN (approved; implement exactly, smallest change that satisfies it)
P1 MULTI-DESTINATION
- Receiver (D1 Worker for static sites, Tovu for live) and delivery destinations stay distinct. Receiver ack = "safely imported into Tovu", independent of delivery.
- Site setting `core.forms/deliveryBindings` (workspace scope, JSON list, default []): each binding `{ bindingId, adapterId, connectionRef, enabled, formIds?, config }`. Absent formIds = every form; [] = none. ≤100 bindings, ≤1000 formIds. `config` is adapter-owned non-secret JSON; validation REJECTS secret-shaped keys/values (token/secret/password/apiKey keys, bearer-looking strings) with a clear error. Credentials are references only (`connectionRef`). Export a pure `parseFormDeliveryBindings` and a validating write adapter (`writeFormDeliveryBindings`) for later admin/plugin UIs (no new admin route or UI in this build).
- On `form.submission.received`: persist a delivery plan ONCE per (workspace, submission), transactionally with one outbox child job per matching enabled binding. The plan freezes selected bindings, the delivery snapshot and child job ids. Replays reuse the plan even if settings changed. Empty selection still records a plan.
- Each child job delivers independently through the Jini outbox worker (claims, retries, terminal failure, restart recovery). A failing binding never blocks another. Retries reuse the SAME job id and idempotency key; never recreate a job.
- Retry policy: optional per-event retry-policy resolver in Jini's outbox (defaults unchanged for every other event). Delivery jobs: longer window (reuse Jini's webhook backoff helper), honor a bounded adapter `retryAfterMs`, and non-retryable errors go terminal at once. Keep this only if it stays small; if you drop it, record why.
- Email (Jini notify-subscriber) is unchanged in v1. Existing webhook delivery is unchanged.
- Status per binding: pending | retrying | completed | failed, attempts, nextRetryAt, safe error code, derived from the outbox rows.
P2 AUTOMATIC PULL (no interval polling)
- Pull ONCE at Tovu serving startup (after subscriptions are installed, only in `createServingApp`) and ONCE when an owner/admin signs in to the admin (every real sign-in path, incl. desktop root-key/owner boot session; dev-auth too). Never from exporters, the CLI outside `serve`, or the enqueue-only agent daemon.
- Setting `core.forms/autoPull` (workspace, boolean, default ON). Read fresh at each trigger; OFF = no automatic pull. Manual pull (existing tool + admin route) always works.
- Per-receiver lease shared by manual and automatic pulls: at most one in flight per receiver; automatic pull is skipped if the last pull STARTED < 60 s ago. Manual pull bypasses the 60 s check but not the in-flight lease: a manual pull while one is in flight returns "already running" instead of starting a second. The lease must outlast the bounded pull (prove it from the pull's page/time bounds in a comment + test); expired leases recover after a crash.
- Sign-in never waits for the pull; a pull failure never affects sign-in. Failures log a safe line; the next trigger retries. No backoff schedule.
- Desktop closed → delivery happens on reopen (startup trigger). Local delete leaves external copies (say so in the binding docs).
AGENT TOOLS
- `forms_delivery_status` (read-only): input `{ submissionId? , limit? }`. With submissionId: that submission's per-binding rows. Without: the most recent ≤50 jobs that are not completed. Output rows: bindingId, adapterId, formId, submissionId, status, attempts, nextRetryAt, errorCode. Never answers, URLs, credentials. Add tool metadata (`contracts/core/tool-metadata/forms.ts`), registration, capability inventory entry, and update any tool-search baseline the suite flags.
- `forms_pull_submissions` (existing): its result now reports per-form counts `{ formId, formSlug, imported, alreadyImported, unmapped, failed }[]` plus totals, and `{ ran: false, reason: 'already-running' | 'recent' }` when the lease refused. The admin pull route returns the same shape (additive).

## DELIVERY CONTRACT (the google-workspace build consumes this; keep it exactly, additive to the existing ABI)
In `apps/website/src/features/form-destinations/types.ts` (plugins are `.mjs` and receive plain objects):
```ts
deliver?(required: {
  kit: FormDestinationKit;                 // existing
  credential: FormDestinationCredential;   // resolved FRESH per attempt by FormDeliveryConnectionPort from binding.connectionRef; never stored in jobs
  form: FormDestinationForm;               // frozen at planning; fields gain OPTIONAL { label?, type? } (stable field name stays the id)
  submission: { id; answers; submittedAt }; // frozen at planning; IP never included
  binding: FormDeliveryBinding;            // frozen at planning
  idempotencyKey: string;                  // stable per (submissionId, bindingId); identical on every retry
}, optional?: Record<string, never>): Promise<void | FormDeliveryResult>;
type FormDeliveryResult = { ok: true; reference?: string }
  | { ok: false; error: { code: FormDeliveryErrorCode; retryable: boolean; retryAfterMs?: number; outcome?: 'not-applied' | 'unknown' } };
type FormDeliveryErrorCode = 'authorization-required' | 'rate-limited' | 'configuration-invalid' | 'mapping-invalid'
  | 'resource-not-granted' | 'destination-limit' | 'outcome-unknown' | 'adapter-unavailable' | 'delivery-failed';
type FormDeliveryConnectionPort = (required: { workspaceId; connectionRef; adapterId }, optional?) => Promise<FormDestinationCredential | null>;
```
- Legacy `void` adapters keep working. A thrown error or unknown code becomes `delivery-failed` (retryable). Only allowlisted codes reach the ledger; adapter messages never do (they can contain secrets).
- `binding`/`idempotencyKey` become REQUIRED fields for the push path in practice, but stay optional in the type so the existing receive-only adapters compile unchanged.
- Generic types (`FormDeliveryBinding`, `FormDeliveryResult`, error codes, planner, `deliverFormJob`, subscriptions, pull lease helper/trigger) live in Jini `@jini-ai/cms/forms` (Jini-first: generic, no Tovu/vendor names). Tovu re-exports/binds them; the plugin ABI file above is the Tovu adapter.
- The only shipped `FormDeliveryConnectionPort` in this build resolves the existing custom-credential vault by stable id (verify the id after any label lookup, as the WIP does). The OAuth implementation comes later in the google-workspace build; keep the port the single seam for it.
- Write the contract, with one example push adapter, into `.cloud-coord/forms-multidest-contract.md` on the branch (lot F2 drafts it; you ratify it before F4 starts).
