/* --- /admin/seo: sections OF the page, not boxes ON the page -----------------
 *
 * Owner report, 2026-09-06, looking at `/admin/seo`: "for seo can you take the stuff out of the
 * cards?"
 *
 * Measured live at 1440 before changing anything (`getBoundingClientRect` over `.page .card`, not
 * read off the rules). What she is looking at:
 *
 *   - Site defaults — ONE `.card`, 1300 x 770, holding the entire seven-field form.
 *   - Sitemap      — ONE `.card`, 1300 x 190, holding a heading, two sentences and two buttons.
 *     A 247,000px^2 bordered rectangle around four short lines on an otherwise empty page is the
 *     clearest statement of the problem: the frame is the largest thing on the screen and it is
 *     drawing attention to nothing.
 *
 * `.card` earns its border on a screen that shows SEVERAL cards — the frame is what says "these
 * are separate objects, and there are three of them" (`Deployment.tsx`'s Overview tab, Workspace's
 * danger zone). Every panel on this screen is a lone child of its tab. A border around the only
 * thing in a region separates it from nothing; all it does is inset the content 24px from a page
 * edge it is already inset from, and add a second rectangle inside the tab strip's.
 *
 * THE GROUPING DOES NOT COME FROM THE CARD, and this is the load-bearing observation. All three
 * field groups — Search appearance / Social sharing / Crawling, added an hour ago in `56e87ae0` —
 * live INSIDE the one card. The card wraps all of them together; it has never distinguished one
 * from another. What separated them was `.card-title` headings and `.field-group + .field-group`'s
 * 20px. So deleting the frame removes no grouping information whatsoever — but 20px between a
 * heading and the group above it is thin, and with the frame gone that thinness is what would read
 * as an undifferentiated wall of fields. The grouping is therefore not merely preserved here, it
 * is made louder than the card ever made it:
 *
 *   1. A HEADING RAIL. Each group is a two-column `<section>` — its title in a fixed left column,
 *      its controls in the right. The titles line up in their own vertical column down the page,
 *      which is a stronger scan structure than headings inline above their fields, because the eye
 *      can read the group names as a list without parsing the form. This is the settings-page
 *      idiom (`interface-design`: reuse a recognizable pattern set rather than invent one), and it
 *      is what replaces the box.
 *   2. A HAIRLINE between sections instead of a border around everything. One 1px rule per seam
 *      rather than four sides per group: the lightest mark that still says "new section".
 *   3. A 32px band above and below each section against 16px between fields inside one — a 2:1
 *      ratio, so proximity alone groups the fields even with the rule ignored
 *      (`kole-jain`: whitespace groups related elements and separates unrelated ones).
 *
 * The rail also fixes something the card was hiding: inside it, every input was 1258px wide. A
 * single-line text field a metre long is not a design decision anyone made, it is what `width:
 * 100%` does in a 1300px container. `--seo-measure` caps the control column at 42rem, so the
 * fields now have a deliberate measure and the rail's left column is paid for out of space that
 * was empty anyway.
 *
 * Feature-scoped file, `.seo-*` classes only, imported from `main.tsx` alongside the other
 * per-screen sheets. Nothing here can reach a screen outside `/admin/seo`, and `styles.css` is
 * untouched — including the one legacy rule this has to defeat (`.seo-entry-section`'s
 * `margin-top`, neutralized below at higher specificity rather than edited in place).
 *
 * UPDATE, 2026-09-13: point 1's two-column rail is no longer how any tab on this screen actually
 * renders — the owner asked all three tabs (Site defaults, Sitemap, Pages & posts) to read like
 * Pages & posts, full width (see the `seo-panel--full` section below for the full account). Points
 * 2 and 3 (the hairline seam, the 32px/16px spacing ratio) still hold exactly as written; only the
 * left rail column itself was retired. `.seo-section`'s own two-column `grid-template-columns`
 * stays defined below as the base case a future single-section tab could still opt into, but no
 * current caller renders it — every `.seo-panel` on this screen now also carries `--full`.
 */

   the app (`styles.css`'s own note on that rule), so the cap belongs on this scoped wrapper, same
   precedent as `.workspace-page` there. Not `--form-measure`'s 42rem: that token is for a single-
   column form and would re-create the truncation `seo-panel--full` was just built to fix (Canonical
   URL, OG/Twitter image refs). 76rem instead — the codebase's other deliberate "wide but not

   field on this screen while still stopping short of the raw viewport. Plain `max-width` rather
   than `min(100%, 76rem)`: a block's width is already 100% of its column below the cap, so it
   shrinks fluidly with the window on its own. */

     the post editor's action row does the same (`top: calc(-1 * var(--space-4))`). */
