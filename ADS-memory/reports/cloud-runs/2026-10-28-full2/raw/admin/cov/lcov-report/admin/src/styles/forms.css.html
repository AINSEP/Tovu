/**
 * `/admin/forms` — FormsList + FormEditor layout pass. This screen was the worst-looking surface
 * in the admin (audit callout: "no responsiveness, crammed together etc.") because it never
 * adopted the shared page primitives (`.page`/`.page-header`/`.card`/`.field*`/`.table-scroll`)
 * the Posts/Media canary pass introduced in `styles.css` — it still used only the older bare
 * `.editor-header` + unstyled `<label>` + unstyled `role="tab"` buttons. This file supplies the
 * handful of rules those shared primitives don't cover (a real tab strip, and an inline
 * checkbox+label row) rather than duplicating anything `styles.css` already provides.
 *
 * A separate partial rather than an addition to `styles.css` because another pass currently owns
 * that file; see `styles/assistant.css` for the established precedent of a scoped partial
 * imported alongside it (`main.tsx`).
 */

/* `FormFieldsEditor`'s field table (`FormEditor.tsx`) — every cell holds a live, unstyled-width
   `<input>`/`<select>`, so the browser's default content-driven table layout let ID/Label/Type/
   MaxLength each claim their own ~180px intrinsic width regardless of the viewport. Measured
   before this rule: the table rendered at 925px wide inside a 566px `.table-scroll` at a 640px
   viewport — MAX LENGTH and the Remove button were still technically reachable by scrolling
   (`.table-scroll`'s `overflow-x: auto` genuinely works, confirmed via `scrollWidth`/`clientWidth`
   before writing this, not assumed broken), but with zero visible affordance that anything was
   off to the right, and a ~360px overflow on a 640px screen is well past "slightly tight."
   `table-layout: fixed` + the TSX's own `<colgroup>` percentages replace the content-driven
   columns with a fixed 100%-of-container layout; `width: 100%` on the controls below fills
   whatever each fixed column ends up being instead of clipping at the control's own intrinsic
   width. Scoped to this one table's class, not `.list-table` generally — every other `.list-table`
   in the app holds plain text cells with occasional buttons, not a live input in every cell, and
   forcing fixed-percentage columns onto those would be a different, unrequested change. */
/* `min-width` (ui-fixes-backlog.md #9, dock-open clipping) — the rule above solved the AUTO-layout
   overflow, but `table-layout: fixed` with percentage `<colgroup>` widths has an overflow problem
   of its own: a fixed-layout table always sizes to exactly 100% of its container, so it can never
   itself be wider than `.table-scroll` and hand that wrapper's `overflow-x: auto` anything to
   scroll. With the assistant dock open (narrowing `.table-scroll`'s own container — the dock is a
   sibling, not a descendant, so its `overflow: hidden` was never the cause; ruled out by reading
   `App.tsx`'s layout, not assumed) the seven percentage columns just get crushed proportionally
   instead — worst on the 8%-width Req/More columns and the button-holding 18%-width Remove column,
   which is the exact "Remove sliced vertically, nothing to scroll to" symptom reported. A `min-width`
   here is what makes the table genuinely overflow again once its container drops below it, giving
   `.table-scroll` real content to scroll — same fix shape as the auto-layout rule above, just for
   the fixed-layout case that rule itself introduced. 720px sized off each column's own worst-case
   content at this table's percentages, not guessed: the tightest columns (Req/More, 8% each) need
   room for a checkbox or the 30px round kebab button plus this table's `--space-4` (16px)
   side padding on each edge — 8% of anything under ~690px starts clipping one of those two; 720px
   clears both with a small margin. The wider columns (ID 14%, Label/Type 17% each, Max length/
   Remove 18% each) are already comfortable at that same total, so this one number is set by the
   narrowest columns, not an average. */
.form-fields-table {
  table-layout: fixed;
  min-width: 720px;
}
.form-fields-table input,
.form-fields-table select {
  width: 100%;
  box-sizing: border-box;
}

   check, 2026-10-11). Its column is wider now (`FormFieldsEditor.tsx`'s colgroup, taken from Max
   length), and here the select gives back padding: the global select reserves 47px of side padding
   for one 14px chevron. */
.form-fields-table select {
  padding-left: 0.5rem;
  padding-right: 1.6rem;
  background-position: right 0.45rem center;
}

/* `.list-table` (`styles.css`) sets no `width` on `th`/`td`, so this table falls back to the
   browser's default AUTO layout: each column's share of the table's width comes out of the
   browser's own content-based distribution, weighted toward whichever column's content wants
   the most room. Here that's always the `<td>` — SOURCE IP/FULL_NAME/EMAIL/MESSAGE values,
   especially a free-text message, routinely want far more width than a five-word label ever
   does — so the `<th>` column is squeezed down near its own min-content width on any
   ordinarily-proportioned admin viewport, not just a narrow one. Measured live on production
   (`/admin/forms/contact-us/submissions`, sidebar expanded, no dock, 1107px viewport): the
   layout gave the `th` column 111px (79px of content after this table's `--space-4` padding),
   while "Submitted at" needs 83px unwrapped — 4px short, which is exactly the "SUBMITTED AT"
   two-line wrap the owner saw, not a one-off caused by a smaller window or the AI Assistant
   dock. "Submitted at" is the one label long enough to lose that race; "Source IP"/"Full_name"/
   "Email"/"Message" all stay under 79px unwrapped at the same measurement and never wrapped in
   either screenshot. `white-space: nowrap` fixes the min-content width itself instead of
   guessing a column percentage (the `.form-fields-table` rule above owns that approach for its
   own all-input table): the layout can no longer shrink this column below one line, and
   `.table-scroll`'s existing `overflow-x: auto` is still there to scroll the rest of the row on
   a genuinely narrow viewport, same fallback `.form-fields-table`'s own comment documents.
   Scoped to `.form-submission-detail` rather than bare `.list-table th`: roughly a dozen other
   `.list-table` call sites in this app hold ordinary list/data rows where a wrapping header is
   either impossible (short one-word headers) or an acceptable, unreviewed tradeoff today —
   forcing `nowrap` on all of them is a different, unrequested change. */
.form-submission-detail .list-table th {
  white-space: nowrap;
}
 
/* `.field-row`'s own definition lives in `styles.css` (off-limits to this dispatch) as a plain
   grid with no `align-items` set, so its default is `stretch`. Stretch is invisible as long as
   every cell's label is one line (true for every OTHER `.field-row` caller today — `FormEditor.tsx`
   "Name"/"Slug", `Media.tsx` "Title"/"Alt"/"Caption"/"Credit", `Jini redirects/react/pages/RedirectsPage.tsx`'s four short labels;
   grepped and rendered every one before writing this, not assumed): a stretched `.field` with a
   one-line label just gains invisible slack at its own bottom, since content still packs to the
   top. `@jini-ai/admin/comments/react` SettingsSection's "Close submissions after (days, blank = never)" breaks that assumption —
   it wraps to two lines at the widths this row actually renders at, so that one cell's label is
   taller top-to-bottom than its three siblings', and stretch's top-packing means the taller
   label pushes only ITS OWN input down, leaving the other three inputs sitting higher — a visibly
   sagging fourth control in an otherwise level row.
 
   Fixed by overriding just `align-items` here rather than editing `styles.css`: `end` anchors each
   `.field` by its own bottom edge instead of stretching it, so the input (the last thing in every
   `.field`) lands on the same line across the row regardless of how tall the label above it is.
   Same-specificity selector, later in the cascade — `main.tsx` imports this file directly after
   `styles.css`, so this wins the tie without `!important` (same reasoning `styles.css`'s own
   `.list-table td button:not([class*="btn-"])` comment documents for an equivalent case).
 
   `styles.css` ALSO carries `.field-row > .field > :is(input, select, textarea) { margin-top: auto }`
   (added independently, same bug, different author, before either of us knew about the other's
   fix) — measured with THIS rule commented out to check whether that one alone was sufficient
   before assuming both were needed: it is not. With only `margin-top: auto` in play, Comments'
   four inputs measured `[578, 592, 578, 578]` at 1440 — the wrapped-label field is still 14px
   off from its siblings, not flush. Whatever the exact flex/grid interaction responsible (not
   fully chased down — a `gap`-and-auto-margin interaction inside a grid-stretched flex column is
   plausible but unconfirmed), the empirical result is that rule does not fix this on its own.
   This rule does, on its own — confirmed earlier today, before `styles.css`'s rule existed, at a
   clean `[591.8, 591.8, 591.8, 591.8]`. With both rules active together (today's actual shipped
   state) the result is `[592, 592, 592, 592]` — this rule carries the fix; the other one is inert
   given this one, not load-bearing, but also not harmful. Do not remove this rule to de-duplicate
   without re-measuring — that was tried in the course of writing this comment and made the row
   sag again.
 
   Checked against the three other callers, none of which have this problem — their labels never
   wrap at any width this app's `.field-row` min-column (`minmax(10rem, 1fr)`) allows, so `end` and
   the previous `stretch` render pixel-identical there. `FormEditor.tsx` (Name/Slug), `Jini redirects/react/pages/RedirectsPage.tsx`
   (all four fields), and `Media.tsx`'s edit panel (Title/Alt/Caption/Credit — a real uploaded item
   finally existed in this environment to check it against) are all confirmed live at 1440 and 640,
   measured via `getBoundingClientRect()`, not eyeballed: every control in every row still lands on
   one shared top offset per row, unchanged from before this rule existed. */
.field-row {
  align-items: end;
}
 
/* A row whose cells carry help text of different lengths UNDER their inputs (Static Site's host
   config fields): `end` would push each input down by its own help's height, so the inputs no
   longer line up. Top-align instead; labels there are one line, so the inputs share one top. */
.field-row.field-row-top {
  align-items: start;
}
