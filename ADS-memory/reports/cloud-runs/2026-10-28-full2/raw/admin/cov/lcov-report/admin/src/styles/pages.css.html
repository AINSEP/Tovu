/*
 * Groups the device-width control and the template picker on the toolbar's right side (owner
 * feedback, 2026-08-11: both move onto the one row the view tabs already occupy). A plain
 * wrapper, not a new flex-item shape — `.page-editor-toolbar`'s own `justify-content: space-between`
 * still just places two things: the tabs on the left, this group on the right.
 *
 * `flex-wrap: wrap` here (independent of `.page-editor-toolbar`'s own wrap) is the narrow-viewport
 * degrade: three variable-width control clusters (tabs, device-width, template) collide sooner than
 * the two-cluster toolbar did before this change, so this group can drop its own two children to a
 * second line without the tabs above it needing to move. The template `<select>` shrinking below its
 * shared 14rem width (`.editor-template-picker select`, `styles.css`) is the OTHER half of that
 * degrade — scoped to this wrapper only, so `PostEditor.tsx`'s own picker keeps its normal width.
 */
.page-editor-toolbar-end {
  display: flex;
  align-items: center;
  justify-content: flex-end;
  gap: 0.75rem;
  flex-wrap: wrap;
}
 
/* Container (2026-10-11): 688px ≈ the old 720px viewport minus a tablet's 2 × 16px page padding. */

    width: auto;
    min-width: 0;
    max-width: 11rem;
  }
}
 
/*
 * `.page`'s own flex `gap: var(--space-6)` (24px) spaces every row evenly — title, slug, template
 * picker, toolbar, content pane — and that even rhythm is right everywhere except the last step:
 * the owner wants "very minimal space" between the toolbar and the content pane specifically,
 * without disturbing the rows above it (2026-08-11 feedback). Cancelling exactly `--space-6` here
 * removes that one flex gap so the ONLY space left between toolbar and pane is the toolbar's own
 * existing `0.75rem` bottom margin (see `.page-editor-toolbar` above) — reusing a token already on
 * the page rather than introducing a new magic number. Measured: 36px -> 12px.
 *
 * Scoped with the `.page >` child combinator, not the bare class: `PageEditor.tsx` renders these
 * as direct children of `.page`, while `ThemeExplore.tsx` (the other consumer of these same class
 * names) nests its copy inside `.theme-explore-main`, one level deeper — so this rule can never
 * reach that screen's own spacing.
 */
.page > .page-preview-frame,
.page > .page-html-source,
.page > .interactive-html-editor {
  margin-top: calc(-1 * var(--space-6));
}
/* The preview surface is deliberately NOT in the negative-pull rule above (owner, 2026-09-16):
   they asked for breathing room between the Save/Delete row and the preview frame, then tuned it by
   eye. `-15px` yields a MEASURED 9px gap, which is the value they settled on.
 
   The number is not derivable — the surface sits 24px below the action row with no margin at all,
   so this margin is negative to pull 24px down to 9px. Re-MEASURE against `[data-agent-element=
   "page-actions"]` if anything above it moves; do not reason from the arithmetic here, it only held
   for the layout as of this date.
 
   Expanded stays flush: `.page-preview-expanded .page-preview-surface` below sets `margin-top: 0`,
   and the surface is not a direct child of `.page` in that state anyway.
 
   `.page-preview-host` (2026-10-05) is the collapsed state's class for the wrapper `PagePreview`
   renders in BOTH states (expanded swaps it for `.page-preview-expanded`) — one element tree, so a
   toggle never remounts the preview iframe. It carries no styles of its own. */
.page > .page-preview-host > .page-preview-surface { margin-top: -15px; }

/*
 * Preview fullscreen (2026-09-16) — the Pages twin of `styles/editor.css`'s `.post-preview-*`
 * block. Duplicated rather than shared: Pages and Posts keep separate stylesheets on purpose (see
 * this file's own header). The geometry genuinely differs too — a Post's expanded iframe fills an
 * `.editor-shell`, and there is no `.editor-shell` ANYWHERE on this screen to hang the equivalent
 * rule off; a Page's preview is a fixed-width `.page-preview-scaler` transform-scaled to fit inside
 * an `overflow: hidden` `.page-preview-frame`, so the height chain has to run through those two.
 *
 * `.page-preview-surface` is the `position: relative` ancestor the fab's `position: absolute`
 * resolves against, and `PageEditor.tsx` renders it in BOTH states so the control never moves.
 * Collapsed it is layout-neutral: it inherits the `-space-6` pull the frame used to take directly
 * (the rule near the top of this file, which now names the surface — the frame is no longer a
 * direct child of `.page`), and its flex column changes nothing about a notice stacked above a
 * fixed-height frame.
 */
.page-preview-surface { position: relative; display: flex; flex-direction: column; }
/* The frame plus the fab, and the fab's containing block (2026-10-05). The surface also holds the
   notice line, so with the surface as containing block the fab sat over that notice instead of
   inside the preview (owner screenshots: over the header line expanded, straddling the frame's top
   border collapsed). */
.page-preview-stage { position: relative; display: flex; flex-direction: column; }
.page-preview-fab {

/* In-page hint replacing the native `title` tooltip, which the desktop app clipped at the window's

/* Collapsed (desktop 2026-10-11, every width 2026-10-13): floating in the frame's top-right corner,
   the control sat over the previewed site's header (its Log in button). It moves just above the
   frame instead, at the right end of the Save/Delete row (empty on this screen), as a plain icon
   button since it no longer floats over page content. `bottom: 100% + 9px` matches the measured 9px
   row-to-frame gap above. Expanded keeps the in-frame float: there is no row above the panel to sit
   in. Phones keep this spot too (owner, 2026-10-13: the control floated alone on its own line
   under the row); see the phone block below for how it follows the row's sticky position there. */
.page-preview-host .page-preview-stage > .page-preview-fab {

/* The control sits over the row without being in it, so the row keeps its width free: a draft's
   wider Draft/Publish/Save/Delete group stops short of it instead of running underneath. */

/* Phones: same as the post editor's `.post-preview-fab` (`styles/editor.css`, 2026-10-10). The
   previewed theme's own menu button sits in the frame's top-right corner, so the floating control
   covered it; here it moves out onto its own right-aligned line just above the frame (`order: -1`;
   it follows the frame in the DOM) as a plain icon button. Expanded only since 2026-10-13 — the
   collapsed control moves up into the row (next rule).
   `position: relative`, not `static`, so the button stays the containing block of its own tip. */
@media (max-width: 640px) {
  .page-preview-stage > .page-preview-fab {
    position: relative; inset: auto; order: -1; align-self: flex-end; margin-bottom: var(--space-1);
    opacity: 1; color: var(--fg-2); background: transparent; backdrop-filter: none;
  }
  .page-preview-stage > .page-preview-fab:hover,
  .page-preview-stage > .page-preview-fab:focus-visible { color: var(--fg); background: var(--surface-2); }
  /* Collapsed: on the Save/Delete row's right end, like wider screens. The row is sticky on phones
     (`styles.css`), and an absolutely placed control scrolled away from it, drifting up over the
     stuck row. So the control is sticky too, at the row's own offset plus its 6px padding, and is
     pulled up into the row by its 40px tap height plus 15px (that padding plus the 9px row-to-frame
     gap), which it hands back below so the frame does not move. `z-index: 7` clears the row's 6,
     whose background would otherwise cover it. */
  .page-preview-host .page-preview-stage > .page-preview-fab {
    position: sticky; inset: auto; top: calc(6px - var(--space-4)); z-index: 7;
    margin: calc(-40px - 15px) 0 15px;
  }
}
 
/* `position: absolute; inset: 0` against `.admin-main-col` (`styles.css`, which is where its own
   `position: relative` lives), NOT `position: fixed` over the whole viewport — deliberately, so it
   is geometrically incapable of covering `.admin-chat-dock`'s separate flex column: the two boxes
   never overlap, so no z-index arithmetic against the dock is needed. `z-index: 25` matches
   `.post-preview-expanded`'s own for the same reasons that rule records — above `.admin-content`'s
   in-flow content, below `.chat-fab`'s 75 (`styles/assistant.css`) and below the mobile sheet
   dock's 55, so the sheet still slides up over this exactly as it does over `<main>`. */
.page-preview-expanded { position: absolute; inset: 0; z-index: 25; display: flex; flex-direction: column; background: var(--surface); }
/* The `-space-6` pull above is a gap fix for sitting directly under the toolbar; expanded there is
   no toolbar above this panel. */
.page-preview-expanded .page-preview-surface { flex: 1; min-height: 0; margin-top: 0; }
.page-preview-expanded .page-preview-stage { flex: 1; min-height: 0; }
/* THE LOAD-BEARING CHAIN, and the one jsdom can never see. The expanded frame has no inline height
   (`PageEditor.tsx` writes one only when collapsed) and takes its height from this `flex: 1`, which
   only works because every ancestor up to `.page-preview-expanded` is a flex column: panel ->
   surface -> stage -> frame. Drop any link and the frame falls back to its intrinsic height — on the Posts
   side the identical omission rendered a ~150px sliver of site header over an empty white box, and
   its unit tests stayed green throughout. `min-height: 0` on each is what lets a flex item shrink
   below its content; without it the chain overflows instead of fitting. Pinned by a CSS-text
   regression test, since no DOM assertion can reach it. */
.page-preview-expanded .page-preview-frame { flex: 1; min-height: 0; border-radius: 0; background: var(--surface-2); }
/* Fullscreen widens the PANE, never the previewed page: the Desktop/Tablet/Mobile choice is the
   operator's statement about which viewport they are inspecting, and inheriting it is what makes a
   fullscreen Mobile preview useful (a 390px box that was being scaled DOWN to fit a narrow pane
   renders 1:1 once the pane is wide enough). Centred here rather than pinned to the corner
   `transform-origin: top left` would leave it in — when the scaler's own box is WIDER than the
   frame, as Desktop on a narrow pane is, `auto` margins resolve to 0 and it stays flush left, which
   is exactly what an over-wide, scaled-down preview wants. */
.page-preview-expanded .page-preview-scaler { margin-inline: auto; }
