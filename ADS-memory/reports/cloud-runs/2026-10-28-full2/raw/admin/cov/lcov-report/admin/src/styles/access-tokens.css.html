  /* A readable-measure CAP, not a percentage of the column (2026-09-01 fix): `max-width: 60%` used
     to fit the summary line's marker + name + "saved <date>" + expand affordance on one row at full
     page width, but the same 60% of a much narrower column (chat dock open) is too tight for that
     same content, and `.access-tokens-row-summary-meta` had no `white-space` of its own — so the
     browser wrapped the DATE mid-value ("saved" / "2026-" / "09-01 16:55") instead of the row simply
     using more of the available width. `40rem` is generous enough to hold every row's content on one
     line at any realistic column width (including with the dock open) while still capping the row on
     a very wide monitor, the way `%` was meant to but couldn't once the column itself got narrow.
     `.source-control-row` (this file's own "visual rhyme" reference, see header) carries no cap at
     all — 40rem is a deliberately looser middle ground, not a return to unbounded width. */

  padding: var(--space-4); background: var(--surface); border: 1px solid var(--border-strong); border-radius: var(--r-md);

   dock open that sum exceeds the column, and a nowrap flex row does not reflow: it overflows, so

/* A small `min-width` (not `0`) overrides the flex-item default of `min-width: auto` (which

   otherwise stop this span from ever shrinking past that, forcing the date or the row itself to
   give way instead). `0` was tried first and over-corrected: with `.access-tokens-row-summary-meta`

   keeps enough of the name legible to still read as ellipsized text, not a vanished label, while

   nowrap/fixed) under pressure. Only a safety net for the narrowest columns —
   `.access-tokens-row`'s own `max-width: 40rem` fix (see that rule's comment) is what actually
   prevents this at any realistic width. */
