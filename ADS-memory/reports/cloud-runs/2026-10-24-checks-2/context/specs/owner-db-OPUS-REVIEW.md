## What the plan got right (verified)
- better-sqlite3 13.0.3 is N-API with flat prebuilds for darwin-arm64/x64 and win32-x64/arm64 (`T/node_modules/better-sqlite3/prebuilds/`), `npmRebuild: false` (`T/apps/desktop/electron-builder.yml:115-126`). The payload ships outside asar, and `smoke-native.ts:110-118` already opens it in the packaged app. **So native SQLite packaging is not a blocker. SQLite stays.**
- tracked-sites.ts avoided SQLite to keep `@jini-ai/sqlite-chat` and `better-sqlite3` out of the **shell's** dependency graph (`T/apps/desktop/src/tracked-sites.ts:2-5`). That was a deliberate choice, not a crash.
- The key-file approach is compatible with `desktop-auth.ts:18` ("Do not reintroduce OS credential storage"). No keychain, no DPAPI.
- Backup by itself, never inside a site backup: correct and already decided.
- Extra fact I measured: Electron 43.6 (Node 24.20) ships `node:sqlite` (SQLite 3.53.4), and it works in both the main process and the run-as-node child. It is the fallback if better-sqlite3 ever breaks. Not needed now, because Jini's kernel is shaped for better-sqlite3 (`J/packages/db/src/kernel/sqlite/driver.ts:13`).

## Binding changes
1. **Never open owner.db in the Electron main process.** Plan shard 6 loads better-sqlite3, Kysely and @jini-ai/db into the shell. That reverses the shell's written decision (`tracked-sites.ts:2-5`). It also brings back the optional-peer bug class: `kysely` and `better-sqlite3` are *optional* peers of @jini-ai/db (`J/packages/db/package.json` peerDependenciesMeta), the shell declares neither (`T/apps/desktop/package.json:16-38`), and that is how the packaged bridge died in 0.1.13–0.1.17. Do what the desktop already does for site work: shell out to the Tovu CLI under Electron-as-node with secrets on stdin. Precedent: `T/apps/desktop/src/agent-plugin-tokens.ts:1-12`, and `T/apps/website/src/cli/commands/agent-plugin-tokens.ts:14-19` ("it shells out to the CLI instead of importing apps/website"). Every native and DB dependency then resolves from the payload, which the existing smokes already cover. "Only the desktop host opens it" still holds, because only the desktop runs that command, with the userData paths on stdin.
2. **The inherited Node IPC broker does not reach the sites the owner named.** The owner decision says "local sites (:3000 etc.)". :3000 is started by `npm run dev`, and the desktop also attaches to sites it did not spawn (`T/apps/desktop/main.ts:25-28,704` `attachRunningSite`). An inherited channel can't reach either kind, and the plan's "restart the desktop" escape fails for :3000. See Q1. If the owner keeps a live broker, it must work without spawning: a loopback server built from Jini's existing `startRenderBridge` (`J/packages/desktop-host/src/render-bridge.ts:44`, which already has the bounded body and the constant-time bearer check), plus a per-site grant token stored in the site root, which no backup scope walks (`T/apps/website/src/features/site-backup/sources.ts:117-120`). No new IPC transport.
3. **The plan wires the wrong consumer.** It only changes the custom-credentials resolver (`credentialed-request.ts:661`). But `custom` is deliberately *not copyable*, while `vendor`, `site-assistant`, `media-provider`, `publish-peer` and `source-control` are (`J/packages/platform/src/secrets/credential-sets/vault.meta.ts:5-11`). Plugin key cards are what people actually share (Resend, Vercel, OpenAI), and they read the site's `secrets_vault`, so the plan would not cover them. The first slice must share a **vendor-kind plugin key card**. Custom credentials stay per-site, as the copy policy already says.
4. **Reuse the existing cross-site copy, which the plan misses entirely.** Jini `SecretsVaultService.copyToSite` reseals one vault's row into another vault (`vault.service.ts:252-310`). Tovu wires it for local sites in `T/apps/website/src/server/runtime/composition/local-credential-copy.ts:163` and exposes it at `system/credential-copy.ts` (owner session plus local-host only). The owner store is one more *source* for that path. It is not a new CRUD lifecycle.
5. **Key file: reuse what exists, add no new file code.** `generateFileRootKey` already creates the key exclusively (`wx`) at mode 0600 (`J/.../keyring.env.ts:345-355`). That settles the multi-instance race on its own (the desktop has no single-instance lock). The read side is `EnvOrFileKeyring({ allowFileAutoGenerate: false, hkdfSalt: "jini-owner-store-v1" })` (`keyring.env.ts:47,373`). Missing key with existing data means a recovery message, never a new key. Cut `key-file.ts` and `key-file.node.ts`, the extra file lock, and the Windows ACL code: userData under the user profile is already user-only.
6. **Export crypto reuses the sealer.** scrypt (Node built-in, bounded N/r/p in the header) feeds a 32-byte key into `FixedRootKeyKeyring` (`keyring.env.ts:174`) and then `AesGcmSecretSealer`. No new cipher code. The header (format, version, KDF parameters) is authenticated as AAD. The export never contains owner.key or anything wrapping it.
7. **Package placement.** @jini-ai/db has an optional peer on @jini-ai/platform, so platform must not import db (that would be a cycle). The owner-store service that composes `SqlSecretsVaultRepo` and the grants goes in **@jini-ai/db/owner-store**. Only the generic passphrase envelope goes in **@jini-ai/platform/secrets**.
8. **UI goes to Opus + Chrome, not Codex** (owner rule 10-22). The desktop renderer has no Settings screen (`T/apps/desktop/src/renderer/`). Don't mount `@jini-ai/admin` in the shell: it is not a desktop dependency and would bring its peers along. Build one small `SharedKeys.tsx` from the shell's existing primitives instead.
9. **Schema.** owner.db is a Jini-owned database with its own ledger, run by Jini's migration runner (`J/packages/db/src/migrate/runner.ts:46`). That is correct. ADR-066 governs Tovu site schemas, and this plan adds no Tovu site schema change.

## Owner questions
1. **Copy the shared key into each chosen site, or have sites fetch it live from the desktop?** *Recommend copy.* When you change a key, the desktop pushes the new value into every chosen site, sealed with that site's own key. This uses the copy machinery Tovu already has. It works for :3000 and for sites the desktop didn't start. It works for every plugin key card. Deploy works on the next redeploy with no extra work. A stopped site catches up when it starts. The leak boundary is the same: a site backup only ever holds that site's chosen keys, sealed, and its site key is never in the backup (`~/.tovu/site-keys/`). The cost: each chosen site holds a sealed copy, which is a change from "only through a broker". A live broker needs a new always-on authenticated server and a hook in every key read, and still leaves deploy for later.
2. **Windows: owner.db and owner.key sit in `%APPDATA%` (Roaming)**, which follows a roaming or domain profile. *Recommend: accept it.* Home PCs don't roam, and putting the key under LocalAppData would split it from the DB for no gain.
