## 1. Does `apps/website` survive?

Half yes.

You are mistaking shared dependencies for app inseparability. A website app importing the same `widgets`, `navigation`, `media`, and theme modules as an admin API is normal. The absence of production back-imports proves there is an extractable public-interface boundary.

But a separately deployed `apps/website` is not justified yet. The “website” area also owns:

- Analytics ingestion
- Comments and form submissions
- Newsletter confirmation/unsubscribe
- Payment webhooks
- Media delivery
- Commerce routes

It is not a read-only renderer. Today `tovu serve` constructs one SQLite dependency graph and passes it to one Express app: [serve.ts](/Users/la/Programming/Tovu/src/cli/commands/serve.ts:76). Splitting processes would make two deployments coordinate around the same `content.db`, secrets, lifecycle, and write paths without a demonstrated scaling or security requirement.

My target would be:

```text
apps/server/
  public-http/
  admin-http/
  composition/
```

Keep one deployed server. Extract the reusable rendering engine into `src/modules/rendering` or the existing presentation/theme domain. `public-http` consumes it. If public traffic later earns independent deployment, promote that already-isolated adapter to `apps/website`.

So: an independent code boundary survives; an independent service does not yet.

Specifics:

- Analytics through origin are domain modules regardless of whether they currently have repositories or tools.
- `connectors` mixes a connector capability with a Composio-specific adapter. Put connector contracts/use cases under `modules/connectors`; put Composio under `platform/integrations/composio`.
- `assistant` is not infrastructure. It mixes site assistant, BYOK execution, credentials, daemon integration, MCP federation, tool registries, and UI protocols. Keep it temporarily as `modules/assistant`, then extract provider/process adapters into platform.
- `theme-archive` contains 41 tracked non-code files, referenced by renderer tests such as [render.test.ts](/Users/la/Programming/Tovu/src/server/http/site/__tests__/render.test.ts:405). Move it to a test-fixture or development archive directory.
- `headless` is semantically correct as a contract, but the admin currently does not consume it and the root package exposes no `exports`. Make it `packages/headless` or an export of `@tovu/sdk`; otherwise it is only a server-internal DTO folder.

Axis (b)—“participates in public rendering”—should be represented by a machine-readable module manifest, for example:

```json
{
  "module": "widgets",
  "surfaces": ["admin-http", "public-http", "agent"]
}
```

Then enforce:

```text
public-http -> modules/*
admin-http  -> modules/*
modules/*   -X-> public-http, admin-http, server
```

Use dependency rules plus public barrels. `package.json` exports are valuable across actual packages, but they do not stop relative deep imports within one package.

## 3. Is `slices/platform/contracts` right?

Not as defined.

Three problems:

1. “Has repo plus agent tools” is not the definition of a vertical slice. It is an accidental inventory heuristic.
2. `platform/` already contains domain capabilities. [routing/INFO.md](/Users/la/Programming/Tovu/src/platform/routing/INFO.md:1) says it owns Tovu’s route vocabulary and resolution policy. Export is likewise a Tovu portability use case, not infrastructure.
3. `contracts/core` is not merely contracts. It contains memory repositories, an outbox worker, mutation gateways, command implementations, rate limiting, and composition code. [core/INFO.md](/Users/la/Programming/Tovu/src/contracts/core/INFO.md:1) is already stale and describes a `ports.ts` that is not present.

I would use:

```text
apps/
  server/
    public-http/
    admin-http/
    composition/
  admin/
  site-chat/

src/
  modules/          business capabilities
  platform/         technical and provider adapters
  contracts/        pure wire/extension contracts
  kernel/           genuinely shared runtime primitives
  cli/
```

Use `modules`, not `slices`. A newcomer can answer “who owns this business behavior?” more reliably than “does this folder currently have two particular filenames?”

Also move `routing` and `export` out of platform. Review `site-dir` separately; it straddles boot infrastructure and a Tovu lifecycle use case.
