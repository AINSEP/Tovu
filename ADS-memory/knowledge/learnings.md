# Learnings

Use this file for lessons learned, postmortem-style findings, and repeated failure patterns.

## Entries

- YYYY-MM-DD: <what failed or worked, why it mattered, and what to do next time>
- 2026-07-21: **`codex exec --ignore-user-config` silently drops `model_reasoning_effort` from `~/.codex/config.toml`, even though `-m <model>` still selects the right model.** During ADR-047's round-2 `/audit-work` dispatch, codex was invoked with `-m "gpt-5.6-sol"` (correct — confirmed via the persisted session rollout file, `~/.codex/sessions/<date>/rollout-*.jsonl`, which records `"model":"gpt-5.6-sol"` in plaintext) but WITHOUT an explicit `-c model_reasoning_effort="high"` override. Because `--ignore-user-config` skips `~/.codex/config.toml` entirely (which is where `model_reasoning_effort = "high"` normally lives as a local default), the actual dispatch silently ran at whatever reasoning effort codex defaults to absent config — not "high" as the audit packet and report claimed. The model name itself was unaffected (an explicit `-m` flag is not part of "user config"), so the "wrong model" concern that prompted the fix turned out to be a false alarm, but the "wrong reasoning effort" concern was real and confirmed. **Next time:** when using `--ignore-user-config` for codex peer-dispatch hygiene, ALWAYS also pass `-c model_reasoning_effort="<level>"` explicitly — never rely on the config file's default surviving `--ignore-user-config`. **Also:** to get airtight proof of which model/effort a codex dispatch actually used (not just what flags you believe you passed), drop `--ephemeral` for at least one verification run and grep the persisted session rollout file (`~/.codex/sessions/<yyyy>/<mm>/<dd>/rollout-*.jsonl`) for `"model"`/`"effort"` fields — this is real session metadata, not model self-report (which the swarm-consensus model-hygiene rules already correctly ban as invalid evidence). `--ephemeral` mode does not persist this file at all, so a fully-ephemeral dispatch cannot be forensically re-verified after the fact if the user later questions which model actually ran.
- 2026-08-01: **The "everything in the Marketing section is ugly" complaint was two screens, not five — confirmed with the user rather than inferred.** A prior session's task list swept Analytics and Newsletter (`Placeholder.tsx`) in alongside SEO and Redirects. The one agent that actually rendered all four at 1440/900/640 reported it could not reproduce any defect on Analytics or Newsletter: both were already on `.page`/`.page-header`/`.card`/`.table-scroll`, have no forms, and contain nothing inline-label-shaped. Rather than either trusting the task list or trusting the agent, the handoff escalated it as an explicit question to the user, who confirmed: **nothing specific was seen on those two — they were included by association with SEO.** SEO and Redirects are the real defects. **Next time:** when a user complaint is phrased by *area* ("the whole X section"), treat the area as a pointer, not a boundary — get the specific screens named before generating one task per screen in that area. A rendered-and-clean report from an agent is grounds to *ask*, not grounds to silently drop the task; and a task list is not evidence that a defect exists. This closed an item that was on track to cost an hour of hunting for a defect that did not exist.
- 2026-08-01: **Second "defect" of the day closed by asking the user instead of investigating — the untranslated Settings panel.** A full 67-shot visual audit ranked as its single HIGH finding that `/settings` renders roughly half in Spanish ("CONFIGURACIÓN", "Puertas de enlace", "Probar conexión") while the surrounding admin shell stays English, reading as broken to any operator. The auditing agent did the right diligence: it probed `navigator.language` in its headless browser (`en-US`) to rule out a misconfigured harness before reporting, and correctly hypothesized the embedded `@jini-ai/ui` execution-settings component as the source. The Coordinator was one dispatch away from spending an agent on scoping it across 13 tabs and tracing the locale plumbing into a **deliberately quarantined vendored dependency** (`SettingsUi.tsx` and `.settings-ui-section` are off-limits by project rule) — and escalated to the user first instead. Answer: **the user simply has no translations in place yet**; the untranslated strings are expected project state, not a bug. **Next time:** an audit finding can be methodologically flawless and still be a non-issue, because *project state is not visible from the code or from the rendered page*. Before spending on any finding whose fix would land in a quarantined dependency or a third-party surface, escalate it to the user first — the cost of asking is one message, and the cost of not asking is an agent-hours investigation into intended behavior. Pairs with the same day's Analytics/Newsletter case: both were "confirmed defects" that dissolved on contact with the person who owns the project.
