# Directus: Multi-Team Collaboration, Environment Sync, and "Git-Like" Versioning — mapped to Tovu

Research date: 2026-07-11. Prepared for Leon (Tovu).

## 1. TL;DR

- Directus does **not** have git-style branch/merge for content or schema. What it has are four *separate*, narrower mechanisms that people lump together under "collaboration": an audit log, per-item drafts, a schema sync pipeline, and a live-editing presence layer.
- **"Other devs work on different parts"** in Directus mostly means: (a) role/policy-scoped permissions so people can only touch their own collections, and (b) a **schema snapshot → diff → apply** pipeline so a developer's local schema changes (new collection, new field) can be captured as a file and replayed onto staging/prod — this is Directus's real answer to "environment syncing," and it is closer to a database migration tool than to git.
- **Content Versioning** (their newest, most git-adjacent feature) is a per-item draft/branch: you fork one entry into a named draft, edit it without touching the published row, compare draft-vs-live side by side, then "promote" (merge) it back. It is scoped to a single row, not a whole site, and there's no cross-item transaction.
- **`directus_revisions`** is a plain append-only audit log per row (who changed what, when) with a single `revert(pk)` operation. It is the ancestor of "history," not a branching tool.
- Concurrency between two humans editing live is handled by **rooms + presence + best-effort collab, not real merge**: WebSocket "collab" rooms show who's in an item, broadcast field-level changes, but there is no CRDT/OT conflict resolution documented — it's closer to "see who else is editing" than "safely merge concurrent edits."
- The payoff for Tovu: your **ADR-022 revision ledger + ADR-008 change-sets + ADR-028 schemas-as-data** already give you the equivalent of `directus_revisions` + content versioning's promote semantics + roughly half of schema-snapshot/apply — for free, as a byproduct of decisions already made for a different reason (never-brick). What Tovu genuinely lacks and Directus genuinely has is (1) a **cross-environment schema/config export-diff-apply pipeline** and (2) **live multi-user presence/collab**. Both are real, buildable, but neither is a v1 must — they're additive on top of what already exists.
- Recommendation: don't build a "GitHub for CMS" clone. Build the Backups/export admin-section item you already have queued (which is effectively Directus's snapshot/export, since ADR-012's `tovu build` + a `content.db` export already gives you a portable unit) and treat named-draft/promote as a small feature on `entries` + `change_sets`, not a new subsystem. Skip live presence/collab entirely for v1.

## 2. What Directus actually offers (four distinct things, precisely distinguished)

### (1) `directus_revisions` — per-item change history / audit log
- **What it is:** a flat, append-only log table. Every mutation writes a revision row capturing `activity`, `collection`, `item`, `data` (full snapshot), `delta` (diff from parent), `parent` (previous revision id), `version`.
- **Mechanism:** `RevisionsService` extends `ItemsService`. Reads are exposed at `GET /revisions`, `GET /revisions/:pk` (read-only at the controller). The only mutation is `revert(pk)`, which re-applies the stored `data` back onto the live item — but that endpoint is *not* exposed on the revisions controller; it's wired through `POST /utils/revert/:revision` in `utils.ts` (and via GraphQL). Revision writes force `autoPurgeCache: false` and `bypassLimits: true` because they're system-generated, not user-initiated.
- **What it is not:** there's no notion of "revision set" spanning multiple items/collections — one revision = one row's one change. No named branches, no cross-entity transaction.
- Source: `other-repos-specs/directus_specs/api/activity-comments-notifications-and-revisions.md` (§6, §6.1–6.2).

### (2) Content Versioning (`directus_versions`) — named per-item drafts with promote/compare
- **What it is:** the actual "different people work on a draft, then merge it" feature, but scoped to **one item at a time**, not a site-wide branch. A "version" is a named fork (`key`, e.g. a slug) of a single item's editable state, keyed uniquely on `(key, collection, item)`. Every versioned item auto-gets a `"published"` reserved-key draft.
- **Mechanism (confirmed both in-repo and via docs.directus.com):**
  - `POST /versions` creates a version; stores an **object hash of the current main item** at creation time so later compare/promote can detect drift.
  - `POST /versions/:pk/save` — "record more delta": prepares a payload delta, writes a revision row (ties into mechanism (1)), merges the new delta into the version's stored delta. This is accumulation, not full-state replacement.
  - `GET /versions/:pk/compare` — reads the version, verifies its stored hash against the *current* live item, returns both the version's delta and the live item, so the caller gets a diff view ("Content Comparison Modal," side-by-side, changed fields color-highlighted per the docs).
  - `POST /versions/:pk/promote` — verifies update access, rejects an empty delta, verifies the caller-supplied `mainHash` (optimistic-concurrency guard: refuses to promote against a live item that moved since the version was compared), splits the delta into payload + overwrite-defaults, runs `items.promote` hook filters, then applies via `ItemsService.updateOne()`. This is the actual "merge into main" step — validation of required fields is deferred until this point, so a partial/incomplete draft is legal until promotion.
  - **Realtime collab rooms are version-aware**: a "versioned room" joins on `(collection, item, version)`, so two people can co-edit the *same draft* and see each other's live changes (see §4 below) — separate from co-editing the published item.
- **What it is not:** whole-site branching. You cannot version 20 entries + a schema change + a plugin config together and promote them atomically. Each versioned item is independent; there's no cross-item change-set concept in Directus at all (this is the single biggest structural gap vs. what Tovu already built with ADR-008).
- Source: `other-repos-specs/directus_specs/api/utilities-import-export-and-versioning.md` §5–6; corroborated by directus.com/docs/guides/headless-cms/content-versioning and directus.com/features/content-versioning (WebFetch, 2026-07-11): "Make different versions of content without messing up what's live," "See versions side-by-side to spot changes," "Push drafts live with one click," "Go back to old versions if you need to."

### (3) Schema snapshot → diff → apply — the dev→prod schema-as-code sync
This is Directus's actual environment-sync story. Full detail in §3 below.

### (4) CLI `directus schema snapshot/apply` + migration files
- The CLI is a thin wrapper over the same `/schema/snapshot`, `/schema/diff`, `/schema/apply` HTTP endpoints (confirmed via WebSearch of directus.com/docs/guides/migration and the SDK equivalents `schemaSnapshot()` / `schemaDiff()` / `schemaApply()` in `@directus/sdk`). `npx directus schema apply ./snapshot.yaml` is the documented invocation for bootstrapping a fresh instance from a committed snapshot file.
- Separately, Directus supports **custom data migrations** (arbitrary `up`/`down` JS files under a migrations directory) for one-off data transforms that schema-snapshot doesn't cover — these are conceptually closer to a classic Rails/Knex migration runner and are a distinct mechanism from schema snapshot/diff/apply.
- This is the mechanism people mean when they say "sync my schema between dev and prod." It is **not** what people mean by "other devs work on different parts of the same live site simultaneously" — that's roles/policies (permission scoping) plus, weakly, Content Versioning + collab rooms.

## 3. The schema snapshot → diff → apply pipeline (detail)

This is the core "sync" mechanism and the one most relevant to "how do multiple devs configure a site without clobbering each other."

**Where schema lives:** Directus has no separate schema-definition language — the schema *is* data, stored in `directus_collections`, `directus_fields`, `directus_relations` (system meta tables), same discipline you already chose for content in ADR-022 ("types are data, not code").

**The three-step pipeline** (confirmed identically in-repo `directus_specs/api/utilities-import-export-and-versioning.md` §4 and via WebSearch of the official "Promoting Changes Between Environments" tutorial):

1. **`GET /schema/snapshot`** (or CLI `directus schema snapshot`) — `SchemaService.snapshot()` reads the *live* schema out of the meta tables and serializes it to a single JSON/YAML document (a full point-in-time schema state, not a diff). This file is meant to be committed to version control.
2. **`POST /schema/diff`** — takes an uploaded snapshot (JSON body or a multipart YAML/JSON file upload) and the *current* live schema on the target instance, computes the difference, and returns `{ data: { hash, diff } }`. Returns `null` diff when nothing changed. The `hash` is produced by `getVersionedHash()`, which hashes the payload **together with the current Directus version** — so a diff is intentionally invalidated if you try to apply it to a differently-versioned instance (bypassable only with an explicit `force` flag). `validateSnapshot()` additionally checks the source snapshot's declared Directus version and DB vendor match the target, again bypassable only with `force`.
3. **`POST /schema/apply`** — takes the diff-plus-hash payload from step 2 and applies it. `validateApplyDiff()` re-checks: empty diffs are no-ops; **create/delete collisions are rejected if the live schema has drifted since the diff was computed**; system-field edits are limited to `schema.is_indexed`; and critically, **a hash mismatch is rejected outright** with an explicit "generate a new diff" error. This is optimistic concurrency at the schema level, not automatic merging.

**Row-sync vs DDL:** the pipeline diffs and replays rows in `directus_collections`/`directus_fields`/`directus_relations` (metadata rows), and Directus's own migration/service layer is what turns those metadata changes into the actual underlying `CREATE TABLE`/`ALTER TABLE` DDL against whichever DB vendor is running (Postgres/MySQL/SQLite/etc. via Knex). So conceptually it's "sync the metadata rows, and let the service layer's own migration logic emit vendor-appropriate DDL as a side effect of writing those rows" — not a raw SQL diff tool. This is architecturally very close to what ADR-022 does for content (`entries` + `content_types` registry: "adding or changing a type is a registry edit — no code release, no schema migration") — Directus does the same trick one layer down, at the *collections/fields* level instead of the *content-type* level, because in Directus, collections/fields ARE the equivalent of Tovu's content-type registry.

**Safety mechanism summary:** version-sensitive hash + drift detection + `force` escape hatch = the whole "don't clobber someone else's concurrent schema change" story. There's no merge; a stale diff is simply rejected and the operator must regenerate it.

## 4. Multi-user concurrency model

Two separate mechanisms, at two separate layers, neither of which is a real merge algorithm:

- **Schema-level (see §3):** optimistic concurrency via versioned hash — reject-and-regenerate, not merge.
- **Content-level, live editing:** WebSocket "collab" rooms (`api/src/websocket/collab/*`), gated by `WEBSOCKETS_COLLAB_ENABLED` + a runtime setting `directus_settings.collaborative_editing_enabled`. Mechanics:
  - `RoomManager.createRoom()` derives a **deterministic room hash from `(collection, item, version)`** so all clients editing the same resource (or the same *named draft*, per §2's version-aware rooms) converge on one room.
  - `onJoin()` runs permission checks (read access to the item, and to the version record if a versioned room) *before* room creation — access control happens at join time, not just page load.
  - Room state (`uid`, `collection`, `item`, `version`, `changes`, `clients`, `focuses`) is held in **shared storage** so a room can be rehydrated across multiple Directus instances/processes (i.e., this is built for horizontally-scaled deployments, using a cross-instance message bus, `COLLAB_BUS`).
  - The handler explicitly **filters out** system collections (`directus_activity`, `directus_notifications`, `directus_revisions`, `directus_sessions`, `directus_shares`) from collab broadcast — not every mutation is a collab signal.
  - `focuses` in room state strongly suggests **field-level presence** (who's focused on which field) — a "Google-Docs-lite" cursor/presence layer, not documented as doing character-level operational transform or CRDT merging of concurrent edits. The spec extraction found no conflict-resolution algorithm — only presence + broadcast + the item-level hash checks from `/versions/:pk/compare`+`/promote` (§2) as the actual integrity guard against lost updates.
- **Net effect:** Directus's concurrency story is "see who else is here and what they're touching, and get hard-blocked (hash mismatch) if you try to save/promote over someone else's more-recent write." It is presence + optimistic locking, **not** automatic merge.

Source: `other-repos-specs/directus_specs/api/realtime-websockets-and-collab.md` (full file).

## 5. What Directus does NOT do

- **No git-style branching/merging of a whole site.** No concept of "branch the site config + N content entries + a schema change together, review as one diff, merge atomically." Content Versioning is per-item only; schema snapshot/diff/apply is schema-only; there is no unified change-set spanning both (this is the one place Tovu is already structurally ahead — see §6).
- **No automatic field-level or three-way content merge.** Promotion is "apply this draft's delta onto main if the hash still matches" — a hard gate, not a merge algorithm. Two people drafting the same item concurrently in the *same* version can collide (mitigated only by presence UI telling you someone else is there).
- **No DDL-level version control (no migration history you can `git log` and `git revert` collection-by-collection).** A schema snapshot is a full point-in-time state; there's no first-class chain of schema commits the way git has commits — you diff two full snapshots, you don't replay an ordered sequence of schema patches (except via the separate, more manual custom-migrations mechanism, which *is* an ordered sequence but is hand-authored, not auto-derived from a diff).
- **No environment topology awareness.** Directus treats dev/staging/prod as three unrelated instances you manually snapshot-diff-apply between; there's no built-in "environments" object graph, no promotion pipeline UI beyond the Deployment module's Vercel/Netlify build triggers (which is about *deploying the app*, not about *syncing the CMS schema/content* — a separate, unrelated feature; see `directus_specs/distribution/deployment-and-cloud.md`).
- **Notification/comment mention delivery is best-effort, not transactional** with the write it's attached to — a minor but real reliability gap versus Tovu's "one write chokepoint, same-transaction" discipline (ADR-022 §4a, ADR-028 §4).

## 6. Mapping to Tovu

|---|---|---|
| `directus_revisions` (per-row audit log, single revert) | ADR-022 §4b "complete revisions" (full post-state + actor + timestamp + monotonic sequence, append-only) on `entries`; ADR-028's `setting_revisions` gives the same for settings | **Free.** Tovu's revision ledger is already stronger — it's chokepoint-enforced with a CI canary (ADR-022 §4a), and it carries `pluginId` write-attribution (ADR-024 amendment) which Directus's `activity`/`revisions` split doesn't cleanly give you. |
| Content Versioning: named draft, save-delta, compare-vs-live, promote | ADR-008 change-sets (`change_sets`/`change_set_items`, `proposed \| applied \| reverted \| discarded`, before/after revision ids) + ADR-022's per-entry revisions | **Small feature.** The storage shape and hash/optimistic-concurrency semantics you'd need (a "propose" state that isn't live yet, a "promote" = apply operation, a "compare" = diff two revisions) map almost 1:1 onto ADR-008's already-designed-but-not-yet-built propose/preview/apply/revert workflow. You don't need a new table; you need the workflow layer ADR-008 explicitly deferred ("Later (the workflow): preview rendering of proposed-but-unapplied change sets, approval UI in admin, revert executor"). This is arguably a superset of Directus's version, since ADR-008's change-sets can span *multiple* entities in one atomic unit — Directus's versions cannot. |
| Schema snapshot → diff → apply (schema-as-data sync between environments) | ADR-022's `content_types` registry (types-as-data) + ADR-028's `setting_definitions` registry (schemas-as-data) are the *storage* analog of `directus_collections`/`directus_fields`; ADR-012's site-template/instantiation + `tovu build` export | **New subsystem, but a thin one.** Tovu doesn't yet have an export/diff/apply *pipeline* for the registries — only the underlying "definitions are rows, not DDL" foundation that makes such a pipeline cheap to build later (no ALTER TABLE risk the way Directus has to manage, since ADR-022 §3's expression-index mechanism means adding a queryable field is `CREATE INDEX`, not a migration). Building "export content_types + setting_definitions as a JSON file, diff against a target site's registry, apply" is realistic and low-risk given the foundation, but it doesn't exist today. |
| Optimistic-concurrency hash guard on apply/promote | Not yet built, but ADR-008's `beforeRevisionId`/`afterRevisionId` inverse-capture model is the right primitive to hang a hash check on | **Small feature** once ADR-008's workflow phase lands — check `beforeRevisionId` still equals the entity's current revision before applying, reject otherwise. |
| Roles/policies scoping "who can touch what" (Directus's real answer to "different people work on different parts") | ADR-021 (principal-centric hybrid RBAC, flat permission strings, `authorize()`) | **Free — already ACCEPTED and arguably stronger.** ADR-021's composite `(workspace_id, id)` FK isolation and fail-closed extensible ABAC seam cover what Directus's roles→policies→permissions three-tier model covers, without Directus's separate-port complexity. |
| Live collab rooms / presence / field-level focus broadcast | Nothing today | **New subsystem — genuinely new work (WebSocket transport, room manager, cross-instance bus).** Not covered by any ADR. This is the one piece of Directus's story that has no analog anywhere in Tovu's design. |
| Deployment module (Vercel/Netlify build trigger + run history) | ADR-012 `tovu build <site>` (binary/artifact export) is a different shape of "deploy" — produces a standalone runtime+data artifact, not a "trigger a build on a hosting provider and poll its status" flow | **New subsystem, but likely out of scope** — Tovu's local-first, self-hosted, single-admin topology (ADR-021 §"Topology is settled... local-first / self-hosted... no hosted multi-tenant server") makes a Vercel/Netlify-style multi-provider deployment dashboard a mismatched feature to import wholesale. |

## 7. Recommendation for Tovu

1. **Do not build a git-like branch/merge system for whole sites.** Nobody in the Directus ecosystem gets that either — even Directus's most git-adjacent feature (Content Versioning) is scoped to one item, with a hard hash-gate instead of a merge algorithm. Your ADR-008 change-sets are already a *more* ambitious version of that idea (multi-entity, atomic), so the honest sequencing move is: **finish the ADR-008 workflow phase** (propose/preview/apply/revert UI + the hash/optimistic-concurrency check) rather than reach for something new. That single piece of work gives you Directus's Content Versioning feature and more, "for free" off primitives you already accepted.

2. **Treat "schema/config sync between environments" as the one real gap worth scoping**, and scope it small: an export/diff/apply pipeline over `content_types` + `setting_definitions` (both already schemas-as-data per ADR-022/ADR-028). This is the actual thing "GitHub-like collaboration for site config" cashes out to in Directus's own architecture — not code, not content, but registry rows. This dovetails directly with **the Backups/export admin-section item already on your list** and with **`tovu build`** (ADR-012) — a `tovu build`-style export of the registries (as a JSON/YAML file, diffable, committable to a real git repo if the owner wants that) is a natural, cheap extension of infrastructure you're already committed to building, rather than a new subsystem bolted on. Suggested sequencing: ship the export side first (snapshot), since that alone gives portability/backup value; diff/apply (the actual "sync to another environment" step) can follow once there's a second environment that needs it.

3. **Skip live collab/presence for v1.** It is the one piece of Directus's story with zero analog in any accepted ADR, requires new infrastructure (WebSocket transport, room manager, cross-instance bus) that doesn't exist anywhere in Tovu today, and — per Directus's own implementation — doesn't even solve concurrent-edit conflicts (it's presence + a hard reject-gate, which ADR-008's future hash-check would already give you without any realtime layer). If/when Tovu ever needs "see who else is editing," it's a UI feature over the already-existing change-set/actor data, not a new subsystem.

4. **Skip the Deployment module (Vercel/Netlify build-trigger dashboard) entirely.** It solves a hosted-multi-tenant problem Tovu's local-first/self-hosted topology (ADR-021) explicitly doesn't have.

5. **Don't build comments/@mentions/notifications** unless a concrete workflow need shows up — Directus itself treats this as best-effort, non-transactional, and outside its core guarantees.

**Bottom line for the owner's original question ("do we need GitHub-like collaboration for multiple people building a site?"):** No — not in the git-branch/merge sense. What you need, and mostly already have blueprinted, is (a) per-entity propose/promote with a concurrency gate — ADR-008, unbuilt workflow phase; (b) role-scoped permissions so people don't collide in the first place — ADR-021, ACCEPTED; and (c) a portable, diffable export of your schemas-as-data registries — new but small, and it's the same shape as the Backups/export work already queued.
