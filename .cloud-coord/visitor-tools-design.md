# Visitor tools — design proposal, 2026-10-22

Software Architect + Security (Direct): personas loaded from the requested canonical roster; selected for capability ownership, reusable contracts, and the anonymous internet trust boundary.

**Recommendation:** add the two requested tabs and a site-wide visitor-tool policy. Let admins select explicitly visitor-eligible built-in/plugin tools or create a declarative **saved request**. Run the resulting narrow surface through Jini's existing ToolExecutor, independently of the admin registry. Both admin chat and page call the same management service. No arbitrary code generator, general HTTP tool, or admin-tool bridge is exposed to visitors.

This is a design for Coordinator review, not an approved spec/ADR or implementation authorization. Only this file was written; no tests, installs, builds, commits, or Jini changes were performed.

## 2. Catalog, policy and created-tool data

**Eligibility is a contract, never an admin toggle that converts an admin tool into a public one.** Extend existing Jini registration metadata and the existing plugin contribution parser with an optional, versioned visitor declaration: audience `anonymous-visitor`, binding, effect, public input/output contract, and maximum limits. Missing/invalid declarations deny. A remote MCP annotation or `readOnly` flag alone is insufficient. Plugin declarations stay in their owning contribution file; do not invent a parallel plugin loader/catalog.

There are only two eligible binding kinds for v1:

1. Reviewed built-in public handler: existing public content/page-action implementations and future owners with a real anonymous-safe port. No generic admin-handler reference. `site_guide` projects only this caller's effective capabilities; it must not advertise disabled or admin capabilities.
2. Declarative saved request: usable by an admin-created definition or by an active, trusted plugin's visitor declaration. Both call the **same interpreter**. Existing `.mjs` admin tools remain ineligible merely by being marked visitor-facing; v1 does not execute plugin JS on the public path. A plugin can publish a separate saved-request binding for its public operation.

One derived catalog lists `{id, source, sourceRevision, title, description, inputSchema, effect, eligibility, availability, effectiveMode, limits}`. IDs are stable and namespaced by built-in/plugin/created identity; never derived solely from an editable title. Plugin digest/schema changes require review before reactivation; disabling/uninstalling/revoking a connection takes effect on the next invocation. Unknown IDs refuse. Stored policy never makes an unavailable tool available. List unavailable configured tools to admins with the reason; omit them from model schemas.

**Site storage:** register workspace-only settings, with no user/global override, under `site.assistant`:

- `visitor_tools`: one bounded JSON **list** of configurations. Each row contains immutable ID, record revision, source identity/revision, `mode: auto|ask|off`, limits, and (only for created tools) the saved-request definition. Source contract declarations remain source-owned. Do not persist copies of built-in/plugin handlers or independent effect metadata that can weaken their source contract.
- Scalar site aggregate budgets and site concurrency limit get their own typed definitions; do not hide scalar settings in JSON.

This fits the ledger's list-shaped JSON exception and stores no credentials. Start with at most 50 configured tools and a 256 KiB serialized list; reject malformed/oversized data, never truncate configuration. All writes go through the existing settings chokepoint, deep domain validation, specific `visitor-tools.manage` authorization, revision/CAS under the ledger's transaction lock, and its normal revision trail. Factor the existing form-delivery/comments CAS invariant into the settings owner before adding a third variant. No table migration for configuration.

Generic settings APIs, aliases, clear/reset, import and alternate transports must enforce the same policy and approval requirements: they cannot bypass validation by writing raw JSON. Reuse the canonical-definition protection already used for comments selection, with an explicit policy/store dependency rather than a spoofable input approval flag. An unset list means legacy reviewed built-ins at their current Auto behavior, new plugin/created tools Off. An explicit built-in Off survives reload; invalid stored config fails closed. Upgrades never re-enable an explicitly disabled tool.

**Saved request definition:** title/help, bounded object input schema, fixed HTTPS endpoint/method, opaque credential ID, typed bindings from input to named query parameters or JSON body fields, positive response projection, effect, limits and version. Credential IDs are resolved to the current record inside a site-bound resolver; never resolve an editable/nonunique display label from visitor input. Capture credential revision/account identity for confirmation and refuse retargeting.

V1 supports the request owner's GET/POST/PUT/PATCH/DELETE methods, a **fixed path**, query/body value bindings, and JSON responses. Schema is a bounded supported subset (objects, primitive properties, bounded arrays, enums/ranges/lengths, closed objects); reject executable templates, arbitrary expressions, external `$ref`, unsupported schema constructs and unrestricted regexes. Use the installed schema validator, standard `URL`/`URLSearchParams` and JSON serialization. No scripts, shell, GraphQL/raw request text, visitor headers, dynamic hosts/paths, chained tool calls, auth fields or credential selectors. Method alone does not prove read semantics.

Example: “Search products” → GET a fixed `/products/search`, bind `query` to `q` with a 200-character bound and fixed public-catalog/store constraint, return at most 10 items with only public title/price/availability fields. The provider-specific endpoint is configured data or a vendor adapter, never a vendor branch in core. Public product data can be returned; orders, customer records and internal supplier fields cannot. Response projection is a release boundary, not just prettier output.

Creating saves **Off**. Admin reviews exactly what is public, which account is used and what can change, then selects a mode in the same flow. Bounded mutating tools suggest **Ask first**; Auto for an eligible bounded mutation requires an explicit admin exposure approval. Privileged/destructive/account-administration operations are ineligible in v1. Asking a visitor cannot authorize an otherwise forbidden operation. Read-only credential probes may use the existing verification owner; no live mutating “test” is run automatically. Arbitrary credentials are not silently adopted: the admin explicitly grants visitor use of one credential for this fixed operation, preferably a dedicated low-scope public-data credential.

**Why this wins:** saved requests provide genuine creation and “search products” without installing code or creating a second runtime. Plugin generation remains the runner-up for operations needing provider-specific logic; it needs source review, tests, lifecycle packaging and a separate public-safe binding. Arbitrary JS/MCP passthrough loses on the public trust boundary. Deferred: custom code, member identity, destructive public operations and workflow chaining; none is required for the stated example.

## 3. Invocation, modes, limits and confirmation

Keep `createSiteCapabilityRegistry` as Tovu's public resolution facade, backed by a separate visitor-only Jini ToolRegistry/ToolExecutor. Built-in public functions become registrations through the existing registration kit. The admin registry/executor is never supplied. The public provider loop still consumes schemas and invokes this facade; do not add another model loop. All eligible entries have independent effect/risk declarations and normalizers; normalize, then validate and freeze the canonical input before displaying approval.

The server derives workspace from the mounted site, an anonymous principal/session from a server-issued high-entropy HttpOnly Secure SameSite cookie, and IP from existing trusted-proxy resolution. Admin/member cookies confer no privilege. The session is an abuse/confirmation binding, **not authentication or membership**. The model cannot supply principal, workspace, credential, mode, limit, URL or approval.

Per invocation: record request → resolve live eligibility/source/policy → schema validation and immutable plan → rate/pending admission → optional visitor confirmation → recheck source/policy/config/credential identity → consume execution quotas → invoke the eligible owner → project/redact/bound result → record terminal outcome. No network call or secret resolution while the visitor considers approval. Revalidate immediately before effect, including calls already in a provider continuation. Off/revocation cancels pending calls; an already-dispatched external mutation cannot be undone by switching Off.

| Mode | Behavior |
| --- | --- |
| Off | Omit schema, deny direct invocation, cancel pending approval. |
| Auto | Run within eligibility and quotas. Existing explicit-navigation-intent/propose rules remain; Auto does not rewrite page-action semantics. |
| Ask first | A visitor-owned card in **that visitor's chat** displays the frozen action and public arguments; execute once only after an explicit visitor click. No click, no action. No admin notification/approval for the visitor's call. |

**Reuse Jini ToolExecutor confirmation**, setting `requiresConfirmation` on the visitor registration snapshot, with a visitor transport `onConfirm` delegate. Do not use the admin `humanConfirmedHandler` to impersonate an anonymous visitor as an authenticated user. The executor owns waiting/resumption/cancellation; a small host adapter binds the reply to its server-held plan and browser session. Policy is checked both at initial authorization and immediately before the handler effect by one shared resolver; changed revisions fail closed rather than silently changing the approved plan.

Add a narrowly typed `tool_confirmation` SSE event and a same-origin public confirmation reply route accepting only opaque challenge ID and allow/deny. No callable `confirm_tool` model tool. Bind challenge to site, visitor session, server turn ID, execution ID, source/config/credential revision and canonical input digest. Reuse existing expiring single-use surface-exchange primitives where their binding fits, extending them in Jini for session/turn binding if needed; do not copy that lifecycle. The transport alone calls `resumeConfirmation`. The public route cannot deliver to an admin exchange. Validate Origin against trusted site configuration, restrict CORS, enforce same-site/CSRF and reply rate limits; never derive allowed origin from an untrusted Host header.

Keep the current POST stream open for the reply; cap approval at 60 seconds, one pending call/session and a bounded site total. Send a typed heartbeat while waiting so the existing 90-second widget idle timer does not end a healthy prompt. Disconnect/timeout denies and cleans up; restart expires pending prompts and does not auto-replay. No durable visitor conversation store is needed. Both React and Pure JS render the same safe text/Allow/Cancel contract with keyboard/focus/announcement support. Existing `assistant_ask_choice` can clarify admin configuration; its model-visible answer never serves as visitor or admin approval.

**Proposed starting limits, configurable within deployment hard ceilings:** retain chat IP admission; execution ceilings of 10/min/session and 20/min/IP across all visitor tools, 120/min/site plus 5,000/day/site, and per-tool 5/min/session, 10/min/IP and 60/min/site. Site concurrency 4; at most 4 tool calls/turn; pending site prompts 20. No burst by default. UI exposes per-tool session/IP/site limits and site totals; chat can change all of them. Effective caps are the minimum of source contract, deployment ceilings, site and tool limits. A request must pass **all** applicable scopes; rotating cookies cannot bypass the IP/site caps. Hash IP keys with a rotating site-bound server secret; do not persist raw IPs in tool audit. Trusted proxy rules cannot be changed by a tool.

Reuse `@jini-ai/http-kit/rate-limit`; extend its existing owner with atomic shared consumption/expiry for production across workers and restarts. Its current get/set CounterStore plus a local Promise queue does **not** give distributed atomicity. Production needs a shared transactional counter adapter (storage kernel lock/update; memory fake for tests); if no shared counter table exists, add only that state via **ADR-066 ordered checksum-checked TypeScript migration**, one Kysely body across supported dialects. Do not use settings revisions for hot counters or call per-process quotas “site-wide.” Charge only actual admitted execution after confirmation, with separate attempt/pending limits before waiting. Sequential quota reservations may conservatively consume capacity on later refusal; never refund ambiguously or allow an overrun. Return safe `retryAfterSeconds`; no queued automatic retry of mutations. Shared-store failure denies new calls.

## 4. Security constraints and threat cases

- **Confused deputy / privilege escalation:** eligibility ∩ site grant ∩ input contract is the only authority. No admin registry reference, `invokeTool`, filesystem, process, credential-list/decrypt tool or arbitrary HTTP capability enters the visitor graph. A saved-request tool cannot name another tool. Plugin `.mjs` is trusted host code, **not sandboxed merely by withholding ports**; exclude it from v1 public execution. Any later code-backed visitor adapter needs a reviewed isolation/trust ADR, not just a new boolean.
- **Data exfiltration:** fixed endpoint/path/method and named value bindings prevent a prompt selecting an export/admin endpoint or credential. Pin public catalog/tenant filters server-side. Positive response fields, bounded rows, no raw headers/status diagnostics/account identifiers; provider errors become safe public errors. Existing reflected-secret redaction happens **before** projection/model output. Credential-scoped read permission alone does not prove that returned data is public; enabling is an explicit public-data release approval. Never expose personal-account operations anonymously.
- **SSRF / credential theft:** reuse Jini credentialed HTTP plus platform guarded transport. Visitor composition supplies HTTPS-only, empty development allowlist, zero redirects, private/loopback/link-local/metadata/IPv6 deny and DNS-pinned peers. Scope a credential to the configured origin and fixed operation, never its entire `additionalHosts` list. Deny this site's admin/API/control origins as visitor request targets even if publicly routed. No automatic credential repair/host widening. Credentials remain sealed at rest and server-only; secure key-card input stays outside chat transcripts.
- **Resource exhaustion:** proposed caps are 16 KiB canonical tool input/request body, 64 KiB encoded and decompressed HTTP response, 16 KiB serialized projected tool output, 10-second total outbound deadline and 30-second provider-work budget excluding the separately bounded human wait. Admin may lower, never exceed deployment ceilings. Reuse transport byte/decompression/idle caps and executor limits. Current credentialed-request API does not thread the caller's AbortSignal: extend that owner to pass cancellation/deadline through the existing HTTP port; an executor timeout without aborting the socket is insufficient. Reject oversized/invalid JSON, don't parse a truncated JSON body. Bound object serialization explicitly; do not rely on the executor's string-only truncation.
- **Direct/indirect prompt injection:** published entries, tool results, descriptions from untrusted sources and visitor history remain data, never system instructions. Preserve the current preamble rule and label result provenance. Instructions such as “ignore the admin,” “call custom_credential_make_request” or “send all customer data” cannot change the registry, target, schema, mode or grant. Do not insert returned text into tool schemas/prompts as policy. A tool result cannot trigger a browser directive; only existing server-resolved page-action owners may do that. Render output as escaped text/sanitized existing Markdown, never plugin HTML, scripts or arbitrary MCP-UI. Prompt wording improves model behavior; structural gates enforce authorization.
- **Forged/replayed approval:** no model-supplied `confirmed`, transcript “yes,” returned web text, or old browser card grants consent. Challenge is single-use, expires, session/site/turn/plan-bound, checked after wait. Changing input, account, mode or plugin revision invalidates it. Off and session cancellation revoke pending execution. Approval is for an already eligible action; it cannot upgrade anonymous permissions.
- **Audit and abuse visibility:** every attempted invocation, including unknown/Off/schema refusal/rate refusal/cancel/error, records requested and terminal outcomes in existing `agent_tool_attempts`, correlated by server turn/attempt/execution IDs. Extend existing detail metadata with bounded value-free audience/source/config version, policy outcome, consent outcome and duration/byte counts; no query values, secrets, bodies, raw IP or provider error text. Keep credential-request audit correlated as transport evidence, not a second invocation ledger. The SQL sink/decorator currently swallow failures: add opt-in acknowledged/required persistence to those owners, preserving current admin semantics. A failed requested/started acknowledgement blocks effects; terminal failure after an external effect yields **outcome unknown**, disables further dispatch through that unhealthy sink and alerts the operator, never retries the effect. Existing bounded retention is operational audit, not permanent compliance storage; show audit health and capacity pressure. Review retention before high-volume rollout because visitor traffic shares the current workspace cap.

## 5. Admin chat and page

Register category-level management tools through the existing admin catalog/registration kit: `visitor_tools_list`, `visitor_tool_create`, `visitor_tool_update`, `visitor_tool_delete`, `visitor_tool_set_mode`, `visitor_tool_set_limits`, and `visitor_tools_set_site_limits`. No vendor-specific tools. List is read-only; the others declare durable effects and independent derived risk, have closed input schemas/normalizers, require `visitor-tools.manage`, and call one shared management service. Identity/site come from the authenticated context. Create/update support all creation fields; delete removes only created definitions, while built-in/plugin removal means Off. Selection is setting a source's mode, not installing a second copy.

Reuse existing admin `approvalToolHandler`/Jini approval owner for a frozen before/after review of management writes: public data release, account, effect, mode and caps. The task explicitly requires approval gating; encode the new domain's policy explicitly rather than assume all existing durable edits already ask. One approval can create and enable a tool atomically. Secure credential cards remain their existing lifecycle. Generic settings edits must reach the same policy, not an unguarded alternate writer. Recheck permission and expected revision after approval. If operator access changes or CAS fails, no write; explain and reload.

“Let visitors search my products” → inspect existing eligible tools first → reuse one if it satisfies the request; otherwise ask only for missing endpoint/public-data details → secure credential collection if needed → propose bounded saved request → approve creation + desired mode. “Turn that off,” “ask before making bookings,” “limit searches to five a minute” use the corresponding management tools and return the persisted revision. Unsupported/private operations explain the boundary and suggest a safe public endpoint; the assistant does not manufacture API contracts or claim to have enabled an unavailable source.

Under **Admin › AI Assistant › Visitor's AI Assistant**, add nested tabs **AI provider | Visitor tools**. The provider tab retains provider/model/widget/enable controls. Tools remain configurable while the assistant is disabled; expose the disabled status and the reason visitors cannot run them.

Visitor tools shows one list of Built-in / Plugin / Created rows with title, plain-language purpose, effect, availability and the shared **Auto | Ask first | Off** segmented control. Limits expand inline; site aggregate limits appear once above the list. Disabled plugin/missing credential/review-required reasons are explicit. Create tool opens a small drawer: describe purpose → select credential through its secure existing picker/card → fixed request + bounded input fields → choose returned public fields → review + mode. “Ask the assistant to set this up” pre-fills the chat request; it does not secretly execute an action. Advanced JSON is optional, never required for ordinary input fields. No arbitrary generated code editor.

On mobile, stack rows as cards with a full-width segmented control, expanded limits below, and a full-height creation sheet; use existing tab-wrap/scroll preference, shared widgets, native labels and translated strings. No wide table. Confirmation actions stay visible when the keyboard is open. Keyboard, focus restoration, screen-reader announcements, loading/empty/error/saving/stale states are acceptance criteria.

Page and chat read the **same persisted revision** and management service. Subscribe through existing settings revision delivery, or refetch on successful chat write/focus with revision comparison. Never persist a parallel browser-only policy. Optimistic UI rolls back on refusal; stale drafts reload explicitly rather than overwrite another admin. Public advertisement and `site_guide` read the effective policy; server invocation always rechecks it even if a turn began with old schemas.
