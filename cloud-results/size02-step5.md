## Design as built
- `MemoryRootContext` is built from the slices' `ReturnType`s (`Pick<ReturnType<typeof composeX>, "names used">` — only the names the fragments read, so a slice can grow) plus 20 explicit local types (`ReturnType<typeof createX>` / class names; `MemoryRouteDeps["removeTheme"]` for `removeTheme`, whose generic return loses its type through `ReturnType`). `options`, `routeDeps: () => MemoryRouteDeps` (a getter: every self-reference runs inside a closure after `createRouteDeps` returned) and `createSiteApp` are the three non-slice entries.
- Each fragment is `(required: MemoryRootContext, _optional = {}) => ({...} satisfies Partial<MemoryRouteDeps>)`; `satisfies` keeps the lambdas contextually typed and the result precise. Bodies are the literal's own text, script-extracted; the only edits are `routeDeps` -> `routeDeps()` and `{ ...opts, routeDeps }` -> `{ ...opts, routeDeps: routeDeps() }` (spread-last order kept).
- `createSiteApp` is built in `createRouteDeps` (app.ts owns `createApp`; a fragment importing `app.ts` would close a cycle — design §2.4). Its long comment moved with it; the fragment key carries a pointer comment.
- `runExportSite` and its 40-line doc moved verbatim to `route-deps/publish-export.ts` (design §2.2: file-private beside its user).
- Comments: every old `//`, `*`, `/*` line of the original `app.ts` exists in the new `app.ts` or a `route-deps/` file (checked by a `comm` of the two sorted sets: 0 lost). Import-leading comments moved with their imports (one stale "Deep-imported … above" comment deliberately stayed with its import in `app.ts`).
- No re-export, no forwarder, no `vi.mock`; fragment functions all <= 50 lines (eslint `max-lines-per-function` clean on `memory-deps/`; two fragments were split once after eslint flagged 57 / 58).

The literal has 8 self-references (`createSiteApp`, `resolveStorefrontProducts`, `resolveActiveThemeId`, `listPublishedPosts`, `exportSiteBound`, `staticSiteContext`, `preferences.write`, the OAuth `applyAccess`); they cannot be removed without behaviour change (`routes/types.ts` documents the in-place-mutation contract), so they read the final object through the context getter and are pinned (M3-M5, MM3-MM6).
- D5-3: the design splits the literal into `route-deps/` runs with `assemble.ts`; done as 14 runs in 5 files, grouped by contiguous theme, not one file per run.
