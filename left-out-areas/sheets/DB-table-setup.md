## Design (smallest that closes the gap)
1. Each domain `/sql` entry exports a typed history FACTORY (judge finding 12): step bodies cannot receive table names through `(kernel, context)`, so the names are closed over.
```ts
// packages/cms/src/redirects/sql/schema/index.ts
export interface RedirectSchemaTables { readonly redirects: string; readonly revisions: string }   // the two tables the Jini adapter uses
export interface DomainSchemaHistory<K> { readonly steps: readonly MigrationStep<K>[]; readonly defaultLedgerTable: string }
export function createRedirectSchemaHistory(
  required: { tables: RedirectSchemaTables },
  optional: { indexPrefix?: string } = {},
): DomainSchemaHistory<StorageKernel<Kysely<unknown>, unknown>>
```
   - Table names are validated in the factory (`/^[a-z][a-z0-9_]{0,62}$/`; a name that fails throws a plain-words error before any step exists) and then interpolated only through Kysely identifier APIs (`sql.table`, schema builder), never string concatenation.
   - Step ids are fixed strings independent of table names: `0001_redirects_baseline`, then `0002_…`. Ids never change after release.
   - Checksum rule: `checksum` is a pinned constant in `schema/checksums.ts`, equal to the sha256 hex of the step's source file text (the same rule `@jini-ai/db/migrate` `sourceChecksum` implements, `db/src/migrate/checksum.ts:12`: read it first and reproduce its exact input normalization; a mismatch between the two = STOP). The checksum does NOT depend on the host's table names (the names are data, the step text is the contract), so two hosts with different names share one checksum per step.
   - Ledger: `defaultLedgerTable` is `"redirect_schema_migrations"`; the host passes the ledger name it wants to `runMigrations` (one ledger per domain is the default; a host that wants one shared ledger passes the same name to every domain run: step ids are domain-prefixed, so they do not collide). This closes D-DB2 without an owner decision.
2. The domain package does NOT import a runner. The host calls `runMigrations(kernel, history.steps, { ledgerTable })` in an order it writes down.
3. **Tovu databases are never touched by these histories.** Tovu keeps its frozen Drizzle chain, its TS steps, ids, checksums and ledgers. A guard test fails if `apps/website/src` references a `create*SchemaHistory` export outside tests. No "adopt existing tables" step exists.
4. A schema change after the baseline = a new numbered step in the domain history AND a matching ADR-066 step in Tovu's own chain, in the same change, proven equal by the parity test. Applied steps are never edited (the checksum pin fails).
5. Other hosts' existing installs: every released step set gets an N-1 fixture BUILDER (a script that runs the released steps; never a stored binary) and a test that upgrades it with the next version automatically.

## DB-1a (JINI-ADD): EXTEND the existing `readSchemaShape` so parity can see what it must protect (revision 3, Opus review N8; judge finding 11)
**ON HOLD with the whole DB lane until owner decision D-DB0 (INDEX "Owner decisions"). Not dispatchable; not in any wave total.** The text below is the design the sheet will carry if D-DB0 releases the lane.
Verified 2026-11-17 on Jini 65d73b0d5 (`origin/refactor/terra`). Owner that already exists (revision 2 missed it): `readSchemaShape(kernel, optional: { exclude? } = {})` in `packages/db/src/kernel/schema-shape.ts:34` (143 lines, blob 0a47961f in `JINI.blobs.txt`), exported from the existing `@jini-ai/db/kernel` entry (`db/src/kernel/index.ts:26`), used in Tovu production by legacy adoption (`platform/db/migrations/legacy-sqlite.ts:135,196`) and by 7 Tovu test files plus 2 Jini test files that `deepEqual` two shapes. Revision 2's NEW `describeSchema` + NEW `./testing/schema-shape` entry would have been a second owner of the same behaviour (implementation-guardrails "Before You Write" 6): withdrawn.
What it sees today: SQLite keeps the table's whole `CREATE` text (`constraints: DEFINITION …`, :67), so CHECK expressions, `COLLATE`, `AUTOINCREMENT`, `WITHOUT ROWID`, `STRICT` and generated columns are already visible there; indexes with partial predicate and FKs with actions are read on both dialects; Postgres CHECK/FK/unique constraints come from `pg_get_constraintdef` (:117-121). The only gaps are Postgres column-level: **identity** (`GENERATED … AS IDENTITY` leaves `column_default` null), **generated-column expression**, **column collation**.
Change (additive, opt-in; the default output is byte-identical, because Tovu's `legacy-sqlite.ts` adoption compares shapes in production):
- `readSchemaShape(kernel, optional: { exclude?; columnDetail?: boolean } = {})`. The positional `kernel` stays: changing the signature would edit 10 caller files for no behaviour (reported, not fixed; the owner's `(required, optional)` rule applies to new APIs).
- With `columnDetail: true`, Postgres column text appends ` COLLATE <collation_name>` (only when not null), ` IDENTITY <ALWAYS|BY DEFAULT>` (`information_schema.columns.is_identity` / `identity_generation`), ` GENERATED <generation_expression>` (`is_generated = 'ALWAYS'`). SQLite ignores the flag (its `DEFINITION` text already carries those properties; a test proves it). The column text moves into one helper `postgresColumnText(required: { column }, optional: { columnDetail? } = {})` so `postgresShape` stays <= 50 lines.
- Files: `packages/db/src/kernel/schema-shape.ts`, NEW test `packages/db/src/kernel/__tests__/schema-shape.column-detail.test.ts` (PGlite via the existing `./testing/pg-fixture` pattern + SQLite), `api-baseline/jini-ai__db.json` (`pnpm api:update`), changeset `@jini-ai/db` minor. NO `db/package.json` change (no new entry), so the revision-2 collision with xpkg R11 / lane S S5 on `db/package.json` is gone. THIRD_PARTY_ALLOWED: none new (`kysely` already used by this file).
Tests (RED on the parent by V4 where they need the flag):
1. Default output unchanged: the two existing Jini test files (`__tests__/typegen-schema-shape.test.ts`, `kernel/__tests__/schema-shape.characterization.test.ts`) pass UNEDITED (`git diff --stat HEAD~1 -- packages/db/src/__tests__ packages/db/src/kernel/__tests__/schema-shape.characterization.test.ts` prints nothing).
2. Mutation pairs with `columnDetail: true` (two small schemas that differ in ONE property; shapes must differ): Postgres identity removed; identity ALWAYS vs BY DEFAULT; generated expression changed; column collation changed. On SQLite, the same four plus `AUTOINCREMENT` removed, CHECK removed, CHECK expression changed: shapes differ WITHOUT the flag (proves the `DEFINITION` text covers them).
3. Already covered, asserted again in the same file (no new code): missing index, changed default, changed FK action, changed partial-index predicate, column order (both dialects).
V3 mutation: delete the identity clause in `postgresColumnText` -> test 2 "identity removed" is RED. Estimate: 90k (was 170k).
