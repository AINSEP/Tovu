## What import and restore really do (read line by line; corrects round 1)
1. An import always CREATES A NEW SITE. `import-backend.ts` `createImportedSite` (:97-123 on merge-a) calls `createSite` with `collisionSafe: true`; `platform/site-dir/site-registry.ts:206-209` refuses an occupied target ("Import target was occupied while waiting for its creation lock"). No code path restores an archive over an existing site. Round 1's BK-0 item 5 ("restore over an existing site") described a contract that does not exist (judge finding 2).
2. Restore runs INSIDE site creation, before the commit marker: `platform/site-dir/init-site.ts` creates the folders and SEEDS stock themes (`createSiteFolders`, step 4b), then `createSqliteSiteStore` calls `verifiedRestore.restore({ dir, dbPath, siteId })` (:351), migrates the placed database to head (`migrateContentDatabase`, :355), then writes `.site-meta.json` last.
3. `import-restore.ts` `restoreStagedImport` (:52-75): (a) `:63` `fs.rmSync(<new site>/themes/<id>, { recursive: true, force: true })` for every live theme tree the archive brings, i.e. it permanently removes the stock theme copies that step 2 seeded seconds earlier; the site's own fallback theme is never replaced (`:60-62`); (b) `:66` copies the REBUILT database with `COPYFILE_EXCL` (initialization of an unoccupied path, never an overwrite); (c) plugin state, then every staged file through `writeExclusive` (live themes and uploads keep their path, everything else lands under `.import-quarantine/`); (d) keep-off notices; (e) optional saved keys: a non-abort failure becomes a notice and the site is still created.
4. Any throw in step 3 propagates to `initSite`, whose cleanup removes the whole uncommitted target (`init-site.ts:116-147`), and `import-backend.ts:117-121` removes the private stage and marks the row `failed` ("Site creation failed and was rolled back. Import the archive again."). A catalog failure after init removes the fresh site (`site-registry.ts:215-219`, `removeUncommittedSite` :250-255).
5. Schema identity. The manifest's `schema` is the head of the FROZEN Drizzle journal (`platform/site-dir/schema-guard.ts:49-65`). `archive-manifest.ts:162-166` refuses every identity that differs from the recipient's, including identities that exist in the bundled journal ("This ZIP was made by a different Tovu version. Export the site again from an updated Tovu, then import the new ZIP."), and the existing test asserts that refusal with `sanitize` never called (`__tests__/integration/import-schema-version.integration.test.ts:55-62`). ADR-066 TypeScript steps do not change the journal head, so archives made before and after a TS step carry the SAME identity; their column differences are handled only in the isolated worker by `share-database/repo.sqlite.ts` `ADDITIVE_COLUMN_DEFAULTS` (:101-104, two tables) and `requireTrustedColumns` (:110-114: any other missing or extra column refuses). `import-database.ts` contains no migration call (round 1 named one as a mutation; it does not exist: judge finding 1).

## Design queue (not dispatchable)

Today's tested contract is refusal with advice for a different manifest identity, and column-level defaults for the same identity. A design must specify: supported `formatVersion` values and manifest identities; how a historical shape is recognised from TRUSTED data only (the bundled journal and a bundled table of historical shapes; never the archive's own DDL); where the upgrade runs (in the isolated worker, on the rebuilt copy; never on archived SQLite bytes; `init-site.ts:355` already migrates the placed copy to head, which is the natural hook); that every existing hostile-schema refusal keeps its code and text (the BK-0a cases are the regression set); and the rule for future ADR-066 steps (a step that changes a shared table adds its trusted default or an upgrade function plus an N-1 archive fixture built by running the chain to head-1). Opus 180k; execution about three runs, 420k.
