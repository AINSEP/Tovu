## 1. Overview

WordPress's i18n/l10n system is a full gettext-compatible internationalization layer. It provides:

- **Text domain** namespacing so that plugins, themes, and core each maintain independent translation tables.
- **Translation functions** that look up translated strings at runtime, returning the original if no translation is found.
- **MO/PO file support** — binary MO files are the runtime format, plain-text PO files are the source format used by translators.
- **Just-in-time (JIT) loading** of translation files so that plugins and themes do not have to explicitly call load functions on every request; the system defers loading until a domain is first accessed.
- **Locale switching** so that individual operations (e.g. sending a notification email) can temporarily execute under a different locale without affecting the global state permanently.
- **JavaScript translations** exposed via JSON files in the Jed format, consumed by the `wp.i18n` browser library.

### Locale codes

Locales follow the POSIX/ICU convention: a lowercase ISO 639 language code (two or three characters) optionally followed by an underscore and an uppercase ISO 3166-1 country code, and optionally a further underscore and lowercase variant. Examples: `en_US`, `fr_FR`, `pt_BR`, `zh_CN`, `de_DE_formal`.

The default locale when no configuration is present is `en_US`. The English (United States) locale requires no translation files; all strings are returned verbatim.

### Translation file formats

WordPress supports three file formats at runtime:

| Format | Extension | Notes |
|---|---|---|
| MO (Machine Object) | `.mo` | Binary gettext compiled format. Traditional runtime format. |
| PHP translation array | `.l10n.php` | PHP file returning an array; faster to parse than binary MO. Preferred when available (since WP 6.5). |
| JSON | `.json` | Used exclusively for JavaScript translations. |

At load time, WordPress prefers the `.l10n.php` format over `.mo`. The `translation_file_format` filter (see Section 11) controls which format is attempted first.

### Global state

```typescript
// All currently loaded text domains, keyed by domain name.
// Values are WP_Translations (live) or NOOP_Translations (unloaded/not found).
const l10n: Record<string, TranslationsInterface> = {};

// Domains that have been explicitly unloaded and must not be JIT-reloaded.
const l10nUnloaded: Record<string, true> = {};

// The single global locale object populated at bootstrap.
let wpLocale: WPLocale;

// The single global locale switcher instance.
let wpLocaleSwitcher: WPLocaleSwitcher;
```

## 2. Translation Functions

All public-facing translation functions are thin wrappers around two internal primitives: `translate()` and `translate_with_gettext_context()`. Neither primitive should be called directly in application code.

### 2.1 Internal Primitives

#### `translate(text, domain?)`

```typescript
function translate(text: string, domain?: string): string
// domain defaults to 'default'
```

1. Call `get_translations_for_domain(domain)` to retrieve the `TranslationsInterface` for the domain, triggering JIT loading if necessary.
2. Call `translations.translate(text)` on the result. If no translation exists, the original `text` is returned by the `Translations` class.
3. Apply filter `gettext` with arguments `(translation, text, domain)`.
4. Apply filter `gettext_{domain}` with the same arguments.
5. Return the final translated string.

#### `translate_with_gettext_context(text, context, domain?)`

```typescript
function translate_with_gettext_context(text: string, context: string, domain?: string): string
// domain defaults to 'default'
```

Same as `translate()` but passes `context` to `translations.translate(text, context)`. The context allows two identical source strings to have different translations based on their grammatical or semantic context (e.g. "Post" as a noun vs "Post" as a verb).

Filters applied (in order):
1. `gettext_with_context` — `(translation, text, context, domain)`
2. `gettext_with_context_{domain}` — same args

### 2.2 Public Translation Functions

#### `__(text, domain?): string`

```typescript
function __(text: string, domain?: string): string
// domain defaults to 'default'
```

Returns the translated version of `text`. If no translation exists, returns `text` unchanged. This is the most commonly used translation function.

#### `_e(text, domain?): void`

```typescript
function _e(text: string, domain?: string): void
// domain defaults to 'default'
```

Echoes (outputs) the result of `__(text, domain)`. Returns nothing.

#### `_x(text, context, domain?): string`

```typescript
function _x(text: string, context: string, domain?: string): string
// domain defaults to 'default'
```

Returns the translated version of `text` with gettext disambiguation context `context`. Delegates to `translate_with_gettext_context()`.

Use when the same source string must have different translations in different situations. The `context` value appears in `.po` files for translators but is not visible to end users.

#### `_ex(text, context, domain?): void`

```typescript
function _ex(text: string, context: string, domain?: string): void
```

Echoes the result of `_x(text, context, domain)`.

#### `_n(single, plural, number, domain?): string`

```typescript
function _n(single: string, plural: string, number: number, domain?: string): string
// domain defaults to 'default'
```

Returns the appropriate singular or plural translated form based on `number`.

1. Call `get_translations_for_domain(domain)`.
2. Call `translations.translate_plural(single, plural, number)` — the translations object evaluates the locale's plural-forms expression against `number` to pick the correct form index.
3. Apply filter `ngettext` — `(translation, single, plural, number, domain)`.
4. Apply filter `ngettext_{domain}` — same args.
5. Return translation.

If no translation is found, the fallback is `number === 1 ? single : plural` (English rule).

#### `_nx(single, plural, number, context, domain?): string`

```typescript
function _nx(single: string, plural: string, number: number, context: string, domain?: string): string
// domain defaults to 'default'
```

Hybrid of `_n()` and `_x()`. Supports both plural forms and gettext context.

Calls `translations.translate_plural(single, plural, number, context)`.

Filters applied (in order):
1. `ngettext_with_context` — `(translation, single, plural, number, context, domain)`
2. `ngettext_with_context_{domain}` — same args

#### `esc_html__(text, domain?): string`

```typescript
function esc_html__(text: string, domain?: string): string
```

Translates and then HTML-escapes the result. Equivalent to `escHtml(__(text, domain))`. Encodes `<`, `>`, `&`, `"`, `'`.

#### `esc_html_e(text, domain?): void`

```typescript
function esc_html_e(text: string, domain?: string): void
```

Echoes `esc_html__(text, domain)`.

#### `esc_html_x(text, context, domain?): string`

```typescript
function esc_html_x(text: string, context: string, domain?: string): string
```

Translates with context and HTML-escapes. Equivalent to `escHtml(_x(text, context, domain))`.

#### `esc_attr__(text, domain?): string`

```typescript
function esc_attr__(text: string, domain?: string): string
```

Translates and then attribute-escapes the result. Encodes `<`, `>`, `&`, `"`, `'`. Will never double-encode existing HTML entities.

#### `esc_attr_e(text, domain?): void`

```typescript
function esc_attr_e(text: string, domain?: string): void
```

Echoes `esc_attr__(text, domain)`.

#### `esc_attr_x(text, context, domain?): string`

```typescript
function esc_attr_x(text: string, context: string, domain?: string): string
```

Translates with context and attribute-escapes. Equivalent to `escAttr(_x(text, context, domain))`.

### 2.3 Deferred Plural Noop Functions

These functions register plural strings for extraction by translation tooling (xgettext) but do **not** translate them at call time. They return a plain data object that is resolved into a translated string later, when the count is known.

#### `_n_noop(singular, plural, domain?): NoopedPlural`

```typescript
function _n_noop(singular: string, plural: string, domain?: string | null): NoopedPlural
```

Returns:
```typescript
{
  0: singular,        // numeric index (legacy)
  1: plural,          // numeric index (legacy)
  singular: singular,
  plural: plural,
  context: null,
  domain: domain,     // may be null
}
```

#### `_nx_noop(singular, plural, context, domain?): NoopedPlural`

```typescript
function _nx_noop(singular: string, plural: string, context: string, domain?: string | null): NoopedPlural
```

Returns:
```typescript
{
  0: singular,        // numeric index (legacy)
  1: plural,          // numeric index (legacy)
  2: context,         // numeric index (legacy)
  singular: singular,
  plural: plural,
  context: context,
  domain: domain,     // may be null
}
```

#### `translate_nooped_plural(noopedPlural, count, domain?): string`

```typescript
function translate_nooped_plural(noopedPlural: NoopedPlural, count: number, domain?: string): string
// domain defaults to 'default'
```

Resolves a noop plural object to a translated string.

Logic:
1. If `noopedPlural.domain` is set (non-null, non-empty), override `domain` with it.
2. If `noopedPlural.context` is set, call `_nx(singular, plural, count, context, domain)`.
3. Otherwise, call `_n(singular, plural, count, domain)`.

The `domain` parameter on this function is only used when the noop object itself has no domain stored.

## 3. Text Domains

A **text domain** is a string identifier that namespaces a set of translations. It allows plugins, themes, and core to each maintain independent translation tables that do not conflict with each other.

### The `'default'` domain

The string `'default'` is reserved for WordPress core. Core strings are loaded via `load_default_textdomain()`. No plugin or theme should use `'default'` as its domain.

### Registering domains

Text domains do not need formal registration. A domain is implicitly created when translation strings for it are loaded. The `WP_Textdomain_Registry` tracks which domains have been encountered and what filesystem path should be searched for their translation files.

When a plugin calls `load_plugin_textdomain('my-plugin')`, it tells the registry where to find `my-plugin`'s files. When a theme calls `load_theme_textdomain('my-theme')`, it does the same. As of WordPress 6.7, neither function immediately loads translations; they only register the path and let the JIT mechanism handle actual loading on first use.

### `load_textdomain(domain, mofile, locale?): boolean`

```typescript
function load_textdomain(domain: string, mofile: string, locale?: string | null): boolean
```

The low-level loader. Reads a single translation file (MO or PHP format) and merges it into the `l10n` registry under `domain`.

Behavior:
1. Return `false` if `domain` is not a string.
2. Apply filter `pre_load_textdomain(null, domain, mofile, locale)`. If non-null result is returned, skip loading and return that result (clearing the unloaded flag if `true`).
3. Apply filter `override_load_textdomain(false, domain, mofile, locale)`. If `true`, mark domain as loaded and return `true` without loading any file.
4. Fire action `load_textdomain(domain, mofile)`.
5. Apply filter `load_textdomain_mofile(mofile, domain)` — allows path rewriting.
6. If `locale` not provided, call `determine_locale()`.
7. Determine preferred format via filter `translation_file_format('php', domain)`. Must be `'php'` or `'mo'`; anything else falls back to `'php'`.
8. Build candidate file list:
   - If format is not `'mo'`: prepend `{mofile-without-.mo}.l10n.{preferred_format}` (e.g. `.l10n.php`).
   - Always append the original `mofile` (`.mo`).
9. For each candidate file, apply filter `load_translation_file(file, domain, locale)`.
10. Attempt to load via `WP_Translation_Controller::load_file(file, domain, locale)`.
11. On first success:
    - If a legacy `MO` object is already in `l10n[domain]`, load its file into the controller too (merge).
    - Remove the `l10n[domain]` entry.
    - Set `l10n[domain]` to a new `WP_Translations(controller, domain)` wrapper.
    - Register the directory in `WP_Textdomain_Registry`.
    - Return `true`.
12. If no file succeeded, return `false`.

**Merging behavior**: If a domain is already loaded and `load_textdomain` is called again for the same domain (e.g. when supplemental files like `admin-{locale}.mo` are loaded for the `'default'` domain), the translations are merged. When both sets have the same string, the **first-loaded** translation wins (original set is not overwritten).

### `unload_textdomain(domain, reloadable?): boolean`

```typescript
function unload_textdomain(domain: string, reloadable?: boolean): boolean
// reloadable defaults to false
```

Removes translations for `domain` from the runtime registry.

- If `reloadable` is `true`: the domain is unloaded from the controller but is **not** added to `l10nUnloaded`, allowing JIT reload later.
- If `reloadable` is `false`: the domain is added to `l10nUnloaded`, permanently preventing JIT reload for this request.
- If `l10n[domain]` is a `NOOP_Translations` (never actually loaded), the entry is deleted but `false` is returned.
- Filter `override_unload_textdomain(false, domain, reloadable)` can short-circuit.
- Action `unload_textdomain(domain, reloadable)` is fired before the actual unload.

### `load_default_textdomain(locale?): boolean`

```typescript
function load_default_textdomain(locale?: string | null): boolean
```

Loads WordPress core translations for the `'default'` domain.

1. If `locale` is null, call `determine_locale()`.
2. Call `unload_textdomain('default', true)` (reloadable) to clear previously loaded core strings.
3. Load `{WP_LANG_DIR}/{locale}.mo` into the `'default'` domain.
4. If multisite and no `admin-{locale}.mo` exists, additionally load `{WP_LANG_DIR}/ms-{locale}.mo`.
5. If in admin context or installing, additionally load `{WP_LANG_DIR}/admin-{locale}.mo`.
6. If in network admin or installing network, additionally load `{WP_LANG_DIR}/admin-network-{locale}.mo`.

Returns the result of step 3 (`true` if core locale file loaded, `false` if not found — which is normal for `en_US`).

### `load_plugin_textdomain(domain, deprecated?, pluginRelPath?): boolean`

```typescript
function load_plugin_textdomain(
  domain: string,
  deprecated?: string | false,
  pluginRelPath?: string | false
): boolean
// deprecated: ignored (deprecated since WP 2.7)
// pluginRelPath: path relative to WP_PLUGIN_DIR
```

Registers the plugin's translation path with `WP_Textdomain_Registry`. Does not load any files immediately (as of WP 6.7). The JIT mechanism will load files when the domain is first accessed.

Path resolution:
- If `pluginRelPath` is set: use `{WP_PLUGIN_DIR}/{pluginRelPath}`.
- If `deprecated` (old `$abs_rel_path` parameter) is set: use `{ABSPATH}/{deprecated}` (deprecated, warns).
- Otherwise: use `WP_PLUGIN_DIR`.

If the domain already has a `NOOP_Translations` entry in `l10n` (meaning JIT was triggered but found nothing), that entry is removed so JIT will retry.

### `load_muplugin_textdomain(domain, muPluginRelPath?): boolean`

```typescript
function load_muplugin_textdomain(domain: string, muPluginRelPath?: string): boolean
// muPluginRelPath defaults to ''
```

Same as `load_plugin_textdomain` but for must-use plugins. Path is `{WPMU_PLUGIN_DIR}/{muPluginRelPath}`.

### `load_theme_textdomain(domain, path?): boolean`

```typescript
function load_theme_textdomain(domain: string, path?: string | false): boolean
// path defaults to get_template_directory()
```

Registers the theme's translation path. If `path` is not provided, uses the active theme's template directory. Same JIT-deferred behavior as plugin loading.

### `load_child_theme_textdomain(domain, path?): boolean`

```typescript
function load_child_theme_textdomain(domain: string, path?: string | false): boolean
```

Convenience wrapper around `load_theme_textdomain`. If `path` is not provided, uses `get_stylesheet_directory()` (the child theme directory). Otherwise identical to `load_theme_textdomain`.

## 4. MO File Loading and Directory Structure

### Language directory structure

```
{WP_LANG_DIR}/
  {locale}.mo                          # Core (default domain)
  admin-{locale}.mo                    # Core admin strings
  admin-network-{locale}.mo            # Core network admin strings
  ms-{locale}.mo                       # Core multisite strings
  continents-cities-{locale}.mo        # Timezone strings
  plugins/
    {domain}-{locale}.mo               # Plugin translations (preferred location)
    {domain}-{locale}.l10n.php         # Plugin translations (PHP format)
    {domain}-{locale}-{md5-of-script-path}.json  # JS translations for plugins
  themes/
    {domain}-{locale}.mo               # Theme translations (preferred location)
    {domain}-{locale}.l10n.php         # Theme translations (PHP format)
    {domain}-{locale}-{md5-of-script-path}.json  # JS translations for themes
```

### Just-in-time loading (`_load_textdomain_just_in_time`)

This is a private function called automatically by `get_translations_for_domain()` when a domain that has not yet been loaded is first used.

```typescript
function _load_textdomain_just_in_time(domain: string): boolean
```

1. Skip if `domain === 'default'` (core is loaded explicitly).
2. Skip if `domain` is in `l10nUnloaded`.
3. Skip if `WP_Textdomain_Registry` has no record of `domain`.
4. Call `determine_locale()` and look up the path in the registry.
5. Determine the MO filename:
   - If the path starts with the template or stylesheet directory (theme's own language folder): filename is `{path}{locale}.mo`.
   - Otherwise (standard language directory): filename is `{path}{domain}-{locale}.mo`.
6. Call `load_textdomain(domain, mofile, locale)`.

The JIT mechanism also emits a `_doing_it_wrong` notice if translation loading is triggered before the `after_setup_theme` action has fired.

### `get_translations_for_domain(domain): TranslationsInterface`

```typescript
function get_translations_for_domain(domain: string): TranslationsInterface
```

Returns the live `Translations` object for a domain, or a shared `NOOP_Translations` singleton if no translations exist.

1. If `l10n[domain]` is set, return it.
2. Attempt `_load_textdomain_just_in_time(domain)`.
3. If `l10n[domain]` is now set (load succeeded), return it.
4. Store a reference to the shared `NOOP_Translations` singleton in `l10n[domain]` and return it.

The `NOOP_Translations` object acts as a null object: all translation calls pass through unchanged. Storing it in `l10n` prevents repeated JIT load attempts for domains that truly have no translations.

### `is_textdomain_loaded(domain): boolean`

```typescript
function is_textdomain_loaded(domain: string): boolean
```

Returns `true` only if `l10n[domain]` exists **and** is not a `NOOP_Translations` instance.

### MO binary file format

The `.mo` file format is a binary format defined by the GNU gettext project:

**Header (28 bytes):**

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | Magic number: `0x950412de` (little-endian) or `0xde120495` (big-endian) |
| 4 | 4 | File format revision (must be 0) |
| 8 | 4 | Number of strings N |
| 12 | 4 | Offset of original strings table |
| 16 | 4 | Offset of translated strings table |
| 20 | 4 | Size of hash table (may be 0) |
| 24 | 4 | Offset of hash table |

**String tables:** Two tables of N entries follow, each entry being an 8-byte `(length, offset)` pair pointing into the string data section.

**String encoding in the originals table:**
- Singular-only entry: `singular\0`
- Plural entry: `singular\0plural\0`
- Entry with context: `context\x04singular\0` or `context\x04singular\0plural\0`

**String encoding in the translations table:**
- Singular: the single translated string
- Plural: `form0\0form1\0form2\0...` (forms separated by NUL, number of forms defined by `Plural-Forms` header)

**Special entry (msgid = empty string):** The first entry (msgid = `""`) contains the file headers as a `Name: Value\n` formatted string. Key headers include:
- `Content-Type: text/plain; charset=UTF-8`
- `Plural-Forms: nplurals=2; plural=n != 1;`
- `Language: fr_FR`
- `PO-Revision-Date: ...`
- `Project-Id-Version: ...`

WordPress reads both little-endian and big-endian MO files, determined by the magic number.

### Translation entry key

The key used to look up a translation entry in the in-memory map:

- Without context: `singular`
- With context: `context\x04singular`
- Line endings normalized: `\r\n` and `\r` converted to `\n`

## 5. WP_Locale

`WP_Locale` is instantiated once at bootstrap as the global `$wp_locale` object. It populates itself by calling the translation functions, so it automatically reflects whatever locale is currently active. It is re-instantiated whenever the locale switches.

### Properties

```typescript
class WPLocale {
  // Full translated weekday names, indexed 0 (Sunday) through 6 (Saturday)
  weekday: string[];        // e.g. ['Sunday', 'Monday', ..., 'Saturday']

  // Single-letter weekday initials, keyed by the full weekday name
  // e.g. { 'Sunday': 'S', 'Monday': 'M', ... }
  // Note: Tuesday and Thursday both map to 'T', Saturday and Sunday both map to 'S'
  // in English; translations must ensure uniqueness for their language
  weekday_initial: Record<string, string>;

  // Three-letter weekday abbreviations, keyed by full weekday name
  // e.g. { 'Sunday': 'Sun', 'Monday': 'Mon', ... }
  weekday_abbrev: Record<string, string>;

  // Full month names, keyed by zero-padded month number string '01' through '12'
  month: Record<string, string>;

  // Month names in genitive case (for languages requiring it), keyed '01' through '12'
  // Falls back to nominative form if locale does not distinguish
  month_genitive: Record<string, string>;

  // Three-letter month abbreviations, keyed by full month name
  month_abbrev: Record<string, string>;

  // AM/PM strings
  meridiem: {
    am: string;   // e.g. 'am'
    pm: string;   // e.g. 'pm'
    AM: string;   // e.g. 'AM'
    PM: string;   // e.g. 'PM'
  };

  // Text direction: 'ltr' or 'rtl'
  // Default: 'ltr'
  text_direction: 'ltr' | 'rtl';

  // Number formatting characters
  number_format: {
    thousands_sep: string;   // e.g. ',' for English, '.' for German
    decimal_point: string;   // e.g. '.' for English, ',' for German
  };

  // Locale-specific list item separator
  // e.g. ', ' in English, '、' in Japanese
  list_item_separator: string;

  // How words are counted for this locale
  // 'words' | 'characters_excluding_spaces' | 'characters_including_spaces'
  // Default: 'words'
  word_count_type: string;
}
```

### Initialization

The constructor calls `init()` then `register_globals()`.

`init()` populates all properties by calling `__()` and `_x()` with the default domain. Because these calls happen after core translations are loaded, they produce translated strings for the current locale.

Number format detection: the strings `'number_format_thousands_sep'` and `'number_format_decimal_point'` are submitted to `__()`. If the translation returns the same string (no translation exists, which is the case for `en_US`), the default values `','` and `'.'` are used respectively. This is an intentional hack: translators provide the locale's separator characters as the "translation" of these sentinel strings.

Text direction detection:
1. If `$GLOBALS['text_direction']` is set, use that value directly.
2. Otherwise, call `_x('ltr', 'text direction')`. If the translation returns `'rtl'`, set `text_direction = 'rtl'`. This is another sentinel-string hack: RTL locales translate the string `'ltr'` to `'rtl'`.

### Methods

#### `get_weekday(weekdayNumber: number): string`

Returns the full translated weekday name. `weekdayNumber` is 0 (Sunday) through 6 (Saturday).

#### `get_weekday_initial(weekdayName: string): string`

Returns the single-character initial for the weekday, keyed by the translated full name.

#### `get_weekday_abbrev(weekdayName: string): string`

Returns the three-letter abbreviation, keyed by the translated full name.

#### `get_month(monthNumber: string | number): string`

Returns the full translated month name. `monthNumber` is `'01'` through `'12'` or the integers 1–12 (zero-padded internally). Returns empty string if not found.

#### `get_month_abbrev(monthName: string): string`

Returns the three-letter translated month abbreviation, keyed by the translated full month name.

#### `get_month_genitive(monthNumber: string | number): string`

Returns the genitive-case translated month name for `'01'`–`'12'`. Used in date formatting for languages where the month name inflects based on grammatical case (e.g. Russian).

#### `get_meridiem(meridiem: 'am' | 'pm' | 'AM' | 'PM'): string`

Returns the translated AM/PM string for the given untranslated form.

#### `is_rtl(): boolean`

Returns `true` if `text_direction === 'rtl'`.

#### `get_list_item_separator(): string`

Returns `list_item_separator`.

#### `get_word_count_type(): string`

Returns the word count type. Validates the value is one of the three accepted strings; falls back to `'words'` if not.

#### `register_globals(): void`

Copies `weekday`, `weekday_initial`, `weekday_abbrev`, `month`, and `month_abbrev` to PHP global variables with matching names. This is a backward-compatibility shim for very old code that referenced these arrays directly. In TypeScript, this would not be reproduced; the class properties are canonical.

## 6. WP_Locale_Switcher

Manages a LIFO stack of locale contexts, allowing code to temporarily operate under a different locale.

### Properties

```typescript
class WPLocaleSwitcher {
  // Stack entries: each is [locale: string, userId: number | false]
  private stack: Array<[string, number | false]>;

  // The locale that was active when the switcher was constructed (at bootstrap)
  private original_locale: string;

  // Full list of available locale codes (from installed language files + 'en_US')
  private available_languages: string[];
}
```

### Constructor

```typescript
constructor()
```

1. Set `original_locale = determine_locale()`.
2. Set `available_languages = ['en_US', ...get_available_languages()]`.

### `init(): void`

Registers `filter_locale` on both the `'locale'` and `'determine_locale'` filters. Once initialized, all calls to `get_locale()` and `determine_locale()` are intercepted when the stack is non-empty.

### `switch_to_locale(locale, userId?): boolean`

```typescript
switch_to_locale(locale: string, userId?: number | false): boolean
// userId defaults to false
```

1. Call `determine_locale()` to get the current effective locale.
2. If `locale === currentLocale`, return `false` (no-op).
3. If `locale` is not in `available_languages`, return `false`.
4. Push `[locale, userId]` onto the stack.
5. Call `change_locale(locale)`.
6. Fire action `switch_locale(locale, userId)`.
7. Return `true`.

### `switch_to_user_locale(userId): boolean`

```typescript
switch_to_user_locale(userId: number): boolean
```

Convenience method. Calls `get_user_locale(userId)` and passes the result to `switch_to_locale(locale, userId)`.

### `restore_previous_locale(): string | false`

```typescript
restore_previous_locale(): string | false
```

1. Pop the top entry from the stack.
2. If stack was empty before the pop (`null` popped), return `false`.
3. Peek at the new top of stack.
   - If stack is non-empty: use `stack[top][0]` as the locale to restore to.
   - If stack is now empty: restore to `original_locale`.
4. Call `change_locale(locale)`.
5. Fire action `restore_previous_locale(locale, previousLocale[0])`.
6. Return the locale that was restored to.

### `restore_current_locale(): string | false`

```typescript
restore_current_locale(): string | false
```

Collapses the entire stack to a single entry and restores to the original locale.

1. If stack is empty, return `false`.
2. Replace the entire stack with `[[original_locale, false]]`.
3. Call `restore_previous_locale()` (which will pop that single entry and restore to `original_locale`).
4. Return the result.

### `is_switched(): boolean`

Returns `true` if the stack is non-empty (any locale switch is active).

### `get_switched_locale(): string | false`

Returns the locale at the top of the stack, or `false` if stack is empty.

### `get_switched_user_id(): number | false`

Returns the user ID associated with the current stack top entry, or `false` if stack is empty.

### `filter_locale(locale): string`

The filter callback registered on `'locale'` and `'determine_locale'`. Returns `get_switched_locale()` if the stack is non-empty, otherwise returns the `locale` argument unchanged.

### `change_locale(locale): void` (private)

The internal implementation of actually switching the locale:

1. Call `load_translations(locale)` — reloads translation files for the new locale.
2. Instantiate `$wp_locale = new WP_Locale()` — rebuilds the locale object under the new locale's translations.
3. Call `WP_Translation_Controller::get_instance()->set_locale(locale)`.
4. If a `PHPMailer` instance exists as `$phpmailer`, call `$phpmailer->setLanguage()` to update its language.
5. Fire action `change_locale(locale)`.

### `load_translations(locale): void` (private)

1. Collect all currently loaded domain keys from `l10n`.
2. Call `load_default_textdomain(locale)` to reload core strings.
3. For each non-default domain in the collected keys: call `unload_textdomain(domain, true)` (reloadable), then immediately `get_translations_for_domain(domain)` to trigger JIT reload under the new locale.

### Global wrapper functions

These module-level functions delegate to the `$wp_locale_switcher` global instance:

```typescript
function switch_to_locale(locale: string): boolean
function switch_to_user_locale(userId: number): boolean
function restore_previous_locale(): string | false
function restore_current_locale(): string | false
function is_locale_switched(): boolean
```

All return `false` if `$wp_locale_switcher` is not initialized.

## 7. `get_locale()` vs `get_user_locale()`

### `get_locale(): string`

```typescript
function get_locale(): string
```

Returns the current site locale. Determination order (first non-empty value wins):

1. If the global `$locale` is already set, skip re-determination and jump directly to the filter.
2. If `$wp_local_package` global is set, use it.
3. If the `WPLANG` PHP constant is defined (set in `wp-config.php`), override with it.
4. In multisite:
   - If installing: read the `WPLANG` site option via `get_site_option('WPLANG')`.
   - Otherwise: try `get_option('WPLANG')` (current blog), fall back to `get_site_option('WPLANG')` (network).
5. In single-site: read `get_option('WPLANG')` from the database.
6. If still empty after all of the above, default to `'en_US'`.
7. Apply filter `locale($locale)` and return the result.

The filter runs **every call** even if the locale was already resolved. This allows `WP_Locale_Switcher` to intercept and return the switched locale transparently.

### `get_user_locale(user?): string`

```typescript
function get_user_locale(user?: number | WPUser): string
// user defaults to 0 (current user)
```

Returns a user's preferred locale, falling back to `get_locale()`.

1. Resolve the `WP_User` object:
   - `user === 0`: use `wp_get_current_user()`.
   - `user instanceof WP_User`: use directly.
   - `user` is numeric: call `get_user_by('id', user)`.
2. If no valid user object found, return `get_locale()`.
3. Read `user_object.locale`.
4. If `locale` is non-empty, return it. Otherwise return `get_locale()`.

The user locale is stored as a user meta field (`locale`). An empty string means "use the site default."

### `determine_locale(): string`

```typescript
function determine_locale(): string
```

Determines the most appropriate locale for the **current HTTP request context**, not just the site default.

1. Apply filter `pre_determine_locale(null)`. If non-null string returned, use it immediately.
2. On the login page (`wp-login.php`): check `$_GET['wp_lang']` then `$_COOKIE['wp_lang']`; sanitize with `sanitize_locale_name()`.
3. In wp-admin, or a REST request with `_locale=user` parameter: use `get_user_locale()` (the logged-in user's preference).
4. During installation with `$_REQUEST['language']` set: use that value (sanitized). If not set but `$wp_local_package` global is set, use that.
5. If still not determined: use `get_locale()`.
6. Apply filter `determine_locale($determined_locale)` and return.

## 8. JavaScript Translations

JavaScript code using the `wp.i18n` library needs access to the same translations as PHP. WordPress bridges this via JSON translation files loaded into the page as inline script data.

### `wp_set_script_translations(handle, domain?, path?)`

This function (in `wp-scripts.php`, not `l10n.php`) attaches translation data to a registered script handle. It calls `load_script_textdomain()` to find the JSON file, then inlines the data as a script before the registered script runs.

### `load_script_textdomain(handle, domain?, path?): string | false`

```typescript
function load_script_textdomain(handle: string, domain?: string, path?: string): string | false
// domain defaults to 'default'
// path defaults to ''
```

Finds and returns JSON-encoded translation data for a script.

**File naming conventions:**

The base file name prefix is:
- For `domain === 'default'`: `{locale}`
- For other domains: `{domain}-{locale}`

Two file name patterns are attempted:

1. **Handle-based:** `{fileBase}-{handle}.json` — allows translations scoped to a specific script handle.
2. **MD5-based:** `{fileBase}-{md5(relativePath)}.json` — where `relativePath` is the script's source URL made relative to the content or plugin URL (with `.min.js` suffix stripped to `.js` before hashing).

**Path resolution order:**
1. If `path` is explicitly provided (or found in registry), try `{path}/{handleFilename}`.
2. Try `{path}/{md5Filename}`.
3. Try `{WP_LANG_DIR}/plugins/{md5Filename}` or `{WP_LANG_DIR}/themes/{md5Filename}` depending on whether the script URL is under a plugin or theme directory.
4. If the script source URL is not from the site, call `load_script_translations(false, handle, domain)` (triggers the filter with no file).

### `load_script_translations(file, handle, domain): string | false`

```typescript
function load_script_translations(
  file: string | false,
  handle: string,
  domain: string
): string | false
```

1. Apply filter `pre_load_script_translations(null, file, handle, domain)` — allows short-circuiting.
2. Apply filter `load_script_translation_file(file, handle, domain)` — allows path rewriting.
3. If `file` is falsy or not readable, return `false`.
4. Read the file contents.
5. Apply filter `load_script_translations(contents, file, handle, domain)`.
6. Return the JSON string.

### Jed JSON format

The JSON translation files follow the Jed 1.x format expected by `wp.i18n`:

```json
{
  "domain": "my-plugin",
  "locale_data": {
    "my-plugin": {
      "": {
        "domain": "my-plugin",
        "lang": "fr",
        "plural-forms": "nplurals=2; plural=(n > 1);"
      },
      "Original string": ["Translated string"],
      "context\u0004Original string": ["Translated string with context"],
      "Singular original\u0000Plural original": ["Singular translation", "Plural translation"]
    }
  }
}
```

Key points:
- The empty-string key `""` holds metadata.
- Context is encoded as `context\x04singular` (EOT character `U+0004`).
- Plural originals are encoded as `singular\x00plural` (NUL separator `U+0000`).
- Translation arrays have one entry per plural form.

## 9. Plural Forms

### How `_n()` selects a form

When `_n(single, plural, number, domain)` is called:

1. The `Translations` object's `translate_plural(single, plural, number)` is called.
2. This looks up the entry by key (`single` + optional context).
3. If found, `select_plural_form(number)` is called to get the 0-based index into the `translations` array.
4. If the index is valid, the corresponding translation is returned.
5. If no translation is found or the index is out of bounds, the fallback is: `number === 1 ? single : plural`.

### Plural-Forms header parsing

The `Plural-Forms` header in a `.mo` or `.po` file has the format:

```
nplurals=N; plural=EXPRESSION;
```

Where:
- `nplurals` is the total number of distinct plural forms the language has.
- `plural` is a C-style expression involving the variable `n` that evaluates to a 0-based form index.

Examples:

| Language | nplurals | Expression | Notes |
|---|---|---|---|
| English | 2 | `n != 1` | 0 for n=1, 1 otherwise |
| French | 2 | `n > 1` | 0 for n=0 or n=1, 1 for n>=2 |
| Russian | 3 | `n%10==1 && n%100!=11 ? 0 : n%10>=2 && n%10<=4 && (n%100<12 || n%100>14) ? 1 : 2` | Three forms |
| Arabic | 6 | complex | Six forms |
| Japanese | 1 | `0` | No plural distinction |

### `Plural_Forms` expression evaluator

The `Plural_Forms` class (in `pomo/plural-forms.php`) parses the expression string into an RPN (Reverse Polish Notation) token array using the shunting-yard algorithm, then evaluates it for a given `n`.

Supported operators (by precedence, high to low):

| Operator | Precedence |
|---|---|
| `%` | 6 |
| `<`, `<=`, `>`, `>=` | 5 |
| `==`, `!=` | 4 |
| `&&` | 3 |
| `\|\|` | 2 |
| `?:`, `?` (ternary) | 1 |

Tokens: `{ type: 'var' }` for `n`, `{ type: 'value', value: number }` for integer literals, `{ type: 'op', op: string }` for operators.

Results are cached per `n` value to avoid redundant evaluation.

Default plural form (if `Plural-Forms` header is absent or invalid): `nplurals=2; plural=n != 1;` (English rule).

### `Gettext_Translations.gettext_select_plural_form(count)`

Lazily initializes the plural form function from the `Plural-Forms` header, then calls it. Caches both `_nplurals` and `_gettext_select_plural_form` after first invocation.

## 10. RTL Support

### `is_rtl(): boolean`

```typescript
function is_rtl(): boolean
```

Global function that checks whether the current locale is right-to-left.

1. If `$wp_locale` is not a `WP_Locale` instance, return `false`.
2. Return `$wp_locale->is_rtl()`.

`is_rtl()` returns `true` only if `wp_locale.text_direction === 'rtl'`.

### How `text_direction` is determined

During `WP_Locale::init()`:

1. If the PHP global `$text_direction` is set (legacy override): use it directly.
2. Otherwise call `_x('ltr', 'text direction')`:
   - If the translation returns `'rtl'`: set `text_direction = 'rtl'`.
   - If it returns anything else (including `'ltr'` or the original string for `en_US`): keep `text_direction = 'ltr'`.

This means RTL support is entirely driven by the translation file. An RTL language's `.mo` file translates the string `'ltr'` in the context `'text direction'` to the string `'rtl'`. No hardcoded list of RTL locales exists in the code.

### Usage

`is_rtl()` is called throughout WordPress to:
- Load `rtl.css` stylesheets instead of or in addition to `style.css`.
- Apply `dir="rtl"` attributes on HTML elements.
- Mirror UI elements (e.g. navigation arrows, floats).
- Adjust JavaScript that manipulates text direction.

## 11. Key Hooks and Filters

All filters follow the pattern `apply_filters(hookName, value, ...additionalArgs)`.

### Filters

#### `locale`

```
apply_filters('locale', string $locale): string
```

Fires on every call to `get_locale()`. Used by `WP_Locale_Switcher` to override the active locale when a switch is in effect. Since this filter runs every time `get_locale()` is called, any code that calls `get_locale()` repeatedly within a locale switch correctly sees the switched locale.

#### `determine_locale`

```
apply_filters('determine_locale', string $locale): string
```

Fires at the end of `determine_locale()`. Used by `WP_Locale_Switcher` (same callback as `locale` filter). Allows altering the locale used for loading translations for a specific request.

#### `pre_determine_locale`

```
apply_filters('pre_determine_locale', null|string $locale): null|string
```

Fires at the start of `determine_locale()`. Return a non-null string to short-circuit the entire determination process.

#### `gettext`

```
apply_filters('gettext', string $translation, string $text, string $domain): string
```

Fires after every `translate()` call. Allows replacing any translated string site-wide.

#### `gettext_{$domain}`

```
apply_filters("gettext_{$domain}", string $translation, string $text, string $domain): string
```

Domain-scoped version of `gettext`. Fires after `gettext`. Only fires for the specific domain.

#### `gettext_with_context`

```
apply_filters('gettext_with_context', string $translation, string $text, string $context, string $domain): string
```

Fires after every `translate_with_gettext_context()` call.

#### `gettext_with_context_{$domain}`

Domain-scoped version of `gettext_with_context`.

#### `ngettext`

```
apply_filters('ngettext', string $translation, string $single, string $plural, int $number, string $domain): string
```

Fires after every `_n()` call.

#### `ngettext_{$domain}`

Domain-scoped version of `ngettext`.

#### `ngettext_with_context`

```
apply_filters('ngettext_with_context', string $translation, string $single, string $plural, int $number, string $context, string $domain): string
```

Fires after every `_nx()` call.

#### `ngettext_with_context_{$domain}`

Domain-scoped version of `ngettext_with_context`.

#### `pre_load_textdomain`

```
apply_filters('pre_load_textdomain', null|bool $loaded, string $domain, string $mofile, string|null $locale): null|bool
```

Fires at the start of `load_textdomain()`. Return a non-null value to completely skip the default loading logic. Return `true` to signal success (clears unloaded flag), `false` to signal failure.

#### `override_load_textdomain`

```
apply_filters('override_load_textdomain', bool $override, string $domain, string $mofile, string|null $locale): bool
```

If `true` is returned, `load_textdomain()` returns `true` immediately without loading any file.

#### `load_textdomain_mofile`

```
apply_filters('load_textdomain_mofile', string $mofile, string $domain): string
```

Fires inside `load_textdomain()` after the `load_textdomain` action. Allows rewriting the `.mo` file path. Applied specifically to the `.mo` path before the PHP format variant is derived.

#### `translation_file_format`

```
apply_filters('translation_file_format', string $format, string $domain): string
// $format: 'php' | 'mo'
```

Controls which file format is preferred. Returning `'mo'` disables PHP translation files. Any value other than `'php'` or `'mo'` is coerced back to `'php'`.

#### `load_translation_file`

```
apply_filters('load_translation_file', string $file, string $domain, string $locale): string
```

Fires for each candidate file path (both `.l10n.php` and `.mo`) during `load_textdomain()`. Allows final-stage path rewriting per locale and format.

#### `override_unload_textdomain`

```
apply_filters('override_unload_textdomain', bool $override, string $domain, bool $reloadable): bool
```

If `true` is returned from `unload_textdomain()`, the default unloading logic is skipped.

#### `plugin_locale`

```
apply_filters('plugin_locale', string $locale, string $domain): string
```

Historically used to filter the locale used when loading a specific plugin's text domain. Plugin authors are expected to apply this filter to get the effective locale when calling `load_textdomain()` directly for their plugin.

#### `theme_locale`

```
apply_filters('theme_locale', string $locale, string $domain): string
```

Same pattern as `plugin_locale` but for themes.

#### `pre_load_script_translations`

```
apply_filters('pre_load_script_translations', null|string|false $translations, string|false $file, string $handle, string $domain): null|string|false
```

Short-circuit filter for `load_script_translations()`. Return non-null to override.

#### `load_script_translation_file`

```
apply_filters('load_script_translation_file', string|false $file, string $handle, string $domain): string|false
```

Allows rewriting the JSON file path in `load_script_translations()`.

#### `load_script_translations`

```
apply_filters('load_script_translations', string $translations, string $file, string $handle, string $domain): string
```

Fires after reading the JSON file contents, allowing modification of the translation data before it is returned.

#### `load_script_textdomain_relative_path`

```
apply_filters('load_script_textdomain_relative_path', string|false $relative, string $src): string|false
```

Filters the relative path of a script source URL used to compute the MD5 filename for JS translations.

#### `get_available_languages`

```
apply_filters('get_available_languages', string[] $languages, string $dir): string[]
```

Filters the list of available locale codes returned by `get_available_languages()`.

### Actions

#### `load_textdomain`

```
do_action('load_textdomain', string $domain, string $mofile)
```

Fires before a `.mo` file is loaded.

#### `unload_textdomain`

```
do_action('unload_textdomain', string $domain, bool $reloadable)
```

Fires before a domain is unloaded.

#### `switch_locale`

```
do_action('switch_locale', string $locale, int|false $userId)
```

Fires when `switch_to_locale()` successfully switches.

#### `restore_previous_locale`

```
do_action('restore_previous_locale', string $newLocale, string $previousLocale)
```

Fires when `restore_previous_locale()` completes. `$newLocale` is the locale being restored to; `$previousLocale` is the one being discarded.

#### `change_locale`

```
do_action('change_locale', string $locale)
```

Fires inside `WP_Locale_Switcher::change_locale()` after translations are reloaded and `$wp_locale` is rebuilt. Fires on both switches and restores.

## 13. Design Patterns to Carry Over

1. **Null object for missing translations.** `NOOP_Translations` implements the full `TranslationsInterface` but passes all strings through unchanged. Storing it in `l10n[domain]` after a failed JIT load prevents the lookup from being retried on every subsequent translation call for that domain. Do not return `null` or throw when a domain is not found — return a NOOP object.

2. **Translation lookup by structured key, not by position.** The in-memory translation table is a `Record<string, TranslationEntry>` keyed by `context\x04singular` (or just `singular`). This means lookup is O(1) and the entry also carries its full plural forms array. This key format must be reproduced exactly, including the `U+0004` EOT separator for context.

3. **Sentinel-string translation for locale metadata.** The text direction, thousands separator, decimal point, and word count type are all communicated through translatable strings that have no visible end-user meaning. The "translation" of `'number_format_thousands_sep'` in French is `' '` (a non-breaking space). This is deliberate and must be preserved: locale metadata lives in translation files, not in a separate configuration database.

4. **JIT loading is the normal path.** Plugins and themes do not load their translations at `plugins_loaded`; they register their path and the system loads on demand. The implementation must support: (a) looking up a domain that has never been touched and immediately loading it, (b) detecting domains that have been explicitly unloaded and refusing to reload them, (c) re-attempting a domain that had a NOOP entry if the path registration changed.

5. **Locale switching is a stack, not a toggle.** Code that calls `switch_to_locale` must always call the corresponding `restore_previous_locale`. Nested switches work correctly because the stack tracks every level. `restore_current_locale` is the escape hatch for code that cannot guarantee balanced pairs.

6. **`change_locale` rebuilds `$wp_locale` on every switch.** After a locale switch, not just the translation lookup tables change — the `WP_Locale` object itself is discarded and recreated. Any cached references to the old `WP_Locale` object's properties (weekday names, etc.) become stale. Code must always access these through the current `$wp_locale` instance.

7. **Multiple `.mo` files can be merged into one domain.** Core does this for `'default'`: it loads the base locale file, then overlays `admin-{locale}.mo` and `admin-network-{locale}.mo` for more specific contexts. When both sets have the same string, the first-loaded value wins. This merge-with-original-wins semantics is important for overlay scenarios.

8. **Context is invisible to end users but visible to translators.** Context strings passed to `_x()` and `_nx()` appear only in `.po`/`.pot` files. They never appear in the rendered output. They exist purely to disambiguate identical source strings that should be translated differently. This distinction must be clear at the API level.

9. **JavaScript translations use MD5-hashed file names.** The JSON file for a script's translations is named after the MD5 of the script's path relative to the plugin/theme root (not the full URL). The `.min.js` suffix is stripped before hashing so that minified and unminified versions share the same translation file. The implementation must normalize script paths before computing the MD5.

10. **Plural-forms expressions are C-like, not JavaScript.** The `plural=` expression in `.po` files uses C operator semantics including right-associative ternary. The `Plural_Forms` evaluator handles this by converting to RPN via shunting-yard with special handling for the `?:` pair. A naive `eval()` in JavaScript would also work for most cases but would fail on edge cases with nested ternaries. The safe implementation is a proper expression evaluator that respects C ternary associativity, as the `Plural_Forms` class does.

11. **`before_last_bar()` handles legacy role names.** Some translatable strings use a `|` character as a context separator in the old style: `'Administrator|User role'`. `translate_user_role()` strips everything after the last `|` before looking up the translation. New code uses `_x()` properly, but the cleanup function exists for backward compatibility with strings already stored in the database.

12. **Available languages are discovered from filesystem, not a registry.** `get_available_languages()` scans the language directory for `*.mo` and `*.l10n.php` files and derives locale codes by stripping extensions. Files with prefixes `continents-cities`, `ms-`, and `admin-` are excluded (they are supplemental files, not standalone locales). The result is filterable.

## Tovu Reconstruction Notes

### Why this exists

The i18n/l10n layer exists so strings can be translated at runtime without coupling the application to a single locale. The core lesson for Tovu is that text domains, catalog loading, and locale switching are runtime concerns, not build-time decoration.

### What Tovu should preserve

- Namespaced translation catalogs per module or domain
- Lazy loading so translations are only loaded when needed
- Scoped locale switching for request-local or task-local operations
- Separate handling for server-side strings and JavaScript translation assets

### What Tovu can simplify

- Tovu does not need WordPress's full POMO file stack if it can standardize on a smaller catalog format
- Legacy context-cleanup helpers can stay out of the hot path if stored content is already normalized
- The key requirement is stable runtime translation lookup, not a clone of every file format

### Possible Tovu seams

- `src/i18n/catalogs/` for translation loading and caching
- `src/i18n/locale/` for locale selection and temporary overrides
- `src/i18n/js/` for frontend translation manifest generation
- loaders and translators should be swappable behind a domain-level port

### Suggested priority

- `V1`: runtime catalog lookup, locale selection, and translation helpers
- `Later`: broader file-format support and advanced legacy compatibility
