## 2. Plan

**From request to result.** The owner asks in chat or fills in the admin form. Both paths save the same name, prompt, schedule, agent, and model selection under the authenticated site owner. Chat mutations show the existing approval card with the proposed change before saving. Direct admin actions use the existing authenticated action and confirmation patterns. On each scheduled fire, Jini claims the due slot. Tovu creates a fresh durable conversation and starts the normal owner-chat run. The Routines screen reads the current state and links to that conversation, where the owner can review any pending card.

**Missed runs.** Persist one next-due timestamp per enabled routine. On startup or Mac wake, the existing scheduler fires an overdue routine once, marks the run as a catch-up, and moves the due timestamp straight to the first future occurrence. Claim and advance in one durable transaction. Pause clears the due timestamp. Resume and schedule changes start from the next future occurrence. Keep at most one active run per routine, including one waiting for approval. Display its result until it settles. The desktop starts routine-enabled owned sites in the background and keeps their daemon scopes available even when no chat is open.

**Permissions and cost.** Re-resolve the saved owner and ordinary run permissions at launch and again at the existing action gates. A routine’s creation approval authorizes the schedule, and runtime actions still require their normal approvals. Use the existing run-bound card and authenticated redemption. Show **Waiting for approval** while the call waits. A quit or terminal failure closes the attempt and records what happened. Never convert a missing card, timeout, or restart into consent. Show the selected agent/model before save and the model reported by the last run when available; label an unspecified model **Agent default**. If the selected agent or explicit model is unavailable, expose that failure without substituting a different one.

**Ownership.** Jini owns schedule validation, timer/claim behavior, reusable storage, and neutral mutation contracts. Tovu owns desktop/site lifecycle, identity and authorization, the durable chat binding, and admin presentation. Initial execution uses the local CLI path across supported CLIs. A site owner can create a routine from either staff chat surface when the tool is available. Provider-direct scheduled execution is a separate product decision.

## 6. Owner decisions

- **Which sites resume when Tovu opens?** Recommend starting previously registered local sites with enabled routines in the background. This fulfils catch-up from Sites Home without a manual site reopen. An explicitly withdrawn site stays stopped for the current desktop session.
- **Should a pending approval survive a full quit?** Recommend keeping it live across tab close, reload and sleep, and marking it interrupted after a full quit. Resuming the same approval across process death would require durable continuation of the approved action and its authority checks.
- **Should routines run on BYOK in the first release?** Recommend local CLI execution first, with creation available from the authorized staff chat surface. If provider-direct runs are required at launch, they need their own unattended acceptance, replay and approval-lifetime verification.
